1 The big picture

A database is a stack of smart spreadsheets

A database is a collection of tables. A table is like one sheet in Excel: columns are the fields (what you store), rows are the records (one thing each). The KDPS stock ledger is a table — each movement is a row.

Three things make a database far more than a spreadsheet, and all three matter for KDPS:

  1. It enforces rules. A column can refuse blanks, refuse duplicates, refuse a sale pointing at a SKU that doesn't exist. A spreadsheet lets anyone type anything.
  2. Tables link to each other by id, so a fact (a brand's commission %) lives in exactly one place.
  3. It answers questions instantly with queries, over millions of rows, and guarantees a sale either saves completely or not at all.

The kind KDPS will use is a relational database (e.g. PostgreSQL) — "relational" just means tables that relate to one another by id. You talk to it in a language called SQL ("sequel").

🧭 Hold this whole handbook together with one sentence: a database stores facts in tables, links them by id, refuses bad data, and answers questions — all while guaranteeing nothing is ever left half-saved.

2 Columns have types

Every column holds one kind of value

When you create a column you say what it holds. The type decides what's allowed in and how it sorts and adds up. These are the handful you'll see across KDPS:

TypeHoldsKDPS example
TEXT / VARCHARwords, codesbrand name, SKU code, colour
INTEGERwhole numbersquantity, a row's id
NUMERIC(12,2)exact decimalsmoney — MRP, cost, commission
BOOLEANtrue / falseis_active, is_returnable
DATE / TIMESTAMPa day / a momentsale date, return-window close, created_at
ENUM / CHECKone of a fixed listcommercial_model, movement type

💰 The money rule — this one bites real ERPs. Always store money as NUMERIC/DECIMAL, never as a FLOAT/REAL. Floats are approximate — 0.1 + 0.2 famously isn't exactly 0.3 — and over thousands of bills those rounding crumbs become real rupees that don't reconcile with Tally. If you see a money column typed FLOAT in a schema review, flag it.

NULL — "we don't know / not set"

A cell can be empty — that's NULL. It is not zero and not blank text; it means "no value". It matters because NULL behaves oddly: NULL = NULL is not true, and a NULL in a sum is skipped. A column can be told to forbid NULL (next section). Rule of thumb: money and quantities should rarely be NULL; optional notes can be.

3 Keys & relationships

How rows point at each other

Every table should give each row a unique id — its primary key. Other tables refer to that row by storing its id — a foreign key. That's the entire idea of "relational".

sku
id (PK)stylecoloursizebrand_id (FK)
NK-AM90-WHT-8Air Max 90White812

The brand_id = 12 points at the brand row whose id = 12 (Biba). Store the brand's details once, in the brand table; everywhere else just hold the id.

The three relationship shapes

One-to-many (the common one)

One brand has many SKUs. One SKU has many movements. The "many" side holds the foreign key (sku.brand_id, stock_movement.sku_id).

One-to-one (rare)

One sale has one bill PDF. Sometimes split off for tidiness; often just more columns on the same row.

🔗 Many-to-many needs a third table. A store stocks many brands, and a brand sells in many stores. You can't put that in one column, so you add a junction table — store_brand(store_id, brand_id) — one row per pairing. Whenever you hear "X can have many Y and Y can have many X," expect a junction table in the schema.

📌 Why this is the heart of KDPS: follow the foreign keys — movement → sku → brand — and from a single sold piece you can reach its brand and therefore its commercial model. Set SOR once on the brand row and every sale of its SKUs inherits it. The relationships are the spine.

4 Reading a schema

CREATE TABLE — the blueprint you'll review

A schema is the set of CREATE TABLE statements that define every table, its columns, types and links. You won't write these — you'll read them. Here's the brand table, fully annotated:

CREATE TABLE brand (
  id                 SERIAL       PRIMARY KEY,   -- auto-numbered unique id
  name               TEXT         NOT NULL,      -- must be filled
  commercial_model   TEXT         NOT NULL
        CHECK (commercial_model IN ('BNS','CORRECTION','SOR','CONSIGNMENT')),
  commission_pct     NUMERIC(5,2),                -- e.g. 35.00 ; NULL for owned models
  return_window_days INTEGER,
  is_active          BOOLEAN      NOT NULL DEFAULT true
);

Read it top to bottom: a brand has an auto id, a required name, a model that must be one of your four, an optional commission %, a return window, and an active flag that defaults to true. That single CHECK means the database itself will reject a typo'd model — the rule lives in the data, not in hope.

CREATE TABLE stock_movement (
  id          BIGSERIAL   PRIMARY KEY,
  sku_id      TEXT        NOT NULL REFERENCES sku(id),   -- foreign key
  type        TEXT        NOT NULL,                  -- GRN / SALE / TRANSFER / RETURN
  qty         INTEGER     NOT NULL,                  -- +ve in, −ve out
  document    TEXT        NOT NULL,                  -- which document caused it
  store       TEXT        NOT NULL REFERENCES store(id),
  created_at  TIMESTAMP   NOT NULL DEFAULT now()
);

👀 What to notice in any schema: there is no on_hand column here. Stock is the SUM of qty — derived, never stored. Rows are only ever inserted, never edited. That's the ledger, correctly built. (If you instead saw stock_qty on the sku table, you'd be looking at a count — the thing to reject.)

5 Constraints — how the database refuses bad data

The rules that make bad rows impossible, not just unlikely

A constraint is a rule the database enforces on every write. They're your safety net: even buggy code can't slip past them. Six you'll meet:

ConstraintPromisesKDPS use
PRIMARY KEYunique, never NULL — the row's identityevery table's id
NOT NULLmust have a valueqty, model, name
UNIQUEno duplicates in this columna barcode, a GSTIN
FOREIGN KEYmust point at a real row elsewherea movement's sku_id must exist
CHECKvalue must pass a testmodel ∈ your four; qty <> 0
DEFAULTauto-fill when not givencreated_at = now(); is_active = true

🛡️ Why this matters for review: constraints are how the schema makes your domain rules physically true. "A sale can't reference a SKU that doesn't exist" should be a FOREIGN KEY, not a comment. "Commercial model is one of four" should be a CHECK. When you review a schema, half the job is asking: are the business rules I care about actually enforced here, or just hoped for in the code?

6 Asking questions — SELECT

Read it right-to-left as a sentence

A SELECT reads rows out and changes nothing. The clauses always come in this order:

SELECT   name, mrp          -- which COLUMNS
FROM     sku                -- which TABLE
WHERE    brand_id = 12      -- which ROWS to keep
ORDER BY mrp DESC           -- sort, biggest first
LIMIT    10;                -- only the first 10

SELECT picks columns. WHERE picks rows. That one split unlocks most queries.

Filtering: the WHERE toolkit

WriteMeans
WHERE colour = 'White'exact match
WHERE mrp >= 2000comparisons (> < >= <= <>)
WHERE brand_id = 12 AND size = '8'both must hold
WHERE colour = 'Red' OR colour = 'Blue'either
WHERE size IN ('8','9','10')any of a list
WHERE name LIKE 'Kurti%'text starts with "Kurti"
WHERE created_at BETWEEN '2026-06-01' AND '2026-06-30'a range
WHERE return_window_days IS NULLthe empty/unknown ones

⚠️ NULL gotcha: to find empty cells you must write IS NULL, never = NULL (that's never true). It's the most common "why did my query return nothing?" trap.

7 Aggregating & grouping

Squash many rows into one number — per bucket

An aggregate collapses many rows into a single value: SUM, COUNT, AVG, MIN, MAX. Your stock-on-hand query is just a SUM over the ledger:

SELECT SUM(qty) AS on_hand FROM stock_movement WHERE sku_id = 'NK-AM90-WHT-8';
-- → 3   (the +5 −1 −2 +1 added up)

GROUP BY runs that aggregate once per bucket. The rule: every column you select is either in the GROUP BY or wrapped in an aggregate.

SELECT   sku_id, store, SUM(qty) AS on_hand
FROM     stock_movement
GROUP BY sku_id, store;          -- on-hand per SKU per store

To filter after grouping (e.g. "only SKUs with under 3 left"), you use HAVING — it's a WHERE for groups:

SELECT sku_id, SUM(qty) AS on_hand
FROM stock_movement GROUP BY sku_id
HAVING SUM(qty) < 3;             -- low-stock list

💡 WHERE vs HAVING: WHERE filters rows before grouping; HAVING filters groups after. "Only this season's movements" → WHERE. "Only SKUs whose total is low" → HAVING. This single GROUP BY pattern powers most dashboards: sales per brand, pieces per store, revenue per day.

8 Combining tables — JOIN

Stitch related rows together by their keys

Your movement rows store a sku_id, not the brand name. To show the brand name beside each sale, you JOIN the tables along the foreign keys:

SELECT b.name, SUM(m.qty) AS on_hand
FROM      stock_movement m
JOIN      sku   s ON s.id = m.sku_id      -- movement → its SKU
JOIN      brand b ON b.id = s.brand_id    -- SKU → its brand
GROUP BY  b.name;                          -- stock on hand per brand

Read it as: "walk from each movement to its SKU, then to its brand, and total the quantities per brand." The m, s, b are short nicknames (aliases) for the tables.

INNER JOIN (default)

Keeps only rows that match on both sides. A movement with no matching SKU drops out — usually what you want.

LEFT JOIN

Keeps every row from the left table even if the right has no match (you get NULLs). Use for "all brands, including those with zero sales."

🔎 In review: a JOIN should always connect a foreign key to the primary key it points at (m.sku_id = s.id). If a JOIN's ON joins unrelated columns, or is missing, you can get a "cross join" — every row paired with every row — which explodes the result and is almost always a bug.

9 Changing data — and the dangerous one

INSERT, UPDATE, DELETE

Writes change what's stored. In a ledger system the everyday write is INSERT — you add a movement, you don't edit one:

INSERT INTO stock_movement (sku_id, type, qty, document, store)
VALUES ('NK-AM90-WHT-8', 'SALE', -1, 'BILL#902', 'Store-7');

UPDATE changes existing rows; DELETE removes them. On both, the WHERE decides which rows are affected.

🚩 The single most important review check in this whole handbook. An UPDATE or DELETE with no WHERE hits every row in the table.

-- 😱 zeroes every movement, every SKU     -- ✅ scoped to one document
UPDATE stock_movement SET qty = 0;          UPDATE stock_movement SET qty = 0 WHERE document = 'BILL#902';

For a system holding money and stock, never let an un-scoped write through. Your append-only ledger softens the blow (you'd add a correcting entry rather than edit), but the reflex stands.

10 Indexes — why queries are fast or slow

The book's index, for your data

Without help, finding rows means scanning the whole table top to bottom — fine for 100 rows, painful for 5 million movements. An index is a pre-sorted lookup (like the index at the back of a book) on a column, so the database jumps straight to the rows.

CREATE INDEX ON stock_movement (sku_id);   -- on-hand lookups get fast

Index the columns you filter/join on

The ones in WHERE and JOIN ... ON — here, sku_id, store, created_at. Primary keys are indexed automatically.

But don't index everything

Each index makes writes a little slower and uses space. It's a trade-off: faster reads, slightly slower inserts.

🐢 The practical signal: if a KDPS screen gets slow as data grows, "a missing index" is the usual suspect — the database is scanning the whole table. You don't need to tune indexes yourself, but knowing the word lets you ask the AI the right question: "is this query using an index, or scanning the whole table?"

11 Transactions & ACID — all or nothing

The guarantee that money is never half-saved

A single business action often needs several writes together. A counter sale must: add a −1 stock movement and create the bill row and (for SOR) accrue the vendor payable. If the power dies after step 1, you must not be left with stock reduced but no bill.

A transaction wraps those writes so they happen as one indivisible unit — all of them, or none:

BEGIN;
  INSERT INTO stock_movement (...) VALUES (...);   -- −1 stock
  INSERT INTO bill (...)            VALUES (...);   -- the bill
  INSERT INTO vendor_ledger (...)   VALUES (...);   -- payable accrues
COMMIT;   -- all three become real together; any failure → ROLLBACK, none happen

This is the famous ACID promise, four words worth knowing:

LetterMeansFor KDPS
Atomicall-or-nothingsale's writes never split
Consistentconstraints always holdno sale pointing at a missing SKU
Isolatedtwo tills at once don't corrupt each other50 stores billing simultaneously is safe
Durableonce committed, it survives a crasha saved bill stays saved

🧾 In review: any time you see several related writes (stock + money + document), ask "are these wrapped in one transaction?" If not, a crash mid-way can leave your books inconsistent — exactly what an ERP must never do.

12 Migrations — changing the database safely

Git commits, but for the shape of the database

The schema changes over time — you add a season column, a new table. A migration is one such change, saved as a numbered file and applied in order. You never hand-edit the live database; the migration runs the same way on your laptop, the test database, and every store's live database, and each database records which migrations it has run.

-- 014_add_season_to_sku.sql
ALTER TABLE sku ADD COLUMN season TEXT;

When the AI changes your data model, it should produce a migration — and that file is exactly what you review. Your eye goes straight to whether anything is dropped or renamed:

The migration…RiskWhy
adds a table or column🟢 safenothing existing is touched
adds an index🟢 safe(can be slow to build on a huge table)
renames / drops a column🔴 riskycan lose data; old code may break
changes a column's type🟠 carefulcan fail or corrupt if values don't fit
back-fills / updates rows🟠 carefulcheck the WHERE; runs over real data

↩️ Reversible by design: good migrations come in pairs — an "up" (apply) and a "down" (undo) — so a bad change can be rolled back, just like git revert. When reviewing, a safe migration tells you exactly what structural change is about to happen, everywhere, in one readable file.

13 Why so many tables

Normalisation — each fact in exactly one place

Beginners expect one giant table. Databases instead normalise: split data so each fact lives once. Why not store the brand name on every movement row? Because then renaming a brand means editing thousands of rows, and one missed row means contradictory data.

❌ One fat table

Brand name, commission %, SKU details all repeated on every single movement. Update anomalies guaranteed; storage wasted.

✅ Split & linked

brand, sku, stock_movement — each fact once, joined by id. Rename a brand in one place.

The intuition (you don't need the formal "normal forms"): if you're copying the same value into many rows, it probably wants its own table, referenced by a foreign key.

⚖️ The deliberate exception — snapshots. Sometimes you copy a value on purpose. When a sale happens you record the price and the commercial terms as they were that day, even though the brand's master may change later. That's a snapshot, and it's correct: history must not move when a master is edited. So "don't repeat data" has one principled exception — capturing a point-in-time fact. In review, ask: is this duplication a mistake, or a deliberate snapshot?

14 The ledger pattern, in depth

The one pattern the whole KDPS spine rests on

You designed this; here's its database shape and why it's bulletproof. Stock (and money) are stored as an append-only list of movements. Rows are only ever inserted; none is updated or deleted. The current balance is derived by summing.

stock_movement · one SKU
typeqtydocumentrunning total
GRN+5GRN#415
SALE−1BILL#9024
TRANSFER−2TR#882
RETURN+1EXCH#53

This buys you four things a stored count can never give:

  • Audit trail. Every unit traces to a document. You can answer "why is on-hand 3?" exactly.
  • Self-healing. A momentary wrong order (sell-before-inward → −1) is corrected by the next entry; the sum is always eventually right.
  • Time travel. On-hand "as of last Tuesday" = sum of movements up to that date. Stock history for free.
  • Scale & safety. Tiny rows that never change are easy to index and impossible to corrupt by editing.

📒 The same pattern repeats across KDPS: the vendor ledger (payables accrue per SOR sale), the return-allowance budget (drawn down per Correction return). Whenever the answer is "a balance," the right shape is almost always "a ledger you sum," not "a number you overwrite." Spot a stored running total being edited in place, and you've found the bug.

15 The KDPS schema at a glance

How the core tables link

A rough map of the spine's main tables and their relationships (arrows point from the foreign key to the table it references):

MASTERS                         DOCUMENTS                  LEDGERS
brand   ─┐                       booking ──┐
         ├─< sku ─< (barcode)      grn / shipment ─┤
vendor ──┘         │             bill / sale ───┼──> stock_movement   (stock balances)
store ────────────┘             transfer ──────┤
                                 return ────────┴──> vendor_ledger     (payables)
                                                └──> return_allowance   (GR budget)

─< means "one-to-many":  one brand has many SKUs;  one SKU has many movements.
Every document WRITES ledger rows. Nothing edits a balance directly.

🧭 Reading any KDPS feature: find which master it reads, which document it creates, and which ledger that document writes. That three-part trace — master → document → ledger — is the architecture's backbone, and it maps one-to-one onto tables here.

16 The reviewer's checklist

What to actually look for — schema, query, migration

Reviewing a schema

  • Stock/money is a movement ledger (append-only), not a stock_qty you overwrite.
  • Size & colour are their own columns — SKU = Style × Size × Colour survives.
  • The commercial model lives on the brand (one column), not copied per product.
  • Money columns are NUMERIC, never FLOAT; profit is derived, not a typed column.
  • Business rules are real constraints (FOREIGN KEY, CHECK, NOT NULL), not just hopes.
  • State/GST modelled as data (store → state GSTIN; dated tax rates), not hard-coded.

Reviewing a query

  • Three questions: read or write? which table? what's the WHERE?
  • An UPDATE/DELETE with no WHERE → reject.
  • JOINs connect a foreign key to the primary key it points at.
  • Several related writes (stock + money + doc) → wrapped in one transaction?

Reviewing a migration

  • Adding tables/columns → safe. Renaming/dropping or type-changes → look hard, ask about data loss.
  • Any row back-fill → check its WHERE and that it's reversible.

🗣️ Your universal fallback question to the AI: "Walk me through this table/query/migration — what's one row, what gets added versus changed, and where does the data end up?" If the honest answer involves overwriting a balance or an un-scoped write, push back.

17 Glossary

Table
A grid of rows (records) and columns (fields). One kind of thing per table.
Row / Column
A row is one record; a column is one field across all rows.
Schema
The blueprint — all the tables, columns, types, and links.
Primary key (PK)
A row's unique id within its table.
Foreign key (FK)
A column holding another table's id — the link between tables.
Constraint
A rule the database enforces on every write (NOT NULL, UNIQUE, CHECK, FK, DEFAULT).
Query
A request to the database, written in SQL.
SELECT / INSERT / UPDATE / DELETE
Read rows / add a row / change rows / remove rows.
WHERE
Filters which rows a statement affects or returns.
Aggregate
SUM, COUNT, AVG, MIN, MAX — many rows collapsed to one value.
GROUP BY / HAVING
Bucket rows for an aggregate / filter those buckets.
JOIN
Combine rows from two tables along their keys.
Index
A pre-sorted lookup that makes filtering/joining a column fast.
Transaction
A group of writes that all succeed or all fail together.
ACID
Atomic, Consistent, Isolated, Durable — the safety guarantees of a transaction.
Migration
A versioned, ordered change to the schema, applied identically everywhere.
Normalisation
Splitting data so each fact lives in exactly one place.
Snapshot
A deliberate copy of a value as it was at a moment (e.g. price at sale time).
Ledger (append-only)
A table you only ever add to; balances are summed, never stored.
NULL
"No value / unknown." Not zero, not blank. Test it with IS NULL.
NUMERIC vs FLOAT
Exact vs approximate decimals. Money must be NUMERIC.

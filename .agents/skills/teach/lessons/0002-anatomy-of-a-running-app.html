Anatomy of a running app

You designed the spine as ideas — a ledger, a brand master, an AI edge. This lesson shows where those ideas physically live when the software is actually running. It's just four boxes. Once you can see them, "I don't know how any of this works" mostly goes away.

Why this lesson: when you vibe-code, the AI will hand you files. If you know which of the four boxes each file belongs to, you can tell where things go, where they break, and whether the AI's answer even makes sense. That's the end of building blind.

1 The four boxes

Every web app you'll ever build is some version of this

Your ERP isn't one thing. It's four pieces that talk to each other. Each has one job. Learn the one job and you'll never mix them up.

🖥️The ScreenFRONTEND

Shows things & takes taps.

  • Runs in the browser on the store computer
  • Buttons, lists, the bill on screen
  • Knows nothing on its own — it just shows and sends
KDPS: the screen a clerk taps to make a bill
🧠The BrainBACKEND

Decides what's allowed.

  • Where your rules live
  • Checks every request before it counts
  • The bouncer: "AI proposes, the brain decides"
KDPS: the SOR-vs-outright rules, return windows, GST checks
🗄️The MemoryDATABASE

Never forgets.

  • Tables and rows on disk
  • Your ledger physically lives here
  • Survives when everything else restarts
KDPS: every stock movement row, every bill, the brand master
🔌The Outside WorldAPIs

Things you talk to but don't own.

  • Other systems your app calls
  • You send a request, you get an answer
  • If they're down, you cope — you don't control them
KDPS: Ten Software POS, Tally, the AI invoice-reader, WhatsApp

📌 The one-line memory hook: the Screen shows, the Brain decides, the Memory remembers, the Outside World is everyone else. Four jobs, never shared.

2 One sale, through all four

A clerk sells one pair of shoes

Watch a single tap travel through the boxes. This is literally what happens, every time, in every web app — yours included.

  1. ScreenClerk scans the shoe and taps “Bill”. The screen packs up “sell 1 × this SKU” and sends it off. It does not decide anything.
  2. BrainThe request arrives. The brain checks the rules: does this SKU exist? Is the price right? Is GST correct? It's allowed.
  3. MemoryThe brain writes one new movement row — −1 for that SKU — into the ledger. Nothing is overwritten; a line is added. (Lesson 1!)
  4. BrainBrain reads back the new balance and builds the bill total.
  5. ScreenThe screen gets the answer and shows “Sold — stock now 4. Print bill?”
  6. Outside WorldLater, a quiet sync pushes that sale to Tally and pulls nothing back. The store never waited on it.

🧭 This is the whole game. Almost every feature you'll vibe-code is just a new version of this trip: the Screen asks, the Brain rules on it, the Memory records it, and sometimes the Outside World is looped in. When something's broken, your first question is always: which box?

3 Why this kills the fear

What changes for you, the vibe coder

A vibe coder without this map sees one undifferentiated blob of "code" and just hopes. With the map, three things get easier — immediately:

📂 Placing things. AI gives you a file — you can tell if it's Screen, Brain, or Memory, so you know if it landed in the right place.

🔧 Fixing things. "The stock number is wrong" → that's the Memory and the Brain that writes to it. You don't go hunting in the Screen.

🚦 Judging the AI. If the AI says "let the Screen calculate the GST," you now know that's wrong — rules live in the Brain. You can push back.

Who is allowed?

The Brain knows the rules. But before it runs them, it must answer two questions: who are you? and what are you allowed to do? This is the lock on the door — and the place where most real-world breaches happen.

Why this lesson: KDPS holds money, stock and customer data, across 50+ stores and two states. Get "who is allowed" wrong and a cashier sees the owner's profit, or one store edits another's data. This is your design's safety lock — you must be able to review it.

1 Two words people mix up

Authentication vs Authorization

They sound the same and are always said together, but they are two different jobs. Keep them apart.

🪪 Authentication — "who are you?"
  • Proving your identity
  • Done by logging in (password, OTP)
  • Short word: authN
  • KDPS: "are you really cashier Ravi?"
🔑 Authorization — "what may you do?"
  • Your permissions
  • Decided by your role
  • Short word: authZ
  • KDPS: "may Ravi give a discount?"

🏨 Hotel picture: authentication is showing your ID at the front desk (you are who you say). authorization is your room key — it opens your room, not every room. You can be let in the building (authN) and still not be allowed in a room (authZ).

2 How login actually works

The flow, step by step

Follow what happens when Ravi logs in, then makes a sale:

  1. Ravi types his username + password on the screen.
  2. The Brain checks the password against a scrambled (hashed) copy in the database — never a plain one.
  3. If it matches, the Brain sends back a token — a small signed pass that says "user Ravi, role cashier, store 7, expires 6pm."
  4. The screen keeps the token and sends it with every later request.
  5. On each request, the Brain checks the token first (the gatekeeper from L6). No token or expired → 401, stop.

🧠 Connect it to L6: the Brain is stateless — after each reply it forgets you. That's why the token must ride along on every request: it re-proves who you are, each time. The server doesn't "remember" you're logged in.

3 What's inside a token

A signed pass — not a secret to trust blindly

A token is a small bit of text the Brain hands you at login. Think of it as a wristband at an event:

The token says…Why it matters
who you are (user Ravi)so the Brain knows the person
your role (cashier)so it can check permissions
your store (Store 7)so it can scope your data
an expiry (6pm today)so an old/stolen token stops working
a signatureso it can't be faked or edited

🔏 Signed = tamper-proof. If someone edits the token to say "role: owner", the signature breaks and the Brain rejects it. That's why the Brain can trust the token — but, as you'll see in §5, only the token, never a role typed into the request.

4 Roles & permissions

The KDPS permission table (this is authZ)

Instead of setting permissions per person, you group people into roles, and give each role a set of allowed actions. (The proper name is RBAC — role-based access control.) Example for KDPS roles:

ActionCashierStore ManagerOwner
Make a sale✅✅✅
Give a big discount❌✅✅
Approve a return past the allowance❌✅✅
See profit / margins❌❌✅
Edit master data (brands, prices)❌❌✅
See other stores' data❌own storeall stores

💡 Why roles, not per-person: with 50+ stores you can't set rights for each of hundreds of staff. You set them once per role, and every cashier inherits "cashier" rights. New cashier joins → give them the role, done. (Same idea as setting the commercial model once on the brand.)

5 Where the checks happen — in code

Gatekeepers, before the work

Both checks run as gatekeepers (Lesson 6, stage 2) — before the real work, on every request:

// must be logged in (authN)
app.post('/sales', requireLogin, makeSale);

// must be logged in AND a manager (authN + authZ)
app.post('/discounts', requireLogin, requireRole('manager'), giveDiscount);

And here is the most important habit — where the role comes from:

// ❌ WRONG — trusting what the screen sent
const role = req.body.role;     // a user could just type  role: "owner"

// ✅ RIGHT — read it from the verified token
const role = req.user.role;     // put there by requireLogin, can't be faked

🚩 Never trust a role in the request body. Anyone can send { "role": "owner" }. The role must come from the verified token (which is signed and can't be edited). This one mistake hands the keys to anyone who asks.

6 The screen lock is not a lock

Same trap as Lesson 7 — worth repeating

The screen greys out "Discount" for cashiers. Looks safe. It is not, on its own.

❌ Screen only
  • Button greyed out for cashiers
  • But the /discounts endpoint has no role check
  • Anyone can call it directly → discount given
  • The lock is fake
✅ Brain too
  • Screen greys it out (nice for staff)
  • And the endpoint checks the role
  • A direct call without the role → 403
  • The lock is real

🔑 The rule: the screen check is for comfort (fast, friendly). The Brain check is the real lock. Always do both, but never rely on the screen alone.

7 The #1 real-world mistake

"Logged in" is not "allowed to see this"

The most common serious bug in real apps is this: a user is logged in, so the app lets them see anything — including other people's data. Watch:

// Ravi is a cashier at Store 7. His screen asks for:
GET /stores/7/sales      // ✅ his own store — fine

// He edits the URL by hand, 7 → 3:
GET /stores/3/sales      // 🚩 another store! must be BLOCKED

Being logged in is not enough. The Brain must also check: does this user's store match the store they're asking for?

// the missing check
if (req.user.store !== requestedStore)
  return res.status(403).json({ error: 'not your store' });

🏬 Why this matters for KDPS: two states, 50+ stores. Without this check, any logged-in cashier could read every store's sales, the owner's profit, or another state's data — just by changing a number in the address. This is called broken access control, and it is the most common real breach. Always check the user is allowed this specific thing, not just logged in.

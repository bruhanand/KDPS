Chapter 10 · Control plane

Extensibility & Customization

The extend-without-forking toolkit: hooks.py event subscriptions and class overrides, Custom Fields and Property Setters as data, client/server scripts, regional overrides, fixtures, and schema migrations (patches).

Why this is the subsystem that decides whether the ERP lives

Every other chapter in this handbook describes a thing the ERP does: post a ledger, move stock, run a workflow. This chapter describes the thing that decides whether any of that survives contact with real customers. An ERP is not bought and left alone — it is bought and bent. Customer A wants two extra fields on the item master. Customer B operates in a state with a tax regime your core knows nothing about. Customer C's offer logic is unlike anyone else's. And six months later the vendor ships v15 with bug fixes everyone needs.

There are exactly two ways this can go. In the first, every customer's bend is a patch to the core code — a forked branch, a hand-edited controller, a hard-coded if customer == "ACME". That ERP is dead within two upgrade cycles: the vendor cannot push v15 to any customer without re-merging dozens of private forks by hand, so they stop upgrading, so the product rots. In the second way — ERPNext's way — every bend is data or a layer, never an edit to a shipped file. The customer is deeply customized and the vendor can still drop v15 on top, because the core source on disk is byte-for-byte the same on every site. That single property is the difference between an ERP business and a graveyard of one-off forks.

Key idea

Build the ERP so that variation is data and layers, never forks. The data model is itself data (custom fields, property setters); behavior is extended only through a closed, declared catalog of hook points; every region / vertical / client tweak ships as a separate installable app that depends on core; cross-cutting policy lives in named data lists a generic engine reads; and schema evolves through an ordered, run-once, idempotent migration list. The payoff is the one thing a long-lived ERP must have: customers can be deeply customized and the vendor can still upgrade them.

ERPNext shows the layering idea through its hook catalog and regional modules: country and client variation plugs into declared seams instead of forking transaction controllers. India GST / india_compliance is useful external ecosystem context, but it is not present in this ERPNext checkout, so treat it as an example of the broader app-layering pattern rather than source evidence from this repo.

Gotcha · the framework half is not in this checkout

ERPNext is an application; the machinery that reads hooks, realizes custom fields against the live schema, runs the patch log, and resolves overrides lives one layer down in the Frappe framework Frappe core, which is not in this source tree. ERPNext shows you how to use every seam — create_custom_fields(...), @erpnext.allow_regional, hooks.py entries, patches.txt — but the resolver behind each is framework code. If you rebuild this on Django, you are building both halves: the declarations and the engine that wires them.

The two layers that make it work

The whole story is two layers stacked on each other, and it is worth fixing the mental model before the patterns.

Layer 1 makes the data model extensible: because a table is a JSON schema record rather than hand-written DDL, you add a field by inserting a Custom Field row and change a property by inserting a Property Setter row — no schema fork. Layer 2 makes behavior extensible: ERPNext never reaches into Frappe's internals; it only appends entries to the erpnext/hooks.py manifest, which Frappe reads. Layer 3 is the same trick recursively — every region, vertical, and customer is another app that extends ERPNext through that same catalog, with conflicts resolved by install order. The patterns below walk each layer in turn.

Pattern 1 · A fixed catalog of declared hook points

Pattern

The closed hook manifest (hooks.py)

The idea

An app extends another app only through a closed, named set of extension points declared in one manifest file — never by importing and monkey-patching internals.

The host reads the manifest and wires the callbacks. New behavior is added by appending entries, so apps compose cleanly and a host upgrade can never break an extender, because the extender touched nothing in the host.

How ERPNext does it

erpnext/hooks.py is the manifest; Frappe reads it via frappe.get_hooks(...). The catalog is exhaustive — doc_events (per-doctype lifecycle), scheduler_events (cron jobs), extend_doctype_class, override_whitelisted_methods, regional_overrides, doctype_js, jinja.methods, notification_config, on_session_creation, boot_session, website_route_rules, after_install.

Crucially, get_hooks merges the same key across all installed apps — so a client app appends to the very lists ERPNext defined.

Apply to any ERP

On Django/Postgres: a registry module exposing a settings dict {model:{event:[dotted.path]}} plus signal connectors. Use Django signals (pre_save/post_save) as the doc_events analog, Celery beat for scheduler_events, and a settings list of installed extension apps.

The discipline is the whole point: one declarative manifest per app, the host iterates it, no extension ever edits host code.

The heart of the manifest is doc_events — the lifecycle event bus. It maps a doctype (or a wildcard, or a list of doctypes) to lifecycle events (validate, on_submit, on_cancel, on_trash, after_insert, on_update) and the dotted paths to call. Three keying styles do an enormous amount of work:

doc_events = {
    "*": {
        "validate": [
            "erpnext.support.doctype.service_level_agreement.service_level_agreement.apply",
        ],
    },
    tuple(period_closing_doctypes): {
        "validate": "erpnext.accounts.doctype.accounting_period.accounting_period.validate_accounting_period_on_doc_save",
    },
    "Stock Entry": {
        "on_submit": "erpnext.stock.doctype.material_request.material_request.update_completed_and_requested_qty",
        "on_cancel": "erpnext.stock.doctype.material_request.material_request.update_completed_and_requested_qty",
    },
}

erpnext/hooks.py :351

  • The "*" wildcard subscribes a handler to every doctype — here, SLA application runs on the validate of any document.
  • The tuple(period_closing_doctypes) list-key binds one handler to a whole named list at once — every period-closing doctype gets the accounting-period guard with no repetition. (Note how the key is a named list defined elsewhere in the same file — pattern 6.)
  • The plain "Stock Entry" key is the ordinary per-doctype case: submit and cancel both keep Material Request quantities in sync — without Stock Entry's controller ever importing Material Request.

That last point is the whole reason the bus exists: it decouples modules. Stock and purchasing stay in separate files that never reference each other; the manifest is the only thing that knows they are related. When a fourth module needs to react to a Stock Entry submit, it appends one line to its own hooks.py — nothing in stock changes.

The dispatch flow, end to end
User submits a documentany doctype, docstatus 0 → 1
Frappe reads doc_events from ALL appsget_hooks merges every installed app's manifest
Match this doctype + "*" + any list-key containing itcollect every subscribed dotted path
Run each handler in turnSLA apply, period lock, UAE reverse-charge, MR qty update

None of those handlers live in the submitting doctype's controller. The manifest is the wiring; the doctypes stay ignorant of each other.

Pattern 2 · DocType-as-data — custom fields & property setters

Pattern

Make the data model itself data

The idea

A table/form is a declarative schema record, not hand-written code. So fields can be added and properties overridden by inserting more records — customization needs no code change and no schema fork.

Customizations live in their own rows, separate from the core definition, so they re-apply cleanly over a core upgrade instead of being clobbered by it.

How ERPNext does it

Each doctype is a .json schema plus a thin controller (erpnext/stock/doctype/item/item.json carries fields[], permissions[], autoname:"field:item_code").

To extend an existing doctype ERPNext calls create_custom_fields({Doctype:[{fieldname,label,fieldtype,insert_after}]}) and frappe.make_property_setter({doctype,property,value,...}) — both in erpnext/setup/install.py and the regional setups.

Apply to any ERP

Store model definitions in a metadata table. Add a CustomField table whose rows become real columns (or JSONB attributes) at migrate time, plus a PropertyOverride table consulted when rendering forms and validations.

Postgres JSONB or an EAV side-table gives you "add a field as data." A metadata layer reads core schema + override rows to build the effective form. Keep each customer's customizations in their own rows so upgrades never touch them.

The developer-facing API is one call. A regional or client setup builds a dict of {Doctype: [field specs]} and hands the whole thing to create_custom_fields once. The UAE VAT setup is the textbook example — it adds tax fields to Item and Sales Invoice with no edit to either doctype's JSON:

from frappe.custom.doctype.custom_field.custom_field import create_custom_fields

custom_fields = {
    "Item": [
        dict(fieldname="tax_code", label="Tax Code", fieldtype="Data", insert_after="item_group"),
        dict(fieldname="is_zero_rated", label="Is Zero Rated", fieldtype="Check",
             insert_after="tax_code", print_hide=1),
    ],
    "Sales Invoice": sales_invoice_fields + invoice_fields,
}
create_custom_fields(custom_fields, ignore_validate=True)

erpnext/regional/united_arab_emirates/setup.py :185

Note the insert_after key on every spec: a custom field is positioned relative to an existing core field, so it lands in a sensible place on the form. That is also where the first real hazard hides.

Gotcha · insert_after binds to the live schema, and ordering is install-order

Custom Fields and Property Setters are realized against the live schema, so insert_after must reference a field that exists at apply time. If two apps both insert after the same field, the resulting order depends on install order, not on what you intended. Pin insert_after to a stable core field, and write the injection idempotently — check the doctype's existing fieldnames before adding, exactly as the dimension code does (next section).

The runtime case: end-user field injection

Custom fields are not only a developer tool. The Accounting Dimension doctype hands the same power to an end user with no code at all. When a user saves a new dimension, its handler loops every doctype named in the accounting_dimension_doctypes hook and injects a Link field into each — at runtime, on a live system:

# accounting_dimension.make_dimension_in_accounting_doctypes (paraphrased)
for doctype in frappe.get_hooks("accounting_dimension_doctypes"):
    if dimension.fieldname in frappe.get_meta(doctype).get_valid_columns():
        continue                      # idempotent: skip if already injected
    create_custom_field(doctype, df, ignore_validate=True)
    frappe.clear_cache(doctype=doctype)  # bust stale meta so the new field shows

Gotcha · injection mutates the meta cache — and is slow

create_custom_fields and make_property_setter mutate frappe.get_meta's cache. You must frappe.clear_cache(doctype=...) afterward, or stale metadata keeps serving the old form. That is why the dimension loop clears the cache per doctype. And because realizing fields against a live table is expensive, bulk injection is enqueued to a background queue, never run inline in the request — design your own field-injection the same way.

Applying to KDPS

This is exactly how to honour KDPS's Rule 12 ("variation is data, not code") for item attributes. Season, Collection, and Age tags and brand-specific attributes should be custom fields on the item, not new columns hand-cut into the core SKU table — so that SKU = style × size × colour stays the immovable spine while every brand decorates it differently. When a brand needs one more attribute, it is a row, not a migration of the core table.

Pattern 3 · App layering — region & vertical as a separate app

Pattern

Variation ships as a stacked app, not in core

The idea

Variation — a country's tax law, an industry vertical, one client's tweaks — is a separate installable app stacked on top, using only the public hook catalog and data-defined fields.

The base product never carries the variation. When two layers conflict, layering order resolves it: last installed app wins.

How ERPNext does it

ERPNext is itself an app on Frappe (erpnext/modules.txt lists 20 modules in this clone; hooks.py is its manifest). In-tree, erpnext/regional/* holds regional setup/override code such as UAE and Italy, all wired through hooks.

The source-tree proof is that major country behavior is layered through hooks instead of being hard-coded into transaction controllers. This checkout does not contain erpnext/regional/india or an india_compliance app, so India GST references should be treated as external ecosystem context, not ERPNext-source evidence.

Apply to any ERP

Make every customer / region / vertical a Python package (a Django app) that depends on the base ERP app and registers only through the same hook manifest. Resolve overrides by install order.

Never put a client's or country's logic in core. If core lacks a seam, add a generic decorated-overridable function to core first, then implement it in the layer (pattern 4).

The source-backed lesson is that statutory variation belongs behind declared seams: regional setup code, custom fields, regional overrides and hook lists. For very large regimes, the same pattern can be lifted into a separate app. This ERPNext checkout does not contain India GST implementation files, so use the in-tree UAE/Italy hooks as the source example and treat India-specific packs as external context. The default answer to "where does this variation live?" is still a layer.

What "depends on core, registers through hooks" buys you

Because the layer only appends to merged hook lists and adds custom-field rows, the core source on disk is identical whether the layer is installed or not. That is what makes vendor upgrades safe: bench update replaces core files wholesale, the layer's rows and manifest entries are untouched, and the merged behaviour re-composes on next boot. Forking would break this; layering preserves it by construction.

Pattern 4 · Overridable function seams (the allow_regional decorator)

Pattern

Explicit, decorated override points

The idea

Designate specific functions as official override points with a decorator, so an extending app can replace just that function's body for its context — without subclassing or monkey-patching.

The seam is explicit and discoverable (it is right there in the source), and the default body is a safe no-op / passthrough, so an unconfigured tenant runs base behaviour.

How ERPNext does it

@erpnext.allow_regional wraps a function; at call time it looks up frappe.get_hooks("regional_overrides")[get_region()] and, if the company's country maps this function path to a replacement, calls that instead (erpnext/__init__.py :133–152).

Core declares the seam as a passthrough; a regional app's hooks.py maps the path to its own implementation. The class-level cousin is extend_doctype_class (Address → ERPNextAddress, chaining super().validate()).

Apply to any ERP

Wrap extensible business logic in a small dispatcher: a decorator (or strategy lookup) keyed by tenant / region / company that resolves to a registered override or falls back to the default.

On Django: a registry dict {('region','func'):callable} populated by each app's AppConfig.ready(), consulted by a decorator. Keep defaults as explicit no-ops so an unconfigured tenant runs base behaviour.

The decorator itself is small enough to read whole. The mechanism is: compute the fully-qualified path of the wrapped function, look up the current company's region in the merged regional_overrides map, and if that region remaps this exact path, call the remapped target — otherwise call the original:

def allow_regional(fn):
    """Decorator to make a function regionally overridable"""
    @functools.wraps(fn)
    def caller(*args, **kwargs):
        overrides = frappe.get_hooks("regional_overrides", {}).get(get_region())
        function_path = f"{inspect.getmodule(fn).__name__}.{fn.__name__}"
        if not overrides or function_path not in overrides:
            return fn(*args, **kwargs)
        # Priority given to last installed app
        return frappe.get_attr(overrides[function_path][-1])(*args, **kwargs)
    return caller

erpnext/__init__.py :133

Two details carry the whole design philosophy. First, overrides[function_path][-1] — the value is a list (because get_hooks merges across apps), and the code deliberately takes the last one: "priority given to last installed app." Second, the fallback is return fn(*args, **kwargs) — if no region remaps this path, the original runs unchanged. Now look at how core declares the seam — it is a one-line passthrough that returns its input untouched:

@erpnext.allow_regional
def make_regional_gl_entries(gl_entries, doc):
    return gl_entries

erpnext/accounts/doctype/sales_invoice/sales_invoice.py :1206

On a plain-vanilla company this does nothing — the GL entries pass straight through. The same seam exists on Purchase Invoice, and in this ERPNext clone the UAE layer maps the purchase_invoice.make_regional_gl_entries path in hooks.py to erpnext/regional/united_arab_emirates/utils.py, whose version adds reverse-charge lines before returning them. The transaction controller never knows UAE exists; it just calls the decorated function at the right moment, and the right body runs based on the company's country.

Gotcha · you can only override what core decorated

regional_overrides fires only through functions explicitly decorated @erpnext.allow_regional. You cannot override an arbitrary core function this way — there is no monkey-patch escape hatch, by design. If core lacks a seam where you need one, you must first add the decorated passthrough to core (a small upstream change), then override it from your layer. This is a feature, not a limitation: every override point is visible in the source, so the set of things a layer can change is auditable.

Gotcha · class overrides must call super() defensively

The class-level seam, extend_doctype_class (e.g. Address → erpnext/accounts/custom/address.py's ERPNextAddress), chains to the parent with if hasattr(super(), "validate"): super().validate() — guarded, because the parent may or may not implement validate depending on the framework version. Assume the method exists and your subclass breaks across an upgrade. Always probe before chaining.

Applying to KDPS

KDPS's two-GSTIN reality (Bihar and Jharkhand are distinct persons; cross-state transfers are taxable IGST, intra-state is CGST/SGST) is precisely a make_regional_gl_entries-shaped problem. Model an allow_regional-style dispatcher keyed by store → state-GSTIN, so the IGST-vs-CGST/SGST posting decision lives in one overridable place rather than branching through every posting path. The default body posts the simple intra-state case; the inter-state body adds the IGST line. When the apparel GST slab changes (it is date-effective), you edit the data behind that seam — not the posting code in twenty documents.

Pattern 5 · Ordered, idempotent, run-once migrations (patches.txt)

Pattern

The checked-in migration ledger

The idea

Schema and data evolution is a checked-in, ordered list of single-purpose migration scripts, each of which runs exactly once per site and is written to be safely re-runnable / guarded.

A persistent log records what has already run, so upgrades are deterministic across any starting state — fresh, half-upgraded, or years old.

How ERPNext does it

erpnext/patches.txt is a ~490-line ordered list, split into [pre_model_sync] (run before new DocType JSONs are imported) and [post_model_sync] (after the schema is current).

Each non-comment line is a dotted path to a module under erpnext/patches/ exposing def execute(). Frappe records each path in a patch-log table and skips ones already run; date comments and #1/#2 suffixes force a known patch to re-run.

Apply to any ERP

Beyond Django's auto-migrations (schema), keep a separate ordered list of hand-written data migrations with a runner that records applied names and skips them.

Order matters (before vs after schema apply); each guards its own preconditions so partial states don't crash. Never edit a shipped migration in place — append a new one. Treat the migration log as the source of truth for DB state.

The file's two-section structure is not cosmetic — it is a hard ordering contract against the schema import that happens between them:

[pre_model_sync]run vs OLD schema
import DocType JSONsschema becomes current
[post_model_sync]run vs NEW schema

A patch that must read or write a field in the new schema belongs in [post_model_sync]. A patch that must run against the old schema — say, to copy data out of a column before a later schema change drops or renames it — belongs in [pre_model_sync]. Put it in the wrong half and you get either an "unknown column" crash or a silent no-op.

The defining property of every patch is defensive idempotence: it can run on millions of sites in unknown states, so it must guard its own preconditions and tolerate being re-applied. This finance-book patch is the model — early-return if there is no India company, and update=1 so re-adding the field is harmless:

def execute():
    company = frappe.get_all("Company", filters={"country": "India"})
    if not company:
        return                       # guard: nothing to do for non-India sites
    custom_field = {
        "Finance Book": [
            {"fieldname": "for_income_tax", "label": "For Income Tax",
             "fieldtype": "Check", "insert_after": "finance_book_name"}
        ]
    }
    create_custom_fields(custom_field, update=1)  # update=1 → safe to re-apply

erpnext/patches/v13_0/create_custom_field_for_finance_book.py

The list also supports execute: inline one-liners (e.g. a single frappe.reload_doc or db.set_value right in patches.txt) for trivial one-off statements that don't warrant a module. Larger structural patches get their own files — see erpnext/patches/v14_0/rearrange_company_fields.py.

Gotcha · never edit a shipped patch; the log keys on the path

Frappe's patch log keys on the dotted path. So editing a shipped patch in place will not re-run it — the path is already logged as done. To force a re-run, ERPNext appends a date comment and a #1/#2 suffix to change the recorded key. This trick is easy to get wrong (wrong suffix, wrong section). The safe default is the universal one: append a new patch, never mutate an old one, and write every patch to tolerate any starting state — fresh install, half-upgraded, country not India, doctype since renamed.

Pattern 6 · Cross-cutting policy as named data lists

Pattern

Behaviour registries, not scattered conditionals

The idea

Express system-wide rules — which doctypes are period-locked, exempt from auto-cancel, carry accounting dimensions, or trigger which jobs — as named lists/dicts in the manifest, not scattered if conditionals.

Generic engines iterate the list. So opting a doctype into a behaviour is a one-line data change, and the policy stays auditable in one place.

How ERPNext does it

erpnext/hooks.py defines named lists: period_closing_doctypes, pre_submit_validation_doctypes, accounting_dimension_doctypes, auto_cancel_exempted_doctypes, repost_allowed_doctypes, global_search_doctypes.

doc_events then binds a handler to a whole list at once via tuple(period_closing_doctypes) (pattern 1). erpnext/startup/notifications.py's notification_config is a data dict of {doctype: filter} the desk reads for unread counts.

Apply to any ERP

Keep behaviour registries as plain data (lists / dicts / settings) and write one generic engine per behaviour that consults the registry — instead of if doctype in (...) sprinkled through code.

To opt a model into a behaviour, add its name to the list. Because the registry is a hook key, extension apps can extend the list through the same get_hooks merge — without touching the engine.

The most consequential of these lists encodes the ledger's most important cancellation invariant. auto_cancel_exempted_doctypes names ledger doctypes — GL Entry, Stock Ledger Entry, Payment Ledger Entry — that the generic cancel cascade must not cancel as ordinary linked documents. Instead, their owning controllers run ledger-specific reversal logic. In ERPNext classic mode that reversal path can also mark originals is_cancelled=1; immutable-ledger mode leaves originals untouched and posts dated reversals.

Gotcha · ledger immutability is a data convention, not a framework guarantee

Nothing in the framework alone makes GL Entry safe — the exemption list plus the controller reversal path are the rule. Reimplement a cancel cascade naively (cancel every linked ledger row as if it were a normal child) and you will corrupt the books: a cancelled invoice would erase or directly cancel its postings instead of reversing them. When you build your own ledger, the exemption registry and the reverse-don't-delete engine that reads it are both mandatory. See the accounting ledger and the stock ledger for how the reversal entries are written.

Applying to KDPS

This is the mechanism behind KDPS's "documents write ledgers; ledger effects are traceable" rule. The PT-posts-value-and-liability and GRN-posts-quantity events should be doc_events-style lifecycle handlers, and the resulting GL / Stock-Ledger entries belong on an auto_cancel_exempted-style list — so a cancelled or amended receipt reverses, never deletes. With Tally as the statutory book of record, an entry that was silently deleted instead of reversed would put the two books out of sync — which is exactly the failure the exemption list prevents.

Decision rule

Add a field → Custom Field. Change a default / option / label → Property Setter. React to a save/submit → doc_events. Change one piece of regional posting logic → decorated seam + regional_overrides. Replace a whole controller → extend_doctype_class. Make a doctype participate in a system-wide behaviour → add it to the named list. Migrate existing data → a new patch. If none fit because core lacks a seam, the right move is to add a decorated passthrough to core, not to fork.

Putting it together: adding a country without forking

The patterns are not separate tricks — they compose into one repeatable recipe. Here is the entire flow for teaching ERPNext a new country's tax behaviour, using only public seams:

1 · Write setup.pybuild a {Doctype:[fields]} dict, call create_custom_fields — adds VAT/TRN fields to Item & Sales Invoice (pattern 2)
2 · Register replacements in hooks.py regional_overridesmap make_regional_gl_entries, update_itemised_tax_data → your functions (patterns 1 & 4)
3 · Core's @allow_regional routes at runtimeby company country — your reverse-charge body runs, nobody else's changes (pattern 4)
4 · Ship a patch if existing data needs backfillingordered, idempotent, logged (pattern 5)
5 · For a big regime, lift the whole thing into its own appsame layering pattern, outside this checkout when needed

Not one of those five steps edits a core file. The Item and Sales Invoice JSONs are untouched; the Sales Invoice controller is untouched; the ledger engine is untouched. The new country is entirely additive — and that is precisely why the next core upgrade lands cleanly on top of it.

Gotchas, collected

The hazards in this subsystem are not edge cases — they are the places where a naive reimplementation quietly corrupts data or breaks on upgrade. Keep this list at hand while building.

insert_after must already exist; order is install-order
Custom Fields/Property Setters apply against the live schema. If two apps insert after the same field, ordering is decided by install order. Pin to a stable core field and check existing fieldnames first.
patches must be idempotent and section-correct
Guard every precondition (if not company: return, frappe.db.exists, update=1). And [pre_model_sync] vs [post_model_sync] is load-bearing: read/write a new field → post; touch a soon-to-be-dropped column → pre. Wrong half throws "unknown column" or silently no-ops.
never edit a shipped patch in place
The log keys on the dotted path; editing won't re-run. Append a new patch. The date-comment + #1/#2 re-run trick exists but is easy to get wrong.
you can only override decorated functions
regional_overrides fires only through @erpnext.allow_regional. No monkey-patch escape hatch — if the seam isn't there, add the passthrough to core first.
subclass overrides must probe super()
extend_doctype_class subclasses use if hasattr(super(), "validate"): super().validate() because the parent may not implement it on every framework version. Assume it exists and you break on upgrade.
field injection mutates the meta cache and is slow
frappe.clear_cache(doctype=...) after injecting, or stale metadata serves the old form. Enqueue bulk injection to a background queue — never run it inline in a request.
ledger immutability is convention, enforced by a list
GL Entry / Stock Ledger Entry / Payment Ledger Entry are in auto_cancel_exempted_doctypes so a parent cancel never cancels them — reversals are posted instead. Reimplement the cancel cascade naively and you corrupt the books. The exemption list is the rule.

Takeaways

  1. Variation is data and layers, never forks. The single property that keeps a long-lived ERP alive is that the core source on disk is identical on every site, so the vendor can always upgrade. Every customization must preserve that property by construction.
  2. Make the data model itself data. A table/form is a schema record; add fields with a CustomField table and change properties with a PropertyOverride table. Customer customizations live in their own rows and survive core upgrades untouched. (Frappe: create_custom_fields, make_property_setter.)
  3. Publish one closed manifest of named hook points — lifecycle events keyed per-model with a "*" wildcard and list-keys, scheduled jobs, class overrides, whitelisted-method overrides, and decorated overridable-function seams. The host iterates the manifest; extensions append, never patch. (ERPNext: hooks.py, read via get_hooks.)
  4. Ship every region / vertical / client tweak as a separate installable app that depends on core and registers only through the manifest, with conflicts resolved by install order (last app wins). The source-backed pattern is regional behavior through hooks; very large statutory packs can live outside core as separate apps.
  5. Make override points explicit and discoverable. A decorated dispatcher (@allow_regional) with a safe no-op default means unconfigured tenants run base behaviour and there is no monkey-patch back door — the set of overridable points is auditable in the source.
  6. Put cross-cutting policy in named data lists that generic engines consult, not in scattered conditionals. Opting a doctype into a behaviour becomes a one-line data change — and ledger immutability is exactly such a list (auto_cancel_exempted_doctypes): the list is the rule, so build the reverse-don't-delete engine that honours it.
  7. Evolve schema and data through an ordered, run-once, idempotent, logged migration list split into before-schema and after-schema phases. Each patch guards its preconditions and tolerates any starting state; never edit a shipped patch — append a new one.
  8. For KDPS: design the hook catalog and custom-field / override seams up front in the foundation build. That is what lets 40+ brands, two state GSTINs, SOR/Outright/Hybrid commercial models, and an evolving offer engine be configured rather than re-coded — the concrete shape of Rule 12, "variation is data, not code."

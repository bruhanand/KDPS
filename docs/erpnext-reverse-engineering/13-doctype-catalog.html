DocType Catalog & Module Map

A reference index of ERPNext’s load-bearing DocTypes grouped by module and classified (master / transaction / child / ledger / single / setup), with the chapter that explains each.

Why a catalog is the thing you actually build from

Every chapter before this one explained a mechanism: how the meta-model works, how the two ledgers post, how tax resolves, how permissions gate. This chapter is the map — the flat catalog of business objects those mechanisms operate on. It matters for a blunt reason: when you sit down to build a custom ERP, the first irreversible decision is "what are my entities, and what structural role does each one play?" Get that classification right and almost everything downstream — storage, lifecycle, list views, the REST API, status propagation, reports — becomes generic machinery you write once. Get it wrong and you hand-code the same four behaviours over and over, badly, per table.

ERPNext makes this decision unusually legible. The entire ERP is a flat catalog of roughly 700 DocTypes folded into 21 modules (listed in erpnext/modules.txt). Every business object — Account, Sales Invoice, the line item inside it, the settings singleton beside it — is a DocType defined by one JSON file at erpnext/<module>/doctype/<name>/<name>.json, optionally with a Python controller <name>.py and a client script <name>.js. You can classify any object in the system by reading four boolean flags off its JSON. That is the whole trick of this appendix: a small, finite taxonomy that you reuse verbatim on your own stack.

Key idea An ERP is not a hierarchy of bespoke screens — it is a flat catalog of metadata-described entities, each tagged with a structural role, folded into process-aligned modules. Four flags (istable, issingle, is_submittable, is_tree) plus the derived role (master / transaction / child / ledger / single / setup) tell you how each entity stores, lives, and behaves. Build behaviour off the role, not off the entity name.

The five layers below are the shape every module decomposes into — masters and setup are shared at the base, each process owns its documents, and all documents converge on two append-only ledgers (covered in chapter 3 and chapter 4):

The five patterns that organise the catalog

Pattern

The metadata-described DocType is the unit of modeling

The idea

Every business entity is defined by declarative metadata — fields, types, naming, permissions, layout — not by hand-written tables plus forms plus serializers. One artifact describes the schema; the framework generates the table, the REST API, the list view and the form.

This collapses what is normally five files — model, migration, serializer, admin form, template — into one. The catalog is therefore just a directory of these manifests.

How ERPNext does it

Each DocType is erpnext/<module>/doctype/<name>/<name>.json with a field_order array and a fields list, plus an optional Python controller and JS client script.

erpnext/stock/doctype/item/item.json declares autoname: field:item_code, track_changes: 1. erpnext/accounts/doctype/gl_entry/gl_entry.json declares is_submittable: 1 and a date-series name.

The JSON-to-table ORM and form renderer live in Frappe, not in this checkout. Frappe core

Apply to any ERP

On Django/Postgres, keep a declarative schema layer — a model registry, or JSON/YAML manifests — that generates migrations, DRF serializers and CRUD forms, instead of scattering one entity across models.py + migration + serializer + form + template.

Turn the naming convention (field:x, series with date tokens like ACC-GLE-.YYYY.-.#####) into a tiny naming service every entity calls.

The shape of a DocType JSON, reduced to the parts that classify it (real, from the GL Entry manifest):

// erpnext/accounts/doctype/gl_entry/gl_entry.json
{
 "autoname": "ACC-GLE-.YYYY.-.#####",
 "document_type": "Document",
 "is_submittable": 1,
 "field_order": [
  "posting_date", "fiscal_year",
  "account", "party_type", "party",
  "voucher_type", "voucher_no",
  "against_voucher_type", "against_voucher"
 ]
}

Notice there is no SQL, no migration, no form code here — just the schema and the flags. The presence of is_submittable, the date-series autoname, and the voucher_type/voucher_no back-reference are enough to tell you this is a ledger row written by some other document. That is the entire classification, read straight off the file. See chapter 1 for how the JSON becomes a table.

Pattern

Four flags classify every entity

The idea

A tiny set of boolean flags captures an entity's structural role, so behaviour — storage, lifecycle, UI, validation — is driven generically off the flag rather than coded per entity.

Four flags, four behaviours: composition, singleton, state-machine, hierarchy. Everything else is a "plain master or transaction."

How ERPNext does it
  • istable → child line-item table stored only inside a parent (erpnext/accounts/doctype/sales_invoice_item/sales_invoice_item.json).
  • issingle → one-row settings (erpnext/accounts/doctype/accounts_settings/accounts_settings.json).
  • is_submittable → draft→submitted→cancelled, immutable after submit (erpnext/accounts/doctype/sales_invoice/sales_invoice.json).
  • is_tree → nested-set with nsm_parent_field (erpnext/accounts/doctype/account/account.json).
Apply to any ERP

Bake an entity_kind enum into your metadata and let generic machinery branch on it:

  • child = composition with cascade + ordering by idx;
  • single = one-row config table;
  • submittable = state machine + post-submit immutability;
  • tree = adjacency or nested-set with a parent pointer.

Never reimplement these four behaviours per table.

The nested-set master shape, which every hierarchical master in ERPNext reuses (Account, Warehouse, Cost Center, Company, Item Group, Territory, Department, …):

// erpnext/accounts/doctype/account/account.json
{
 "is_tree": 1,
 "nsm_parent_field": "parent_account"
 // children point at their parent; lft/rgt give O(1) subtree queries
}
Gotcha · the flags are independent, classify on the combination is_tree and is_submittable can co-occur conceptually but the JSON flags are independent — classify on the combination, not a single flag. And some masters are unexpectedly submittable: BOM and Product Bundle are masters that carry a submit lifecycle (a BOM must be submitted to be usable). Read intent, not just one boolean.
Pattern

Process-aligned modules with shared ledgers at the bottom

The idea

Modules mirror the real-world business process flow (buy → receive → store → sell → invoice → pay), not technical layers. Masters and setup are shared; each process owns its transactions; all transactions converge on two append-only ledgers.

This keeps the dependency graph a clean funnel, not a web.

How ERPNext does it

erpnext/modules.txt lists 21 modules. Transactions live in their process module: Buying owns Purchase Order; Stock owns Purchase Receipt / Delivery Note / Stock Entry; Selling owns Sales Order; Accounts owns Sales Invoice / Payment Entry.

Every financial posting becomes erpnext/accounts/doctype/gl_entry/gl_entry.json rows; every inventory move becomes erpnext/stock/doctype/stock_ledger_entry/stock_ledger_entry.json rows — each tagged voucher_type/voucher_no. erpnext/stock/doctype/bin/bin.json caches the balance.

Apply to any ERP

Lay packages out by business process. Put master data plus a generic ledger primitive at the base, and make every document post into the ledger via one posting interface: given a document, emit balanced ledger rows tagged with the source voucher.

Reports read the ledger; documents never read each other's internal state. This is exactly KDPS's "documents-write-ledgers" rule.

The two ledgers are themselves DocTypes, and the SLE row carries the running balance plus valuation, back-referenced to the voucher that caused it:

// erpnext/stock/doctype/stock_ledger_entry/stock_ledger_entry.json
"field_order": [
 "item_code", "warehouse",
 "posting_date", "posting_time",
 "voucher_type", "voucher_no", "voucher_detail_no",
 "serial_and_batch_bundle",
 "actual_qty", "qty_after_transaction",
 "incoming_rate", "outgoing_rate"
]
Gotcha · a few names are filed where you don't expect Purchase Receipt and Delivery Note are Stock transactions, not Buying/Selling. Sales Invoice and Purchase Invoice live in Accounts, not Selling/Buying. Quality Inspection lives under Stock, not Quality Management. The file path follows the process the document belongs to (where it posts), not the party it names.
Pattern

A controller inheritance chain factors cross-cutting transaction behaviour

The idea

Common transaction concerns — taxes & totals, stock posting, GL posting, status propagation — are implemented once in base classes and inherited, so a new document type writes only its specifics.

Behaviour composes by walking up the class chain; the catalog stays thin because the heavy logic is shared.

How ERPNext does it

In erpnext/controllers/: SellingController → StockController → AccountsController → TransactionBase → StatusUpdater → Document (and BuyingController → SubcontractingController → StockController).

A Sales Invoice controller inherits erpnext/controllers/taxes_and_totals.py, stock + GL posting, and erpnext/controllers/status_updater.py percent-billed/percent-delivered logic for free.

Apply to any ERP

Provide services / mixins for the orthogonal concerns — TaxCalculator, StockPoster, GLPoster, StatusUpdater — and let each transaction type compose them.

In Django these are service classes invoked from save()/signals rather than deep inheritance, but the lesson holds: never re-derive tax totals or ledger posting per document.

# selling_controller.py
class SellingController(StockController): ...
# stock_controller.py
class StockController(AccountsController): ...
# accounts_controller.py
class AccountsController(TransactionBase): ...
# utilities/transaction_base.py
class TransactionBase(StatusUpdater): ...

The catalog and the chain are two views of the same fact. The catalog says "Sales Invoice is a submittable transaction in Accounts that posts GL and optionally stock." The chain is how it gets all of that without re-implementing any of it. When you read the catalog, every "submittable transaction" entry is implicitly a promise that a shared controller stack will give it taxes, posting and status. See chapter 5 for the chain in motion.

Pattern

Configuration and analytics as data, not code

The idea

Things that vary by business policy — tax rates, price/discount rules, payment terms, reporting axes — are stored as records, so changing them is data entry, not a code deploy.

New analytic slices are declared, then auto-propagated onto ledger rows. The catalog grows a "setup" tier of these policy records.

How ERPNext does it

Tax stacks: erpnext/accounts/doctype/sales_taxes_and_charges_template/sales_taxes_and_charges_template.json + Item Tax Template (slab/HSN overrides). Offers: Pricing Rule + Promotional Scheme (expands into many rules). Terms: Payment Terms Template → Payment Schedule rows.

Analytics axes: erpnext/accounts/doctype/accounting_dimension/accounting_dimension.json declares an extra column pushed onto GL Entry. Even the module navigation is data now — erpnext/accounts/workspace/invoicing.

Apply to any ERP

Model every business-variable rule (tax, discount, terms, commission) as queryable rows with scope + date-effectivity, resolved at transaction time.

Make reporting dimensions registerable so adding "store" or "brand" as an analytic axis is a config row, not a schema migration. This is KDPS's Rule 12, "variation is data, not code."

Applying to KDPS The whole "data not code" tier maps directly onto KDPS's reality: 40+ brands become Brand rows, not code; date-effective apparel GST slabs become Item Tax Template + Tax Category; brand-specific slab offers become Pricing Rule / Promotional Scheme; and adding store or season as a reporting axis becomes an Accounting Dimension-style config row. Nothing in that list should ever require a deploy.

The classification scheme — the table you keep open while building

Six roles cover the entire catalog. The first four are read directly off the flags; ledger, master and setup are derived roles you assign by intent (a ledger is a submittable append-only row written by another document; a setup record is a reference/policy master that no transaction depends on for posting balance). This is the exact taxonomy your own data-model should tag each entity with.

RoleFlag(s)What it isBehaviour you build onceCanonical examples
master none / is_tree Long-lived reference data, edited in place, no submit lifecycle. CRUD + audit trail; nested-set if tree. Item, Customer, Supplier, Warehouse, Account, Brand
transaction is_submittable: 1 A business event with draft → submitted → cancelled; immutable after submit. State machine; on-submit posting; on-cancel reversal. Sales Invoice, Purchase Receipt, Stock Entry, Payment Entry
child istable: 1 Line items stored only inside a parent; no standalone existence. Composition + cascade + order by idx. Sales Invoice Item, Journal Entry Account, Item Barcode
ledger is_submittable: 1 + voucher back-ref Append-only event row written by another document; the source of truth. Atomic write/cancel with parent; never UPDATE a balance. GL Entry, Stock Ledger Entry, Payment Ledger Entry, Bin*
single issingle: 1 Exactly one row; system/module configuration. One-row config table; treat as config, not records. Accounts Settings, Stock Settings, Global Defaults
setup none Policy / reference records resolved at transaction time (tax, pricing, terms). Scoped, date-effective lookup; "variation is data." Item Tax Template, Pricing Rule, Mode of Payment, Incoterm

*Bin is a derived cache (one row per item×warehouse) computed off the SLE — a read model, not an independent ledger. The true history is Stock Ledger Entry.

Gotcha · submittable is not "just a status field" After submit a document is immutable, and editing requires cancel — which must reverse all of its ledger postings. The ledgers (GL Entry, Stock Ledger Entry) are themselves submittable and are written/cancelled atomically with their parent voucher. You cannot just UPDATE a balance row. A naive reimplementation that mutates a single balance silently corrupts valuation on back-dated transactions — which is why ERPNext has Repost Item Valuation to recompute downstream SLE rates after a back-dated change.

How the catalog moves — the canonical flows

The catalog is static; the system is the documents flowing through it. Four flows tie the entries above together, and a fifth — the posting funnel — is what all of them collapse into. Each downstream document pulls forward from the previous one and updates its percent-received / percent-billed status via the shared StatusUpdater.

Applying to KDPS The POS-day flow is exactly KDPS's "Ten Software behind one POS, idempotent-merge" design: per-store POS invoices accumulate during the shift, reconcile at close, and merge into the proper Sales Invoices that hit the GL and stock once. And the procure-to-stock flow encodes the KDPS rule that GRN posts quantity (Purchase Receipt → SLE) while the PT/bill posts value and liability (Purchase Invoice → GL) — two separate documents, two separate ledgers, by design.

Gotcha · child tables and the engine you don't own Two things to keep straight when you implement from this catalog. Child tables (istable) have no independent life — no list view, no standalone permission, always loaded/saved through the parent and ordered by idx. Don't model line items as a top-level entity with a back-FK; the framework owns the composition. And the DocType engine itself is not in this repo — naming, the submit/cancel state machine, child-table storage (parent/parentfield/parenttype/idx columns), nested-set lft/rgt maintenance, permissions and the REST API all live in Frappe. ERPNext only authors JSON metadata + Python subclasses on top of it. Frappe core Reimplementing "ERPNext" means rebuilding Frappe's engine first.

Mapping the catalog onto a KDPS build

This catalog is not academic for the KDPS work — it de-risks it line by line. KDPS's 5-layer constitution (masters → documents → ledgers → controls → intelligence) and its "documents-write-ledgers" rule are ERPNext's GL Entry / Stock Ledger Entry funnel with voucher back-references. Borrow that shape verbatim on Django/Postgres. The mapping is one-to-one:

SKU = Style × Size × Colour

non-unique barcode

GRN posts quantity · PT posts value/liability
Purchase Receipt → Stock Ledger Entry (qty) and Purchase Invoice → GL Entry (value + payable). Two documents, two ledgers.

"variation is data, not code" (Rule 12)
Accounting Dimension + the template family — new analytic axes and policies are config rows, not migrations.

Two structural lessons carry straight into the build. First, tag every KDPS entity in your data-model with one of the six roles in the table above — that classification is the data-model's spine. Second, the controller-chain lesson: build TaxCalculator, StockPoster, GLPoster and StatusUpdater once as services, invoked from each transaction's save path — not re-derived per vertical slice. If you get the entity-classification metadata and the document-writes-ledger funnel right, the rest — list views, APIs, reports, status propagation — becomes generic machinery you build once.

Key idea The deliverable a consultant returns to is not a screen inventory — it is this classified catalog. Name your entities, tag each with a role, draw the process modules, and route every document through one posting interface into two append-only ledgers. Everything else is downstream of those four decisions.

Takeaways

  1. An ERP is a flat catalog of metadata-described entities folded into process-aligned modules — read the catalog, not the screens.
  2. Four flags classify everything: istable (child), issingle (singleton), is_submittable (transaction/ledger), is_tree (hierarchy) — plus the derived roles master / ledger / setup. Build behaviour off the role, six behaviours total.
  3. Modules mirror the business process (buy → receive → store → sell → invoice → pay), masters and setup are shared at the base, and all transactions converge on two append-only ledgers — GL Entry and Stock Ledger Entry — tagged with voucher_type/voucher_no.
  4. Cross-cutting transaction behaviour (taxes, stock posting, GL posting, status) lives in a shared controller stack, not per document. Build it once as services.
  5. Policy that varies by business — tax, discount, terms, analytic axes — is data, not code: queryable, scoped, date-effective rows resolved at transaction time.
  6. Watch the traps: file documents by where they post (Purchase Receipt is Stock, Sales Invoice is Accounts); submit is immutability + reversible posting, not a status field; Bin is a cache, the SLE is truth; and the DocType engine is Frappe, not ERPNext — rebuilding ERPNext means rebuilding the engine first.
  7. For KDPS, the map is one-to-one: tag every entity with one of the six roles, route every document through one posting interface into the two ledgers, and the rest is generic machinery.

Chapter 1 · Foundations

The Meta-Model — everything is a DocType

The single most important idea: model your domain as schema-defined documents, not hand-written tables. How a DocType is just data, and why that buys you the entire admin UI, ORM, REST API and audit trail for free.

Why this is the chapter that decides everything

Before you write a line of an ERP, you make one architectural choice that you cannot cheaply reverse: do business objects live in code, or in data? The instinctive answer is code — a Customer class, a customers table, a customer controller, a customer form, a customer API. Repeat fifty times for fifty entities. Every entity is a small subsystem you hand-wire, and every cross-cutting concern — audit columns, permissions, a draft/submit state machine — has to be remembered and re-implemented on each one. The cost is not the first ten entities; it is the next five hundred, and the day someone asks for a new field and you have to touch six layers to add it.

ERPNext makes the opposite choice, and it is the choice this whole handbook builds on. Its foundational idea is that a DocType is itself data, not code. Every business object — masters, transactions, ledgers, settings, even the child rows inside a grid — is declared as a .json file: a list of fields, each with a type and a handful of flags, plus a few document-level switches. A framework (Frappe, which is not in the ERPNext checkout but underneath it) reads that schema and derives the SQL table, the list view, the form UI, a REST/RPC API, an ORM, the role-based permission engine, and a uniform set of audit columns — none of it hand-written. ERPNext ships roughly 528 DocTypes this way.

Key idea

Model your metadata as a first-class citizen and build (or adopt) one generic engine over it. Then adding an entity is writing one declaration — not wiring six subsystems by hand. Every record shares the same shape, so observability, the state machine, typed links, and polymorphic associations come for free and behave identically everywhere. That uniformity is the entire payoff.

The rest of this chapter walks the meta-model concretely: the file triplet that makes up a DocType, the lifecycle hooks where logic hangs, how relationships and behaviour are themselves encoded as data, and the document-level flags (naming, single, submittable) that turn one schema into a table, a config object, or a ledger. We finish with the standard audit columns the framework injects, the pitfalls of porting this to a plain SQL stack, and the takeaways a builder returns to.

The whole picture: one declaration, six capabilities

Here is the leverage, stated as a flow. You write one schema file. The engine hands you six subsystems back, before you have written any behaviour at all.

Write item.jsonfield_order + fields[] + flags — pure data
SQL tablecolumns derived from fieldtypes; created/migrated by the engine
List view + Form UIfilterable list, editable form, grids for child tables — no front-end code
REST endpoint/api/resource/Item — CRUD over HTTP for free
ORM handlefrappe.get_doc("Item", code), frappe.db.get_value(...)
Permissions + audit columnsper-role/per-field checks; owner/creation/modified injected on every row

Only after that do erpnext/stock/doctype/item/item.py and erpnext/stock/doctype/item/item.js exist, and they exist only to add behaviour on top of the free baseline. The schema is mandatory; the controller and client script are optional. That asymmetry is the signature of a metadata-driven system.

A note on where the line is

Throughout this handbook, Frappe core marks a feature provided by the underlying framework (the generic engine), and ERPNext marks app-level code that uses that feature. The split matters when you port: the DocType .json files are ERPNext's, but the machinery that turns them into tables, APIs and permissions is Frappe's. Copy only the JSON and you copy the data without the engine.

Pattern 1 — Schema-as-data: the DocType is metadata

Pattern

Schema-as-data (DocType = metadata, not code)

The idea

Describe each business object declaratively as data: its fields, their types, and a few flags. A single generic engine then derives the table, the UI, the API, the ORM, the permissions and the audit columns from that one declaration.

You stop writing entities and start declaring them. The marginal cost of the 100th entity is the same as the 1st.

How ERPNext does it

Each DocType is a JSON file with three parts: document-level flags, a field_order list, and a fields array of dicts like {fieldname, fieldtype, options, reqd, read_only, ...}.

erpnext/accounts/doctype/sales_invoice/sales_invoice.json declares is_submittable:1, a naming_rule, a permissions array and roughly 200 field dicts. The Frappe framework Frappe core consumes it to build everything. ERPNext ships ~528 such files.

Apply to any ERP

Two viable shapes on Django/Postgres:

  • Store entity definitions in metadata tables / a JSON registry and write one generic admin + serializer + migration layer; or
  • Lean on Django model classes + ModelAdmin + DRF ViewSets as your "engine".

The durable move either way: pick one declaration format and generate CRUD, list, API and perms from it — never hand-code per entity.

A field declaration carries everything the engine needs. Below, three real lines from the Sales Invoice schema: a typed foreign key, a denormalized fetched value, and an embedded child grid. No SQL, no form code, no serializer — the engine reads these and produces all three.

{"fieldname": "customer", "fieldtype": "Link", "label": "Customer", "options": "Customer", "reqd": 1}
{"fetch_from": "customer.customer_name", "fieldname": "customer_name", "fieldtype": "Small Text", "read_only": 1}
{"fieldname": "items", "fieldtype": "Table", "label": "Items", "options": "Sales Invoice Item", "reqd": 1}

Read those three lines as instructions to a compiler: line one is "make a required FK column to the Customer table and render a picker"; line two is "add a read-only text column and copy customer.customer_name into it on save"; line three is "embed an editable grid of Sales Invoice Item rows". The schema is the source of truth and the build instructions at once.

Gotcha — the standard fields are invisible

owner, creation, modified, modified_by, docstatus, idx and name do not appear in any ERPNext DocType JSON — the framework injects them on every table. A re-implementer who copies only the JSON will silently lose the audit columns, the submit state machine and child ordering. Budget for them in your base layer from day one.

Pattern 2 — The file triplet: schema, controller, client, test

Pattern

.json / .py / .js / test — separate shape, server behaviour, client behaviour

The idea

Separate the shape of a thing (schema) from its server-side behaviour (controller) and its client behaviour (script). Co-locate all of them per entity, plus a colocated test.

Each entity becomes self-contained and discoverable: one folder tells you everything about it.

How ERPNext does it

ls erpnext/stock/doctype/item/ shows the quartet:

  • item.json — schema
  • item.py — class Item(Document) with validate/autoname/on_update
  • item.js — frappe.ui.form.on("Item", {...}) form events
  • test_item.py — class TestItem(ERPNextTestSuite)

Controllers subclass the framework Document; client scripts bind to named form events.

Apply to any ERP

Mirror the layout per entity: a schema/model file, a server service/controller exposing lifecycle hooks, a thin client module bound to form/UI events, and a colocated test.

On Django: a model module, a controller/service with hooks, a small front-end module, and a test file in the same package. The point is one folder = one entity, fully.

The controller is a plain class over the framework's Document, with business logic attached to named lifecycle methods. This is the entire shape of a controller — there is no router, no dispatch table, no decorator soup. The framework knows to call validate, before_submit, on_submit at the right moments because they are named conventions, not registrations.

class SalesInvoice(SellingController):
    def validate(self): ...
    def before_save(self):
        POSService(self).update_paid_amount()
    def before_submit(self):
        self.add_remarks()
    def on_submit(self):
        POSService(self).validate_pos_paid_amount()
    def on_cancel(self): ...

erpnext/accounts/doctype/sales_invoice/sales_invoice.py:62

The client script is the mirror image on the browser: it registers handlers against the same vocabulary of form events. erpnext/stock/doctype/item/item.js:27 opens with frappe.ui.form.on("Item", { ... }), where keys are field names or event names (refresh, onload, item_code) and values are functions. The framework wires them to the form it already generated from the schema — you never build the form, you only react to it.

Pattern 3 — Lifecycle hooks & controller inheritance

Pattern

Business rules attach to lifecycle events; shared behaviour is inherited

The idea

Business rules attach to well-known document lifecycle events — validate, before/on submit, on cancel — instead of ad-hoc call sites scattered through the codebase.

Cross-cutting behaviour (posting, validation) is inherited through a controller class hierarchy, so it is written once and reused, not copy-pasted per entity.

How ERPNext does it

class SalesInvoice(SellingController) defines validate(), before_save(), before_submit(), on_submit(), on_cancel(). The inheritance chain is deep:

SellingController → StockController → AccountsController → TransactionBase → StatusUpdater → Document (erpnext/controllers/selling_controller.py:19, erpnext/utilities/transaction_base.py:20, erpnext/controllers/status_updater.py:181).

The framework Frappe core invokes each hook at the right moment inside the save/submit transaction.

Apply to any ERP

Define a base Document/aggregate with overridable hooks (validate, beforeSave, onSubmit, onCancel) and a dispatcher that calls them inside one DB transaction.

Put cross-cutting posting/validation in base controllers; let entities override. On Django you can override save()/clean() + signals, but a centralized hook dispatcher is cleaner and far easier to reason about.

The inheritance chain is worth internalizing, because it is where the "documents write ledgers" rule lives. A Sales Invoice is a SellingController, but stock posting comes from StockController, accounting posting from AccountsController, status roll-ups (e.g. "Order is now Completed") from StatusUpdater. None of that is in the Sales Invoice class — it is inherited.

SalesInvoiceentity-specific selling rules
SellingControllerselling-side validation, pricing
StockControllerposts the Stock Ledger
AccountsControllerposts GL Entries
TransactionBaseshared transaction plumbing
StatusUpdaterrolls up document status
Documentframework base — runs the hooks
Gotcha — don't skip super()

The chain is deep and a hook you override may be relied on by a base class. Blindly overriding validate() or on_submit() without calling super() can silently skip stock or GL posting — the document submits "successfully" and the ledgers never move. When you override a lifecycle hook on an inherited controller, call the parent unless you are certain you mean to replace its behaviour.

We unpack the submit/cancel transaction itself — what runs in what order, and how reversal works — in the document lifecycle chapter. For now the takeaway is structural: logic lives on named hooks, shared logic lives in base classes.

Pattern 4 — Typed relationships in the schema

Pattern

Link, Table, Dynamic Link — relationships are field metadata

The idea

Foreign keys, one-to-many composition, and polymorphic associations are all expressed as field metadata. Because the relationship is data, the engine can validate referential integrity, render pickers and grids, and join generically — without bespoke code per relationship.

How ERPNext does it
  • Link: {fieldtype:"Link", options:"Customer"} — a typed FK.
  • Table: {fieldtype:"Table", options:"Sales Invoice Item"} — an embedded child grid (child has istable:1).
  • Dynamic Link: in erpnext/accounts/doctype/gl_entry/gl_entry.json, party_type (Link → DocType) + party (Dynamic Link → party_type) gives a polymorphic party (Customer/Supplier/Employee).

Across the codebase: 2159 Link, 298 Table, 78 Dynamic Link fields.

Apply to any ERP

On SQL/Django:

  • Link → ForeignKey
  • Table → a related model with a parent FK + an ordering column (idx)
  • Dynamic Link → GenericForeignKey (content_type + object_id) or a (party_type, party_id) pair

Keep the relationship in metadata so one generic loader can resolve and validate it.

The polymorphic case is the most powerful and the most dangerous, so look at it directly. A single GL Entry schema must be able to point at a Customer on one row, a Supplier on another, an Employee on a third — without three different ledger tables. The Dynamic Link does this by reading the target table name at runtime from a sibling field:

{"fieldname": "party_type", "fieldtype": "Link",         "label": "Party Type", "options": "DocType"}
{"fieldname": "party",      "fieldtype": "Dynamic Link", "label": "Party",      "options": "party_type"}

Read it carefully: party_type is itself a Link whose options is the literal DocType named "DocType" — i.e. it stores the name of a table ("Customer"). party is a Dynamic Link whose options is not a DocType name but the field name party_type. So to resolve party, the engine first reads party_type, learns the row points at "Customer", and treats party as a FK into Customer. One schema, three possible targets.

Gotcha — Dynamic Link has no DB-level integrity

Because the target is decided at runtime, the database cannot enforce the reference. There is no Postgres foreign key that says "party must exist in whatever party_type says". That validation lives entirely in framework/controller code. A naive port using a plain (type, id) pair must add the existence check by hand — and must add it on every write path, or you will accumulate dangling party references that no constraint catches.

The child-Table relationship has its own subtlety. A child DocType (istable:1) is not a standalone entity: it only exists inside a parent's Table field and carries parent, parentfield, parenttype and idx columns the framework adds. It has no list view by design, and querying or creating one independently breaks assumptions. The parent and its children are saved atomically as one document — header and lines in a single transaction — which is exactly what you want for an invoice.

We use the Link/Table/Dynamic-Link triad heavily later: see master data & the Party for the party model in full, and the accounting ledger for how GL Entry rows are produced.

Pattern 5 — Naming, Single and Submittable as flags

Pattern

Primary keys, singletons, and the state machine are configuration, not code

The idea

Three things that are usually re-coded per entity — how the primary key is generated, whether the entity is a single global config row, and whether it has a draft/submitted/cancelled state machine — are instead selected by flags on the schema.

How ERPNext does it
  • autoname: a naming series (ACC-SINV-.YYYY.-), field:item_code (use a field value as PK), or hash (random, for children).
  • issingle:1 (erpnext/stock/doctype/stock_settings/stock_settings.json) — one row, no name. 31 Settings singles.
  • is_submittable:1 adds the docstatus machine (0 draft / 1 submitted / 2 cancelled) that GL Entry and Sales Invoice depend on; ledgers also set in_create:1.
Apply to any ERP

Provide pluggable ID strategies (sequence/series, natural key, UUID) chosen by config. Model singletons as a one-row table or a settings store. Implement submit/cancel as a status column + guarded transitions in the base controller.

Don't reinvent any of these per entity — they are framework concerns.

Naming deserves a close look, because in this model name is the real primary key — not an auto-increment id. The autoname/naming_rule flag decides what name contains. When a flag isn't enough, an entity can override the autoname hook in code. Item does exactly this: it can use a naming series for templates, but for ordinary items it sets name equal to item_code itself.

def autoname(self):
    if frappe.db.get_default("item_naming_by") == "Naming Series":
        if self.variant_of:
            ...  # build variant code from template
        else:
            from frappe.model.naming import set_name_by_naming_series
            set_name_by_naming_series(self)
            self.item_code = self.name
    self.item_code = strip(self.item_code)
    self.name = self.item_code

erpnext/stock/doctype/item/item.py:161

Gotcha — naming is a primary-key decision, with cascade

Because name is the PK and other tables Link to it by value, the naming strategy is a structural commitment. Renaming (when allow_rename is set) has cascading FK implications the framework handles for you — and that a hand-rolled stack must handle itself. Mixing strategies carelessly (a natural key that later collides, a series that resets) is expensive to unwind once data exists. Decide naming per entity before you ship it.

Gotcha — is_submittable changes the semantics, not just adds a column

Once an entity is submittable, docstatus gates editing: a submitted document is immutable except via amend or cancel. Ledger doctypes additionally set in_create:1, meaning rows are written by code, never hand-entered in a form. Do not model a ledger as an ordinary editable master. If your stock or accounting ledger can be edited through the admin UI, your books are not trustworthy. Make ledgers append-only and machine-written from the start.

The document-level flags also drive the whole submit machine declaratively. Here is the header block of the Sales Invoice schema — naming, submittability, module, and per-role permissions, all as data:

"autoname": "naming_series:",
"is_submittable": 1,
"naming_rule": "By \"Naming Series\" field",
"module": "Accounts",
"permissions": [
 {"role": "Accounts Manager", "read": 1, "write": 1, "create": 1,
  "submit": 1, "cancel": 1, "amend": 1, "delete": 1, "report": 1}

Notice that submit, cancel and amend are themselves permission verbs — the state machine and the permission model are wired together in the same data. We dig into the permission engine in permissions & roles.

Pattern 6 — Modules & the free audit columns

Pattern

Every entity names its module; the engine injects identical audit columns everywhere

The idea

Every entity declares the module it belongs to (for organisation, navigation and access grouping), and the engine injects the same audit/metadata columns on every record — so provenance and change-tracking are universal and uniform, never per-entity afterthoughts.

How ERPNext does it

Every DocType JSON has a module (e.g. "Accounts", "Stock"); erpnext/modules.txt lists all 22 module names.

The standard fields owner, creation, modified, modified_by, docstatus, idx, name are not in any DocType JSON — the framework Frappe core adds them to every table. track_changes:1 (on Item, Sales Invoice) records a full versioned audit trail.

Apply to any ERP

Bake created_by/created_at/updated_by/updated_at/version/status into a base model/mixin every table inherits. Add an abstract module/app label for navigation and access grouping.

Make audit columns non-optional and engine-supplied — never something an entity author can forget.

This is the cheapest, highest-leverage thing in the whole meta-model and the easiest to under-build. The reason ERPNext can show you "who created this, who last touched it, and a diff of every change" on any record is that the framework adds the same seven columns to every table and an optional version trail on top. There is no per-entity audit code anywhere. On your own stack this is one abstract base model:

owner / created_by
Who inserted the row. Set once, never changes.
creation / created_at
Insert timestamp. Set once.
modified_by / updated_by
Who last wrote the row.
modified / updated_at
Last-write timestamp — also used for optimistic concurrency.
docstatus / status
0 draft / 1 submitted / 2 cancelled — the state machine, present even on non-submittable types (where it stays 0).
idx
Ordering of child rows within their parent. Without it, grid order is undefined.
name
The primary key — its value set by the naming strategy (Pattern 5).
Note — modules are an access-grouping seam too

The module field is not only navigation. Grouping entities into modules gives you a natural axis for bundling permissions, packaging features, and deciding what ships together. When you design your own module list, treat it as part of the access model, not just the menu.

The variant master in one picture (Style × Size × Colour)

One flow ties Patterns 1, 4 and 5 together and is worth seeing whole, because it is the single most useful template for a retail SKU model. An Item with has_variants=1 is a template; it carries an attributes Table of Item Variant Attribute rows that define the axes (Colour, Size). Each concrete variant is its own Item whose variant_of Links back to the template, and whose name/item_code the autoname hook builds from the template name plus the attribute values.

Applying to KDPS

This is the direct template for the KDPS rule SKU = Style × Size × Colour and for Rule 12 "variation is data, not code". Model the variant axes as child rows — a ProductVariantAttribute table hanging off the style master — rather than as columns or code branches, so a new brand's sizing scheme is data entry, not a deployment. The concrete variant is the unit stock and the POS line reference, so size×colour survives end-to-end. Two other ERPNext patterns map straight onto KDPS: the party_type/party Dynamic Link is exactly how to carry the polymorphic vendor / customer / store party on a ledger posting (a (party_type, party_id) pair or a Django GenericForeignKey); and is_submittable + in_create:1 is the "documents write ledgers" rule — make GRN, PT and POS documents submittable and immutable once submitted, and let posting code (never a form) append rows to the stock and value ledgers, mirroring GL Entry. Tally stays the statutory book; these ledgers are the operational truth that feeds it.

Porting checklist — what the framework was doing for you

Because so much is injected by the engine, the danger when rebuilding on Django/Postgres is reproducing the visible JSON and missing the invisible machinery. Treat this as a punch-list before you ship any entity.

Frappe gives you freeIf you don't rebuild it…Django/Postgres equivalent
Standard audit columns on every table No provenance, no change history, silent data loss Abstract base model mixin: created_by/at, updated_by/at, version, status
docstatus submit/cancel state machine Documents stay editable forever; ledgers untrustworthy A status column + guarded transitions in a base controller
idx ordering on child rows Grid/line order is undefined and jumps around An explicit ordering column on related models
Dynamic Link integrity check Dangling party references no constraint catches Validate (party_type, party_id) existence on every write, or GenericForeignKey
name as natural/series PK + rename cascade Renames break FKs; PK collisions surface late Pluggable ID strategy per entity; handle rename cascades deliberately
Generic CRUD UI / list / REST / ORM 50 hand-built screens you maintain forever DRF ViewSets + ModelAdmin driven from one declaration/registry
Gotcha — fetch_from freezes a value, it is not a live join

customer_name is copied from Customer at save time and will not refresh if the source later changes. This is correct for invoice snapshots — you want the printed name frozen to what it was when the document was issued — and wrong if you assume it behaves like a live join/view. Decide per field whether you want a snapshot (denormalize on write) or current truth (resolve on read). Don't let the convenience of fetch_from hide that choice.

Takeaways

  1. A DocType is data, not code. Declare each business object once — fields, types, flags — and let one generic engine derive the table, list view, form, REST API, ORM and permissions. ERPNext does this ~528 times with no per-entity plumbing.
  2. The schema is mandatory; the controller and client are optional. Co-locate the quartet (.json / .py / .js / test) per entity, but remember the JSON alone already yields six subsystems before any behaviour is written.
  3. Hang logic on named lifecycle hooks, and inherit the cross-cutting parts. validate / before_submit / on_submit / on_cancel on a controller chain (SellingController → … → Document) keep posting and validation written once. Call super() or you skip ledger posting.
  4. Relationships are metadata. Link = typed FK, Table = embedded child grid, Dynamic Link = polymorphic party (party_type + party). The DB can't enforce the polymorphic case — validate it in code on every write.
  5. Naming, single and submittable are flags, not bespoke code. name is the real primary key; issingle is a one-row config object; is_submittable + in_create makes a ledger that code writes and forms cannot edit.
  6. The audit columns are invisible and non-negotiable. owner/creation/modified/modified_by/docstatus/idx/name are engine-supplied on every record. On your own stack, bake them into a base mixin so no entity can omit them.
  7. The decisive win is leverage. Adding an entity becomes writing one declaration, not wiring six subsystems — and observability, the state machine, typed links and polymorphism behave identically everywhere because every record shares one shape. Model metadata as first-class data and build one engine over it.

Chapter 8 · Control plane

Permissions, Roles & Users

Role-based access as a data matrix: permission levels for field groups, User Permissions for row-level scoping, if-owner, document sharing — access control you configure, not code.

Why this subsystem decides whether an ERP survives

Every ERP is a multi-user system over money and stock. The moment a second person logs in, you owe answers to three different questions, and they are orthogonal:

WHAT may they do?
Can this person create a Sales Invoice? Submit it? Cancel one that is already posted? Delete it entirely? Export the list to a spreadsheet? These are actions, and they attach to a role (Cashier, Accounts User, Auditor).
WHICH records may they touch?
The cashier in the Patna store has the same role as the cashier in the Ranchi store — but each may only see their own store's documents, and only their own GSTIN's data. This is a row-level question, and it has nothing to do with the role.
WHICH fields inside a record may they see?
A cashier transacts on an order all day, but must never see the cost price, the margin, or override the discount cap. Same document, same action — but some fields are more sensitive than the body around them. This is a field-level question.

The tempting mistake — the one that kills maintainability — is to answer these with if statements scattered through the controllers: "if the user isn't a manager, hide this button; if the store doesn't match, return 403; if it's the cost field, blank it out." Do that and your access rules live in fifty endpoints, drift apart over time, can never be audited as a whole, and cannot be tuned per customer without a code change and a redeploy.

ERPNext's answer is the durable one: authorization is data, enforced by one engine. Every entity declares a matrix of who-can-do-what; a single generic permission engine reads that matrix and enforces it on every read, write, and state transition. Adding a role, tightening an action, or locking a field is a row edit, never new branching code. This chapter reverse-engineers that matrix along its three orthogonal axes, plus the two escape hatches (if-owner, sharing) that the matrix alone cannot express.

Key idea

Access control is a (role × entity × action × permlevel) matrix declared as data, plus row-level scopes tied to link fields, all composed by one enforcement engine into the SQL WHERE clause of every query. Never scatter if-checks across controllers — declare the rules, enforce them once.

Gotcha · the engine is not in this checkout

ERPNext only declares the matrix (in each DocType's JSON) and occasionally mutates it. The actual enforcement engine — frappe.permissions and frappe.core.doctype.user_permission Frappe core — lives in the framework, not the ERPNext app. If you reimplement this, you must build both: the declarative data model and the engine that AND/OR-composes role grants, User Permissions, sharing, and if-owner into every query. The data without the engine grants nothing; the engine without the data has nothing to enforce.

The shape of the matrix

The whole subsystem is best read off one real file. Every DocType .json carries a permissions array. Each row is a tuple: a role, a set of action booleans, a permlevel, and an if_owner flag. Here is the canonical example — the Sales Invoice — which shows all three layers at once.

"permissions": [
 {"amend":1,"cancel":1,"create":1,"delete":1,"email":1,"print":1,"read":1,"report":1,"role":"Accounts Manager","share":1,"submit":1,"write":1},
 {"amend":1,"create":1,"email":1,"print":1,"read":1,"report":1,"role":"Accounts User","share":1,"submit":1,"write":1},
 {"permlevel":1,"read":1,"role":"Accounts Manager","write":1},
 {"permlevel":1,"read":1,"role":"All"}
]

erpnext/accounts/doctype/sales_invoice/sales_invoice.json

Read it carefully — four rows encode a surprising amount of policy:

  • Row 1 (Accounts Manager): every action bit is set — including submit, cancel, amend, and delete. A manager owns the full lifecycle.
  • Row 2 (Accounts User): everything except cancel and delete. A clerk can create, submit, and even amend (create a corrected version), but cannot cancel a posted invoice or delete it. The difference between the two roles is not a hierarchy — it is just which bits are present.
  • Rows 3 & 4 (permlevel:1): these do not grant access to the document at all — they gate fields tagged as level 1. Accounts Manager may read and write those sensitive fields; All (everyone) may only read them. This is the field-level axis, sitting in the same array.

The full vocabulary of action columns is fixed and small:

ActionMeaningNotes
readMay open / view the documentThe baseline. Without it, the record is invisible in lists and reports.
writeMay edit field values (while in draft)Edits are still blocked once a doc is submitted, regardless.
createMay make a new document of this type—
submitMay move docstatus 0 → 1 (post to ledgers)The lifecycle transition, gated as an action.
cancelMay move docstatus 1 → 2 (reverse the ledgers)Deliberately withheld from clerks.
amendMay clone a cancelled doc into a new draftThe "correction" path.
deleteMay remove a draft entirelyOnly ever applies to docstatus 0.
report / exportMay see in report views / download dataThe read-only auditor's bread and butter.
print / emailMay print / email the document—
shareMay grant another user ad-hoc access to this recordEnables the Document Share feature.
importMay bulk-import rows of this type—
selectMay choose this record in a link field — without full readA weak, distinct action; do not conflate with read.
Gotcha · omitted means zero, and there is NO hierarchy

A row that lists only {read:1, role:"Auditor"} grants read and denies everything else — omitted action keys are 0, not inherited. And there is no role inheritance: Accounts Manager does not automatically include Accounts User rights. Every right a role has is an explicit row. If you assume a "Manager ⊇ User" hierarchy that the data does not encode, you will both over-grant (by inventing it) and be confused (when the matrix doesn't behave that way).

Gotcha · select is not read

select means "may be chosen in a link-field picker" without full read access — Item grants it to Desk User so any logged-in user can pick an item in a dropdown without being able to browse the item master. Conflate select with read and you silently over-expose master data through pickers. Model it as its own action.

Pattern 1 · Permissions as a declarative data matrix

Pattern

Authorization as configuration, not branching code

The idea

Every entity declares a flat table of (role, action-flags, scope) rows. One generic engine enforces it everywhere. Adding a role, or tightening an action, is a data edit — never a code change. A "read-only auditor" needs no special feature: it is simply rows that grant read/report/export and omit write/submit/cancel.

How ERPNext does it

Each DocType JSON has a permissions array; each row is {role, read, write, create, submit, cancel, amend, delete, report, export, import, print, email, share, select, permlevel, if_owner}. The engine in frappe.permissions Frappe core reads it on every operation. Roles are pure strings, auto-created the moment a JSON names them. The matrix can also be mutated at runtime via add_permission / update_permission_property.

erpnext/accounts/doctype/sales_invoice/sales_invoice.json

Apply to any ERP

On Django/Postgres: a doctype_permission table (entity_type, role, action, permlevel, if_owner) plus a single has_permission(user, entity, action) checked in a base ViewSet / manager. Or map each action to a Django permission assigned via Groups — but keep it in a queryable table so an admin UI can render and edit the matrix. The non-negotiable: one enforcement path, many declarative rows.

The proof that the matrix is genuinely data — constructible without touching any JSON — is ERPNext's regional install code. The Italian e-invoicing module builds its permission rows entirely in Python at install time:

def add_permissions():
    doctype = "Import Supplier Invoice"
    add_permission(doctype, "All", 0)
    for role in ("Accounts Manager", "Accounts User", "Purchase User", "Auditor"):
        add_permission(doctype, role, 0)
        update_permission_property(doctype, role, 0, "print", 1)
        update_permission_property(doctype, role, 0, "report", 1)
        if role in ("Accounts Manager", "Accounts User"):
            update_permission_property(doctype, role, 0, "write", 1)
    add_permission(doctype, "Accounts Manager", 1)  # permlevel-1 grant

erpnext/regional/italy/setup.py · the 0 / 1 third argument is the permlevel

Note the structure: add_permission(doctype, role, permlevel) creates a row; update_permission_property(doctype, role, permlevel, action, value) flips one action bit on that row. A read-only role (Auditor here gets a bare row plus print+report) and a read-write role (Accounts User, same plus write) differ only in which properties get flipped. This is the same API the framework calls when you edit the matrix through the UI — there is no separate "code path" for permissions.

Gotcha · the matrix is scattered across ~1300 rows in hundreds of files

There is no single permissions table to eyeball — the matrix lives in one JSON per DocType. Across the corpus System Manager appears in 175 permission rows and Auditor in 49 (all read-only). Without tooling, over-grants and drift hide everywhere. If you build this model, also build a flattening report — an admin view that renders the entire matrix as one queryable table — or you will never be able to audit "who can cancel an invoice?" across the whole system.

Pattern 2 · permlevel — field-level security as a numeric tier

Pattern

Tag sensitive fields with a level; grant roles per level

The idea

Some fields are more sensitive than the document around them — cost, margin, a discount-override flag. Give each field a numeric security level; grant roles access per level. A role can read/write the whole document body (level 0) yet be completely blind to flagged fields (level 1+) — with no per-field if-checks anywhere.

How ERPNext does it

A DocField carries a permlevel (default 0); permission rows also carry one. A role only touches fields whose level it has a row for. Sales Order's ignore_pricing_rule is permlevel:1 and the only level-1 row belongs to Sales Manager — so an ordinary Sales User can edit the order but cannot see or change that field. 27 transaction doctypes use a level-1 tier.

erpnext/selling/doctype/sales_order/sales_order.json

Apply to any ERP

Add an integer perm_level column to field metadata and a (role, perm_level) grant table. In serializers/forms, strip or read-only any field whose level the user lacks — on read (hide the value) and on write (refuse the change). Without an engine, this is a serializer mixin that filters fields by the user's max granted level per action.

The mechanism is two halves that must agree. First, a field is tagged with a level; second, a permission row "unlocks" that level for a role. Here both halves for Sales Order:

// the field — tagged level 1:
{"fieldname": "ignore_pricing_rule", "permlevel": 1, "label": "Ignore Pricing Rule"}

// the permission row that unlocks level 1:
{"permlevel": 1, "read": 1, "role": "Sales Manager", "write": 1}

erpnext/selling/doctype/sales_order/sales_order.json

Because Sales User has only level-0 rows, every level-1 field on that form is invisible and immutable to them. Crucially, this is declared once and produces two visibilities of the same document with zero conditional code:

Sales Order JSONignore_pricing_rule = permlevel 1 · level-1 row = Sales Manager only
Sales Manager opens ithas a level-1 row → field is visible & editable
Sales User opens the SAME orderlevel-0 only → field hidden / read-only · all other fields normal

ERPNext reserves higher tiers for the most sensitive surfaces: most transactions use levels 0 and 1; Monthly Distribution goes to level 2; Voice Call Settings uses levels 0, 1, 2. The pattern is the same at every tier — a field's level must be matched by a role's level-row, or the field is dark.

Gotcha · enforce the level on WRITE, not just read

permlevel is enforced in the UI/serializer layer — it is not a database-column grant. A naive reimplementation that filters fields on read (hides the value) but forgets to reject writes to those fields leaves a hole: a crafted request can still set ignore_pricing_rule or cost_price even though the field never rendered. Strip on read and refuse on write.

Gotcha · a level-1 grant can look like dead code

Customer and Sales Invoice ship level-1 permission rows even though their level-1 fields may be assigned later via Property Setter / customization — the field's permlevel can be 0 in the base JSON. Don't delete the grant as unused: it exists so a customizer can raise a field to level 1 and have an owner already authorized. (See extensibility for Property Setters.)

Applying to KDPS

This is exactly how KDPS keeps cashiers transacting without ever seeing margin. Tag cost / P-RATE, landed cost, margin %, and discount-override fields as permlevel:1; grant the level-1 row only to Store Manager / Buying Manager / Owner. A cashier rings up a sale on the full document at level 0 but is blind to cost and cannot lift the discount cap — mirroring how ERPNext locks ignore_pricing_rule. No per-field if on the POS screen; the serializer strips the fields for cashier sessions.

Pattern 3 · User Permissions — row-level restriction decoupled from roles

Pattern

Roles say WHAT; User Permissions say WHICH records

The idea

A user keeps the same role everywhere but is confined to specific master values — one Company, one Warehouse, their own Employee record. This is enforced by automatically AND-ing a WHERE filter into every query for that user. Roles and row-scope are independent axes: change neither when you confine someone to a store.

How ERPNext does it

Frappe-core User Permission records Frappe core are (allow=doctype, for_value=record, user). ERPNext writes them when an Employee is linked to a User: add_user_permission("Company", company, user) confines that user to one company's documents. The effective set is read back via get_permitted_documents("Price List") to auto-select a default when exactly one is allowed.

erpnext/setup/doctype/employee/employee.py · erpnext/accounts/party.py

Apply to any ERP

Django: django-guardian object-level perms, or a user_object_scope(user, scope_type, object_id) table queried by a manager that injects .filter(company__in=allowed) into every queryset. The key insight ERPNext encodes: link-field values are the scope axes. Restrict on the FK (Company, Warehouse) and every transaction that references that master is transitively restricted.

The clearest live example is Employee onboarding. When HR links an Employee record to a login User and ticks the create_user_permission checkbox, ERPNext writes two row-level scopes — confining that user to their own Employee record and their Company — and removes them if the box is later unticked:

if employee_user_permission_exists and not self.create_user_permission:
    remove_user_permission("Employee", self.name, self.user_id)
    remove_user_permission("Company", self.company, self.user_id)
elif not employee_user_permission_exists and self.create_user_permission:
    add_user_permission("Employee", self.name, self.user_id)
    add_user_permission("Company", self.company, self.user_id)

erpnext/setup/doctype/employee/employee.py

From that point on, every list and report query for that user is silently AND-ed with "Company in {their company}" and "Employee in {their own record}". They cannot widen their view — the filter is composed below them, in the engine. No role changed; the same Accounts User in two different companies sees two different datasets.

The same scope set doubles as a smart default. When ERPNext sets a party's price list it reads back the permitted documents and, if exactly one Price List is allowed, picks it automatically:

# erpnext/accounts/party.py — set_price_list()
get_permitted_documents("Price List")   # row-level scope reused as a default

erpnext/accounts/party.py

Where the filter is built

The composition of all of this into the SQL WHERE clause is documented in erpnext/utilities/query.py: role permissions, User Permission match-conditions, document sharing, the if-owner constraint, and any permission_query_conditions hooks all get AND/OR-composed into the filter that limits list and report views. A restricted user does not get a "403" on a forbidden row — the row never appears in their results.

Gotcha · restriction is on the LINK FIELD, not the transaction

A User Permission on Company restricts a transaction only if that transaction actually references Company via a link field. Miss the link and the restriction silently does nothing. Worse: if a user has a User Permission for a doctype that a given form does not link to, behaviour depends on the "apply only if linked" / strict-user-permissions toggle — get it wrong and users are unexpectedly locked out of unrelated forms. Reimplement that toggle deliberately, and make sure every entity you want scoped carries the FK you scope on.

Applying to KDPS

This is the data-layer enforcement of the Bihar ↔ Jharkhand "distinct persons" boundary. Put a User Permission on the Store / Warehouse link field (and through it, the GSTIN): each store's staff are confined to their own store's documents and their own GSTIN's data, with the same "Store Cashier" role everywhere. Cross-state transfers become visible only to roles whose scope spans both states (Owner, head-office Accounts). One role definition, fifty stores, zero leakage between GSTINs — and the scope doubles as the default store on every new document.

Pattern 4 · if_owner and Document Sharing — the two escape hatches

Pattern

Own-records-only, and per-record ad-hoc grants

The idea

Two things the role matrix cannot express: (a) a role that may only touch records it created (ownership), and (b) granting one user access to one specific record on demand (sharing). Both narrow or widen access without minting new roles.

How ERPNext does it

if_owner is a boolean on a permission row: Video gives role All full CRUD but with if_owner:1, so a user only manages their own videos. Sharing is the share action flag, which lets Frappe's Document Share Frappe core grant per-record access. Both are composed into the same query filter.

erpnext/utilities/doctype/video/video.json

Apply to any ERP

if_owner → a flag on the permission row; AND owner_id = current_user into the query when set. Sharing → a document_share(entity_type, entity_id, user, can_read/write) table OR'd into the visibility filter. Get the AND/OR precedence right: the rule is role-grant OR shared OR (role-grant AND owner) — or you over- or under-expose.

The only DocType in ERPNext using if_owner:1 is Video — a deliberately small example of the pattern:

"permissions": [
 {"role":"System Manager", "read":1, "write":1, "create":1, "delete":1},
 {"role":"All", "read":1, "write":1, "create":1, "delete":1, "if_owner":1}
]

erpnext/utilities/doctype/video/video.json · role All may CRUD only its own videos; System Manager is unscoped

Gotcha · a broad row silently defeats if_owner

if_owner is per-permission-row, and a user may match multiple rows — one scoped by owner, one not. The engine takes the OR of matching rows. So adding a broad, non-owner row anywhere silently defeats the if-owner restriction for any user who also holds that role. In the Video example, System Manager's unscoped row overrides any if-owner narrowing for that user. Audit composition carefully: a single over-broad row can unlock everything the owner-scope was meant to fence off.

The composition rule is the part teams get wrong. All five sources — role grants, User Permission match-conditions, sharing, the if-owner constraint, and query-condition hooks — collapse into one WHERE clause in erpnext/utilities/query.py. Sharing and an unscoped role row widen (OR); User Permissions and if-owner narrow (AND). Mis-order the precedence and you either hide rows a user should see or expose rows they should not.

Pattern 5 · Roles bundled into Role Profiles; read-only roles as data

Pattern

Assign a job-function bundle, not ten atomic roles

The idea

Don't hand-assign ten atomic roles to a user one at a time. Define named bundles (job functions) once and assign the bundle. And a "read-only" principal is not special code — it is simply a set of rows that grant read/report/export and withhold write/submit.

How ERPNext does it

DEFAULT_ROLE_PROFILES declares bundles (Inventory, Accounts, Sales, Purchase, Manufacturing) as data; create_default_role_profiles() inserts/reconciles Role Profile records at install. The Auditor role is read-only purely by data: across 49 doctypes its rows carry read+report+export but never write/create/submit.

erpnext/setup/install.py

Apply to any ERP

Model Role and RoleProfile (a Role↔RoleProfile m2m); assign profiles to users; expand to effective roles at login. A read-only role needs no feature — just omit the mutating action columns. Seed default profiles as fixtures so a fresh install ships sane job-function bundles.

The bundles are plain data — a dictionary of profile name → list of role strings:

DEFAULT_ROLE_PROFILES = {
    _("Inventory"): ["Stock User", "Stock Manager", "Item Manager"],
    _("Accounts"):  ["Accounts User", "Accounts Manager"],
    _("Sales"):     ["Sales User", "Stock User", "Sales Manager"],
    _("Purchase"):  ["Item Manager", "Stock User", "Purchase User", "Purchase Manager"],
}

erpnext/setup/install.py · materialized by create_default_role_profiles()

Two details worth internalizing. First, the bundles overlap deliberately — a Sales profile includes Stock User because a salesperson must read stock levels; a Purchase profile includes Item Manager. Job functions are not disjoint, and the bundle captures that. Second, roles themselves are auto-created strings: the moment any DocType JSON names "Stock Manager", the framework creates that Role record. You never declare a role separately from using it — naming it in a permission row is declaring it.

And the read-only auditor needs no engine support whatsoever. It is purely the absence of mutating columns, repeated across the doctypes it should see:

Pattern 6 · The document lifecycle is gated by the SAME matrix

Pattern

State transitions are just action bits — not a separate ACL

The idea

The document lifecycle — draft → submitted → cancelled — is governed by the same permission matrix, not a parallel access list. Whether a user may advance a document's state is just whether their role holds the corresponding action bit. Lifecycle and authorization never diverge because they are one table.

How ERPNext does it

submit, cancel, amend are action columns. In Sales Invoice, Accounts Manager has all three; Accounts User has submit+amend but cancel:0 — so a clerk can post and correct, but only a manager can cancel. The engine refuses the docstatus 0→1 / 1→2 transition if the bit is absent.

erpnext/accounts/doctype/sales_invoice/sales_invoice.json

Apply to any ERP

Tie each state-machine edge to a named action (submit/cancel/amend) and check the same permission table before allowing the transition. Reserve imperative role checks for cross-cutting actions that aren't a single document's CRUD/state edge.

Because the lifecycle and the auth matrix are the same table, the difference between "clerk" and "manager" on a Sales Invoice is purely which state-transition bits are present:

Draftdocstatus 0
Submitteddocstatus 1 · posts ledgers
Cancelleddocstatus 2 · reverses ledgers
TransitionAction bitAccounts UserAccounts Manager
0 → 1 (post to ledgers)submit✓ allowed✓ allowed
1 → 2 (reverse the ledgers)cancel✗ cancel:0 — blocked✓ allowed
2 → new draft (corrected copy)amend✓ allowed✓ allowed

A clerk can post a sale and create a corrected amendment, but cannot make the system reverse the GL entries and stock ledger of a posted invoice — that destructive move is a manager's bit. See the document lifecycle for the full docstatus machine.

The imperative fallback — only where the matrix can't reach

The matrix expresses CRUD and state edges on a single document. For cross-cutting actions it cannot express, ERPNext drops to sharp imperative guards in the controllers — and only there:

# a hard role gate — for a cross-cutting bulk operation
frappe.only_for("Accounts Manager")

# an explicit per-doc permission check that raises if denied
frappe.has_permission(dt, "write", doc, throw=True)

erpnext/controllers/accounts_controller.py · erpnext/setup/doctype/transaction_deletion_record/transaction_deletion_record.py Frappe core API

The discipline here is what keeps the system maintainable: only_for and explicit has_permission(..., throw=True) appear for things like a bulk transaction-deletion utility or a closing operation — actions that are not one document's CRUD or state edge. They are the exception, not the rule. Everything that can be a row in the matrix is a row in the matrix.

Applying to KDPS

Gate the KDPS document state machine the same way. A POS sale, a GRN / stock-in, and a store transfer all move through draft → submitted → cancelled. Give Store Cashier submit on a sale but not cancel — so a cashier rings up sales all day, but cancelling a posted sale (which must reverse stock and the ledger) requires a Store Manager's cancel bit. This is the data-layer expression of "documents write ledgers" and "flag, don't block": the cashier can flag a mistake, but only a manager can unwind a posted document.

How the layers compose — the whole picture

The four axes stack from coarsest to finest. A request must clear every band that applies before a row is visible or a field is editable:

1 · Role × Action (does the role hold this bit?)
read / write / createbaseline CRUD
submit / cancel / amendlifecycle edges
report / export / printread-side
share / select / importancillary
2 · Row-level scope (which records?)
User Permission on Companyone GSTIN's data
User Permission on Store/Warehouseone store's docs
if_owneronly my own records
Document Sharethis one record, ad-hoc
3 · Field-level (which fields inside the record?)
permlevel 0the document body
permlevel 1cost / margin / overrides
permlevel 2+most sensitive surfaces
4 · Imperative fallback (only where the matrix can't reach)
frappe.only_for(role)cross-cutting bulk ops
has_permission(..., throw=True)explicit per-doc gate
Key idea — the composition

For visibility, the engine builds one WHERE clause per user per doctype: role-grant AND (User-Permission match) AND (owner-id = me, when if_owner) — with Document Share and any unscoped role row OR'd in to widen it. Field access is then resolved per field by comparing the field's permlevel to the user's granted levels. Build this composition in one place (a base manager + a serializer mixin) and authorization is uniform across every endpoint. Build it per endpoint and it will drift.

Reimplementing on Django / Postgres

The research target — KDPS — is a React PWA over Django/Postgres. Here is the concrete mapping from ERPNext's four axes to that stack, with the pitfalls baked in:

Role × Action matrix
A queryable entity_permission(entity_type, role, action, permlevel, if_owner) table — not only Django's auth_permission, because you want an admin UI to render and edit the matrix as one grid. Enforce in a single has_permission(user, entity, action) called from a base DRF ViewSet. One enforcement path.
permlevel field security
An integer perm_level on field metadata + a (role, perm_level) grant table. Implement as a serializer mixin that, per request, computes the user's max granted level per action and (a) strips higher-level fields on read and (b) rejects writes to them. Both halves — or you have a hole.
Row-level scope
A user_object_scope(user, scope_type, object_id) table (or django-guardian), read by a base model manager that injects .filter(store__in=allowed) / .filter(company__in=allowed) into every queryset. Scope on the link field — and make sure every entity you want confined actually carries that FK.
if_owner + sharing
An if_owner flag (AND owner = request.user into the queryset when set) and a document_share(entity_type, entity_id, user, can_read/write) table OR'd into the visibility filter. Mind the precedence: a broad non-owner grant defeats an owner-scope.
Role Profiles
Role and RoleProfile models with a Role↔RoleProfile m2m; assign profiles to users; expand to effective roles at login. Seed KDPS job-functions (Store Cashier, Store Manager, Stock/Warehouse User, Accounts/Tally Operator, Buying Manager, Owner/Admin, read-only Auditor) as fixtures.
Lifecycle gating
Each state-machine edge (sale/GRN/transfer: draft→submitted→cancelled) checks the same permission table for its submit/cancel/amend action before transitioning. Don't write a parallel ACL for the state machine.
Gotcha · build the audit view from day one

ERPNext's matrix is invisible because it is scattered across hundreds of JSONs (System Manager appears 175×, Auditor 49×). If you store yours in one queryable table, you can — and should — ship an admin "flatten the matrix" report from the start: "show me every role that can cancel a Sales Invoice", "show me every level-1 field and who can write it". Without it, over-grants accumulate unseen. This is the one advantage you have over ERPNext — don't waste it.

Takeaways

  1. Authorization is data, enforced by one engine. Every entity declares a (role × action × permlevel × if_owner) matrix; a single generic engine enforces it on every read, write, and state transition. Adding a role or tightening a right is a row edit, never new branching code.
  2. Three orthogonal axes answer three different questions. Role×action = what may they do; User Permissions = which records (row-level, decoupled from roles, scoped on link fields); permlevel = which fields inside the record. Keep them independent.
  3. permlevel locks fields without per-field ifs — but enforce it on read and write. Tag cost/margin/override fields at level 1; a clerk edits the document yet is blind to its sensitive fields. A read-only filter leaves a write hole.
  4. Row-level scope rides the link field. Restrict a user to one Company / Store / GSTIN by AND-ing a filter on the FK into every query — same role everywhere, different data. Miss the link and the restriction silently does nothing.
  5. The lifecycle is the same matrix. submit/cancel/amend are action bits, so "a cashier may post but not cancel" is encoded once. Lifecycle and authorization never diverge because they are one table. Imperative only_for / has_permission guards are the rare exception, for cross-cutting actions only.
  6. Compose carefully, and audit relentlessly. Role-grant OR shared OR (grant AND owner) for visibility; omitted actions mean zero; there is no role hierarchy; a broad row defeats if_owner. Store the matrix queryably and ship a flatten-and-audit admin view — the one thing ERPNext's scattered JSON cannot give you.

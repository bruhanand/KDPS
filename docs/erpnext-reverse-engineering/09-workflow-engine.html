The Workflow Engine

Configurable approval state machines layered on top of docstatus: states, transitions, role-gated actions, conditions, and self-approval guards — multi-step sign-off without writing a state machine by hand.

Why this subsystem matters

Every ERP eventually meets the same demand from the business: "this document cannot post until someone signs off on it." A purchase above ₹50,000 needs the owner's nod. A stock transfer across a state border needs the accounts team to verify the tax treatment. An end-of-season markdown needs the category head to bless the new prices before the tills honour them. These are not data-validation rules — a valid document can still be unauthorised. They are approval gates: a human, holding a particular role, must act before the document is allowed to take effect.

The naive way to build this is to add a status column to each document (Pending Approval, Approved, Rejected) and scatter if user.role == "Manager" checks through the controller. That approach rots fast. The moment the business says "actually, orders over ₹2,00,000 need a second approval", or "the junior buyer can approve up to ₹20,000 but not above", you are redeploying code to change a number. Worse, the rule lives in five places and they drift. Approval policy is exactly the kind of thing business users want to tune without an engineer — so it should be data, not code.

ERPNext's answer is a generic, configurable workflow engine. It is a small, universal state machine — states, transitions, role guards, conditions — authored entirely as configuration rows and attached to any document type at runtime. One engine serves Sales Order, Purchase Invoice, Expense Claim, Leave Application and everything else. Crucially, it does not invent a parallel lifecycle: it drives the existing docstatus (Draft → Submitted → Cancelled) you met in the document lifecycle, so reaching the "Approved" state is what actually submits the document and fires the ledger postings.

Key idea

A workflow is an optional, per-doctype, fully-configurable state machine layered on top of docstatus. It does not replace the Draft/Submitted/Cancelled lifecycle — it drives it. Each named state declares which docstatus it maps to, so arriving at a state can submit or cancel the document. Admins author flows as data; the same engine serves every document type; and all other code must be written to cooperate with whatever workflow an administrator has (or has not) configured.

Where the code actually lives

The workflow engine is Frappe-framework core, not ERPNext app code. The Workflow, Workflow Document State, Workflow Transition, Workflow State and Workflow Action doctypes are not in the erpnext checkout — you cannot read their JSON there. Everything in this chapter is reverse-engineered from how ERPNext uses the engine: the helper functions apply_workflow(), get_workflow_name() and doc.meta.get_workflow(), and the child-table field names exercised in ERPNext's own tests and patches. ERPNext ships no workflow fixture and registers no workflow hook — workflows are end-user configuration only.

The cast: the doctypes that make up the engine

The engine is five doctypes. A Workflow header binds one document type to a state field and holds two child tables: Workflow Document State rows (the nodes) and Workflow Transition rows (the edges). Workflow State is a global catalogue of reusable state names, and Workflow Action is the per-user to-do that materialises when a document needs someone's approval. All five live in Frappe core; the table below records where ERPNext references each one.

Pattern 1 — The state machine is configuration data, not code

The foundational move: an approval workflow is not a class hierarchy or a switch statement, it is a row in a table plus child rows for states and transitions, attached to a document type at runtime. Admins author flows without deploying code, and one engine serves every document type.

Pattern

State machine as configuration data

The idea

An approval workflow = one header row (which doctype, which state column) + state rows + transition rows. The machine is interpreted from data at runtime, never compiled into the document's code.

Because the flow is data, a business user can add an approval level, change a threshold or re-route a state without an engineer. The same generic executor reads any flow and serves any model.

How ERPNext does it

ERPNext ships no workflow fixture and registers no workflow hook — a grep of erpnext/hooks.py and the JSON finds none. It only consumes the framework engine. Its cleanest example is make_sales_order_workflow() in erpnext/selling/doctype/sales_order/test_sales_order.py, which builds a complete "Pending → Approve → Approved" machine purely by frappe.get_doc() plus .append("states", …) and .append("transitions", …).

Apply to any ERP

On Postgres/Django, three tables and no state machine in code:

  • workflows — (doctype, state_field, is_active)
  • workflow_states — (workflow_id, state, maps_to_status, allow_edit_role)
  • workflow_transitions — (workflow_id, from_state, action, to_state, allowed_role, condition, allow_self_approval)

Load the rows and interpret them. One generic apply_action(doc, action, user) service serves all models.

Here is the full machine ERPNext constructs in its test, expressed as nothing but appended dicts. Note how the entire flow — states, their docstatus mapping, the edges, the role and condition guards — is just data: 

workflow = frappe.get_doc(dict(
    doctype="Workflow", workflow_name="Test SO Workflow",
    document_type="Sales Order", is_active=1,
    workflow_state_field="workflow_state", send_email_alert=0))

workflow.append("states", dict(state="Pending", allow_edit="All"))
workflow.append("states", dict(state="Approved", allow_edit="Test Approver", doc_status=1))
workflow.append("transitions", dict(
    state="Pending", action="Approve", next_state="Approved",
    allowed="Test Junior Approver", allow_self_approval=1,
    condition="doc.grand_total < 200"))
workflow.append("transitions", dict(
    state="Pending", action="Approve", next_state="Approved",
    allowed="Test Approver", allow_self_approval=1,
    condition="doc.grand_total > 200"))

Gotcha · the workflow_state field is injected, not declared

The workflow_state column is dynamically injected by Frappe when a workflow is active — it is deliberately absent from the doctype JSON. A grep of erpnext/selling/doctype/sales_order/sales_order.json finds amended_from but no workflow_state. Reimplementers who expect a static column will be surprised. The field name itself is configurable — it is whatever workflow_state_field says — so never hard-code the string workflow_state; read it from the header.

Pattern 2 — The workflow drives docstatus, it does not replace it

This is the single most important architectural decision in the whole subsystem. A workflow does not invent a parallel lifecycle that competes with the Draft/Submitted/Cancelled docstatus from Chapter 2. Instead each named state declares which docstatus it corresponds to — so the act of reaching a state is what submits or cancels the document and fires its ledger postings.

Pattern

Workflow drives the existing lifecycle

The idea

Layer the approval machine on top of the universal docstatus rather than inventing a second lifecycle. Each named state carries a doc_status mapping (0 = Draft, 1 = Submitted, 2 = Cancelled).

Arriving at a state with doc_status=1 submits the document; arriving at one with doc_status=2 cancels it. The state machine and the posting machine stay one and the same.

How ERPNext does it

In make_sales_order_workflow() the Approved state is appended with doc_status=1. So the action Approve that lands on it transitions the Sales Order from Draft(0) to Submitted(1). The Pending state has no doc_status (defaults to 0 = Draft).

One call — apply_workflow(so, "Approve") — both changes workflow_state and submits the document, in the same transaction.

Apply to any ERP

Keep your existing docstatus / lifecycle column from Chapter 2. Give each workflow state a doc_status mapping (0/1/2, or draft/active/void).

The transition executor sets current_state = next_state and performs the lifecycle side-effect (insert vs submit vs cancel) implied by the destination state's mapping — inside one DB transaction so state and postings never diverge.

Driving the machine is a single function call. Because Approved → doc_status 1, this one line advances the state and submits the Sales Order, which in turn runs its on_submit chain and posts the ledgers: 

from frappe.model.workflow import apply_workflow

workflow = make_sales_order_workflow()
so = make_sales_order(item_code="_Test Item", qty=1, rate=150, do_not_submit=1)
apply_workflow(so, "Approve")   # sets workflow_state=Approved AND submits (docstatus 0→1)

Gotcha · doc_status is a mapping, not the docstatus itself

doc_status on a state row is the state's mapping onto docstatus — not docstatus directly. A workflow with no Submitted state never submits the document, leaving it in Draft forever; a state mapped to doc_status=2 cancels it. Getting this mapping wrong fails silently: documents either never post, or post and then unexpectedly reverse. Always check that exactly the states which are meant to post carry doc_status=1.

Pattern 3 — Per-transition role + condition guards, with self-approval control

A transition is not a free edge — it fires only when two things hold: the actor holds the allowed role and a boolean condition over the document evaluates true. The same action name can fan out to different next-states by condition, and a per-transition flag decides whether the document's own creator may approve their own document — the segregation-of-duties knob auditors demand.

Pattern

Role + condition guards on every edge

The idea

An edge fires only if the actor holds the allowed role and a condition over the document is true. The same action name can route to different next-states by condition. A allow_self_approval flag controls whether the creator may approve their own document.

How ERPNext does it

Two transitions share action="Approve" but split on condition="doc.grand_total < 200" (allowed="Test Junior Approver") vs "doc.grand_total > 200" (allowed="Test Approver"), each with allow_self_approval=1. The test test_update_child_qty_rate_with_workflow asserts the junior cannot push grand_total over 200 while the senior can.

Apply to any ERP

Per transition row store: allowed_role (FK), condition (an expression string), allow_self_approval (bool). The executor:

  • filters candidate transitions by current_state + action;
  • drops ones whose role the user lacks;
  • evaluates conditions against the doc;
  • rejects self-approval when owner == actor and the flag is off.

The condition fan-out is the part worth dwelling on. The same action Approve, pressed on the same state Pending, resolves to a different required role depending on the document's own value — encoded purely as data: 

workflow.append("transitions", dict(
    state="Pending", action="Approve", next_state="Approved",
    allowed="Test Junior Approver", allow_self_approval=1,
    condition="doc.grand_total < 200"))
workflow.append("transitions", dict(
    state="Pending", action="Approve", next_state="Approved",
    allowed="Test Approver", allow_self_approval=1,
    condition="doc.grand_total > 200"))

Gotcha · never eval() the condition string

Conditions are python expressions evaluated against doc (e.g. "doc.grand_total > 200"). On any other stack do NOT run bare eval() on these strings — an unsandboxed condition field is a remote-code-execution hole, because business users can edit it. Use a restricted / whitelisted evaluator (a safe Python sandbox, or CEL / JSONLogic). Frappe itself runs these through a guarded frappe.safe_eval-style mechanism; replicate that discipline.

Gotcha · make conditions total and mutually exclusive

Multiple transitions can share the same (state, action) pair and are disambiguated only by condition + role. If conditions overlap or leave a gap — note the example uses < 200 and > 200, so grand_total == 200 matches neither — behaviour is order/first-match dependent or the action silently does nothing. Design condition sets to be total and mutually exclusive (use <= on one side), and decide the tie-break rule consciously.

Gotcha · self-approval defaults matter for audit

allow_self_approval left on lets a creator approve their own document. For segregation-of-duties — a real audit requirement in finance — you must explicitly set it off per transition. The test leaves it on for convenience; production money-flows generally must not.

Pattern 4 — allow_edit vs allowed: two different axes

There are two distinct authority questions a workflow answers, and conflating them is a classic bug. One is "who may move the document along this edge?" — that is the transition's allowed role. The other is "who may edit the document while it sits in this state?" — that is the state's allow_edit role. They are independent.

Key idea

Performing a transition does not grant edit rights in the destination state. The role that moved a document into a state can be deliberately unable to edit it there, because edit rights come from the state's allow_edit, not from having performed the transition. ERPNext's test_update_child_qty_rate_follows_allow_edit exists specifically to pin this down.

The allow_edit rule is enforced outside the normal save path, for features that edit a submitted document in-flight. ERPNext's "Update Items" feature re-derives edit permission directly from the active workflow's current state: 

def _validate_workflow(self) -> None:
    workflow = get_workflow_name(self.parent.doctype)
    if not workflow:
        return
    workflow_doc = frappe.get_doc("Workflow", workflow)
    current_state = self.parent.get(workflow_doc.workflow_state_field)
    roles = frappe.get_roles()
    allowed = any(
        state.state == current_state and (not state.allow_edit or state.allow_edit in roles)
        for state in workflow_doc.states
    )
    if not allowed:
        frappe.throw(_("You are not allowed to update as per the conditions set in {} Workflow.")
            .format(get_link_to_form("Workflow", workflow)))

erpnext/accounts/services/child_item_update.py:216–237

Read the logic carefully: it fetches the active Workflow, reads the document's current state via the configurable workflow_state_field (not a hard-coded column), and allows the edit only if some state matches the current state and that state's allow_edit role is held by the user. This is the engine's "who may edit a document while it sits in state X" rule, enforced independently of normal table-level CRUD permissions.

Gotcha · allow_edit and allowed are different axes

allow_edit (state-level) and the transition's allowed role are different axes. A user may be allowed to push a document into "Approved" yet not allowed to edit it there. Once a workflow is attached, do not rely solely on table-level CRUD permissions to decide editability — re-derive it from the current state's allow_edit.

Pattern 5 — Cooperate with the engine: gate programmatic submit/edit

This pattern is the one most likely to bite you later, because it is about code you write elsewhere. Any code that programmatically submits or edits a document must first ask "is a workflow governing this doctype?" and defer to it. If a workflow is active, the code must not auto-submit — submission is now the workflow's job — and it must re-derive edit rights from the workflow's allow_edit rule rather than just writing.

Pattern

Workflow-aware programmatic submit & edit

The idea

Code that auto-advances a document must cooperate with the engine. If a workflow is active for that doctype, leave the document in Draft for human approval instead of auto-submitting; the workflow owns submission.

For mid-flight edits, compute the allow_edit role of the current state and check membership before permitting writes.

How ERPNext does it

erpnext/assets/doctype/asset/depreciation.py guards every auto-submit with if not je.meta.get_workflow(): je.submit() (lines 249, 445, 559), so depreciation Journal Entries created under a workflow stay in Draft.

child_item_update.py::_validate_workflow() (Pattern 4) loads the active workflow via get_workflow_name() and gates the in-flight "Update Items" edit on the current state's allow_edit.

Apply to any ERP

Expose one helper get_active_workflow(doctype). Anywhere you programmatically submit, wrap it: if an active workflow exists, leave the doc in Draft.

For mid-flight edits, compute the allow_edit role of the current state and check membership — don't rely solely on table-level CRUD permissions once a workflow is attached.

The depreciation poster is the canonical example. Code that would normally auto-submit a Journal Entry must not submit when a workflow governs Journal Entry, because submission is now the workflow's job: 

je.flags.ignore_permissions = True
je.save()

if not je.meta.get_workflow():
    je.submit()    # only auto-submit when NO workflow governs Journal Entry

erpnext/assets/doctype/asset/depreciation.py:249 (also 445, 559)

Gotcha · forgetting this guard silently bypasses approvals

Programmatic submits must be wrapped in if not doc.meta.get_workflow() — otherwise the code submits a document the workflow was supposed to gate, bypassing approvals entirely. The asset/depreciation module had to add this guard in three places, and still needed a later data-fix patch (erpnext/patches/.../correct_asset_value_if_je_with_workflow.py) to repair asset values that had drifted because depreciation entries sat unsubmitted under a workflow. The lesson: design every auto-poster to be workflow-aware from day one — an approval gate added later will be silently bypassed by any poster that forgot to ask.

Pattern 6 — Mirror internal state onto a denormalised status column

The engine tracks a precise internal workflow_state, but reports, list views and other code often read a simpler, human-facing status or approval_status column that predates the workflow. Rather than rewrite every consumer, the engine can stamp that legacy column on arrival at a state — keeping the machine's vocabulary and the reporting column in sync.

Pattern

Stamp a denormalised status on transition

The idea

Keep an engine-internal workflow_state plus a human/reporting-facing status field, and let arrival at a state write the status. This decouples the machine's vocabulary from the column other code and reports already read.

How ERPNext does it

A Workflow Document State can carry update_field/update_value. The patch erpnext/patches/v11_0/set_update_field_and_value_in_workflow_state.py backfills these: for Expense Claim it sets update_field="approval_status", for Leave Application update_field="status", with update_value = the state name — so transitioning to a state also stamps the legacy status column.

Apply to any ERP

Add optional update_field/update_value to each state row. After a transition, in the same transaction, set doc[update_field] = update_value.

This lets you bolt a workflow onto a model that already has a status enum without rewriting every consumer of that enum. 

for state in workflow_states:
    if state.update_field:
        continue
    status_field = "approval_status" if doctype == "Expense Claim" else "status"
    frappe.set_value("Workflow Document State", state.name, "update_field", status_field)
    frappe.set_value("Workflow Document State", state.name, "update_value", state.state)

erpnext/patches/v11_0/set_update_field_and_value_in_workflow_state.py:7–20

Why two columns instead of one

The internal workflow_state may use precise engineering vocabulary (Pending Manager Approval, Pending Finance Review) while the legacy status column other reports read only needs Pending / Approved. The update_field/update_value mirror lets the two evolve independently — and is exactly the hook you use to surface a friendly status to non-technical staff while the engine tracks the exact internal state.

Pattern 7 — Workflow Action as the per-user actionable to-do

A state machine that only changes a column is half a feature. The other half is telling the right person there is something to approve. When a document lands in a state needing sign-off, the engine materialises a per-user task record — the Workflow Action — so approvers have a queryable inbox instead of having to hunt for documents.

Pattern

Materialise a to-do for each approver

The idea

When a document enters a state needing approval, create a per-user task record so approvers get an inbox / notification, rather than expecting them to find documents. The state machine produces work items, and those work items are an audit trail.

How ERPNext does it

The Workflow Action doctype (Frappe core; autonamed SYS-WACT-.##### per erpnext/patches/v11_0/refactor_autoname_naming.py:80) is the generated to-do. The Workflow header carries send_email_alert controlling email-on-transition — the test sets it to 0 to silence emails during testing.

Apply to any ERP

On a transition into a state with pending approvers, insert workflow_action rows (one per eligible approver); optionally fire email / WhatsApp.

Completing the action = applying the transition; mark sibling actions resolved. You get an audit trail and a queryable approver inbox for free.

End-to-end: the five flows

Pulling the patterns together, here is the whole subsystem as five sequences a consultant should keep in their head.

Configure
An admin creates a Workflow row (document_type=Sales Order, workflow_state_field=workflow_state, is_active=1), appends Workflow Document State rows (Pending=doc_status 0, Approved=doc_status 1, each with an allow_edit role) and Workflow Transition rows (Pending --Approve--> Approved, allowed=role, condition=python expr). Frappe injects a workflow_state Select field onto the document at runtime — it is not in sales_order.json.
Advance
A user opens a Draft Sales Order and picks the action Approve. apply_workflow(doc, "Approve") finds transitions from the current state whose action matches, filters by the user's roles, evaluates each condition against the doc, blocks self-approval if disallowed, sets workflow_state = next_state, applies the destination state's doc_status (here submit → docstatus 1), optionally stamps update_field, and fires email / Workflow Action notifications.
Condition fan-out
An order with grand_total 150 can be Approved by Test Junior Approver (condition < 200), but the same order edited above 200 fails for the junior and requires Test Approver — proven by test_update_child_qty_rate_with_workflow, which expects a ValidationError for the junior and success for the senior.
Mid-flight edit guard
While a submitted SO sits in a workflow state, the "Update Items" feature calls _validate_workflow(), reads the current state via workflow_state_field, and permits the edit only if the current state's allow_edit role is held — independent of normal CRUD permissions.
Programmatic-submit guard
Asset depreciation creates a Journal Entry and checks je.meta.get_workflow(); if a JE workflow is active it leaves the JE in Draft for human approval instead of auto-submitting (and a later patch fixes asset values that drifted because of manual, workflow-gated depreciation entries).

When to use a hard-coded status instead

The configurable engine is not free — it adds tables, an evaluator, an approver inbox and a notification path. Do not reach for it when the lifecycle is genuinely fixed. Use a plain status column when, and only when:

Use a hard-coded status field when…Switch to the configurable engine when…
The lifecycle is fixed and will not gain new states. Business users need to add or re-order approval levels themselves.
It is single-actor — one role, no "who approves what". Different roles approve under different conditions (value thresholds, store, brand).
No conditional routing — every document follows one path. The same action must fan out by a condition on the document.
Segregation of duties / self-approval is not a concern. Audit requires self-approval to be blocked and the trail to be queryable.
Key idea

The moment the business says "who approves what, under which condition, in which order", a status enum will start sprouting if role == branches across the controller. That is the signal to switch to the data-driven engine. Until then, a few hard-coded states are fine — but design the document tables so a transitions table can be bolted on later without reposting ledgers.

Applying this to KDPS

Applying to KDPS

This is the model to copy for any human-approval gate over the documents-write-ledgers spine: vendor PT approval before it posts liability, high-value purchase-booking sign-off, EOSS / markdown approval before the tills honour new prices, and inter-state (Bihar ↔ Jharkhand) stock-transfer authorisation — each of which is a taxable IGST event that accounts must verify. Rather than a status enum per document, build one transitions table plus a current_state column in Postgres/Django, with each state mapped to the document's submit/cancel lifecycle so that "Approved" actually posts the ledger entries.

Three KDPS-specific rules fall straight out of the patterns:

  • Honour the depreciation lesson (Pattern 5). Any KDPS code that auto-posts — the PT → liability poster, or an auto-submitting transfer — must check for an active workflow and leave the document in Draft for approval, exactly like if not je.meta.get_workflow(): je.submit(). Otherwise an approval gate added later (and the owners will ask for one on high-value vendor bills) is silently bypassed. Design the posters workflow-aware now.
  • Keep AI at the edges (Rule: AI-at-edges-only). The condition expressions stay deterministic data — doc.grand_total > 200000, not a model call. An LLM may suggest who should approve or summarise a document; it never is the gate.
  • Use the update_field/update_value mirror (Pattern 6) to surface a Hindi / WhatsApp-friendly status to store staff ("Manzoori baaki" / pending) while the engine tracks the precise internal state. Store staff on low-end Android phones read the friendly column; accounts reads the exact one.

Sequencing: the full configurable engine is deferred until the roles/access model (D4 left it thin) is built. Until then a few hard-coded states are fine — but design the document tables so a transitions table can be bolted on without reposting ledgers, and never strip a workflow's right to drive docstatus. And remember Tally stays the statutory book of record: a KDPS workflow gates when a document posts, it does not change what posts.

Takeaways

  1. Approval is data, not code. Build it as a generic state machine — three tables (workflow header binding doctype → state field; states with a doc_status mapping, allow_edit role and optional status mirror; transitions as from_state → action → to_state guarded by role + condition + self-approval flag) — authored by admins, serving every transaction type. ERPNext ships no workflow fixture; it only consumes the Frappe-core engine.
  2. The workflow drives docstatus, it does not replace it. Each state declares which docstatus (0/1/2) it maps to, so reaching "Approved" submits the document and fires its ledger postings — inside one transaction. A workflow with no Submitted state never posts; a state mapped to 2 cancels.
  3. Guard every edge with role AND condition, and gate self-approval per transition. The same action can fan out to different roles by a condition over the document. Make conditions total and mutually exclusive, and never eval() them unsandboxed — an open condition field is an RCE hole.
  4. allow_edit and allowed are different axes. Moving a document into a state does not grant the right to edit it there; edit rights come from the state's allow_edit. Re-derive editability from the current state, not from CRUD permissions, once a workflow is attached.
  5. All other code must cooperate with the engine. Anywhere you programmatically submit, first ask if not doc.meta.get_workflow() and defer to it — ERPNext's depreciation poster needed this guard in three places and still needed a data-fix patch when it was missed. An approval gate added later is silently bypassed by any poster that forgot to ask.
  6. Mirror internal state onto a friendly status column via update_field/update_value, and materialise a per-user Workflow Action to-do on each transition — giving you an approver inbox and an audit trail for free. Defer the full engine until you genuinely need configurable approvers, conditions and segregation of duties; until then, design tables so a transitions table can be bolted on without reposting ledgers.

Chapter 6 · Documents & data

Master Data & the Party Model

The nouns: Item (with template/variant/attribute — the SKU = style × size × colour model), the Customer/Supplier "Party" abstraction, Address/Contact via dynamic links, multi-company, and the snapshot-the-master rule.

Why master data is where an ERP is won or lost

The previous chapters built the meta-model and the two ledgers — the accounting engine and the stock ledger — and chapter 5 showed how a transaction flows into them. Those are the verbs. This chapter is about the nouns: the Item you sell, the Customer who buys it, the Supplier you buy from, the Company whose books you keep. Master data sounds like the boring part of an ERP — the reference tables you set up once and forget. It is the opposite. It is where the hardest modelling decisions live, and where a careless choice quietly poisons every report you will ever run.

Two questions decide the fate of the whole system, and both are answered in master data:

  1. How granular is a "thing you sell"? If you store stock at the wrong level — by style instead of by style×size×colour — no downstream report can ever recover the detail, because the detail was never captured. Granularity is a one-way door.
  2. What happens to posted history when a master changes? A customer renames their firm; you correct a typo in an item description; you switch a default account next year. If your transactions reference the live master, every one of those edits silently rewrites the past. If they copied the master at the time of the deal, the past stays true.

ERPNext answers both with a small set of patterns that are worth learning verbatim, because they are durable across any stack: the template / variant / attribute model for SKUs, the Party abstraction that unifies Customer and Supplier behind one ledger handle, dynamic links that attach an Address or Contact to any owner, the per-company defaults cascade for multi-company master data, and — the rule that ties them together — snapshotting the master onto the transaction at creation time.

Key idea

Keep masters metadata-light and transaction-heavy. The master is the editable "current truth"; the transaction is the frozen "historical truth". Almost every pattern in this chapter exists to keep those two separate — so you can fix a name or change a default this year without corrupting last year's books.

Stated as the architecture band this handbook keeps returning to, the master layer sits beneath documents, which write the ledgers:

Pattern 1 — Template / Variant / Attribute (the SKU = style × size × colour model)

This is the single most important master-data pattern for any retailer, and it maps exactly onto "a product family that comes in several sizes and colours". ERPNext models it once and reuses it everywhere; learn it as the canonical answer to "how do I represent a SKU?".

Pattern

Template / Variant / Attribute model for SKUs

The idea

Model a product family once (the template) and let each sellable SKU be a concrete child (the variant) that pins exactly one value per axis of variation.

The axes themselves — Colour, Size — are data (master records), not columns and not code. Adding a new axis like "Sleeve Length" is inserting rows, never a schema migration. Stock and price live on the variant only.

How ERPNext does it

An Item carries either has_variants=1 (it is a template) or variant_of (it is a variant of that template). The child table attributes (Item Variant Attribute) lists the axes on the template and pins the values on the variant.

Item Attribute holds the allowed values (Item Attribute Value rows, each with an abbr). The engine is erpnext/controllers/item_variant.py: create_variant() + copy_attributes_to_variant() clone template fields, make_variant_item_code() builds the code, get_variant()/find_variant() dedupe, generate_keyed_value_combinations() expands the cartesian product for bulk creation.

Apply to any ERP

On Django/Postgres: a product_template table, an attribute table, an attribute_value table, a product_variant table with an FK to template, and a variant_attribute_value join (variant_id, attribute_id, value).

  • Generate the SKU code from value abbreviations.
  • Enforce uniqueness of the (template, full attribute-set) tuple.
  • Offer a cartesian-product helper for bulk create.
  • Keep stock and price at the variant level, never the template.

The shape, made concrete

A T-shirt that comes in three colours and three sizes is one template Item and up to nine variant Items. The template carries the family identity (name, item group, brand, HSN, tax) and a list of axes; each variant carries one value per axis plus its own code, stock and cost.

Item Attribute: Colourvalues Red(R), Blue(BL), Black(BK)
Template Item: TSHIRThas_variants=1; attributes = [Colour, Size]
Variant Item: TSHIRT-RED-Mvariant_of=TSHIRT; Colour=Red, Size=M

The variant's item code is assembled from each attribute's abbreviation. This is the literal code that produces TSHIRT-RED-M:

# erpnext/controllers/item_variant.py — make_variant_item_code()
abbr_or_value = (
    cstr(attr.attribute_value) if item_attribute[0].numeric_values else item_attribute[0].abbr
)
abbreviations.append(abbr_or_value)

if abbreviations:
    variant.item_code = "{}-{}".format(template_item_code, "-".join(abbreviations))
    variant.item_name = "{}-{}".format(template_item_name, "-".join(abbreviations))

Notice the branch on numeric_values: a numeric attribute (a size ladder defined by from/to range + increment) contributes its raw value, while a list attribute contributes its abbreviation. That branch is the seam where the two attribute code-paths meet.

Creating a variant — the sequence

When the UI or API asks for "the Red / M variant of TSHIRT", the controller runs this sequence:

get_variant(template, {Colour:Red, Size:M})entry point
find_variant()search existing variants for an exact attribute-set match
match found?return it — never create a duplicate SKU
create_variant()new Item; set variant_of
copy_attributes_to_variant()clone template fields, skipping no-copy fields
make_variant_item_code()derive item_code/item_name from abbreviations
validate_variant()each attribute valid & enabled for the template

For bulk creation, enqueue_multiple_variant_creation(item, {Colour:[Red,Blue], Size:[S,M,L]}) computes the total number of combinations (and rejects ≥ 600 to avoid a runaway job), then create_multiple_variants() uses generate_keyed_value_combinations() to expand the cartesian product and create each variant that does not yet exist.

Numeric attributes — the second code path

Size ladders are not an enum. Item Attribute supports a numeric mode with from_range, to_range and increment, validated by validate_is_incremental() with floating-point precision handling. A waist size from 28 to 44 in steps of 2 is sixteen valid values without sixteen Item Attribute Value rows. If you model every attribute as an enum, you miss this — and your size handling will be clumsy.

Gotcha — variant uniqueness is application-enforced

There is no DB constraint guaranteeing one variant per attribute-set. find_variant() dedupes by comparing the number of attributes and each row. A naive reimplementation that forgets to check "same number of attributes" will happily create duplicate SKUs for the same Colour/Size. If you rebuild this, add a real unique index on the normalised (template, sorted attribute-value set) — do not trust application code alone.

Gotcha — what must NOT be copied to a variant

copy_attributes_to_variant() carries an explicit exclude list: item_code, item_name, opening_stock, variant_of, valuation_rate, naming_series. Forgetting to exclude valuation_rate or opening_stock would copy the template's cost and stock onto every variant — a silent inventory corruption. Worse, which other fields propagate is itself configurable via the Variant Field table and Item Variant Settings, so propagation is data-driven and easy to get subtly wrong.

Gotcha — a template holds no stock

A template Item must not hold stock (ItemTemplateCannotHaveStock), and you cannot un-set has_variants once variants exist (validate_has_variants throws "Item has variants"). Stock and price live only on concrete variants. Any design that tracks stock at the style level violates this rule at the schema level.

Gotcha — renaming a value is a propagate, not a snapshot

Renaming "Maroon" → "Burgundy" runs Item Attribute.on_update → update_variant_attribute_values(), which bulk-updates every variant's Item Variant Attribute rows so existing variants stay consistent. Attribute spellings are reference data, so they propagate. This is the deliberate opposite of the snapshot rule in Pattern 4 — and conflating the two breaks both (see the "snapshot vs propagate" warning later).

Applying to KDPS

This is the model verbatim. A Style is the template Item (has_variants=1); Size and Colour are Item Attributes; every sellable SKU is a variant with variant_of + its size/colour pinned. Stock and cost live on the variant only — so "stock at style level" is impossible by construction, which is exactly the domain rule that size×colour must survive end-to-end. The 40+ brand structure rides on top as a brand field + the defaults cascade in Pattern 5, not as a second variant axis.

Pattern 2 — The Party abstraction (one ledger handle for Customer and Supplier)

The naive ledger has a customer column and a supplier column, both nullable, exactly one filled per row. It works until you need a third kind of party — an Employee you owe an advance, a Shareholder, a Student — and then every nullable-FK report and every posting routine has to learn the new kind. ERPNext never lets that happen.

Pattern

The Party abstraction

The idea

Don't bake Customer/Supplier into the ledger. Treat "a party we owe, or who owes us" as a generic pair: (party_type, party).

New party kinds (Employee, Shareholder, Student) then slot in without touching the ledger schema or the posting code — they are just new values of party_type.

How ERPNext does it

GL Entry carries party_type (a Link → DocType) and party (a Dynamic Link keyed by party_type). All party behaviour is centralised in erpnext/accounts/party.py.

get_party_account() resolves the control account with a 3-level fallback (party record → group → company default), choosing receivable vs payable from the Party Type's account_type. get_party_details() snapshots address, contact, currency, price list, taxes and payment terms uniformly for any party_type. Customer and Supplier both subclass TransactionBase and reuse this code.

Apply to any ERP

Add a party_type (enum/text) column and a party_id column to ledger and transaction tables — a polymorphic reference.

  • Put all party resolution (control account, currency, price list) in one module parameterised by party_type.
  • Keep a config table mapping party_type → account_type.
  • Avoid one nullable FK per party kind — that explodes as kinds grow.

The ledger never links a Customer directly

The whole abstraction rests on two field declarations in erpnext/accounts/doctype/gl_entry/gl_entry.json. party_type is an ordinary Link whose target is the DocType registry itself; party is a Dynamic Link whose target doctype is read at runtime from the value in party_type:

// gl_entry.json — the two fields that make the ledger polymorphic
{ "fieldname": "party_type", "fieldtype": "Link",         "options": "DocType" }
{ "fieldname": "party",      "fieldtype": "Dynamic Link", "options": "party_type" }

So a receivable row reads (party_type="Customer", party="CUST-0001") and a payable row reads (party_type="Supplier", party="SUPP-0042") — same two columns, same posting code, same report. The accounting ledger aggregates receivables and payables across all party kinds uniformly because it never had to know which kind it was looking at.

Resolving a party to its control account — the 3-level fallback

The most-used function in party.py is get_party_account(). Given a generic party and a company, it finds the right control account by walking three levels and stopping at the first hit:

# erpnext/accounts/party.py — get_party_account() (condensed)
account = frappe.db.get_value(
    "Party Account", {"parenttype": party_type, "parent": party, "company": company}, "account")

if not account and party_type in ["Customer", "Supplier"]:
    party_group_doctype = "Customer Group" if party_type == "Customer" else "Supplier Group"
    group = frappe.get_cached_value(party_type, party, scrub(party_group_doctype))
    account = frappe.db.get_value("Party Account",
        {"parenttype": party_group_doctype, "parent": group, "company": company}, "account")

if not account:
    account_type = frappe.get_cached_value("Party Type", party_type, "account_type")
    account = frappe.get_cached_value("Company", company, "default_" + account_type.lower() + "_account")

Read it top to bottom as a precedence chain:

1 · Party Account on the party recordthis specific Customer/Supplier, this company
2 · Party Account on the party's GroupCustomer Group / Supplier Group, this company
3 · Company default by account_typedefault_receivable_account / default_payable_account

The third level is the elegant bit: it does not hard-code "receivable" or "payable". It reads the account_type from the Party Type record (Customer → "Receivable", Supplier → "Payable") and builds the company-default field name as default_<account_type>_account. Register a brand-new party type with account_type="Receivable" and this code resolves it correctly without a single edit.

Gotcha — you cannot JOIN a Dynamic Link in SQL

party's target table is decided at runtime by party_type, so there is no single table to JOIN against. Aggregating across parties requires party_type-aware queries or a resolver, and every index that touches the party must cover (party_type, party) together — never party alone. On Postgres this is the standard cost of a polymorphic reference; budget for it.

Applying to KDPS

Vendors and customers should share one Party abstraction so payments and ledgers reference (party_type, party) uniformly. This is what lets a single receivables/payables view span the whole business, and it means the SOR/consignment vendor liability that posts only on sale lands on the same generic party plumbing as an outright purchase. Map each Party Type to its account_type once; the control-account fallback then does the rest per company (Bihar / Jharkhand).

Pattern 3 — Dynamic Links (one Address for any owner)

A Customer has addresses. So does a Supplier, and a Company, and a warehouse. The wrong fix is an address table with one nullable FK column per possible owner — it grows a column every time a new owner type appears, and most columns are null. The right fix is to let the address point at its owner, polymorphically.

Pattern

Dynamic Link — polymorphic attachment

The idea

Let a satellite record (Address, Contact) belong to any kind of owner without one FK column per owner type. The link stores the target's doctype and name, so one Address row can be shared by a Customer, a Supplier and a Company at once.

How ERPNext does it

Frappe provides the Dynamic Link child doctype (link_doctype + link_name); Frappe core — ERPNext uses but does not define it. Customer.onload calls load_address_and_contact().

erpnext/selling/doctype/customer/mapper.py creates the link rows — appending {link_doctype, link_name} to the Address/Contact's links table — and queries Dynamic Link by {link_doctype, link_name, parenttype:'Address'} to find a party's address.

Apply to any ERP

An address table plus a party_link join (address_id, owner_type, owner_id) — a generic many-to-many. Or store (owner_type, owner_id) columns on the address directly.

  • Index on (owner_type, owner_id).
  • This is the standard polymorphic-association pattern: it trades FK integrity for flexibility, so enforce existence in app code or with check constraints.

The lookup is a single query against the Dynamic Link table, parameterised by the owner's doctype and name — no per-owner-type branch:

# erpnext/selling/doctype/customer/mapper.py — find a party's address
address = frappe.get_all(
    "Dynamic Link",
    {"link_doctype": source.doctype, "link_name": source.name, "parenttype": "Address"},
    ["parent"], limit=1,
)
if address:
    target.customer_address = address[0].parent

Because source.doctype and source.name are just passed through, the same code finds a Supplier's address (source is a Supplier) or a Company's. The address is the parent of the Dynamic Link row; the links child table on the address holds one row per owner it belongs to.

Gotcha — Dynamic Links have no referential integrity

link_doctype/link_name are plain strings — there is no foreign key. Deleting a Customer does not cascade to its Address links; ERPNext has to call delete_contact_and_address() explicitly. If you rebuild this with a polymorphic join table, you own orphan cleanup yourself: a deletion hook, a periodic sweep, or check constraints. The flexibility is real, but so is the housekeeping debt.

Applying to KDPS

Addresses carry the state GSTIN that decides whether a transfer is intra-state (CGST+SGST) or inter-state (IGST). Attaching them via dynamic links means a store's billing address — and its Bihar-or-Jharkhand GSTIN — lives in one place and is reused by every document for that store, vendor or company, without duplicating the address per relationship.

Pattern 4 — Snapshot masters onto transactions (history immutability)

This is the rule that quietly underwrites everything: when a transaction line is created, copy the master's values onto the line rather than referencing the live master. If the master changes tomorrow, posted history stays exactly as it was at the moment of the deal. It is the difference between an ERP whose reports you can trust years later and one whose history mutates under you.

Pattern

Snapshot the master onto the transaction

The idea

At line creation, copy the master's values — name, description, rate, accounts, tax, currency — onto the transaction line. Do not just reference the master.

The master is the editable "current truth"; the line is the frozen "historical truth". Editing the master later can never rewrite posted documents, because the document already owns its own copy.

How ERPNext does it

get_basic_details() in erpnext/stock/get_item_details.py assembles an ItemDetails dict copying item_name, description, stock_uom, income_account, expense_account, cost_center, etc. onto the line.

Defaults resolve per-company via the item_defaults child and cascade item → item-group → brand → company. get_party_details() snapshots party fields the same way. Item.cant_change() then freezes structural fields once submitted transactions reference the item.

Apply to any ERP

Transaction-line tables carry their own copies of the snapshotted columns (item_name, rate, tax_rate, account_id…), filled by a "get details" service at line creation.

  • Keep a soft FK to the master for drill-through, but treat the copied values as the source of truth for that document.
  • Add immutability guards that block edits to cost/valuation-defining master fields once any posted document references the master.

What gets copied, and when

Two services do almost all the snapshotting. Adding an item to a sales or purchase line calls get_item_details → get_basic_details(), which resolves the per-company defaults and copies the result onto the line:

User adds Item to a Sales/Purchase lineor an API does
get_item_details() → get_basic_details()resolve per-company item_defaults
cascade: item → item-group → brand → companyfirst hit wins (Pattern 5)
snapshot onto the lineitem_name, description, stock_uom, income/expense/COGS account, cost_center, conversion_factor

Adding a party to a transaction calls get_party_details(party_type, party, company) → _get_party_details(), which snapshots the party's default currency, billing/shipping address (looked up through the Dynamic Link of Pattern 3), primary contact, price list, tax template and payment terms onto the document. Both services share the same philosophy: resolve once, copy, freeze.

The per-company snapshot, in code

Here is the exact mechanism that copies the matching company's defaults onto the item dict. It iterates the item_defaults child rows, finds the one for this company, and overlays it:

# erpnext/stock/doctype/item/item.py — get_item_defaults()
def get_item_defaults(item_code, company):
    item = frappe.get_cached_doc("Item", item_code)
    out = item.as_dict()
    for d in item.item_defaults:
        if d.company == company:
            row = d.as_dict(no_private_properties=True)
            row.pop("name")
            out.update(row)
    return out

The returned dict is what the line copies. Because the copy happens at creation, re-pricing the Item or correcting its description next month does not touch a single posted invoice.

The other half: immutability guards

Snapshotting frees you to keep most master fields editable — but a few fields the ledger structurally depends on must not change once a posted document relies on them. ERPNext's Item.cant_change() freezes exactly those: is_stock_item, valuation_method, has_serial_no, has_batch_no — once submitted transactions reference the item. (It even allows a one-way FIFO → Moving Average switch.) Everything else stays editable, which is safe precisely because the transactions already snapshotted what they needed.

Gotcha — cant_change() is NOT "masters are immutable after use"

It freezes only a handful of structural fields. Most master fields remain editable forever. People misread this as a blanket immutability rule and either over-lock masters (frustrating users) or assume nothing is locked (corrupting valuation). The correct model is narrow: snapshot freezes the document; the guard freezes only the few master fields the ledger derives from.

Gotcha — snapshot vs propagate is a deliberate split

Deal terms (rate, accounts, tax) are snapshotted and frozen onto documents. Reference data (attribute value spellings, an attribute's disabled flag) is propagated to existing variants. Treat an attribute rename as a snapshot and your variants drift out of sync; treat a rate as a live reference and your old invoices silently re-price. Decide, per field, which category it is — and never mix them.

Applying to KDPS

This rule is "profitability is derived, never hand-entered" and "documents write ledgers". When a PT/GRN or POS sale posts, it must copy the unit cost (P RATE), the GST breakup, the brand and the commercial terms onto the document line. Then re-pricing a master, or correcting it later, never rewrites posted GST or margin history — and Tally, the statutory book, stays reconcilable. The structural fields a posted document depends on (is it a stock item, its valuation method) must be frozen once referenced, exactly as cant_change() does.

Pattern 5 — Per-company defaults & the cascade (multi-company master data)

One master, many companies. You do not want to duplicate an Item per company, nor hard-code accounts per company on the Item. ERPNext stores company-specific defaults as child rows keyed by company and resolves them at runtime with a precedence cascade. This is the engine that feeds the snapshot of Pattern 4.

Pattern

Per-company defaults child + resolution cascade

The idea

Store company-specific defaults (accounts, warehouse, price list, supplier) as child rows keyed by company, and resolve them at runtime with a precedence cascade — so you never duplicate the master per company, and a blank field still resolves to a sensible value.

How ERPNext does it

Item Default is a child table on Item — one row per company; validate_item_defaults() forbids two rows for the same company. Company holds default_receivable_account, default_payable_account, default_expense_account, default_inventory_account, stock_adjustment_account, etc.

The cascade in erpnext/stock/get_item_details.py tries get_item_defaults → get_item_group_defaults → get_brand_defaults in turn, falling back to Company defaults; get_party_account uses the same party → group → company chain.

Apply to any ERP

A *_company_default child/satellite table keyed by (master_id, company_id), plus a defaults table on the company.

  • Write one resolver function per default that walks the chain (record → group → company) and returns the first hit.
  • Scope every transaction by a company column so defaults and ledgers stay partitioned.

The cascade, for an Item's expense account, reads: try the Item's own per-company default; if blank, the Item Group's default; if blank, the Brand's default; if blank, the Company default. The first non-empty value wins.

Item Default (this item, this company)get_item_defaults
Item Group defaultget_item_group_defaults
Brand defaultget_brand_defaults
Company defaultdefault_expense_account, default_inventory_account, …
Gotcha — a blank field still resolves; trace the whole chain

Because of the cascade, an Item can have no expense account set yet still post to one at transaction time. When you debug "where did this account come from?", you must trace item → item-group → brand → company — not just stare at the Item. Document the chain somewhere visible, or your support tickets will be a maze.

Applying to KDPS

The two-GSTIN Bihar / Jharkhand structure maps onto the Company multi-company anchor: each is a Company with its own default accounts and warehouses, and every store/warehouse and transaction is scoped by company. The brand-as-first-class dimension and the SOR / Outright / Hybrid commercial terms ride the cascade — set them once at the Brand or Item-Group level and let individual Items inherit, overriding only where a specific style differs.

How the patterns compose — one item, one party, one ledger row

Put the five patterns end to end and a single sale tells the whole story. The Item resolves through the variant model and the defaults cascade; the party resolves through the abstraction; both are snapshotted onto the document; the document writes a GL Entry that names the party generically.

Pick variant TSHIRT-RED-MPattern 1 — variant, not template; stock/cost live here
Resolve item defaults: item → group → brand → companyPattern 5 — first hit wins, scoped by company
Snapshot item_name, rate, accounts, tax onto the linePattern 4 — frozen historical truth
Resolve party (Customer / Supplier) + its addressPattern 2 + 3 — generic party, dynamic-linked address
Post GL Entry (party_type, party, account)Pattern 2 — control account via 3-level fallback

Edit any master tomorrow — rename the customer, re-price the style, switch a default account — and this posted row does not move. That immovability is the product. Everything in this chapter exists to deliver it.

Takeaways

  1. Model variation as data, not columns or code. Template + attribute catalogue + a (variant, attribute, value) join. Adding "Sleeve Length" is a row, not a migration. SKU = style × size × colour falls out for free — and stock/price live on the variant, never the template.
  2. Abstract "who we transact with" into one polymorphic (party_type, party) pair. Centralise all party logic — control account, currency, tax — in one module parameterised by party_type. New party kinds need zero ledger changes. Index on (party_type, party); you cannot JOIN a dynamic link.
  3. Attach addresses and contacts with polymorphic links, not one FK per owner type — and accept that you own orphan cleanup, because there is no FK integrity.
  4. Snapshot masters onto transactions at creation — copy name, rate, accounts and tax onto the line, resolved through a per-company defaults cascade. The master is editable "current truth"; the transaction is frozen "historical truth". This is what lets you fix a typo or change a default next year without corrupting last year's books.
  5. Guard only the few master fields the ledger structurally depends on (is_stock_item, valuation_method). Everything else stays editable — safely, because the documents already kept their own copy.
  6. Snapshot vs propagate is a per-field decision. Deal terms freeze onto documents; reference data (spellings, disabled flags) propagates to existing records. Mixing them breaks both directions.
  7. Enforce variant uniqueness in the database, not only in application code — ERPNext checks it in code, and a naive port duplicates SKUs. Add a unique index on the normalised attribute-set.

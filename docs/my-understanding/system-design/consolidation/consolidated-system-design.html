The whole system as one design

Eight module discussions (D1–D8), reconciled into a single coherent design. The document a developer reads to understand the entire system.

Consolidated 24 June 2026 · Living document · Supersedes reading D1–D8 separately (those remain the deep-dive appendices).

Three ideas hold the whole system together:

  • The data spine is the PT file. From inbound onward, one record carries all product truth — identity, price, cost, tax. Everything keys off it.
  • The structural spine is documents → ledgers. Every event is a document; documents are the only things that write the books; the books are derived, never hand-edited.
  • The system is built to grow. New modules and a future in-house POS slot in without rebuilds.

The system in one picture

Read it as a flow. Goods move left → right along the spine. Master data feeds down into every step. The spine writes the ledgers below it, which feed Tally. The Brain reads everything on top. And the Money layer (rust) sits under the spine and fans up to touch every stage — payment is the connective tissue, not a separate silo.

goods / document flow money snapshot from masters Brain reads (writes nothing)
Follow the rust line — Money touches every module. That is the point of the diagram: payment is woven through the system, not bolted on the side.
  • Vendor & Buying → sets the payment terms (who we pay, when).
  • Inbound (PT) → creates the payable (vendor liability is born here).
  • Selling & Stock → SOR/Consignment liability accrues on sale, and cash is collected.
  • Ledgers → payments debit the vendor ledger; collections feed the cash ledger.
  • Tally → payment & receipt vouchers are pushed.
  • The Brain → reads it all for safe-to-pay, duplicate and fraud checks.

Design principles — the rules the whole design obeys

The twelve rules are stated in full on the architecture page. Here they are in one breath — every module below honours them.

  1. Every business event is a document with a numbered identity and a status life cycle.
  2. Documents write ledgers; ledgers are never hand-edited — balances are sums of postings; corrections are reversing entries.
  3. Master data lives in one place; documents snapshot it — changing a margin tomorrow never rewrites yesterday's bill.
  4. Every fact has exactly one owner — stock = stock ledger, the sale moment = POS, statutory truth = Tally, offer logic = rulebook.
  5. Flag, never block — mismatches raise an exception with a named owner; goods, sales and files keep moving.
  6. Derived numbers are computed, never typed — cost, profit, aging, MRP.
  7. Integrations are contracts, reconciled daily — push/pull, join key, retry, failure queue.
  8. AI at the edges only AI — reads messy inputs, writes read-only suggestions; never posts.
  9. Identity discipline on every line — quantity only at SKU grain; every piece carries barcode + season + commercial model.
  10. Every action has an actor — who created / edited / approved, on every document.
  11. Deadlines are data, not memory — return windows, offer dates, due dates, EOSS windows are stored and alarmed.
  12. Variation is data, not code — document types, posting reasons, commercial models, offers, roles, taxonomy, GST slabs and seasons are configuration rows, not code; the small kernel stays frozen.
Rule 12 in practice — Built to grow. extensibility

The system has a small stable kernel (documents → postings → ledgers + identity + masters). Everything variable is configuration data, not code — document types, posting reasons, commercial models, offer patterns, roles, taxonomy, GST slabs, seasons.

New modules and a future in-house POS attach to the kernel; they never reshape it. Flexibility comes from the kernel and from data-driven config — never from making everything generic. See Extensibility.

The data spine — the PT file is the source of truth

From inbound onward, one record is where all product truth crystallises at once: the PT line (the OWNER work-sheet row).

A single PT row carries product identity, classification, pricing, cost, margin and tax — together. So almost every master can be normalised out of it, and the two core postings (priced stock-in, vendor liability) are computed from it. That is why the data model is built outward from the PT.

Why the PT — and not the booking — is the spine.
  • Booking is deliberately thin — style + size only, no colour, barcode or price (it posts to no ledger, so full grain isn't needed yet).
  • The GRN → PT fills identity to full grain — this is where SKU, barcode+season, cost and tax all first exist together.
  • Everything downstream only references that identity — sale, exchange, transfer, return and stocktake look up the barcode+season the PT established; they never recreate it.

The system is one spine of goods (left → right), with cross-cutting tracks (money, accounting) and a read-only Brain on top, all standing on a base of master data.

Base layer · D8 · master-data & users

0 · Master Data & Users — the one owned home

Solves
The same lists kept differently everywhere; anyone could change anything; no audit trail.
Owns
Vendor & commercial terms (per brand, per season) · brand (supplier → brand → sub-brand) · store/warehouse (+ store-groups → state GSTIN) · SKU registry · barcode + season cohort · the season calendar (Open → EOSS → Closed) · taxonomy (from the PT Master Sheet) · date-effective GST/HSN · the offer rulebook (+ the no-discount "AMM" list) · users & roles (RBAC as data).
Governance
Hybrid stewardship — one HO owner accountable, editing delegated to the nearest role. A "dangerous four" need a second pair of eyes: brand terms, GST slabs, vendor bank/GSTIN, user roles. Every change logged; documents snapshot masters.
AI
drafts only reads brand offer sheets, suggests category/vendor cleanup — a person confirms.
Extends via
seam a new master is a new governed table under the same audit + snapshot + second-eye standard.
Spine · start · D1 · vendor management & booking

1 · Vendor & Buying — orders with deadlines, not memory

Solves
Orders live in people's heads; no track of booked-vs-received or return deadlines.
Documents
Booking — one vendor + one brand + one season; lines at style + size grain. Status derived from goods received: Booked → Partially → Fully received → Return window open → Closed/Cancelled.
Posts
Nothing — the order book only. (The conscious identity exception: full SKU grain begins at GRN/PT.)
Decisions
The commercial model is stored as a two-axis registry — ownership (KDPS-owns vs brand-owns) × return-terms (none / capped / uncapped), plus a rolling-top-up flag — and the friendly label is derived from those axes. Screens still read Outright (BNS) · Correction (25-18-10) · SOR · Consignment, but the books key off the axes (ownership drives the GST trigger), so a new deal shape is a new combination, not new code. The model defaults from the brand master but is overridable per booking / per stock-received (one brand can run any of the four models) — 26 Jun 2026. Margin % and return-window are configurable per brand (not fixed), filled by a KDPS steward. Snapshotted per brand per season (a first-class dimension, not a flag). A return-allowance budget per brand for Correction. Return-window alarms at 30/15/7 days. v1 = branded vendors; non-branded records → v2 (the non-branded inbound flow is v1).
AI
AI reads the brand's order paper → drafts the booking; a person confirms.
Extends via
seam a new commercial model is a new row in the model registry.
Spine · D2 · inbound ingestion

2 · Inbound (Goods-In) — from arrival to priced, sellable stock

Solves
Every arrival re-typed by hand into Excel; no priced size×colour stock; no reconciliation.
Documents
Shipment (anchor; invoice upload triggers it) → GRN (count vs order list; over-receipt flagged; counted-by ≠ entered-by) → PT (priced, barcoded — the data spine) → Store split → TIR export (→ Tally purchase).
Posts
Two steps. GRN posts the quantity — pieces in at SKU grain (location, condition, season, owned-flag provisional), so goods are sellable day one even before pricing. PT at Patna inward posts the valuation — priced stock-in per piece at landed ex-GST cost — and the Outright/Correction vendor liability (incl. GST) on receipt. For SOR/Consignment the PT only flags the piece not-owned; the sold-liability is posted later by the Sale (D3), never from the PT.
Decisions
Both paths v1 — branded (AI invoice → per-brand mapping → PT) and non-branded (AI invoice → chat-assist → editable PT, the "PT Mapper Type 2"). One barcode → many pieces. Season system-derived. Unit cost frozen at stock-in. Booking-less direct receipt works for any brand — the Shipment (not the booking) is the anchor; a "Receive without order" GRN posts the quantity, the model defaults from the effective-dated brand master but is overridable on this receipt (26 Jun 2026), no phantom booking is created, and the GRN can be retro-linked to (and its booking details updated by) a later booking.
AI
AI reads invoices into data, chat-builds the non-branded PT, fuzzy item-name match. Conversion, recon, pricing and Tally export are plain software.
Extends via
seam a new vendor PT layout is a new mapping rule (data).
Spine · end · D3 + D5 · outbound & offers

3 · Selling & Stock (Offers inside) — one machine, many reasons

Solves
POS per store with no central truth; exchange / transfer / returns / counts all manual; discounts run on memory.
Documents
Sale (Ten Software ingest · own KDPS POS, concurrent · manual-bill fallback) · Exchange · Inter-store transfer (two-step, in-transit) · RTV (defective/GR, credit or replacement) · Seasonal return (window-driven) · EOSS / V-flip · Stocktake + adjustment (ABC blind counts; negative-SOH policy).
Posts
Stock (out / in-transit / quarantine / liquidation, with reason) · Cash (collections in) · Vendor (SOR/Consignment liability accrues on sale; returns debit).
Decisions
Our system is the book of record; POS is the sale counter (we ingest, we don't recreate) — joined on barcode + season, with season inferred at the adapter (a reused barcode resolves oldest-cohort-first; ambiguity is a one-tap "which season?", never a blocked sale), all behind one swappable adapter. POS integration is deferred — the last module, not in the current build (26 Jun 2026): Ten Software will sell API access at a cost plus lead time; when POS is built KDPS uses their API if ready, else builds its own (decided then). The Sale stays source-agnostic so any source (Ten Software · own KDPS POS · manual bill) writes the same document; each store runs exactly one POS. Free-to-sell = physical − locked. Exchange credit = what the customer paid; new item at live offer price. EOSS V-flip flips ownership to KDPS (keep real brand, owner = KDPS, status = liquidation, "V<brand>", barcode unchanged).
Offers (inside)
One rulebook — trigger + reward + dials, eight patterns + an open model. Applied per item (a multi-brand bill carries many offers); best-for-customer precedence; brand vs KDPS funder tag (reporting, never a claim); a daily applied-vs-rulebook audit. Offers post nothing — a discount only lowers price.
AI
AI markdown suggestions on dead stock (cost floor + step-down) → a human authors the offer; reads offer sheets into clean rules.
Extends via
seam a new movement = new document type + reason code; a new offer = a new pattern row; a new sales channel (online) = a new Location type + a new Sale source.
Cross-cutting · D4 · payments & collection audit

4 · Money — every rupee justified, approved, traceable

Solves
What's owed to which brand is guesswork; cash-to-bank unchecked; duplicate/fraud risk.
Documents
Two layers — Payable (the debt, derived) ↔ Payment (the disbursement), linked by Allocation (bill-wise). Plus the daily Store-collection audit.
Lifecycle
Draft → Pending approval → Approved → Executed → Confirmed (UTR) → Reconciled (side branches: Rejected / On-hold / Failed / Cancelled).
Posts
Vendor ledger debit on payment. Cash ledger for the three-rail store audit. Balance derived: Opening + Invoices − cash discount − goods return − Payments + Interest = Due.
Decisions
Payables accrue per brand; payments anchor to the vendor (legal entity, bank, GSTIN). Eligibility gates — hard blocks (no bank+GSTIN, not tied to TIR, SOR not sold) and soft holds (discrepancy, over-allowance, over-tolerance → flag, human releases). Segregation of duties: maker ≠ checker ≠ payer, tiered by ₹. Three-rail collection audit: cash / card net-of-MDR / UPI vs bank, daily.
AI
copilot, read-only bank-narration reader · duplicate-payment guard · vendor bank-change fraud alert · one-line "safe to pay?" brief · cash-to-bank auto-match · brand-statement reconciler. A human always approves and posts.
Extends via
seam approval bands and tiers are configuration; new payment rails reuse the Payment lifecycle.
Cross-cutting · D6 · Tally sync

5 · Accounting (Tally) — the statutory book, fed exactly once

Solves
Everything re-keyed into Tally by hand. Scope (26 Jun 2026): the Tally / accounting sync is deferred — not in the current build; this is the design of record for when it is built.
Documents (vouchers)
Purchase (from TIR) · Sales (per-bill for B2B with customer GSTIN; daily consolidated per store per GST rate for B2C) · Receipt (combined daily per store; tender split) · Payment (from D4) · Debit/Credit Note · Journal (SOR/Consignment settlement).
Posts
To Tally only — one-way push, no re-keying. Tally stays the statutory book; this system feeds it, never replaces it.
Decisions
KDPS-owned deterministic voucher number (DEO-SAL-20260620-001 = store · type · date · seq) = idempotency guard + Tally join key (outbox → exactly-once). GST computed once by KDPS, carried, never recomputed; date-effective slab; a cross-state (Bihar↔Jharkhand) move is legally a taxable IGST supply between distinct persons, but the system only records the move and flags it — the IGST tax invoice and e-way bill are produced manually by KDPS, outside the system (26 Jun 2026 scope decision); intra-state moves are stock-ledger-only. Hybrid route: export → Vyapar TaxOne (default), direct-XML fallback. Daily tie-out + a plain-words "needs attention" list. Open (26 Jun 2026): IRN / e-invoicing ownership — assign an owning module and confirm applicability at the CA sitting; most is external/manual (counter bills are B2C, no IRN; cross-state paperwork is manual), but B2B / cross-state IGST invoices need an IRN above the turnover threshold.
AI
None — by design. The books are exact, machine-made.
Extends via
seam the export contract is stable, so a self-built Tally bridge later is a drop-in.
Top layer · D7 · analytics & intelligence

6 · The Brain — reads everything, writes only suggestions

Solves
Month-end built by hand; no daily picture; no early warnings.
Has
A 9 PM WhatsApp digest (exception feed) · a one-click report-maker (brand Sale + SOH pack) · size-level forecast (feeds the store split) · dead-stock hunter (age × velocity → markdown band) · profit & store scorecards · an anomaly / leakage watchdog · a read-only ask-anything assistant.
Posts
Nothing. Reads ledgers + masters + POS; writes only messages, reports and suggestions. The worst failure is a wrong message, never a wrong book.
Decisions
Built on a clean data spine (canonicalisation → a metrics layer where every number is defined once → a data-trust score). The assistant answers through the defined metrics, never raw SQL. Stockout windows logged from day one. AI has its own login; the suggestion and the human decision are logged separately.
AI
AI lives here code computes, AI narrates, a human decides.
Extends via
seam a new report or model is a new read over the same metrics layer — it can never corrupt the books.

The ledgers — where the spine converges

Three derived books. Only documents write them; humans and AI only read. Every balance is the sum of its postings; corrections are reversing entries; every row traces to a document.

LedgerOne row =Written byAnswers
Stock ledgerOne movement of one piece/SKU: qty, location, condition, season, reason, source document, owned-flag, unit costGRN (quantity in), PT (valuation), split, sale, exchange, transfer, returns, adjustmentSOH anywhere, aging, what moved and why
Vendor ledgerOne credit/debit per vendor per documentPT (Outright/Correction liability), Sale (SOR/Consignment sold-liability), returns (debit), payments (debit)What we owe each brand, return-window exposure
Cash ledgerStore × day × payment modePOS collections, manual bills, depositsDid yesterday's cash reach the bank
Build-ready sharpenings folded in:
  • Masters that drive history (GST slab, GSTIN, cost, price) are effective-dated (SCD Type 2), not only snapshotted — so an old bill never changes.
  • A second clock runs per SOR/Consignment lot (India GST deems a supply at ~6 months even if unsold), alarmed alongside the vendor return window.

Controls — keeping the truth honest

Four reconciliations. Each is a small loop: runs on a schedule, produces differences, pushes them to an exception queue with a named owner. They flag; they never block the floor.

ReconciliationComparesCadence
StocktakePhysical count ↔ stock ledgerCyclic (ABC, by store / brand)
Bank auditBank statement ↔ cash ledgerDaily
POS reconPOS SOH ↔ our SOH per storeDaily
Tally reconVouchers sent ↔ accepted in Tally (on voucher number)Daily

On top sit the spine of accountability — roles & approvals as steps inside each document's state machine — and a full audit trail (who created / edited / approved, and what AI suggested vs what a human decided).

Extensibility — how the system grows future modules · own POS

This is a multi-year operating system, not a one-off build. New modules, a future in-house POS and new channels are expected — so the design carries that expectation in its structure. Growth is configuration and addition, never a rewrite.

The stable kernel — what new things attach to

Five things almost never change. Everything else is built on them:

  1. Identity — SKU (brand+style+colour+size) and the piece cohort (barcode+season). Every module speaks this language.
  2. The document skeleton — number, type, status, actor/audit fields, snapshots. Every document, present and future, reuses it.
  3. The posting model — append-only entries into the three ledgers, keyed by (document type, reason code).
  4. The masters — one owned home, snapshotted onto documents.
  5. The edge-contract pattern — push/pull + join key + recon + failure queue, behind a swappable adapter.

Configuration (data) vs code

Configuration — add a row, no releaseCode — changes deliberately, money-safe
Document types & status flows · posting reason codes · commercial models · offer patterns · roles & the permission matrix · taxonomy · GST/HSN slabs · season calendar · approval bands · store-groupsThe posting rules (which reason posts what, per model) · the ledger invariants (append-only, balance = Σ postings) · the unit-cost formula · the edge adapters

Worked examples

Building our own POS later. The Sale is already source-agnostic — source = Ten Software | manual bill | KDPS POS, joined on barcode+season.
  • Today an adapter pulls Ten Software's sales into Sale documents.
  • A future KDPS POS simply becomes a new writer of the same Sale document.
  • Stock/cash/vendor postings, offers, Tally vouchers and every report are unchanged — the book of record was always ours; only the counter changes.
Adding the Attendance & Payroll module (the client's WAPCS) later.
  • It arrives as a new bounded module with its own documents (employee, attendance event, payroll input) and masters (employee, store assignment, shift rules).
  • It reuses the document skeleton, the actor/audit standard, the roles model and the store master.
  • If it ever touches money (salary payouts) it posts through the same Payment lifecycle. Nothing in the spine moves to accommodate it.
Selling online later. An online channel is a new Location type and a new Sale source. The offer rulebook already anticipates online-only offers (parked). Stock, identity, ledgers and Tally treat an online sale like any other.
The guardrail — flexibility, not over-engineering. The verified build research warns against the opposite failure, so this system is deliberately not:
  • microservices · event-sourced · a plugin runtime · attribute-everything (EAV).

It is one modular monolith over one database. Flexibility comes from the stable kernel + data-driven config + clean boundaries — the cheapest kind to maintain, and the only kind a small team can keep correct.

Tech shape — deliberately boring

One modular monolith, one database

  • Modules in code mirror the modules above, with clean internal boundaries — but one application over one relational database (PostgreSQL with app-layer scoping — django-scopes, fail-closed; the schema is RLS-ready). Store / brand / season / state-GSTIN are carried as foreign-key dimensions on every ledger leg, so the books can always be sliced by any of them.
  • No microservices, no queues between services, no second database.
  • One developer, fifty stores: strong by being simple. The rules are enforceable because everything lives in one place.

Browser PWA, light and offline-tolerant

  • A browser app on the store's POS machine — no installs, light pages, bad-network tolerant, big tap targets.
  • Hindi where staff face it. Owners get WhatsApp, not logins. INR in Lakh/Crore format (₹28,50,000).
  • Typed end-to-end — a typed React/TypeScript PWA on the glass, a typed Python/Django engine (mypy + pydantic), and a generated typed client at the API seam so the two halves agree by construction. Money bugs are caught by the compilers, not in production.

AI & hosting

  • Hosted top model (AI platform to be decided later), model swappable; hosting to be decided later.
  • AI only ever sees edge data and computed numbers, never raw customer/payment data.
  • All AI combined < ₹2,000/month — the cost is the always-on database, not the models. Confirm AI processing arrangements before go-live.

Degraded modes are designed, not improvised

  • POS down → manual-bill fallback (a real document, reconciled later).
  • Internet down → capture offline, sync when back.
  • Tally rejects a voucher → failure queue, not a phone call.

KDPS Operating System · Independent review

Code, UI and ERP-process review — and what was fixed in this pass

Reviewed on 26 July 2026 against the working tree at /app (main, through PR #112), with the full stack brought up locally — Postgres 15, Django/ASGI on uvicorn, Vite dev server — and clicked through as owner, store manager and store staff on desktop (1920 / 1440) and mobile (390). All 31 open GitHub issues were read first: nothing in this pass overlaps them.

Verdict

The engineering is in unusually good shape. The problem was what the app said, not what it did.

ruff clean, ruff format clean (208 files), 3/3 import-linter contracts kept, the 697-test backend suite green, tsc clean and the frontend suite green. No TODO/FIXME anywhere in 283 Python files, no dead frontend modules, no console errors on any screen visited. The documents, voucher series, append-only ledgers, fail-closed scoping and RBAC contract tests are better than most production ERPs carry.

The findings were concentrated in one place: screens that told the user something the database did not say. A dashboard of hand-typed figures, page captions naming sections that no longer exist, a bell with a permanent red dot and no click, a master that had no screen, and a purchase commitment with no way to end it. Those five are fixed and tested in this pass. The rest of the review is recorded as ERP-process gaps for the backlog — no code was written for them.

What was fixed

P0 The dashboard was inventing numbers

Found: every KPI on pages/Home.tsx was a literal. The owner opened on “Net sales today ₹18.42 L”, “Owed to brands ₹42.60 L” and “Open exceptions 5”; the store manager opened on “Net sales today ₹2,84,500” and “Items to receive — 3 shipments”. At that moment the trial balance was ₹0 with 0 vouchers, the vendor ledger held nothing, and there was exactly one pending booking. Two of those tiles even carried a “live” label, and tapping a tile opened a modal with an invented sparkline and no marking that the series was fiction.

Why it matters more than it looks: Rule 6 of the constitution is that calculated numbers are never typed by hand, and the planned-page rule is that a planned page may not flatter. The dashboard broke both — and a plausible wrong total is exactly the number nobody goes and checks. On a demo to a brand or a bank it is the first screen shown.

Fixed: every tile is now one of two things and says which — a figure the ledgers can answer today, or a screen that is not built (value —, chip “Not built”). Live tiles read /finledger/vendor/ageing, /stockledger/on-hand, /approvals/inbox, /inbound/queue and /inbound/pending; a request that has not landed shows …, never 0. The payable tile is only requested when the person holds money: manage, so nobody gets a tile that 403s. Clicking a tile opens the screen that owns the number. The invented sparkline is gone.

Owner now opens on Owed to brands ₹0 · Stock on hand ₹0 (0 pcs, 0 SKU lines) · Waiting for your approval 0 — which is the truth, and matches “Books tie · ₹0 · 0 vouchers” two panels below it. Store manager opens on Bookings awaiting receipt 1.

P1 Thirteen sections, always open — and a bell that rang for nothing

Found: the sidebar rendered every section expanded. For an owner that is ~45 links in one column: Money, Reports and Setup sat below the fold on a laptop, so the sidebar was a list to scroll rather than a map to read. Separately, the notification bell was a <button> with no onClick and a permanently lit red dot — dead UI that also lied about there being something to see.

Fixed: sections fold and remember (kdps-nav-collapsed), with aria-expanded, a rotating chevron, keyboard focus ring, and auto-unfold whenever you land inside a folded section (search, deep link, redirect) so the sidebar can always show where you are. Everything stays open by default — nobody loses a link they had. Single-item sections still behave as a direct link, untouched. The bell now counts what is actually waiting on this person (/approvals/inbox), opens the inbox, and shows nothing at all when there is nothing waiting.

This is presentation only — it does not touch which sections a role gets (#96 / #133 / #118 keep that work).

P1 The vendor master had no screen — and its write gate was open to everyone

Found: /api/vendors answered POST on a bare IsAuthenticated, while stores, brands, seasons and GSTINs have been steward-gated since D8. A store cashier could mint the supplier that every future booking, GRN, PT and payable hangs off. There was no detail route at all, so a vendor — once created — could never be corrected or retired through the API, and no screen existed anywhere in the app: vendors arrived only via seed_foundation. For a retail ERP, a supplier master you cannot maintain is a foundational gap, not a nicety.

Fixed: the steward gate moved to masters/permissions.py and now covers vendors (reads stay open — the booking form needs the list; only the edit is a stewardship act). Added GET/PATCH /api/vendors/<id>, ?include_inactive=1, and search across code / name / city / GSTIN. New screen Setup → Vendors: create, correct, retire (never delete — ledger rows point at it), payment terms, PAN/GSTIN, and the brands a vendor supplies as a chip picker. VendorListCreateView has been struck off the UNGATED_VIEWS baseline, which is how that list is supposed to shrink.

P1 A booking had no ending — and the table's Booking “Approve” cell gated nothing

Found: Booking.Status has carried CLOSED and CANCELLED since the first migration and nothing in the codebase could ever reach them. A season that delivered 40 of 100 pieces stayed “Partially received” for ever: the pending-bookings list kept offering it, the open-order figure counted 60 pieces nobody was waiting for, and the only exits were editing the quantity (rewriting history) or ignoring the row. Every ERP has this as the short-close. Separately, the ratified access table grants booking: approve to the owner and no endpoint read that rung — the cell was decoration.

Fixed: POST /api/bookings/<id>/close with {action: close|cancel, reason}, gated at booking: approve — so the buyer who places an order cannot write off its balance, the same separation that stops the buyer confirming receipt of their own goods. The reason is mandatory (it is the answer to “why did the other 60 never come?” six months later), the actor and timestamp are stored, cancellation is refused once anything has been received (short-close it instead), and a second attempt is a 409. Receiving against an ended booking is refused with a 409 that quotes the reason, so a stale tab cannot silently reverse the decision. The detail screen gains the panel, the write-off count and a record of who ended it and why. Nine new backend tests.

What is genuinely strong (so the review is fair)

  • The money spine. Append-only ledgers with a BEFORE TRUNCATE guard that binds the superuser, reversal-only corrections, gap-free voucher series allocated under a row lock, and a trial-balance health endpoint. Very few systems at this stage have this.
  • RBAC as a contract, not a convention. One ratified matrix, section+capability gates, declare_role_list forcing every hand-kept exception to carry a written reason, and a source-scanning test that fails when a new endpoint ships ungated. The reviewer's job was easy because that test exists.
  • Fail-closed scoping. Store-scoped users are filtered at the queryset, and the tests probe the negative case, not just the happy path.
  • The planned-page honesty rule. 27 unbuilt screens each say what will live there and what is missing. That rule is why the dashboard finding stood out so sharply — the rest of the app already lives by it.
  • Comments that explain the decision, not the syntax. Rare, and worth protecting as the team grows.

ERP-process gaps — recorded, not built

Measured against how a standard retail ERP runs, not against the PRDs. Nothing below was coded in this pass; each is a candidate ticket, and none of them collides with the 31 open issues.

There is no “bill vs received vs ordered” variance screen and no tolerance rule, so an overbilled invoice can be paid. This is the single biggest control gap left in the buy cycle.

Documents carry created_by/posted_by and approvals record decisions, but master-data edits, permission changes, logins and break-glass use leave no trail. Smaller observations (no code written)

  • P2 The login screen lists ten demo logins with passwords. Correct for an alpha; it must be behind an env flag before anyone outside KDPS sees the URL.
  • P2 Frontend tests are all pure logic — 102 of them, and not one renders a component. A jsdom + Testing-Library setup would let the sidebar, the approval flow and the dashboard tiles be tested as a user meets them.
  • P2 mypy --strict runs on core and config only. Widening it one app per sprint (vendors, inbound, masters are the small ones) is cheap now and expensive later.
  • P2 The six outbound screens are visibly copy-descended (list + tabs + status pill + detail drawer, five times over). A shared DocumentListScreen would remove a few hundred lines — worth doing when the outbound issues (#137 / #141 / #147) settle, not before.
  • Obs PtMapper.tsx is 1,352 lines in one file. It works and is well commented, but it is the one file where a change is likely to be made nervously.
  • Obs Python 3.12 + Postgres 15 were used locally (the repo targets 3.12/16). Nothing in the suite depends on 16-only behaviour.

Where the AI agents belong

The architecture already has the right shape for this: agents at the edges, drafts that a human approves, and a fence written on the screen (“AI never writes stock, money or Tally”). Two are live — the invoice reader on booking capture, and the PT mapper's learning proposals. The natural next edges, in the order they pay for themselves:

  1. Invoice ↔ GRN match. The reader already parses the bill; comparing it to what was received is the same data with a variance rule on top — and it closes the three-way-match gap above.
  2. Short-close suggestions. Now that a booking can end, an agent can propose the list (“season closed, 60 pcs undelivered for 90 days”) with a drafted reason. The decision stays at booking: approve.
  3. Duplicate master detection. Two vendors called “Arvind Fashions” and “Arvind Fashion Ltd” — flag on create, steward decides. Cheap, and it protects the master that everything hangs off.
  4. Count variance triage. Rank submitted variances by value and pattern (one size missing across a style = mis-ticketing, not shrinkage) before they reach the approver.
  5. Ageing / anomaly narration for the morning brief — but only once the reports layer exists, so the agent is summarising real figures and not, as the old dashboard did, making them up.

Refused, with evidence

1 · “Syntax error: missing ( at core/textsearch.py:41”

Line 41 is def text_filter[QS: QuerySet[Any]](qs, term, fields) -> QS: — a PEP 695 generic function, valid Python 3.12+ and the version this project targets (requires-python = ">=3.12", ruff target-version = "py312", mypy python_version = 3.12). Adding the “expected” character would have created the syntax error the report was reporting. The analyser was a 3.11-era parser; the same tool almost certainly produced finding 3.

3 · “31 possibly-undefined variables”

ruff's F rule set — which is pyflakes, and includes F821 undefined-name — is enabled repo-wide and reports zero across 283 files. It is not a theoretical check either: during this very pass it caught a real Any I left undefined in rbac_matrix.py within seconds. A file that cannot be parsed yields undefined-name noise for every symbol in it, which is the shape of a 31-item list from a 283-file codebase.

4b · “Add tests/_creds.py to .gitignore”

That file is imported by about twenty suites: removing it from version control breaks the test run for every other developer and for CI, on the next clone. It also holds no secret — two os.environ.get lookups with throwaway dev defaults, one of them a demo password already printed in memory/test_credentials.md and on the alpha login screen. The literals were the problem; the constants module is the fix.

5b · Refactor masters/migrations/0002_phasef_identity.py::backfill_identity (complexity 22)

An applied migration is frozen history, not live code: it has already run on every database and will only ever run again on a fresh one. Rewriting it changes nothing about the running system, risks a divergence between what was applied and what the file says, and cannot be meaningfully tested. Ruff excludes migrations/ for this reason.

6 · Split outbound/posting.py (40 imports) and ptmapper/views.py (33)

Not refused so much as not done blind. The import count is high because posting is the one seam every outbound document type crosses — models, stock ledger, value GL, voucher series, approvals. Cutting it apart is a real design change (one module per document family, with a shared kernel) that deserves its own ticket, tests written first, and a working alpha to compare against — not a change made to move a number. The cycle fix above removed the coupling that actually hurt.

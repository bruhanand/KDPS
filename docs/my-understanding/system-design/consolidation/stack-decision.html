The recommendation

One line each. The "why" is right below.

Python engine · React screens · PostgreSQL · no shortcut backend

The screens
React — a website that runs in the store browser. Nothing to install, works on any store computer or phone.
The brain
Python (Django) — where stock, ledgers, GST, payments and the rules live.
The data
PostgreSQL — the database every serious accounting system uses.
Where it runs
Hosting (cloud provider and region): to be decided later.
Not using
No Supabase / no backend-as-a-service. We run a real backend we control.

Why this: Django hands us login, user-roles, the entire back-office admin and safe all-or-nothing money-transactions for free — and a system like this is mostly back-office. Python is the same language as your invoice→PT code and the analytics/AI work, so it's one toolbox, not three. React keeps the store screens fast and is exactly where the AI build tools are strongest.

Your two doubts — answered straight

Supabase  DROP IT

You were right. Three real problems for an accounting-grade system:

  • No clean money-transactions. A ledger needs "all of this happens, or none of it does." Supabase can't do that simply — you'd push the logic into raw database scripts, which is fragile.
  • Permissions get slow and tangled at the size of an ERP (many roles, many stores).
  • Lock-in. Put your logic inside it and moving off it later means a rewrite.

Instead: plain PostgreSQL with our own backend. Same database, full control, no lock-in.

TypeScript as the main language  NOT THE CORE

The engine should be Python (Django), not TypeScript, because for this project Python wins on three counts: it comes with the back-office and login built in; it's the same language as your existing code and the analytics/AI; and it's the proven choice for complex, data-heavy business systems.

TypeScript still earns its place — but only on the screens (React), where it and the AI design tools are strongest. Python for the engine, TypeScript for the glass.

The one fork worth your conscious call

Build it (recommended) vs. start from ERPNext. ERPNext already has GST, e-invoice and e-way-bill done — the hardest compliance plumbing, free, built in India. The catch: it has its own opinions about stock, pricing and accounting, and your design (documents→ledgers, SOR as a first-class thing, PT-file pricing, Tally as the statutory book, our own POS) doesn't match those opinions. Bending it to fit can cost as much as building, and it fights the "you design it yourself" approach you've followed all along.

My call: build it ourselves, but steal ERPNext's GST data model so we don't reinvent the slab/HSN tables. If you'd rather seriously evaluate adopting ERPNext, say so — that's the only thing here that changes the whole plan, so it's worth deciding on purpose, not by default.

When I'd change this recommendation

  • If you want one language everywhere and you're fine building the back-office screens by hand → go all-TypeScript. (You'd still use Python for the AI/analytics bits.)
  • If getting GST-compliant fast matters more than full control of the design → reconsider adopting ERPNext.
  • If you plan to hire an in-house team later in a specific language → weight the choice toward whatever they'll know.

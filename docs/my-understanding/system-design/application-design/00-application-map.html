KDPS · Application design · The page map

Application Map — every page of the KDPS system

This is the complete page map for the KDPS operating system: a browser-based React PWA front end over a Django/Postgres back end. It lists every screen, what it is for, who uses it, how important it is, and how the pages fit together — organised by the five-layer architecture and the D1–D8 module designs. Anand reads and shares this; build follows it foundation-first, then one vertical slice at a time.

How to read this map. Section 2 gives the count and a one-line summary of each module. Section 3 is the full inventory — one table per module, each row a page with a stable ID, its purpose, the role that owns it, a priority chip, and its key states. Sections 4–8 cover the shared frame (information architecture), who can see what (roles & access), the reusable building blocks (design system), the order we will build in, and the questions still open.

This is a merged map. Many screens surfaced across several module readers (the three ledger viewers, the season calendar, the exception queue, the recon boards). Duplicates are collapsed into one canonical page each and cross-referenced, so the system resolves to about 190 distinct pages across 14 modules plus the global app shell. It respects the load-bearing rules: documents write ledgers (ledger views are read-only), masters are snapshotted onto documents, flag-don't-block, AI suggests at the edges only, and Tally stays the statutory book of record.

Information architecture

A single responsive React PWA shell wraps every page. The frame is a persistent top bar plus a collapsible left sidebar organised by the canonical five layers — Master data · Documents · Ledgers · Controls · Intelligence — with the outside-system edges as a sixth admin group. The shell renders only the modules and actions the signed-in role may use. Ledger views are strictly read-only (no hand-edit affordances anywhere). AI surfaces are always labelled read-only suggestion. The flag-don't-block problem queue and the deadline/alerts surface are reachable from every page. Money is rendered everywhere through one INR Lakh/Crore primitive (for example ₹28,50,000 or ₹1.74 Cr); quantities through one SKU-grain primitive. The shell never presents itself as replacing Tally — Tally appears only as feed/tie-out health.

Responsive form factors

Three layouts from one component set.
  • Store tablet/phone (in-store): mobile-first, big tap targets, Hindi-readable labels, scan-first entry (the barcode box is prominent), offline-tolerant with a visible sync queue; the till/receive/count tasks are reduced to the minimum fields and heavy back-office tables are hidden or read-only.
  • Desktop back-office (HO/Patna/accounts/buyer/admin): full sidebar, dense tables with filters and column-choosers, side-by-side document+source viewers, multi-pane reconciliation diff tables.
  • Owner phone: a lean read/summary surface — dashboards, digest, approvals and exception drill-downs that mirror the WhatsApp message. Owners rarely log in, so every owner action must also work as a WhatsApp reply or deep-link.
The PWA degrades gracefully on weak networks (degraded-mode banners, queued-for-sync notices) and never blocks the counter.

Design system plan

One token set and one component library serve every screen, so the store till and the back-office table are the same parts at two densities. The foundations encode the architecture's spine: a per-layer colour band so a screen's layer is legible at a glance, one money primitive, one SKU-grain primitive.

Foundations

  • Colour. A calm navy (#1f2d4d primary) with a rust accent (#c4623f) for emphasis and the brand mark, and a per-layer band palette reused as the system's spine — grey (master data), navy (documents), rust (ledgers), amber (controls), purple (intelligence/AI), blue (edges). Semantic states: green = ok/matched/locked, amber = needs-attention/open, red = error/blocked/overdue, blue = info/next, purple = AI.
  • Typography. The system UI stack (-apple-system / Segoe / Roboto) for fast rendering on low-end store hardware; one display size for page titles, a compact data-table size, and a tabular treatment for money and quantities so columns align. Hindi must render cleanly — labels stay short, plain and non-technical.
  • Spacing & density. Two density modes from the same tokens — a roomy big-tap store mode (mobile-first, scan-prominent) and a compact desktop back-office mode (dense tables, filters, column chooser). 8px spacing grid; cards with a 12px radius and a 1px hairline.
  • INR money formatting. One money primitive renders integer paise as ₹ with Indian Lakh/Crore grouping (₹28,50,000 / ₹4.2L / ₹1.74 Cr); it shows the ex-GST/GST breakup where relevant, never uses floats, and never recomputes carried tax — it displays the value computed once at the event.
  • Quantity & SKU formatting. One SKU-grain primitive always shows Brand · Style · Colour (or P/M/E tier) · Size — never style-only; a cohort chip shows barcode + season; size×color renders as a matrix, never a single number.
  • Iconography. A small, literal, high-contrast set (scan, receive, count, sell, transfer, return, flag, lock, sync, AI-spark) sized for touch; status conveyed by chip + icon + colour together (never colour alone) for accessibility and for screens viewed in bright stores.

Cross-cutting patterns

  • Scan-first entry. In every store task (sell, receive, count, transfer) the barcode box is the primary control; typing is the fallback; an unreadable/clashing barcode drops to manual entry, never a dead end.
  • Season inference at the edge. A scanned barcode resolves oldest-cohort-first (FIFO) and only asks 'which season?' when genuinely ambiguous — never blocking the sale.
  • Offline POS queue. Capture work offline (sales, counts, receiving), mint a client-UUID, show a durable outbox, sync idempotently when the network returns; store+bill-no dedup; one store = one POS.
  • Flag-don't-block. Mismatches raise an exception row with a named owner; the floor keeps moving. Only two ingest hard-blocks (cost>MRP, non-canonical season), the brand-alias fuzzy-merge hold, and the money pay-gate ever stop the flow.
  • Documents-write-ledgers. Ledger and balance views are strictly read-only; corrections are reversing entries / correction documents, never edits.
  • Snapshot masters. Documents show the values they copied at creation; editing a master tomorrow never rewrites yesterday's document — surfaced by the snapshot panel.
  • Maker ≠ checker ≠ payer / second-eye. The UI hides or disables actions the current user is conflicted on; the dangerous-four master changes and tiered payments route to an approval queue.
  • Approval queues + WhatsApp mirror. Approvals (payment, discount, transfer, master change) appear both in-app and as a WhatsApp message/deep-link, with a recorded audit stamp; owners can act from the phone.
  • AI suggest → human confirm → document posts. AI outputs are read-only suggestions with a visible 'why', shown and logged separately from the human decision; AI never auto-posts; AI has its own read-only login.
  • Two-axis commercial model with derived label. The deal is edited as ownership × return-terms (+ rolling-top-up); the friendly Outright/Correction/SOR/Consignment label is always derived, snapshotted at receipt/PT, and drives the money on every downstream event.
  • Cohort (barcode+season) everywhere. Aging, dead-stock, SOR windows, returns, EOSS/V-flip and any list/filter run per cohort — SS-25 never mixes with SS-26.
  • Deadlines are data. Stored deadlines (return windows, SOR two clocks, offer dates, payment due, season dates) drive 30/15/7-day alarm chips and reminder surfaces.
  • Bulk actions on clean, review-only on flagged. Approval gates (WH, Patna, payments) auto-validate and let the user bulk-approve clean lines while drilling only into exceptions.
  • Master snapshotting + SCD-2 effective dating. GSTIN, GST slabs and brand/vendor terms are versioned by date and resolved by document date; changes never overwrite history.
  • Deterministic voucher number as join key. A human-readable store·type·date·sequence number is the idempotency guard and the Tally recon join key, visible and copyable everywhere a voucher appears.
  • Read-only intelligence with data-trust. Every analytics number carries a coverage/confidence badge, reads the one metrics layer (never recomputes), and frames forecasts as 'narrow the decision', not 'predict the number'.

Proposed design & build sequence

Build foundation-first, then one verified vertical slice at a time, with just-in-time per-slice specs (data model, posting entries and golden files grow per slice, not all upfront). The three externals — Ten POS, Tally, barcode/labels — are spiked in parallel because they have lead time. Money-out (payments) and the statutory bridge (Tally) come late, after the masters, ledgers and recon they depend on exist.

Phase 6 — Tally bridge

Tally is the statutory book of record and consumes the postings produced by inbound, sales, collections, transfers and payments — so the voucher contract, deterministic numbering, daily tie-out and plain-words needs-attention queue come once those postings are real. Open questions

These must be answered before the slices they touch are built. Several are money-critical and wait on a CA ruling; the config screens are designed to hold either answer until then.

  • Tally company shape (CD4). One Tally company with two GSTINs (Bihar & Jharkhand) vs two separate companies — changes voucher addressing, the GSTIN registry binding and the cross-state IGST pair view; config screens (EDG-13) hold either answer but the default must be chosen before the Tally slice.
  • Per-brand SOR/Consignment GST recognition path (CA). Path A (at-arrival, Schedule-I) vs Path B (at-sale, Rule-55 + 6-month deemed-supply clock) awaits a CA ruling; the SOR two-clock register, the GST-recognition monitor and the SOR settlement voucher all branch on it. Four other money-critical items (late-freight-after-PT, sold-before-PT, no-reposting, single-recognition) are also flagged pending CA.
  • POS specifics — now ours to decide, not discover (26 Jul 2026). The sale line carries season and MRP; voids and edits are reversing documents, never edits; bill numbers are gap-free per store. Formerly asked of a third party: does the sale line carry season and MRP, how are voids/edits represented, is the bill number stable and unique per store, what auth scope/rate limits, is there a test store and timeline? These shape OUT-05/OUT-01, the barcode+season edge resolution and the dedup key.
  • Tally export route as the committed default (C1–C2). Vyapar TaxOne import vs direct Tally-XML, plus TaxOne licensing/template determinism — needed before EDG-14 is more than a spike.
  • The deep roles/access model is intentionally thin. Before drawing the RBAC/approval screens we need the final list of named roles, the exact permission matrix, the rupee approval tiers and escalation SLAs, and the data-scope rules — including who the named employees are (currently placeholders).
  • Own-POS scope and timing. Which store(s) pilot the KDPS-built POS, the go-live gate definition (how green is 'recon green'), and and whether manual billing is the only mode at launch.
  • Exchange policy ground-truth conflict. Some readers describe value-credit-at-paid-price + live-offer (D3); others describe strict MRP-to-MRP swap with no money back and no discount audit trail (Workflows). Confirm the actual rule(s) and whether they vary by store/brand before building OUT-04.
  • Brand-report 'hold-back'. The target re-dating/re-numbering feature (INT-20) bends only the presentation layer while Tally/GST/cash stay truthful — confirm this is sanctioned by the client/CA and define the guardrails and audit before building it.
  • WhatsApp provider and message class. AiSensy or similar, utility-grade templates; and whether owner approvals truly round-trip via WhatsApp reply or only deep-link into the PWA — affects the digest/alert edge and the approvals-mirror pattern.
  • Hosting provider/region is deferred. The ADR keeps the stack but drops the host — needs deciding before deployment (Phase 0) and before any data-residency-sensitive screens (bank/payment data must stay in India; AI sees only safe edge data).
  • Number of distinct 'queue' surfaces. This map keeps a unified cross-module exception inbox (CTL-01) plus role/module-scoped queues. Confirm whether stores/HO want one inbox with filters or several dedicated queues, to avoid near-duplicate screens.
  • Attendance & Payroll. Named as deferred but referenced by store dashboards (staff present/absent) — decide whether a minimal attendance capture is in scope for the store dashboard before go-live or fully deferred to a later module.
  • Direct-receipt unknown-brand default. Confirmed default Outright + HO flag, but the 'truly unknown brand → Unconfirmed model → withhold vendor posting → hard pay-gate' chain needs a named owner and an SLA so the awaiting-invoice payable queue doesn't grow unbounded.
  • Negative-SOH auto-resolution boundary. Define exactly which negatives auto-resolve via a known allocation (auto-create missing inward) vs escalate as an HO exception, so STK-06/CTL-03 behaviour is unambiguous.

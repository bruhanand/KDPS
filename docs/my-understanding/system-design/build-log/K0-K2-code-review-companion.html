1 · The one trick: read the tests, not the code

You cannot validate this code by reading the Python — and you don't have to. Here is the trick the whole build is designed around:

A test is a promise written as an English sentence. Every promise the code makes has a matching test whose name is that promise. The computer re-checks every promise on every change. So your job is not "is this Python correct?" — it's "is this list of promises the right list, and are they all passing?" That you can absolutely judge.

Here is a real one from the code. You don't need to read the body — just the name and the shape:

# file: core/tests/test_document_fsm.py
def test_a_posted_document_cannot_be_edited(series):
    doc = _draft()
    doc.post()                          # turn the draft into a real posted document
    reloaded.memo = "tampered"          # try to secretly change it
    with pytest.raises(DocumentEditError):   # the code MUST refuse — or this test fails
        reloaded.save()

Read only the name: "a posted document cannot be edited." That is a business promise — once a voucher is posted, nobody can quietly alter it. The body sets up the attempt and says raises, meaning "we expect this to be rejected." If the code ever stopped rejecting it, this test goes red and the change cannot merge. The test is the contract; the code just has to satisfy it.

The second thing to recognise everywhere: two locks, not one. For every money rule, the code guards it in two independent places — once in the database itself (a "trigger," the deepest possible lock, which stops even the system administrator) and once in the application code (a friendly early error). You'll see this pattern in every file. It's the single most important sign that this code takes money seriously: the rule survives even if someone bypasses the app and goes straight to the database. The team calls this "binds even the superuser."

2 · A 5-minute primer: the eight words you'll meet

WordIn plain language (with a shop analogy)
Model / tableA kind of record, stored as a table with rows. Like a register: each row is one line. LedgerProbe, VoucherSeries are tables.
MigrationA dated instruction that changes the shape of the database (add a table, add a rule). They run in order, like numbered amendments to the rule book. There are 4 so far.
TriggerA rule baked into the database itself. It fires automatically on every write and can reject it. The strongest lock there is — it stops even an administrator. Think: a safe that physically won't close if the entry is wrong, no matter who's holding the pen.
ORM / "the app code"The ordinary Python layer the application uses to read and write. It does a friendly check first ("you can't do that") before the database has to slam the door.
Paise (integer)All money is stored as a whole number of paise (₹1 = 100 paise). Never as ₹1.005 with a decimal point — decimals drift and lose fractions of a paisa over millions of rows.
Append-onlyA ledger you can only add to, never erase or edit. A mistake is fixed by adding a reversing line, exactly like an accountant's ledger — you never white-out a posted entry.
docstatus / FSMEvery document has a status that walks a fixed path: draft → submitted → cancelled. "FSM" just means it can only move along that path, never jump or go backwards. A draft can be edited; once submitted (posted) it's frozen; cancelled reverses it but the record stays.
Voucher series / doc-numberThe official document number, e.g. 26-27/DEO/SAL/74 — financial year / store / type / running number. It's the key that joins our system to Tally, so it must be gap-free (no skipped numbers) and never reused.

5 · K0 — the foundation

K0 is mostly plumbing (project setup, the quality gate). Only one line of it carries a real rule worth your eyes:

The "PostgreSQL or refuse to start" guard  config/settings.py

# The kernel's invariants — append-only ledgers, isolation — are meaningless
# on SQLite. Fail loudly rather than let the tests pass on the wrong engine.
if not _engine.endswith("postgresql"):
    raise RuntimeError("KDPS requires PostgreSQL" ...)
Why this matters to you: all the deep money locks (the triggers) are a PostgreSQL feature. A lighter test database (SQLite) would let the tests pass without actually testing the locks — a false green. This line makes that impossible: the system won't even start on the wrong database. It guarantees "green" always means "green on the real thing."

The two smoke tests  tests/test_smoke.py

  • "1 + 1 = 2" — proves the test machinery itself runs.
  • "the database is PostgreSQL" — proves the guard above is actually in force during tests.

6 · K1 — money is integer paise

core/money.py — 88 lines

One promise, and it's the bedrock of every rupee figure the company will ever see: money is stored as a whole number of paise, and anything with a hidden fraction is rejected, never silently rounded.

class MoneyField(BigIntegerField):
    # refuses to *coerce*: plain integer fields run int(1.9) -> 1, truncating paise.
    def _ensure_int_paise(self, value):
        if value is None: return None
        if isinstance(value, bool) or not isinstance(value, int):
            raise TypeError(... "a float/Decimal must never reach a money column.")
        return value
The bug this prevents (and the one that was actually caught). An ordinary number column, handed 1.9, quietly stores 1 — it drops the 0.9 with no warning. Across millions of sale lines that silent drift corrupts every total and breaks the Tally reconciliation. This field instead throws an error the moment a decimal shows up, forcing the conversion to happen properly at the edge. Commit 3 (the K1 fix) is exactly this hole being closed after a review.

Two small helper functions convert at the edges, using exact decimal math (never the lossy float type): rupees_to_paise("2850000") → 285000000 paise, and its exact reverse. The famous example ₹28,50,000 = 285000000 paise round-trips perfectly.

The promises that prove it  test_money.py

  • Paise round-trips with no drift — save a value, reload it, get the exact same whole number back (tested across 1 paisa, sub-rupee, ₹28.5 lakh, and a negative).
  • A direct decimal/float/text write is rejected — not rounded. Tested at every entry point.
  • The ₹↔paise conversions are exact, rounding half-up at the paisa, the India standard.

7 · K1 — the append-only ledger

core/ledger.py — 105 lines

The promise: a ledger line, once written, can never be edited or deleted — only reversed by adding a new line. This is the accountant's golden rule, enforced by the computer. And here you meet the "two locks" pattern for the first time:

# LOCK 1 — the database trigger (the deep one). Installed by migration 0001.
CREATE TRIGGER ... BEFORE UPDATE OR DELETE ON core_ledger_probe
    ... RAISE EXCEPTION 'append-only: ... is forbidden';
REVOKE UPDATE, DELETE ON ... FROM PUBLIC;        # belt-and-braces

# LOCK 2 — the friendly app-code guard, in the Python base class.
def save(self, ...):
    if not self._state.adding:                    # i.e. this row already exists
        raise AppendOnlyError("ledger rows are append-only; post a reversing entry")
Why two locks? Lock 2 gives a clean, early error to normal app code. But a clever person could try to skip the app and edit the database directly. Lock 1 — the trigger — sits inside the database and refuses them too, even if they're the administrator. That belt-and- braces design is the whole reason you can trust the ledger.

The promises that prove it  test_ledger_append_only.py · test_ledger_reversal.py

  • A raw database UPDATE is forbidden even for the superuser — and the row is verified unchanged afterwards.
  • A raw database DELETE is forbidden even for the superuser.
  • A raw INSERT still works — adding is always allowed; only editing/erasing is blocked.
  • The app's own edit and delete both raise a clean error before the database is even touched.
  • A correction nets to exactly zero — post ₹X, then post −₹X; the sum is the exact integer 0, the original line is byte-for-byte untouched, and both rows still exist. That's "fix by reversal."

8 · K2 — the document skeleton

core/documents.py — 441 lines · the heart of this review

This is the part you're about to merge, so it gets the most space. K2 builds the generic skeleton that every future business document (booking, goods-receipt, product-transfer, sale) will inherit. It owns exactly three things — and the whole file is just these three, locked twice each.

8a · The status lifecycle (docstatus FSM)

A document walks one fixed path and can never jump or reverse: draft (0) → submitted (1) → cancelled (2). A draft is editable; post() submits it (and is the only way to do so); a submitted doc is frozen; cancel() reverses it but keeps the record.

# The database trigger that enforces the path — it cannot be talked around.
IF TG_OP = 'INSERT'  ... a new row must start as draft            # can't be born posted
IF TG_OP = 'DELETE'  ... a posted/cancelled row is cancelled, never deleted
IF OLD.docstatus = 2 ... a cancelled row is frozen
IF OLD.docstatus = 1 ... submitted may only move to cancelled
                     ... and the cancel may not change any other column  # no tampering
IF OLD.docstatus = 0 ... a draft may only stay draft or be posted
Read that block as six business rules: you can't create a document that's already posted; you can't delete a posted document (you cancel it, and the record survives for the audit trail); once cancelled it's frozen; a posted document can only ever move to cancelled; cancelling is only a status change and can't secretly rewrite the amount or memo; and a draft can only stay a draft or become posted. Every one is enforced inside the database.

8b · Gap-free numbering (the Tally join key)

Every posted document gets an official number like 26-27/DEO/SAL/74. Because this is the key that joins to Tally, it must never skip a number and never be reused. Two careful decisions make that true:

  • The number includes the type (SAL, GRN…). The running counter is kept per type, so a sale and a goods-receipt both start at 1 — without the type in the number they'd collide as 26-27/DEO/1. (This was review-1 finding #1.)
  • The counter steps up only inside the posting transaction. If a post fails and rolls back, its number is handed back — so there are no gaps. A regular accounting "sequence" would leak a gap on every rollback; this uses a plain counted row instead, precisely to avoid that.
# The number is taken atomically; a rolled-back post returns it. And review-2
# added a DB trigger so even a raw edit can only step the counter by +1:
IF NEW.next_seq <> OLD.next_seq AND NEW.next_seq <> OLD.next_seq + 1 THEN
    RAISE EXCEPTION 'next_seq may only advance by one';   # can't rewind or jump
IF OLD.next_seq > 1 AND (fy/store/type changed) THEN
    RAISE EXCEPTION 'scope is frozen once numbering has started';

8d · The two safety nets again

As in the ledger, every K2 rule is locked twice. The app code (post(), cancel(), the edit/delete guards) gives clean early errors; the database triggers and CHECK rules are the deep backstop that binds even an administrator. K2 also adds two database CHECK rules worth naming in plain terms:

  • "a posted document must have a number" — it's impossible to have a submitted/cancelled row with a blank number, by any path.
  • "status can only be 0, 1, or 2" — a raw write can't park a document at some undefined status like 99.

The promises that prove K2  test_document_fsm.py · test_voucher_series.py · test_document_idempotency.py

There are 36 of these — the complete list is in the promise list below. The headline ones:

  • A new document starts as a draft with no number; posting it mints 26-27/DEO/SAL/1.
  • A posted document cannot be re-posted, edited, or deleted; a draft can be freely edited or thrown away.
  • Cancelling is a reversal, not a delete — the record stays.
  • Numbers are gap-free even when 12 tills post at the exact same instant (a real concurrency test), and a rolled-back post leaves no gap.
  • A sale and a goods-receipt in the same store get different numbers, never a clash.
  • A retried sale with the same one-time code returns the original, never a duplicate.
  • Raw database attempts to rewind the counter, tamper during a cancel, or forge a posted row are all rejected.

Document lifecycle K2

A new document starts as a draft with no number.
Posting moves it to submitted and mints its number (26-27/DEO/SAL/1).
A posted document cannot be re-posted (and no extra number is burned).
A posted document cannot be edited.
A draft can be freely edited.
Cancelling is a reversing transition, not a delete — the row remains.
A draft cannot be cancelled (only a posted one can).
A cancelled document is frozen — no re-post, re-cancel, or edit.
A posted document cannot be deleted; an unposted draft can be discarded.
Raw database attempts to re-post or delete a submitted row are refused (superuser included).
A posted/cancelled row can never exist without a number — blocked on both create and bulk-update.
A row cannot be born already posted/cancelled, and status can't be set to an undefined value (e.g. 99).
A raw cancel that also tampers with another field is rejected; a clean status-only cancel is allowed.
Posting uses the committed, current details — a stale in-memory copy can't stamp the wrong type's number.

Gap-free numbering K2

The number renders as the canonical 26-27/DEO/SAL/74, type included.
Two types in one store get distinct numbers (sale ≠ goods-receipt), never a clash.
Admin-set prefix/suffix are data, not code — configurable without a release.
Sequential posts are gap-free (1, 2, 3, 4, 5).
A rolled-back post leaves no gap — the number returns and the next post reuses it.
12 tills posting at the same instant get 12 distinct, gap-free numbers — no collisions, no duplicates.
A stale config save cannot rewind the counter (the app guard), and a raw database rewind or jump is refused (the deep guard).
A long-but-valid number fits without overflowing.
A used series can't be re-pointed to a new store/type; an unused one can still be corrected.

Offline-safe numbering keys K2

A retry with the same one-time code returns the original document — never a duplicate.
Different codes make different documents; every document gets a code by default; a duplicate code is refused by the database.

CHECKA simpler database rule: "this column may only hold these values."
ORMThe Python layer the app uses to talk to the database; gives friendly early errors.
MigrationA dated, ordered instruction that changes the database shape or rules.
Paise (integer)All money stored as whole paise (₹1 = 100). No decimals, so no drift.
Append-onlyAdd-only; corrections are new reversing lines, never edits.
docstatus / FSMThe fixed status path draft → submitted → cancelled.
Voucher seriesThe configured counter behind document numbers; one per store-and-type.

Idempotency codeA one-time key per sale so a retried write returns the original, not a duplicate.
Probe tableA throw-away test table (LedgerProbe, DocumentProbe) that exists only to prove the locks work; not part of the live system.

CI / npm run ciThe automatic gate that runs all checks and tests; must be green before merge.

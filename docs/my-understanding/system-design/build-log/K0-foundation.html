2 · Why — every decision and its reason

Each choice exists for a reason that pays off later. This is the part to challenge if you disagree.

DecisionWhyWhat we rejected
Empty skeleton firstK0's only job is to prove the repo builds and the gate is real. Adding any model now would mean reviewing money code before the rails exist.Starting with tables/models.
Monorepo app/{backend,frontend}One repo, one PR per slice, one CI command spanning both halves. Matches the build manual.Two separate repos (extra coordination).
Empty core app nowcore is the kernel. It exists from line one so everything has a home; it gains its first primitive (money + append-only ledger) at K1.Creating core later (churn).
KEY Postgres-or-fail guardThe kernel's invariants — append-only ledgers, cross-store isolation — are meaningless on SQLite. Settings raise a hard error if the DB isn't Postgres, so the foundation tests can never pass vacuously on the wrong engine.Trusting the dev DB to "probably" be Postgres.
import-linter contractOne rule from day one: core (kernel) may not import config (project wiring). This is the seed of "the kernel knows nothing about the modules" — enforced by CI, not willpower.An architecture rule that lives only in docs.
mypy strictMoney code is unforgiving; strict types catch a class of bugs before tests. The strict surface starts tiny and grows with the code — it never shrinks.Loose typing "for now" (never tightens).
Money deferred to K1Money = integer paise (never float). That's a K1 primitive with its own tests; K0 stays empty so the gate is what's under test here.Sneaking a money type into the scaffold.
pre-commit = static onlyFormat, lint, types, import-rules, tsc run on every commit (fast). The full suite incl. pytest runs in npm run ci. Keeps committing quick without losing the safety net.Running the whole DB test suite on every commit (slow).
Lockfiles committeduv.lock + package-lock.json in git → every machine and the Sandcastle container build the same versions.Floating versions (works-on-my-machine).

3 · How it was built & proven

The commands you'd re-run, and the proof it actually holds.

Reproduce it

npm run setup    # one-time: uv sync (backend) + npm install (frontend)
npm run ci       # the full gate — must print all green

The gate, in order: ruff format --check → ruff check → mypy (strict) → makemigrations --check (no drift) → import-linter → pytest (on real Postgres) → frontend tsc --noEmit.

The two proofs that matter

1 · It really hits Postgres. The test test_database_is_postgresql asserts connection.vendor == "postgresql" — and it passes. ✓
2 · The guard bites (not vacuous). Pointed at SQLite on purpose, the app refuses to start: 
$ DATABASE_URL="sqlite:///tmp.db" python manage.py check
RuntimeError: KDPS requires PostgreSQL, got ENGINE='django.db.backends.sqlite3'.
              Point DATABASE_URL at a postgres:// URL.
This is the one non-obvious requirement of K0, and it's verified — the safety net can't silently fail open.

Final run: npm run ci → ALL GREEN. pre-commit run --all-files on the staged files → all five hooks Passed.

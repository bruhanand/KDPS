Build philosophy — what this is & how we build

What this is

This is the concrete plan for turning the finished design into running software. The thinking is done: the system is settled as 5 layers and 12 rules (master data → documents → ledgers → controls → intelligence), and every module D1–D8 is designed and locked. What remains is to build — and the builder is unusual: one architect (Anand) working with AI agents, not a team. That single fact shapes every rule below. A solo-plus-AI build cannot afford a big-bang, cannot hold ten half-finished modules in its head, and cannot trust generated code on money without a gate. So the plan is deliberately narrow at any one moment: one thing scaffolded, then one slice proven, then the next.

The agreed shape, in one line: build the foundation first (repo, database, login, roles, deploy), then one verified vertical slice at a time, in engineering order along the spine — never all the PRDs upfront, never one module built to completion before the next is started.

The agreed approach (carried straight from the design)

STEP ZERO — FOUNDATION FIRST
What gets built
The skeleton that holds everything and carries no business logic: the repository, the database, login, the roles/access model, and a working deploy pipeline. This is the “walking skeleton” floor — a request can come in, a user can authenticate, the system can write to the database and ship to a server.
Why first
Every slice that follows needs a place to live, a way in, and a way out to a server. Scaffold only what the first slice needs (core + masters + the first module), then grow per slice — do not pre-build all the empty rooms.
STEP ONE ONWARDS — ONE VERIFIED VERTICAL SLICE AT A TIME
A slice is a tracer bullet
Each slice cuts top to bottom through all five layers for a single real workflow — a master record, a document, the ledger postings it produces, the control around it, and a screen to see it. A slice is “done” only when it is verified end-to-end, not when the screen renders.
Just-in-time per-slice specs
The detailed spec is written per slice, not all upfront. The data model, the double-entry posting catalogue, and the golden files grow with each slice — the inbound slice adds the inbound tables, postings and golden invoices; the payments slice adds the payment ledger entries; and so on. We never freeze the whole data model on day one and we never write a slice's posting code before its golden tests exist.
Engineering-led order along the spine
Slices follow the process order of the system (a shipment exists before it can be sold; a sale exists before it can be reported), not the client's wishlist order. The sequence (single canonical numbering, matching the slice roadmap below): 0 foundation scaffold → 1 master data + identity + PT-line model → 2 inbound thin slice (one outright brand: GRN qty → PT value → stock ledger, ending at the ledger, not at POS) → 3 vendor liability + vendor ledger → 4 selling thin slice (ingest one POS sale) → 5 offers on the sale → 6 payments + collection audit → 7 Tally voucher export → 8 SOR / Consignment + GST clock → 9 the Brain / analytics + WhatsApp digest.
Why the first inbound slice stops at the ledger
The first end-to-end proof must not be hostage to the riskiest unknown. Tally import and the barcode tool are the external gates with real lead time, so they are spiked in parallel (the POS was a third gate until 26 Jul 2026, when KDPS decided to build its own counter) — slices 1–2 (master data, then inbound ending at the stock ledger) prove the spine on ground we fully control first, before the POS edge arrives at slice 4.
THE BUILD LOOP — TWO SPEEDS
Per slice
Gate 1 (freeze the slice spec) → tests-first (golden files + ledger invariants written before posting code) → build → verify (CI green, golden files match) → design the screen → Gate 2 (review) → ship. “CI green” is the definition of done.
Money code vs everything else
SUPERVISED Ledgers, payments, Tally vouchers and GST are read diff-by-diff by a human even when CI is green. FREE Screens, reports and scaffolding the agents run freely and are reviewed after. The slow lane is where the rupees are.

Working norms for this build

How the work is recorded and communicated.
  • Deliverables are HTML, never markdown — everything Anand reads or shares is an HTML file (PDF via the house generator when a hand-off needs it).
  • Plain, non-technical language in every client-facing doc and chat; money always in INR Lakh/Crore (e.g. Rs 28,50,000), never raw digits.
  • GitHub issues are the source of truth for work — the backlog, each slice's frozen scope, and its acceptance live as issues, not in scattered docs. Project status lives only in CLAUDE.md and PROJECT-MAP.html; build docs do not carry their own status (the one habit that has already produced stale “not yet designed” claims).
  • The ADR / foundation-sketch set is being replaced, not ratified. The earlier ADRs (0001-stack.md … 0007-entity-gstin-scoping.md) presented unsettled choices — most sharply the stack — as if locked, and even disagreed with each other. They are treated here as input and ideas only. This report re-ratifies the foundation as a fresh set: the stack (FD-0, Q11: Python/Django + React-TS-PWA + PostgreSQL) and data-scoping (FD-8, Q12: app-layer django-scopes, schema RLS-ready) calls are now closed, alongside the stack-independent decisions (integer-paise money, append-only ledgers, snapshotted state/GSTIN, the relational entity→GSTIN→store hedge, one unified RBAC, golden-file + cross-store-isolation CI gate).
Two things this plan refuses to do. It will not write all module PRDs upfront (the design already plays that role; re-specifying it whole would rot before code catches up), and it will not build one module to 100% before starting the next (that path leaves the spine untested end-to-end until the very end). The discipline is always the same: scaffold the floor, prove one slice through every layer, then the next.

(C) Sandcastle — the autonomous build engine

AUTONOMOUS AGENT · THE WORK QUEUE IS A GITHUB LABEL
What it is
An autonomous coding loop ("Sequential Reviewer" variant) that turns labelled GitHub issues into reviewed branches with no human at the keyboard. Driven by @ai-hero/sandcastle, launched with npx tsx .sandcastle/main.mts.
The loop
Up to 10 iterations, one issue per iteration. Each iteration spins up one Docker sandbox shared by two phases:
  • 1 · Implement. A Claude Code agent runs gh issue list --state open --label Sandcastle — that filtered list is the sole source of truth. It picks the highest-priority unblocked issue (bug > tracer bullet > polish > refactor), works it red–green–refactor, runs npm run typecheck + npm run test, makes one RALPH:-prefixed commit on a fresh branch sandcastle/sequential-reviewer/<timestamp>, then closes the issue with "Completed by Sandcastle".
  • 2 · Review. A second Claude Code agent diffs the branch against target, checks correctness/clarity/security/tests, applies .sandcastle/CODING_STANDARDS.md, and either fixes & commits on the same branch or does nothing if clean. Refactor only — functionality preserved.
The implement phase opens commits on a branch, not literally a PR — a human (or /ship) turns the reviewed branch into a merged PR. If Phase 1 produces no commits, the loop stops: empty or blocked backlog. If the agent is blocked it comments and leaves the issue open.
How you drive it
Triage an issue to state ready-for-agent, which maps to the GitHub label Sandcastle. There is no separate ready-for-agent label — Sandcastle IS the ready signal. Run the launcher; the agent picks the top unblocked labelled issue, implements, reviews, closes. You ship the reviewed branch.

What a GOOD Sandcastle issue looks like

The agent reads only an issue's title, body, labels, comments and works it autonomously in one pass (maxIterations: 1), so the issue must carry everything:

  • Has the Sandcastle label — without it the agent literally cannot see the issue.
  • One thin vertical slice / tracer bullet, small enough for a single commit. Big issues stall the per-issue review model.
  • Self-contained body — states the change, acceptance criteria, and a reference to the parent PRD (the agent pulls it in). No assumed external context.
  • Spells out the test expectation — RGR writes the failing test first; say what "green" looks like, especially the all-or-nothing ledger path for posting work.
  • Encodes dependencies ("blocked by #N") — the agent skips issues blocked by other open issues.
  • Sets priority via type so ordering works: bug > tracer bullet > polish > refactor.
  • One concern per issue — multiple concerns get only one iteration of attention and risk a partial commit.
The repo precondition. Sandcastle gates its commit on a green npm run typecheck and npm run test, and copies node_modules in from the host to skip a cold install. So both scripts must exist and pass on main before a run. Inputs needed: CLAUDE_CODE_OAUTH_TOKEN (or ANTHROPIC_API_KEY) for agent auth, and a fine-grained GH_TOKEN (Issues read/write + Metadata read) for the gh issue calls.

The foundation checklist — seven cards

1 — REPO + MODULE LAYOUT (FD-1)

Monorepo. One Django app per design module mirroring D1–D8, over one Postgres database. ERPNext is the existence proof: modules are just folders (erpnext/stock/, erpnext/accounts/, erpnext/selling/) over one SQL schema, posting cross-module by an in-process call not a network hop (stock/doctype/stock_entry/stock_entry.py → accounts/general_ledger.py). Do the same: clean internal boundaries, one deployable app.

Layout
app/{backend,frontend}. Backend Django project + apps: core (kernel), masters, then vendors, inbound, outbound, payments, offers, tally, analytics — added per slice, not upfront.
Slice-0 scope
Scaffold only what the first slices (1 master data → 2 inbound → 3 vendor liability) need: core + masters + vendors + inbound. Other apps are empty until their slice.
Dependency rule
Peers never FK each other (use IDs / snapshot); downward FK to core and masters only. Enforce with import-linter contracts in CI.
One DB
Single Postgres — all-or-nothing multi-row ledger writes need one transactional relational DB. This is exactly why BaaS/Supabase was rejected; ERPNext's GL independently arrived at the same constraint (general_ledger.py:process_debit_credit_difference).
Tasks · tool. Run /spec to freeze the slice-0 layout, then scaffold by hand (Bash django-admin startproject + startapp per app; Write the import-linter contract file and pyproject.toml deps). Use /setup-pre-commit-adjacent wiring for the linter in CI (card 6).
2 — DB CONVENTIONS (FD-2) · the heart of correctness

The most stack-independent, most load-bearing card. These conventions are properties of the ledger, not of Django, and align one-for-one with the 12 rules.

Money = integer paise
All amounts bigint paise (Rs 28,50,000 stored as 285000000). Rates and GST% are NUMERIC. GST / discount split computed in Decimal, rounded half-up, with an explicit rounding line so Σdr=Σcr holds — mirrors ERPNext's round-off GLE in general_ledger.py. Never float.
Append-only ledgers
Ledger rows INSERT-only, enforced three ways: app writes only via the posting engine; REVOKE UPDATE, DELETE from the app role; a trigger as backstop. Correction = a new dated reversing row, originals untouched — ported from ERPNext's immutable-ledger mode (gl_entry.py:325 hard-throws on single-leg cancel; general_ledger.py:make_reverse_gl_entries posts sign-swapped legs with today's date).
Effective-dated masters
SCD-2 on slab/price/rate masters (apparel GST slabs, offer dials): valid_from/valid_to, look up "the row in force on the document date." GST and offers are data, not code. ERPNext has no native season/effective-date on items — this is a KDPS add.
Three distinct keys
(1) bigint surrogate PK; (2) a human naming series doc-number = idempotency guard + Tally join key — ported from ERPNext autoname:"naming_series:" + atomic Series table (stock_entry.json:4, gl_entry.json:3 = ACC-GLE-.YYYY.-.#####); re-implement as a Postgres sequence-per-prefix or SELECT … FOR UPDATE counter, prefix = state-GSTIN/store/type, e.g. DEO-SAL-20260620-001; (3) a UUID idempotency key for external-edge retries.
docstatus lifecycle (ported from ERPNext)
Re-implement draft(0) → submitted/posted(1) → cancelled(2) as an explicit Django status FSM + a single post() method per document type that emits balanced legs in one DB transaction. Mirrors stock_entry.py:323 on_submit (writes ledgers) and :346 on_cancel (reverses). Do NOT inherit a generic submittable base that mutates global behaviour — that is the meta-runtime trap.
Snapshotted state + GSTIN
state and gstin are first-class columns copied onto the document at post time from the entity tree (card 4) — never re-derived later. Plus actor + UTC timestamp on every row; single writer = the server.

The per-slice build loop — one repeatable cycle, one named tool per gate

The build is one verified vertical slice at a time (a tracer bullet: booking → document → ledger postings → screen — cutting through all 5 layers for one workflow). This section is the repeatable cycle run for every slice, from the slice-0 foundation scaffold through slice-9 analytics. Each gate names the exact skill or tool that drives it and the artifact it must hand to the next gate. The spine is the same every time: ubiquitous-language/CONTEXT → spec → plan-review → to-issues → tdd implement → review → qa → ship → deploy → canary → docs → retro → memory. Nothing is built ahead of its slice — the data model, posting catalog, and golden files grow per slice, never all upfront.

The through-line. The loop is built so a slice cannot reach “done” until it posts correctly. The spec gate writes the golden files before any posting code exists; tdd turns them red then green; review + ship refuse to land unless they stay green. Golden files (built from the ~150 real invoices) and ledger-invariant tests are the contract that money code is held to — “CI green” is the definition of done, and money code (ledgers / payments / Tally / GST) gets a mandatory human read of every diff on top of green.

The slice roadmap

After the foundation is in place, the system is built one vertical slice at a time — each slice a thin but complete path from a real document to its postings, ledgers and reconciliation, never a half-finished layer. The order follows the spine (master data → documents → ledgers → controls → intelligence) and the study's “borrow first” rule: where ERPNext / india-compliance already solve a problem, reimplement the pattern in the Django/PostgreSQL kernel rather than invent; where KDPS is genuinely different (season, the four commercial models, frozen lot cost, Tally-as-book), build greenfield and attach it to the borrowed scaffolding.

How to read a slice. Each card states: what it delivers end-to-end (the thin complete path), the ERPNext artefacts it borrows, the external spike it depends on, and the golden file / reconciliation that proves it. A slice is only “done” when its golden file ties out. Per-slice specs (data model, posting entries, golden files) grow just-in-time — never all upfront.
Three external spikes run in PARALLEL from day one — they have lead time and must not sit on the critical path. SPIKE Tally / Vyapar TaxOne import (voucher XML/TDL, prevent-duplicates semantics) feeds slice 7. SPIKE Barcode tool (13-digit EAN print/scan, vendor-else-generate) feeds slices 1–2. Start all three as throwaway spikes now; fold the findings into the slice when its turn comes.

The day-to-day workflow — issues & Sandcastle in practice

This is how work actually flows once the foundation is up: a written slice becomes a set of small GitHub issues, the autonomous loop drains the ones that are safe to drain, and a human keeps the gate on anything that touches money or the books. The rules below are not aspirational — they are wired into the harness and the labels.

1 · GitHub issues are the single source of truth

One tracker, no side-channels. Every unit of work lives as a GitHub issue on the project repo — the tracker docs hard-code bruhanand/KDPS, but that remote is UNCONFIRMED (do not assume it; verify before any gh run) — driven through the gh CLI (gh issue create/list/view/close -R <repo>). No scratch files, no local TODOs, no second system. If something needs doing, you open an issue instead. Domain language lives in one root CONTEXT.md and one-decision-per-file ADRs under docs/adr/ — issues reference those, they don't re-litigate them.

Each issue carries exactly one category role (bug or enhancement) and walks one state through a state machine. The state is the label, and the label is what every actor — human or agent — reads.

Triage stateGitHub labelWhat it means / who acts

2 · How to write a slice as AFK-ready issues

A "slice" is one verified vertical — it cuts every layer (UI → API → ledger → test) for one thin behaviour. You don't hand Sandcastle a slice; you hand it the issues that make up the slice. Use to-issues to break the PRD into independently-grabbable tracer bullets, then triage to label them. The loop reads only an issue's title, body, labels, and comments and works it end-to-end alone — so the issue body has to carry everything.

SHAPE OF A GOOD SANDCASTLE ISSUE
Labelled Sandcastle
Without this label the agent literally cannot see the issue — implement-prompt.md:5 lists only --label Sandcastle.
Thin vertical slice, one commit
One concern, small enough to land as a single RALPH: commit. The agent gets maxIterations: 1 per issue, so a big issue produces a partial commit, not a finished feature.
Self-contained body + PRD link
State the change, the acceptance criteria, and reference the parent PRD by issue number. The agent pulls the PRD in (implement-prompt.md:30); don't assume any other context.
Spec + golden files referenced
Point to the spec and the golden files for this slice (posting entries, sample PT/invoice, expected ledger rows). RGR writes a failing test first, so spell out exactly what "green" looks like.
The all-or-nothing test, named
For any posting work, say it explicitly: the posting either fully succeeds or fully rolls back, and that path must have a test. The standards demand it; the issue should pre-name it.
Dependencies encoded
Write "blocked by #N". The agent skips issues blocked by other open issues (implement-prompt.md:26).
Priority set by type
Ordering is bug > tracer bullet > polish > refactor. Frame the issue as the right type so the queue drains in the right order.
Golden files are the contract for money. Because profitability is derived and ledgers are append-only, the spec's golden files (a known PT/invoice in, the exact ledger rows and GST breakup out) are what the test asserts against. An issue that posts to a ledger without a referenced golden file is not AFK-ready — send it back to needs-info.

3 · Human-in-the-loop gates

The loop is autonomous on a branch, never on the books. Three gates are non-negotiable.

THE THREE GATES
You review the PR
Sandcastle commits to a branch (sandcastle/sequential-reviewer/<timestamp>) and closes the issue with "Completed by Sandcastle" — it does not open or merge a PR. A human (or a /ship / land-and-deploy step) turns the reviewed branch into a merged PR. Nothing reaches the default branch without that human step.
You approve money-touching code
Anything that writes a ledger, computes GST, derives margin, or posts to Tally is ready-for-human, not Sandcastle — or, if drafted on a branch, it does not merge until you have read the diff and the golden-file test. Money logic is reviewed by a person, every time.
AI never posts to the books
A bright line from the architecture: AI is at the edges only. The intelligence layer reads ledgers and never writes them; Tally stays the statutory book of record. The Sandcastle loop writes code, reviewed by a human; the running system's AI writes nothing to any ledger.

4 · Coding standards enforced by the reviewer

Phase 2 of the loop loads .sandcastle/CODING_STANDARDS.md and reviews the branch diff against it (review-prompt.md:41), fixing refactor-only issues directly on the branch — functionality is preserved, never changed. The standards are the same domain rules the whole system obeys:

  • Stack & style — React (TS) PWA + Python/Django + PostgreSQL. TS: camelCase vars/fns, PascalCase components/types, named exports. Python: PEP 8, snake_case, PascalCase classes. No commented-out code, no stray TODOs.
  • Testing — every new behaviour gets a test; ledger/posting logic must test the all-or-nothing path (fully succeeds or fully rolls back); descriptive test names.
  • SKU = Style × Size × Color — never collapse stock to style level; size×color survives end-to-end.
  • Documents write ledgers; ledgers are append-only — never mutate a posted row; reverse and repost.
  • Snapshot masters onto documents at write time (price, tax, vendor terms) — don't read live masters for historical documents.
  • GST is data, not code — slab/date-effective tables, two GSTINs (Bihar / Jharkhand); Tally is the book of record.
  • Profitability is derived (cost from PT/invoice, revenue from POS) — never hand-entered.
  • AI at the edges only — reads ledgers, never writes them.
  • Single-responsibility modules, composition over inheritance; money in INR with Lakh/Crore grouping (e.g. Rs 28,50,000).
  • Reviewer's non-domain checks — reduce nesting/complexity, no nested ternaries, no unsafe casts or any, no injection or credential leaks.
Belt and braces at commit time too. setup-pre-commit (Husky + lint-staged: Prettier, typecheck, test) and git-guardrails-claude-code (a PreToolUse hook blocking dangerous git — push, reset --hard, clean -f, branch -D) are wired once at repo init and run continuously, under both human and agent commits.

5 · When to use Sandcastle vs codex/interactive vs prototype

Pick the tool by how well-known the answer is, not by habit.

Use…When the work is…Because…

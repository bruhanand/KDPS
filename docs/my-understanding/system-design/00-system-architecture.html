System Architecture — simple map of the whole system

This page explains how the KDPS system fits together. The main flow is simple: buying creates documents, documents update stock and money records, and reports only read those records. D1–D8 are designed. D9 (migration and rollout) is still left.

How to read this page. Start with the picture, then read the 12 rules, then read the layer-by-layer detail. For any module, ask three questions: what document is created, what statuses can it move through, and which record does it update?

Why this page exists. The early modules were designed one by one. Later modules touch stock, payments, GST, Tally, and AI. This page keeps them in one order so future work does not contradict earlier decisions.

Read the picture from top to bottom. Master data tells the system what exists. Documents record what happened. Ledgers show current stock and money by adding up those documents. Checks find mismatches. Reports and AI only read. Stock and money never enter the system without a document.

The 12 rules — every module obeys these

These rules keep the system simple. If a new design breaks one of these rules, either the design is wrong or this page must be updated first.

1

Every business event is a document with a life cycle

  • A booking, GRN, sale, transfer, return, or payment must be a numbered document.
  • Each document has lines, dates, owners, and statuses.
  • If there is no document, the event did not happen in the system.
Used in: Booking, GRN, PT, sale, transfers, returns, and payments.
2

Documents write ledgers; ledgers are never hand-edited

  • Stock, vendor balance, and cash balance are calculated from document entries.
  • No one types today's stock or today's payable directly into a ledger.
  • If something is wrong, add a correction document. Do not edit old history.
Used in: inbound stock movements and all money postings.
3

Master data lives in one place; documents copy it

  • Brand terms, prices, margins, users, stores, and GST rules are maintained in master screens.
  • When a document is created, it copies the values it needs.
  • If a brand margin changes tomorrow, yesterday's booking must stay unchanged.
Used in: booking terms, PT pricing, offers, GST, and roles.
4

Every fact has exactly one owner

  • Stock is owned by the stock ledger.
  • The sale event comes from POS.
  • Official accounting and GST books stay in Tally.
  • Offer logic is owned by the offer rulebook.
Used in: POS integration, Tally sync, and offer design.
5

Flag, never block

  • If there is a mismatch, create a clear problem item for the right owner.
  • Do not stop store staff from billing or receiving goods unless it is truly dangerous.
  • The flow should continue, and the problem should be visible.
  • "Truly dangerous" is defined for money: a stock movement whose value the books cannot work out is refused, not flagged. A flag is an approximation everyone can see; a zero-value posting is a wrong number wearing the clothes of a right one. The pieces leave, the rupees stay, and every quantity-based check — including a physical count — passes over it. Refusing is the only thing that stays visible.
  • The same holds for the quantity, not just the value: a line whose quantity the system cannot read is refused too (ruled 27 Jul 2026, issue #122). An unreadable quantity that quietly becomes zero drops the line out of stock entirely, which is worse than valuing it wrong - nothing on screen, in a report or in a ledger says the goods were ever there, and the only thing that ever disagrees is a physical count months later. A quantity that is genuinely blank is different: it is skipped, and the count of skipped lines is reported when the document posts.
Used in: GRN mismatch flags, unmapped PT files, POS stock mismatch, and Tally failures. Refused instead: valuing an outbound line the books cannot price, and posting a PT line whose quantity cannot be read.
6

Calculated numbers are not typed by hand

  • Profit comes from cost and sale price.
  • Stock age comes from the stock-in date.
  • MRP comes from a formula where possible.
  • If the system can calculate it, a human should not type it.
Used in: profitability, aging, MRP, and brand reports.
7

Outside systems need written rules and daily checks

  • For POS, Tally, banks, and WhatsApp, write down exactly what we send and receive.
  • Write down the matching key, such as barcode, voucher number, or bank reference.
  • Check daily that the other system accepted what we sent.
Used in: POS item/sales sync, Tally vouchers, bank checks, and WhatsApp alerts.
8

AI only reads and suggests AI

  • AI may read messy inputs like invoices, names, and sales patterns.
  • AI may suggest forecasts, alerts, reports, and store splits.
  • AI must not write stock, vendor balance, cash, or Tally entries.
Used in: invoice reading, forecasts, daily digest, and unusual activity alerts.
9

Every line must say exactly what item it is

  • Stock lines need brand, style, colour, size, season, and barcode.
  • Money lines need the commercial model: Outright, Correction, SOR, or Consignment.
  • Do not keep vague stock like "100 shirts" without the exact identity.
Note: booking lines can stay at style + size because booking does not update stock or money. Full identity starts at GRN/PT.
Used in: SKU registry, barcode registry, PT lines, and vendor terms.
10

Every action has an actor

  • Every document must show who created it, edited it, approved it, and when.
  • Approvals happen inside the system, not in side emails or calls.
  • Roles decide who can take each step.
Used in: warehouse approval, Patna inward approval, payments, and user roles.
11

Deadlines are data, not memory

  • Return windows, offer dates, payment due dates, and season dates must be stored.
  • The system should remind people before a deadline is missed.
  • No important date should live only in someone's memory.
Used in: SOR returns, offers, payments, EOSS, and daily alerts.
12

Business differences are data, not code

  • Brand models, GST slabs, offer rules, roles, seasons, and report timings should be rows in master data.
  • A trained admin should be able to add a season, GST slab, offer rule, or brand model without a code release.
  • Code should contain the small posting engine. Business variation should live above it as data.
Used in: brand models, season calendar, GST tables, offer rulebook, roles, and digest timing.

Layer 4 — Reports and AI AI lives here

Reports and AI read master data and ledgers. They can send messages, suggestions, forecasts, and alerts. They cannot update ledgers or approve documents. That keeps AI useful without letting it corrupt stock or money.

Selling and Tally are deferred; the POS is ours (26 Jul 2026). The Tally/accounting sync is designed but is not in the current build. Selling is the last module, and KDPS builds its own POS — the earlier plan to integrate the incumbent third-party POS behind an adapter is dropped, so selling no longer waits on anyone else's API and there is no external sales feed to ingest. The Sale document stays source-agnostic regardless.

How we build — the development process

Build one small complete slice at a time. Do not build the whole system in one pass. Do not finish one module in isolation while the rest of the flow is missing.

1 · Keep one rulebook and one build checklist

  • This page is the rulebook.
  • The feature inventory is the build checklist.
  • Each item must be something a user can test end to end.

2 · Write the spec only when the slice starts

  • Before coding a slice, write a short self-contained spec.
  • Name the files, inputs, outputs, and what is out of scope.
  • End the spec with a command or screen flow that proves the slice works.

3 · Test with real samples

  • Use the real invoices, PT files, and ledger examples as test data.
  • Every ledger balance must equal the sum of its entries.
  • Every ledger entry must trace back to a document.
  • "Looks done" is not enough. Tests must pass.

4 · Watch money code closely

  • Ledger entries, payments, and Tally vouchers need supervised coding sessions.
  • Screens, reports, and scaffolding can be more automated.
  • Money code gets tests plus human review.

5 · Test outside systems early

  • Test Tally or TaxOne import before finalizing voucher export.
  • Test the barcode tool before building around it.
Open build risk: rollout still needs D9. That is where opening stock, store-by-store rollout, training, and rollback rules will be decided.

Tech shape — deliberately boring

One codebase, one database

Build one application over one PostgreSQL database. Keep module boundaries clear in code, but do not split into many services. This is easier to build, test, and maintain.

Browser app, light and offline-tolerant

KDPS runs in the browser on store computers and browsers. Pages should be light, work on bad networks, and use Hindi where store staff need it. Owners get WhatsApp updates.

Plan for failure

If POS is down, use manual bill fallback. If internet is down, capture work and sync later. If Tally rejects a voucher, put it in a failure queue. Do not rely on phone calls to fix system gaps.

Stack decided. ADR-0001 chooses Python/Django back end, React/TypeScript front end, PostgreSQL, with hosting to be decided later. ERPNext ideas are reused as plain Django models. The Frappe framework is not used.

Glossary — architecture vocabulary

Document
A numbered record of one business event, such as a booking, GRN, PT, sale, transfer, return, or payment.
Ledger
A stock or money record built from documents. People do not edit it directly.
Posting
One entry that a document adds to a ledger. If something is wrong, add another entry to correct it.
Master data
The shared reference data: vendors, brands, stores, products, GST rules, offers, users, and roles.
Snapshot
The copy of master data stored on a document so old documents do not change later.
Problem queue
A list of mismatches or failures that need a named person to fix them.
Outside-system rule
The written rule for what KDPS sends, receives, matches on, retries, and checks daily.
Main flow
Booking → inbound → outbound. Stock enters, moves, sells, returns, or gets adjusted through this flow.

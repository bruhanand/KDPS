The shape

  • Read-only "brain" — reads ledgers + masters + POS pull; writes only messages, reports, suggestions. A human always decides. (Rule 8)
  • One spine of numbers — every metric defined once (semantic/metrics layer), computed by deterministic code.
  • Code computes, AI narrates — the LLM only phrases / explains / translates to Hindi; it never calculates.
  • Copilot, not autopilot — AI suggests → a human approves.
  • Delivered — WhatsApp for owners; drill-down screens for head office.
  • Built crawl → walk → run — rules now, ML later wraps them.

Product 1 · The daily owner digest shape locked · Grill 2

  • Shape: hybrid (C) — a small text summary on top, then what needs attention, then the numbers lower.
  • Top = percentages / direction only (vs target, vs last week, margin %) — no absolute ₹ up top (Anand, 19 Jun): keeps the notification preview light.

Working definitions thresholds → dead-stock grill

TermWorking definition
Dead stockAn item (barcode = brand×style×colour×size, in its season cohort) with zero sales for N days and an old cohort; valued at frozen cost. N is a per-brand dial (fast ~60–90d, slow ~120–180d). Fresh-season stock is never condemned.
Broken sizeA style still holds stock, but its core/sellable sizes are sold out — only fringe sizes (e.g. 38, 44) remain. Costs: invisible lost full-price sales + leftover odd sizes become markdown fodder. Uses the PT size data as its input — it's a pattern across sizes within a style, per store.

Product 2 · The report-maker Grill 4

What it is

  • The monthly brand-facing settlement / reporting pack: two sheets — Sale (List of Sales Vouchers) + SOH (List of Stock Details), in the exact KDPS format ("Voucher Series : {BRAND}").
  • Generated per brand × per store × month (e.g. LP April 2026 = 6 store files: AS-DEO · Bokaro · Dumka · HZB · Sanskar · Vas-Deo).
  • Sale cols: Date · Vch/Bill No · Particulars · Item Details · Brand · Size · Style Code · Barcode · Unit · Qty · Price · Dis% · Dis · Total. SOH cols: Date · Item Details · Barcode · Size · Style Code · Brand · Qty · Unit · MRP · Total MRP.

Today vs the new system

Today (manual / skills)New system (clean export)
Gather varied raw files from each store; map columns by meaningRead clean sales straight from the system (one source)
Fabricate missing bill numbers / dates (fragile)Real bill numbers & dates already captured
Hand-apply discounts via AMM List + offer-list clubbingPer-line discount = what the offer rulebook applied at sale — just read it
Build SOH from a separate stock fileClosing SOH from the stock ledger

So the report-maker becomes a clean one-click export in the exact format — the manual rebuild pain disappears. The one genuinely new D7 feature is the target hold-back.

The target hold-back direction locked · 19 Jun

  • The brand-facing report is a flexible presentation layer — to hit targets and maximise what KDPS earns from the brand, bills can be re-dated, re-numbered and shifted between two adjacent months.
  • The AI never sets the hold-back, it only suggests it (Rule 4). The re-dating / re-numbering / cross-month shift is proposed by the system and a human approves every move — the AI sits at the edge, the human decides. Goal: automatic is a later discussion; even then it stays suggest-then-approve until consciously changed.
  • Guardrail: the bending lives only in the brand-report layer; the real ledgers + Tally/GST/cash stay truthful (Rule 4). How the two reconcile = part of the deferred hold-back discussion.

Product 3 · Profitability & margin depth locked · Grill 5

  • Headline = trading + contribution margin (B) — derived from frozen PT cost × POS revenue; honest, day-one. Full net store P&L (C, Tally opex) added later as a flagged estimate. Scope kept open.
  • Per commercial model: owned (Outright/Correction) → margin ₹ + GMROI; SOR/Consignment → margin% + margin-₹-per-shelf-slot (no GMROI — no owned cash at risk).
  • Margin-leakage waterfall: MRP → −markdown → −free gifts → −returns → net, so "low margin" is attributable.
  • Scorecard: Realisation × Velocity quadrant (Lean-in · Defend · Churn · Pull-back), owned vs SOR on separate boards; stores scored on peer-percentile.

Product 4 · Dead-stock & markdown Grill 6

  • Classification = combined age × velocity matrix — start age/season (day-one from the cohort), layer velocity (Hot/Warm/Cold/Dead) as sales history builds. Thresholds per brand (Account Manager tunes).
  • Markdown helper (from Offers §7): age + sell-through + margin floor → suggested band + plain-Hindi reason → a human authors the offer. Crawl→walk→run; feeds D5.
  • Action per model: SOR/Consignment → return in window · owned selling elsewhere → transfer · selling nowhere → markdown · past window → V-flip.
  • Routes to Account Manager + store manager. Every output is a suggestion a human confirms.

Product 5 · Anomaly & leakage watchdog Grill 7

  • Flag & rank for a human, never block. No CCTV → human review is the verification; a flag is a suspicion, not proof.
  • Day-one rules: discount-leakage (billed ≠ offer) per store/brand · cash-deposit shortfall ranking · data errors (cost>MRP, duplicate bills, stuck transfers, persistent negative stock).
  • Leakage depth (C): per-cashier leakage score + a flag→review→confirm/dismiss→learn loop — the tool against hand-keyed-placard pocketing.
  • Rules day-one → statistics month-3+ (z-score, peer-cluster, seasonal baselines). LLM narrates a flag, never computes it. Routes per the role table.

Product 6 · Forecasting & replenishment Grill 8

  • Full cold-start engine now (suggest-only): rate-of-sale · analogy forecast for new styles · regional size curves · weeks-of-cover reorder · inter-store rebalancing suggestions · broken-size alerts.
  • Honest accuracy: new-product ~40–55% (WAPE) — "narrow the decision", not "predict the number". Conditional on the Grill-0 cleanup. Set in writing with the client.
  • ML "Fashion Demand AI" (demand-sensing, elasticity, weather, promo-uplift) — future roadmap, once 2–3 clean seasons exist.
  • Feeds the inbound store-split, the markdown helper, and the digest.

Product 7 · Conversational AI Grill 9

  • V1 = narrator only. The LLM writes the Hindi/English digest line, explains "why did this move?", and translates — always from numbers the code computed. It never calculates.
  • Foundation is built agent-ready: the semantic/metrics layer is exposed as read-only, role-scoped data tools (function-calling) — so any agent plugs on top later by calling the tools, never raw SQL on the messy DB.
  • Deferred conversational agent = a low-cost bolt-on; off-the-shelf open-source is fine (e.g. an OpenClaw-style runner + a Hermes-class function-calling model). It fetches & answers within each person's scope.
  • Two rails: read-only — it fetches & tells, never acts on the books (Rule 8); grounded via our tools — not "self-learning" on live data (we control what it sees).

From here, to the first line of code, to the whole product

The day-to-day operating rhythm for the build: what you do now (before any code), what the first line of code is, and the single repeating loop that carries you from the kernel through booking, inbound and every slice after — chat by chat, with the exact skills and Sandcastle at each step.

27 June 2026 · operational companion to build-process-and-roadmap.html (the what/why; this is the how-to-operate) · you are the planner & reviewer, the AI writes the code.

The short answer

Two journeys and one rule. Read this and you have the shape.

Journey 1 — here → the first line of code. One short runway of setup work: wire the issue tracker, the glossary, the safety rails, and install + modify Sandcastle. No product code yet. This is a handful of one-time chats. It ends the moment the repo can build.

Journey 2 — first line → the whole product. The first line of code is K0 (the empty scaffold). After that it is the same loop forever: one slice → one spec → one issue → build → review → you approve → merge → next slice. Kernel first (built by hand, supervised), then booking, then inbound, then the rest — in spine order.

The one rule that answers “what do I do in a new chat?” One chat = one stage of one slice. Chats are disposable; the GitHub issue is the memory that survives between them. You don’t build in one giant chat — you turn each slice’s spec into an issue, then spin a fresh chat for spec, for review, for ship. The issue is what you “turn something into.”

1 · Here → the first line of code the runway

Do these top-to-bottom. Each numbered step is a fresh chat (or a short cluster). The output of the runway is: a tracker you can file issues into, a glossary the AI reads, safety rails, and a Sandcastle that builds one slice and stops. Then — and only then — you write K0.

1

Confirm the rails YOU · 1 chat

Confirm the live GitHub remote (the tracker docs mention bruhanand/KDPS — verify it points at the real repo, or AFK agents grab the wrong backlog). Decide: GitHub Issues is the work tracker and the source of truth for what to build.

2

Wire the issue pipeline /setup-matt-pocock-skills

Wires the tracker + the triage labels so /spec, /to-issues, /triage, /review all work. Decide the “ready for the agent” label and make Sandcastle’s planner look for that exact label — a mismatch means Sandcastle silently picks zero issues. This is a hard check, not a nicety.

3

Mint the glossary the AI reads /ubiquitous-language

Turn consolidation/glossary.html + .context/qa-decisions.md into one machine-read file. PICK ONE NAME Call it CONTEXT.md and point every skill at it — /grill-with-docs, /review and /tdd all read a project context file, and if two filenames exist they silently read the wrong one.

4

Safety rails /setup-pre-commit · /git-guardrails-claude-code · /fewer-permission-prompts

Pre-commit (format + mypy/ruff + fast pytest), block dangerous git (push to main, reset --hard, branch -D), and allow-list the routine manage.py/pytest/git calls the loop will run thousands of times so you aren’t clicking “approve” all day.

5

Install + rewire Sandcastle 1 focused chat — see §7

npm i -D @ai-hero/sandcastle → init (the parallel-planner-with-review template, Docker) → then five edits to .sandcastle/main.mts and the prompts so it builds one slice per run and stops before merge, runs your models per stage, and speaks Python/Django + Postgres instead of Node. Full edit list in §7.

6

Slice the kernel into issues /spec → issues

Write the kernel’s ten slices (K0–K9, §3) as issues you can build against. NOTE The kernel slices are horizontal foundation cuts (a base class, a CI gate, the auth layer) — not vertical user workflows. So write them with /spec straight into hand-authored issues; don’t force /to-issues here (its job is to cut vertical slices, and it will fight you on K0–K6). /to-issues comes into its own at booking and onward.

Runway done = a tracker with the kernel issues filed, CONTEXT.md in place, safety rails on, and a Sandcastle that runs one slice and halts on a branch. You have not written product code yet. Now write K0.

The chats, concretely

Chat A — “spec & cut” (you drive)

Fresh chat. Run /spec for one slice; for any money/GST slice run /grill-with-docs first to pin the rule as an ADR. Name the golden test before the code. End by turning the spec into one GitHub issue with the agent label. That issue is the handoff — close the chat.

No chat — Sandcastle run (autonomous)

You launch the loop from a terminal, not a chat. It reads the labelled issue, builds it red-green-refactor in a container, self-reviews, commits to a branch sandcastle/issue-{n}, and stops. It cannot merge — that is by design (§8).

Chat B — “review & ship” (you drive)

Fresh chat on that branch. Run /review (does it do what the issue asked?) and /code-review (is it correct?); /verify runs the app + golden suite. You read the diff yourself — every line on money code. Approve → /ship opens the PR → you merge. /learn + a note to CONTEXT.md carries any new fact to the next slice. Close the chat.

Why fresh chats, not one long one. Three reasons: (1) the skills (/spec, /review, /tdd) are built to run in a clean window — a stale, cluttered context makes them worse; (2) long chats drift and forget; (3) the issue + CONTEXT.md + the merged code already hold the memory, so a fresh chat loses nothing. When you must continue mid-task across a boundary, use /handoff to write a compact pickup note.
Conductor angle. Each slice can be its own Conductor workspace (its own branch), so several slices’ review chats can sit side by side. Sandcastle makes its own branches/worktrees underneath. Keep one slice in flight on money code though — parallel fleets are for chores, never for ledgers.

3 · Build the kernel — K0 → K9

It is built mostly by hand and supervised, because it is small, central, and ruinous to get wrong. Sandcastle’s autonomous loop earns its place at the end of the kernel (seed/components) and then on every business slice.

The kernel’s two speeds. SUPERVISED K1, K2, K3, K6, K7, K8 touch money, ledgers or access — you build them by hand or with a tight /tdd chat and read every diff. What the kernel is not. The spine tables — sku, cohort, pt/pt_line — are not in K0–K9. They arrive with the first business slices (master data, inbound). The kernel builds the engine and the three ledgers; the business slices build the documents and masters that ride on them.
Kernel done = the four foundation tests green on real Postgres (balances Σdr=Σcr · ledger can’t be edited · cross-store isolation · golden-file to the paise), one user logs in and sees only their scope, and a throwaway document posts a balanced reversing pair. The engine is now trustworthy. Booking can begin.

4 · After the kernel — booking, then inbound

Now the slices turn vertical — a real workflow cutting top-to-bottom (master → document → ledger → control → screen). This is where the loop in §2 and Sandcastle run at full stride. Order is fixed by the spine: a shipment must exist before it can be sold; a booking before a shipment.

First vertical slice — Booking Sandcastle, full loop

A booking is a document with light money (it commits an order; it doesn’t post to the ledgers yet). That makes it the ideal first real vertical slice — it exercises the whole loop (spec → issue → autonomous build → review → ship) and the first business screen, without betting the ledgers on a fresh autonomous run.

  • Chat A: /spec the booking slice → /to-issues (now genuinely vertical — it cuts master+document+screen as one tracer bullet) → file the labelled issue, golden test named.
  • Sandcastle: autonomous build of the Booking model + create/list screen + its test; stops on a branch.
  • Chat B: /review + /code-review + /verify; you read it; /ship; you merge.

Then — Inbound (GRN → PT → stock + vendor ledger) SUPERVISED — money

Inbound is the first slice that posts money: goods arrive (GRN = quantity into stock), the PT prices the lot (value + vendor liability). It is the proof that the whole spine works end-to-end, and it is firmly in the slow lane.

  • Before Chat A — lock the conventions as ADRs with /grill-with-docs: cost is frozen at stock-in (no re-posting), how a correction is made (a new dated reversing event + reason code), and how late freight / sold-before-PT are handled. Build the mechanism into the kernel; the brand’s actual rate is data (Rule 12). CA-gated The full SOR/GST ruling can wait for the SOR slice — these three conventions cannot.
  • Chat A: /spec + /plan-eng-review (always, on a ledger slice). Golden file = a real vendor invoice → known-correct PT + ledger rows, to the paise.
  • Sandcastle: implementer on the strong model; /codex challenge in the review prompt because it is money.
  • Chat B: you read every line even when CI is green. /security-review if it touches vendor balances. Then /ship, you merge.
The first inbound slice stops at the ledger, not at the till. The riskiest unknowns (Ten Software POS, Tally import, barcode) are spiked in parallel and do not gate the spine. Prove GRN→PT→stock on ground you control first; the POS edge arrives later, at the selling slice.

7 · Sandcastle setup — the exact edits

Sandcastle ships as a Node demo that picks several issues, builds them in parallel, and auto-merges. You want the opposite: one slice, your models, stops before merge, Python/Postgres. The only file that controls the loop is .sandcastle/main.mts (a plain TS script, not config).

a · One slice, then stop 3 edits to main.mts

  • MAX_ITERATIONS = 1 — run the outer loop exactly once, then exit.
  • After the planner parses issues: issues = issues.slice(0, 1) — one slice, not a batch (the implement prompt is already single-task-scoped).
  • Delete (or guard) the merge phase — that is the only code that crosses into main. With it gone, the slice is built + self-reviewed on a branch and the script exits, leaving the work for your review. This deletion is your “gating node”: the loop now cannot merge — only you can. (Optionally replace it with “open a PR” for a tidy review surface.)

b · A different model per stage

Each stage takes its model as claudeCode("<model>"). Hoist four constants to the top so a slice tunes in one edit:

MODEL_PLAN = "claude-opus-4-8" (high effort) · MODEL_IMPL = "claude-opus-4-8" for money slices, "claude-sonnet-4-6" for scaffolding · MODEL_REVIEW = "claude-opus-4-8" (high) · MODEL_MERGE = "claude-sonnet-4-6" (mechanical). Use the 4-8 ids — older notes reference opus-4-7; explicit constants override the default.

c · Python/Django + Postgres do not skip

  • Dockerfile (.sandcastle/Dockerfile, today node:22): add Python 3.12 + uv/pip + Postgres client; keep gh, git, and the Claude Code CLI; keep Node (the Vite frontend).
  • onSandboxReady hook: change npm install && npm run build → uv sync && npm install && npm run build.
  • Feedback commands in all four prompt files: swap npm run typecheck/npm run test → your npm run ci (mypy + ruff + pytest + tsc…). HARD GATE Miss this and the agent runs Node commands that don’t exist and reports a false green/red.
  • Real Postgres, asserted. Postgres runs outside the single container — point DATABASE_URL at a service. The foundation tests must hit real PG; make CI fail if it isn’t Postgres, or the append-only / isolation tests pass vacuously on SQLite.

d · Skills inside the loop, and committing .sandcastle

  • Sandcastle has no “skill” flag — the sandboxed agent is Claude Code, so wire skills through (1) the prompt text (have review-prompt.md invoke /code-review, etc.) and (2) the Dockerfile (install the skill). Copy the richer agent-workflows/ prompts (they read CONTEXT.md + the ADRs at slice start) into .sandcastle/ — recommended for a money build; init doesn’t bring them.
  • Commit the whole .sandcastle/ folder (git add .sandcastle/) so every clone/worktree shares the loop config — but keep .env, logs/, worktrees/ ignored (secrets + scratch). Don’t blanket-remove the ignore file; just make sure the prompts, main.mts, Dockerfile and CODING_STANDARDS.md are tracked.
  • Money/DB safety even when AFK: set permissionMode explicitly on the implementer for money slices rather than relying on the “skip permissions” default, so a stray REVOKE/migration/git is still gated.

8 · Guardrails — what never runs unwatched

Autonomous merge is impossible by construction. You deleted the merge phase. Sandcastle builds and self-reviews; it cannot reach main. Every slice waits on a branch for you. For money code that is not a preference — it is the architecture.
  • Money is read line by line — ledgers, payments, Tally, GST, RBAC/scoping — even when CI is green.
  • Free-lane work — scaffold, seed, components, screens, reports — runs through Sandcastle and is reviewed after the fact.
  • Corrections are new dated events, never edits. The append-only test and the REVOKE grant enforce it; there is no “fix the old row” path anywhere.
  • One label, one tracker. Confirm the agent label matches Sandcastle’s planner prompt and the remote is the live repo before any AFK run.
  • Discovery still loops — a slice may surface a GST edge case or a missing alias; that fact updates CONTEXT.md/an ADR and feeds the next slice’s spec. It does not reopen the slice in flight.
Bottom line. From here: run the short runway (§1), then write K0. From K0: the same loop forever — spec → issue → Sandcastle builds → you review → merge → next. Kernel by hand and supervised (K0–K9), then booking (your first full autonomous vertical slice), then inbound (money, supervised), then the rest in spine order. One chat per stage; the issue is the memory between them; money is never merged unwatched.

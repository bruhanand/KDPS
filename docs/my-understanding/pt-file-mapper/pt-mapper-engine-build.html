PT Mapper Engine — Build & Results

Turning every brand's "PT file" into KDPS's one in-house format. This documents what the engine needs, why the nine merchandising fields were coming out blank, what was built to fix it, and the measured before/after across all 33 sample brand files.

1 July 2026 · supersedes the earlier pt-file-mapping-analysis.md (which described the mapper as yet-to-build; it was in fact already built but under-fed).

1 · What the engine needs

To convert a brand PT file into the KDPS PT format, five things must work together. The engine had #1 and a thin version of #4–5; the nine fields you flagged failed in #2, #3 and #4.

2 · Why the nine fields were blank — the diagnosis

I built a repeatable audit (manage.py ptmap_audit) that runs the real engine over all 33 files and reports the fill rate per field. The baseline was unambiguous — two separate causes, not one:

Cause A — missing profiles

Only Ginesys and Tally profiles existed. Jockey, Peter England, Blackberry, Madura and the printed invoices fell to generic, which never located their colour / size / fit / date columns — so the value was never even read.

Cause B — starved tables

Where values were read, the lookup tables held ~39 colour keys for 120+ real shades, no size normaliser for 36/XS-style strings, and 30 taxonomy rules for 98 items. Everything else hit the review queue and the cell went blank.

A running instance can also map nothing because its database has never been seeded — the kdps_dev DB had no PT-mapper tables at all. The seed command below fixes that.

3 · What was built

Field(s)Fix
SIZEnormalize_size() — parenthetical alpha 1.14M(2XL)→XXL & XL (105 CMS)→XL, slash duals 36/XS→XS, age bands 8-9 YEARS→8-9 Y, 2XL→XXL, float & CMS cleanup.
COLORnormalize_color() strips code prefixes/suffixes (88-BEIGE, BLACK73/1, BLUE DN89) + a 274-entry shade→bucket seed. Price tiers (PREMIUM/ECONOMY) pass through.
SUB CAT / TYPE / ITEMTaxonomy rules expanded 30→125 covering all 98 items + synonyms; a hybrid word/substring matcher (fixes PANT≠PANTIE yet recovers glued codes like Madura FGTROUSER); SUB/TYPE auto-fill from the ITEM→helper.
GENDERInferred from description words (Senior Girls→KIDS FEMALE, SOCKS-MENS→MALE) as a fallback to a gender column.
FITNew fit source column (Peter England FIT TYPE, Blackberry FIT) + 18 fit aliases.
BRAND / SEASONBetter per-profile extraction, filename→brand for Jockey, corrected aliases (GO COLORS→GOCOLORS). Season derives from the invoice date; an explicit code no longer floods the queue.
ProfilesAdded D Jockey, E Peter England / Blackberry / Madura, F printed-invoice.
ResolverLayered: normalise → direct Master hit → lookup → review, so most values resolve with no lookup row at all.

5 · What's left — and why it's correct

The remaining gaps are structural (the data isn't in the file as mappable text), not engine failures. By design these go to the review queue: a steward maps the value once and every file re-maps forever — no code change.

  • Jockey — colour is a numeric code and the item is hidden in a style number (1250-0105-CANPI); there are no garment words to read. Needs a Jockey style→item lookup or operator entry.
  • Printed invoices (Suvidhi, Fahrenheit) — items are style names (AMBROSIA, CELERY), not garment types.
  • Colour / gender file-averages sit at ~47% / 25% mainly because ~10 files (Jockey, Madura, printed invoices) carry no colour or gender column at all. Files that do carry them now resolve well — the leftover misses are 7 opaque codes (CP, A, B, TINTED…).
  • FIT stays low — brand fit columns are coded (Peter England PJ RG OCTANEMIDSTR); these need a few review-queue mappings.

6 · Decisions for you needs Anand

1. Madura colour & brand. KDPS's own worked sheets put a price tier (PREMIUM/ECONOMY) in COLOR for Madura brands, and the file packs three brands (Allen Solly / Van Heusen / Louis Philippe) into one sheet. Which column holds the tier, and how should brand be split? Until confirmed, both go to review.

2. Operator context at upload proposed next slice. The cleanest fix for structurally brand-less / date-less files (Madura, Jockey, Xerics, printed invoices) is to let the operator pick the brand and consignment date (→ season) once at upload — both are known from the booking. Small, well-scoped follow-up; not built here.

3. Master-data hygiene. The COLOR master contains typos (GREE, STARD) and the 96-vs-96 CM overlap. Worth a one-time clean.

7 · Hardening round — making silent errors visible

A second pass added three guards on top of the engine, then an independent cross-model (codex) review challenged the lot.

Provenance per cell done

Every derived cell now records how it was filled — direct (a Master value) / derived (date→season) are trusted; alias / rule / inferred are judgement calls worth a glance. Stored on each row + served by the API. The audit shows COLOR is only ~46% "trusted" — half its fills are alias guesses. (UI rendering of the flag is the one remaining frontend task.)

Fuzz tests done

Seeded-random + adversarial inputs assert the normalisers never crash and are idempotent (f(f(x))=f(x)). They caught two real bugs (a colour like S M DN89 DN and 100 CMS CMS drifted across passes) — now fixed with a fixed-point loop.

Accuracy harness done — fill-rate ≠ correctness

Fill rate says a value was assigned; it doesn't say it's right. ptmap_goldenset exports the engine's guesses for a sample of rows; a merchandiser corrects the wrong cells; ptmap_accuracy re-runs the engine and reports per field: correct / wrong / missed / over (the wrong column is the dangerous one — a confident mis-map). This is the yardstick that turns "92% filled" into "X% correct".

Cross-model review (codex) — found 12 real defects, fixed

An independent model reviewed the diff adversarially. The legitimate findings, now fixed:

DefectFix
FLOWER TOP matched item LOWER (substring false positive)glued-substring match now restricted to SAP FG-code tokens (Madura) only

Flagged, not fixed (pre-existing, separate scope): a sent (not-yet-posted) PT can be PATCHed by any authenticated user and the hand-edit path doesn't validate values; and READY ignores blank cells. Both belong to the posting/authz hardening pass, not this taxonomy slice.

8 · How to run it

cd app/backend
# 1. create tables + load the lookup vocabulary from the Master Sheet (idempotent)
python manage.py migrate
python manage.py seed_ptmapper

# 2. measure mapping quality across the real brand files (fill rate + provenance)
python manage.py ptmap_audit

# 3. accuracy harness: export guesses → human corrects → measure correctness
python manage.py ptmap_goldenset --out golden.csv --sample 30
python manage.py ptmap_accuracy --golden golden.csv   # after a merchandiser corrects it

# 4. unit + fuzz tests for the normalisers (pure, no DB)
pytest tests/test_ptmapper_normalize.py tests/test_ptmapper_fuzz.py \
       tests/test_ptmapper_color.py tests/test_ptmapper_season.py

Engine: app/backend/ptmapper/engine.py · profiles: ptmapper/profiles.py · seed data: ptmapper/management/commands/seed_ptmapper.py · audit: ptmapper/management/commands/ptmap_audit.py. The mapping is fully deterministic and auditable — no AI anywhere in this path.

# Triage

Turn an unlabelled issue into either a `ready` issue an agent can build from, or a `blocked` issue with
one plain question for Anand. Nothing else.

Labels: [../labels.md](../labels.md). Tracker commands: [../issue-tracker.md](../issue-tracker.md).

Every comment posted during triage starts with:

```
> *This was generated by AI during triage.*
```

## Show what needs attention

Two buckets, oldest first, with a one-line summary each:

1. **Unlabelled** - never triaged.
2. **`blocked` with new activity** - Anand or a reporter has replied since the last triage note.

Let Anand pick. `ready` issues are not triage work; they are waiting for `implement`.

## Triage one issue

**1. Read it whole.** Body, comments, dates. Parse any prior triage notes so you do not re-ask a
resolved question.

**2. Check it is not already built.** Search the codebase for the behaviour by domain concept, not by
the words in the request. Read `CONTEXT.md` and the ADRs for the area first so you search in the
project's own vocabulary. Say where you looked. If it exists, close the issue pointing at where it
lives - that is not a rejection, so nothing goes in `.out-of-scope/`.

**3. Check it was not already rejected.** Read `.out-of-scope/*.md` and surface anything that resembles
this request by concept, not keyword. If it matches, show Anand the prior reasoning and ask whether it
still holds.

**4. Verify the claim.** For a bug, reproduce it from the reporter's steps before anything else. Report
what happened: confirmed, with the code path; failed to reproduce; or not enough detail, which is a
strong `blocked` signal. A confirmed reproduction makes a much better spec.

**5. Size it.** Does the work fit one implementation session? If not, it is a feature and does not
belong on one issue - say so and route it to `spec` → `design` → `to-tickets`, which will emit issues
that do fit.

**6. Sharpen it.** If the request is vague, grill it into shape one question at a time
(the `grilling` skill), updating `CONTEXT.md` or adding an ADR inline as decisions land. Force a
concrete number for every quantitative value; "reasonable" and "fast" are not values.

**7. Apply the outcome.**

- **`ready`** - rewrite the issue body into the spec below, then label it. Add `money` if the work
  touches ledgers, postings, GST, valuation, or the document FSM.
- **`blocked`** - post the triage note below and label it. One question at a time, in plain
  language, with your recommendation.
- **Closed** - already built, or rejected. A rejected *enhancement* gets a `.out-of-scope/` entry
  first; a rejected bug just gets a polite explanation.

## Rewrite the body, do not append a brief

The spec goes in the **body**, replacing what was there. Do not post it as a separate comment.

An issue carrying an old body plus a newer brief in the comments holds two specs, and an agent will
faithfully build the wrong one. That is exactly how #96 got built wrong. Whatever the original reporter
wrote is context; the body is the contract.

## What a `ready` body looks like

```markdown
**Category:** bug / enhancement
**Spec source:** docs/features/<slug>/ (omit if this issue is self-contained)

## Current behaviour
What happens now. For a bug, the broken behaviour and how to reproduce it.

## Desired behaviour
What should happen instead. Be specific about edge cases and error conditions.

## Key interfaces
- `TypeName` - what changes and why
- endpoint or screen - what it should return or show
Name types, signatures and config shapes. Never file paths or line numbers - they go stale
while the issue waits, and the agent will explore the code fresh anyway.

## Acceptance criteria
- [ ] Specific, independently verifiable
- [ ] ...

## Out of scope
- The adjacent thing that must NOT be touched
```

Two rules make a brief durable. Describe **behaviour, not procedure** - "the `SkillConfig` type accepts
an optional `schedule` field", not "add a field in this file". And give **complete acceptance
criteria** - the agent needs to know when it is done, and "it should work correctly" is not a test.

## What a `blocked` note looks like

```markdown
## Triage notes

**Settled so far:**
- ...

**What I need from you:**
- one question, in plain language, with the choices and which one I would pick
```

Everything resolved during grilling goes under "settled so far" so the work is not lost.
Write the question the way you would say it to a shop owner in Patna: shirts, brands, stores and bills,
rupees the Indian way (`₹2,85,000`), dates in words. It must be answerable without reading code.

## `.out-of-scope/`

One markdown file per rejected **concept**, not per issue: what was rejected, why, and the list of
issues that asked for it. Written in plain prose, durable reasoning only - "we are too busy" is a
deferral, not a rejection. Multiple issues asking the same thing get appended to the same file.

Only rejected enhancements go here. Something closed because it already exists must not, or the
deduplication check starts reporting built features as prior rejections.

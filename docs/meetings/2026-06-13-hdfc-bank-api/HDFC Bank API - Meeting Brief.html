KDPS Lifestyle Pvt Ltd · Meeting Brief

Bank API — what we need from HDFC

Prepared for the finance discussion · 13 June 2026
In one line: Our new system does a daily money audit across all 50+ stores. To do that, our software needs to read our own HDFC account statements automatically every day — no logging in, no PDF downloads. That automatic connection is called an API. HDFC already supports this; we just need to know which method we use and how to switch it on.

1. Why the project needs this

Every day, money comes into KDPS three ways: cash, card swipes, and UPI. Right now, checking that the money a store reported actually reached the HDFC account is a manual job in Excel and Tally, done after the fact.

The new system compares two things automatically, every morning:

  • what the POS says was sold and collected, against
  • what actually landed in the bank account.

If a store's card machine shows ₹40,000 but only ₹38,500 reached the bank, the system flags it the next day. For this, the software must pull the bank's transactions on its own — that is the API.

2. What an "API" is (plain version)

An API is a way for our software to talk directly to the bank's computer and ask, “give me yesterday's transactions for this account” — and get the answer back instantly, in a clean format, automatically.

Net-banking is a door for a human to log in and look. An API is a window for software to pull the same data automatically. We want the window — read-only.

3. What HDFC can give us (three routes)

All three are real and work. We don't need to decide today — we just need HDFC to tell us which one they'll approve fastest.

First choice

HDFC API Banking

Live APIs on HDFC's developer portal: Statement Download, Large Statement Generation, Balance Inquiry. Cleanest option for a daily audit.

Reliable fallback

Host-to-Host (H2H) file feed

Bank drops an encrypted statement file daily into a secure folder (SFTP); our system reads it. Older but very dependable.

Backup option

Account Aggregator (RBI)

RBI-regulated, consent-based way to pull statements. Useful if direct API approval is slow.

Note

Read-only, for now

We are not asking to send money or make payments — only to read our own statements. This makes approval faster.

4. What to ask HDFC for — our requirement list

For the corporate current account(s) used for store collections, we need:

  1. Statement / transaction API access — fetch all transactions for a date range (we'll pull daily).
  2. Each transaction must include: date, amount, debit/credit, running balance, the UTR / reference number, and the narration / remarks — this is how we match a UPI or card settlement back to a store.
  3. Balance inquiry — current / closing balance per account.
  4. Read-only access — no payment or fund-transfer rights needed.
  5. All accounts covered — if collections sit in more than one HDFC account, or there are sub-accounts / virtual accounts per store, we need each one.
  6. Sandbox / test access first, then production.

5. Questions to ask in the meeting

  1. Which option does HDFC give us — live API, daily H2H file, or Account Aggregator? (Whichever is fastest.)
  2. How do we apply, and how long does approval take? Any form, relationship manager, setup cost or annual fee?
  3. How far back can the statement go, and how often can we pull? (At least daily; ideally on-demand.)
  4. What format does the data come in? (JSON/XML for API, or what file layout for H2H — we'll need a sample.)
  5. Does the transaction data include the UTR / reference and full narration?
  6. Card settlements (POS machines): do those land in this same HDFC account, and do they show which store / terminal they came from? This is the single most important question for the audit.
  7. Who is HDFC's technical contact we'll work with once approved?

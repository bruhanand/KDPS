01The goal & the rules

You already know a lot of concepts from your front-end work. The gap isn't intelligence — it's a systematic path from "I can't read the syntax" to "I can trace any request through this system, judge whether the design is right, and tell an AI where it cut a corner."

What "top-level" actually means here

Getting code written is now easy. The scarce skill is judgement — knowing what correct code, a sound data model, and a defensible architecture look like, and being able to prove an AI's output wrong. This roadmap builds judgement, layer by layer, using KDPS as the one worked example so nothing is abstract.

Four rules for the roadmap

  • One playground. Every topic is anchored to a real file in app/. You never learn a concept in the abstract — you learn it, then read where KDPS already does it.
  • Read before write. For each layer you first reach READ (understand the code that exists), then WRITE (change it safely), then on the money-critical layers DEEP (defend the design against attack).
  • Bottom-up, because the stack is a stack. You can't judge a Django model without SQL; you can't judge an API without Django; you can't judge the React screens without the API. The order below is the dependency order, not a wishlist.
  • System design is the summit, not the start. Architecture judgement is earned after you can read every layer — so P8 sits late on purpose. You'll pick up architectural intuition along the way; P8 is where it gets named and formalised.

P0Reading code & navigating a repoThe one skill that pays off in every later phase. Before writing a line, learn to find your way.

What this phase covers

  • How a project is laid out; finding "where does X live?"
  • Tracing one feature end-to-end (URL → view → model → DB → back)
  • Reading top-down: entry points, then follow the calls
  • Search tools (grep/ripgrep) as your primary navigation
  • Git for reading: log, blame, diff, "why is this line here?"
  • Reading a diff / a pull request without running it
  • Reading error messages & stack traces as a map, not noise
  • The habit of asking "what would prove this wrong?"

app/backend/masters/{urls,views,serializers,models}.py — trace one booking request through all four files.

Milestone: you can open any of the 11 backend apps and, without help, say what it's for and where its data lands.

P1Python, properly READWRITEYou know basic Python. Django is object-oriented Python with heavy use of classes, inheritance, and decorators — close that gap or everything above stays opaque.

What this phase covers

  • Modules, packages, imports, virtual environments (and uv)
  • Classes & objects: self, methods, attributes
  • Inheritance & composition — the backbone of Django
  • Type hints & what mypy --strict is checking for
  • Decorators (@property, @classmethod, DRF's decorators)
  • Context managers (with) — critical for DB transactions
  • Exceptions: raising, catching, custom exception classes
  • Data structures: dict/list/set/tuple, comprehensions
  • Iterators & generators (lazy evaluation, why QuerySets are lazy)
  • Dunder methods (__str__, __eq__) — the data model
  • A first look at async (why uvicorn/ASGI exists)

Anchored in KDPS

Milestone: you can read any .py file in core/ and explain every line's syntax — no "what does this symbol mean?" left.
P2Relational data · SQL · Postgres DEEPThis is the heart of an ERP. Get this wrong and money is wrong. This phase goes deeper than the others on purpose.

What this phase covers

  • The relational model: tables, rows, columns, keys
  • Primary keys, foreign keys, relationships (1-1, 1-many, many-many)
  • SQL you can read & write: SELECT, JOIN, WHERE, GROUP BY
  • Aggregations (the raw material of every report)
  • Normalisation — and when to denormalise
  • Constraints: NOT NULL, UNIQUE, CHECK, foreign-key rules
  • Indexes: what they cost, what they buy
  • Transactions & ACID; isolation levels; why "all-or-nothing" matters
  • Postgres specifics: data types, numeric vs money-as-integer
  • Database triggers — how KDPS makes ledgers append-only in the DB itself
  • Append-only / immutable-record thinking (never UPDATE a posted entry)

Anchored in KDPS

core/ledger.py & the migrations that install DB triggers · query the live Render Postgres read-only to see real rows.

Milestone: you can explain, in SQL terms, why a posted ledger line can never be silently edited — and what would break if it could.
P3Django & the ORM READWRITEThe framework that turns P1 (Python) + P2 (SQL) into an application. Where the ORM ends and raw SQL begins is a judgement you now build.

What this phase covers

  • Fields, relationships, Meta, custom methods & managers
  • Migrations: how schema changes are versioned & applied

  • The request → URL → view → response cycle
  • transaction.atomic() — the all-or-nothing wrapper
  • The Django admin (free back-office)
  • Signals, and why KDPS mostly avoids them (explicit > magic)

P8Architecture & system design DEEPThe summit you asked for. Now that you can read every layer, you learn to judge the whole: is this the right shape, and why?

What this phase covers

  • Layered architecture — KDPS's five layers (masters → documents → ledgers → controls → intelligence)
  • Domain modelling: getting the nouns & rules right first (SKU = Style×Size×Color, SOR vs Outright)
  • The kernel pattern: a small, hard core everything else obeys
  • Append-only ledgers & "documents write ledgers" (event-sourcing-lite)
  • State machines / FSMs (docstatus) & idempotency
  • Coupling & cohesion; separation of concerns; dependency direction
  • Enforcing boundaries in code (import-linter) — architecture that can't rot silently
  • Data integrity as design, not hope (constraints > app checks > comments)
  • Trade-offs: consistency vs availability, simplicity vs flexibility, when to add a table vs a flag ("variation is data, not code")
  • Reading & writing ADRs — recording why, not just what
  • Designing for change: what KDPS deferred on purpose and why

Anchored in KDPS

Milestone: you can take a proposed feature and say where it belongs in the five layers, which rule it must obey, and what its ledger/document consequences are — before any code is written.

P10Reviewing & guiding AI — the capstone DEEPEverything above exists to make this possible: reading AI output with a senior engineer's suspicion, and steering it with a designer's clarity.

What this phase covers

  • Reading an AI diff critically: what it changed, and what it quietly changed
  • The spec → build → verify loop; never trust "done" without proof
  • Conformance-to-design as the primary review axis (does it obey the 12 rules / CONTEXT.md?)
  • Where AI habitually cuts corners: money paths, permissions failing open, missing the SOR/GST edge, single-entry where double-entry is required — the exact defects KDPS's own reviews caught
  • Writing a spec an AI can't misread; using CONTEXT.md/ADRs as the yardstick
  • Adversarial verification: "what input makes this wrong?"
  • Knowing when to accept, when to send back, when to write it yourself
  • Directing multi-step AI work and keeping yourself in the loop

04What happens after you approve this order

This document is only the sequence. Once you're happy with it, we turn each phase into the real thing — on your say-so, one phase at a time.

The teaching model (for when you give the go)
  • One phase at a time, in this order — never all at once.
  • Each phase becomes: a short explainer in plain language → a guided read of the real KDPS files listed above → small hands-on exercises against the actual repo → the milestone as the exit test.
  • You drive the depth. Where you already know something (front-end concepts, some Python), we move fast; on money/data/architecture we go slow and deep.
  • We keep a running "you can now…" checklist so progress is visible.
Open questions for you (before we start Phase 0)
  • Order check — anything you want moved earlier or later? (Common wish: pull some architecture up front. My advice is to resist it; it lands better after P3.)
  • Do you want the front-end phases (P5/P6) before the API depth (P4), since you're strongest there — or keep the bottom-up order?
  • Should the very first deliverable be Phase 0 as a hands-on "trace one KDPS request" walkthrough, or a written explainer first?

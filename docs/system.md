# KDPS working:

Let's go from the start, taking different things into account, and let's discuss the whole KDPS working.  
The business runs on two seasons:

- Autumn/Winter (AW)
- Spring/Summer (SS)

Commercial models (default per brand, overridable per booking)

Stored as two axes (ownership × return-terms + a rolling-top-up flag); the friendly label is derived:

- Buy & Sell (Outright) — KDPS owns; no returns. (Sub-types: with vendor barcode = MRP capped, or without = KDPS sets MRP.)
- 25-18-10 (Correction) — KDPS owns, but a capped return allowance: 25% full-price margin / 18% EOSS / 10% goods-return, on delivered goods (stretchable to 12–15%).
- SOR — brand owns; all unsold returns, no cap; fresh booking to reorder.
- Consignment — same as SOR but brand keeps topping up (no fresh booking); vendor collects the unsold.

## BOOKING:

The order is placed in advance of the season.
Rules:
Vendor (the legal entity, many brands under it) →
Brand (commercial model + return terms live here, brand by brand) →
Booking (one vendor + one brand + one season; never mixes brands).

Vendor & brand records carry the statutory and commercial detail — GSTIN (more than one, one per billing state; State & PAN are read from the GSTIN, never typed), bank details, the two margins (normal-sale and discount-sale), return window, and payment terms. None of these block a booking: they can be filled in later (flag, never block). Payment terms are not set on the booking — they live on the vendor/brand record, are snapshotted onto the booking, and feed payments (D4) later.

Types:

- branded
- non-branded.

FYI:
What is considered brand?
Let us first understand what is a brand. A brand means that, at booking, you get a proper receiving. When stock comes to KDPS, it comes with an invoice, and the stock PT file is provided by the brand or the supplier.

Brand = booking receipt + stock + invoice + PT file + tagged goods.

When creating the booking in the system: (Software Process)

1. season is picked first — the handler selects the season (or generates the next one from the fixed pattern if it doesn't exist yet),
2. then the vendor/brand,
3. then uploads the receipt.

Tag / Status:

The booking module is deliberately thin. It owns the order and its manual end-states only — everything about receipt lives in inbound. Between booking and the season for which it is booked, the booking stays live and tracked.

Booking states:

Manual states (always with a remark):

1. BOOKED — set when the handler confirms the reviewed draft. The order is now real and tracked.
2. CLOSED — manual, always with a remark. Nothing auto-closes. A CLOSED booking can be re-opened, but everything is logged.
3. CANCELLED — manual, always with a remark. Reachable from any state.
4. PARTIALLY CANCELLED — a booking that is partially received can have the rest cancelled.

Derived receiving statuses (computed from the booking's own GRNs, shown on the booking, never set by hand):

- PARTIALLY RECEIVED — some of the booked quantity is in.
- FULLY RECEIVED — all of it is in.
- RETURN WINDOW OPEN — the return window opens as soon as ANY items are received, even on a partial receipt. It exists only for Correction / SOR / Consignment; Outright has none (KDPS owns the goods). The window date is entered manually — the brand often tells KDPS later, so "return window time set later" is a valid entry.

The GR budget still belongs to inbound. The booking screen shows booked-vs-received ("40 of 100 are in") so the handler can decide when to CLOSE.

Booking structure:

- Primary line data = per style-code → per size: quantity. This is the minimum every booking line carries.
- No colour at booking.
- Other data (price/MRP) is added only if the booking receipt states it — if it's there we capture it, if not we don't. Any price is indicative; the binding MRP/cost is set later at inward.
- No system input for how much to order — the order quantity is decided internally, so there is no budget or spending cap in the system.
- Quantity-led, plus one optional estimated order value for planning if pricing is mentioned.
- Commercial model + snapshot of its terms ride on the booking. The default comes from the brand — whatever model that brand works on. The handler can change it on this booking, but **one booking carries exactly one commercial model, and one GRN carries exactly one commercial model**.
- Auto booking number (e.g. BK-SS26-0012) generated by the KDPS system; if the brand/vendor has its own booking/order number, that is kept too.
- Season picked from a system-derived list, never free text. Only an Open season is pickable. Booking is where a new season is born — if the next season doesn't exist yet, it is created at the point of booking, and all the stock and data that follow ride on that season.

### For non-branded:

- Discussion deferred for later on.
- This is the most unorganized.
- It's done from anywhere: on call, on message, in person or through agents.
- Receipt for the booking is not standard, and sometimes they don't even provide it.
- For non-branded booking, an AGENT (per City for Suppliers) is involved, who takes care of the whole process till the item is received at KDPS. Agents are accountable until the goods are delivered and verified.
- Item is booked for the warehouse (items arrive at KDPS's warehouse in Ranchi).
- At inbound stock can be received in the system without booking information.
- Parked for v2

### For branded:

- Booking receipt from the brand is a source of data.
- Booked mostly for the store and also for warehouse.
- Data is mostly organized.
- Booking is taken care of until it is received at KDPS and verified by the supplier or an agent.
- Included in version 1

- User story for system:

1. Season is selected (or the next one is generated from the fixed pattern; a season can be deleted only while empty).
2. The vendor/brand is picked — or the handler skips straight to upload and lets the system read the vendor and brand off the document.
3. The receipt soft copy (PDF/Image) is uploaded.
4. The AI agent reads it and produces a DRAFT — it never books silently. The handler reviews the draft, completes anything missing, and confirms.
5. On confirm, the booking is created and tagged BOOKED.

### Booking ↔ receiving rules (edge cases)

- **One booking ↔ many GRNs.** Goods come in lots; each arrival makes its own GRN until the booking closes.
- **Over-receipt is normal.** Even on an outright buy the vendor can send more than what was ordered — it is received, not refused: the same screen adds a line, flagged as a variance with a required remark. The original booked line is kept. Returning the extra stays an open option — keep all options open.
- **A GRN can stand alone with no parent booking** — branded or non-branded. No phantom booking is invented. Booking details can be linked to any GRN later (and one booking to many GRNs); the linking is brand-wise. A retro-link is a tracked, dated correction — never a silent rewrite.
- **Editing after BOOKED is allowed, but never silent** — every edit carries a remark (who + why) and goes through authorisation. Full audit trail.
- **Who makes the GRN:** whoever receives the goods at the store or warehouse creates it — they are responsible for what came in from the vendor/brand. The count can be taken physically with a colleague's help; the GRN is made against the invoice, and against the booking when there is one.
- **Vendor numbering:** the system generates its own unique vendor code when a vendor is added; duplicates are caught by PAN/GSTIN match, never by name. The vendor's own reference numbers are kept alongside.
- **Unknown brand at receipt:** brand known but model not set → default Outright, flagged for head office. A truly unknown brand → "Unconfirmed" model: stock-in posts quantity + cost, but the vendor-ledger posting is withheld until the brand is confirmed. Payment (D4) is hard-gated until then.
- **Roles / who-can-do-what:** scoped separately — see `ERP_DASHBOARD_V1.xlsx` in `docs/data-from-kdps/scope-dashboard-detail/`.

## INBOUND:

Starts with Shipment receiving at KDPS.
Shipment may be received either at stores or at warehouse.
At Store Only Branded
At Warehouse branded (considered branded) + non-branded

### Receiving of items:

**What counts as branded is checked per shipment — all three must be there:** vendor barcode + tag, a proper detailed invoice, and the vendor PT file (retrievable from the vendor). Any one missing → the shipment stays non-branded. "Arriving together" is not the test — a shipment may come in several lots.

For branded:
Shipment received at Store or Warehouse.
At Store or warehouse (Shipment + Invoice):  
Items are received and counted against the invoice.
Invoice is uploaded for the particular booking.
GRN is created.
Person taking care of PT files received notification.

For non-branded:
Shipment received at warehouse only.
Items are received and counted against the invoice.
Invoice is being uploaded.

#### How a non-branded item arrives — tagged vs non-tagged

Non-branded arrives **at the warehouse only**. Both come with an invoice carrying the three things a GRN needs — style code, size, quantity. Invoice data is rarely clean, so upload makes a **draft GRN**; the person corrects it, then posts. GRN posts **quantity only** (no value).

**At GRN creation the person marks the consignment `tagged` or `not-tagged`.** That choice sets the flow.

**Identity for non-tagged goods**

- **Style code** — always present, final.
- **Quantity** — always present, final.
- **Size** — if not stated → `Free Size`.
- **Colour** — usually not stated on non-tagged goods. In its place the item carries a **tier: Premium / Medium / Economy**. The tier *is* the colour slot, not an extra field.
- SKU key = **style × size(or Free) × tier**. Many pieces can sit under one barcode — accepted, not a defect.

**The three arrival shapes (all start from the GRN)**

A **draft PT** is built off the GRN; the warehouse person edits it and chases any missing detail from the vendor. The PT file is the source of truth for stock in the system, and it is needed for every commercial model.

- **Tagged, and the vendor PT is retrievable** → the shipment counts as branded (all three present). Vendor barcode + printed MRP kept; barcode tab is **live**.
- **Tag + printed MRP, but no PT file** → KDPS authors the PT itself. The printed MRP is the **base** — the tag caps it, and KDPS applies the company's already-decided margin. It never invents a fresh MRP.
- **Not-tagged** → barcode tab is **greyed out** — there is nothing to generate yet; it comes after the PT is done. KDPS sets the MRP (below).

**PT-making chatbot (non-branded)**

A chat assistant that knows the PT process. The person feeds it whatever he retrieves from the vendor; it fills the PT fields. Trained on real invoices + their converted PT files.

**MRP (KDPS-set, non-tagged)**

`Base + ~1.1% transport + GST + slab margin`, where the slab is chosen by **price bracket × supplier**. Stored as a versioned, date-effective table. MRP is **frozen onto the PT** — never recomputed later.
*(Note: 30–35% here is markup on cost, not margin on price — state which. Plan says 20–25%; this number overrides it.)*

**Barcode generation — one PT at a time, in sequence**

When a completed PT enters the barcode step it **claims the counter, takes a contiguous block of numbers row-by-row, releases it** — then the next PT. Drafting is concurrent; only the barcode step is single-file. This is what keeps the sequence unbroken and makes duplicate barcodes impossible.

**Review → Patna**

Tags print → PT gets a **final review** → **Send to Patna**. Patna receives PTs **in sequence** and enters them (data entry, not re-checking — the real check happens at the warehouse). The inward action stays with Patna; the system auto-validates and flags only exceptions (GST rate vs HSN, margin outside the expected band) for a human to approve. This is where system stock becomes true.

**Store split**

When stock lands at the warehouse, the store split is **suggested by AI and adjustable manually** — the warehouse proposes the per-store allocation, Patna confirms and inwards the per-store PT. Per-line allocations are captured as structured data from day one (the future training set for the AI suggestions).

**Unmapped PT format**

A brand PT in an unknown or changed format never auto-converts — it parks in an **unmapped queue** and comes to Anand/the developer.

**Ownership**

Non-tagged non-branded is **Outright / KDPS-owned by default** — KDPS sets the MRP, prints the tag, and sells it. (Ownership follows the commercial model; for these goods that model is Outright.)

> **Open — needs a legal-metrology consultant before go-live:** when KDPS prints its own MRP tag it becomes the declarer/brand-owner. The tag must carry name + address + country of origin, consumer-care email + phone, size, and MRP inclusive of taxes; MRP may only be reduced by sticker, never raised. Same sign-off gate as the CA questions below.

### What the GRN and the PT each make true

- The **GRN is the count truth** — it posts quantity only, the moment goods arrive.
- The **PT makes the stock true** — at Patna inward it stamps the frozen unit cost on every piece and posts the money: **vendor liability per the commercial model** (Outright & Correction → at inward; SOR → accrues per piece on sale; Consignment → never from the PT).
- The GRN is also checked against the PT — invoice ↔ GRN ↔ PT reconciliation runs as an end-of-day batch; a mismatch raises a correction, not a block.
- Corrections are always **new, dated events** — nothing is ever silently rewritten or re-posted.

### Selling before the PT (manual billing)

Goods are sellable off the GRN, but only through **manual billing, and only where a tag exists** — at the store, for branded/tagged items, or items not yet inwarded into the KDPS system. Non-tagged goods sit at the warehouse and are **not sellable** until they are tagged and the PT is done. Manual billing is a stop-gap to be restrained, not a norm.

### Money rules at PT-making

- All money fields — base rate, P RATE, unit cost, margins — are **configurable per brand, per booking, per shipment**, by the authorised person (admin setting), until the detailed prices arrive.
- **Unit cost below MRP is the fact** — the system checks it at PT-making and flags a breach; the values stay configurable per GRN, so it is a check, not a blocker. *(Note: the built kernel currently enforces cost ≤ MRP as a hard database check — align one way or the other.)*
- **SKU reuse:** key = vendor + style-code + size. Seen before → roll up to the existing SKU/barcode and add to its count; never mint a duplicate identity.
- **Barcode + season** is the full identity of a cohort. The POS infers the season at scan (oldest season first when more than one matches; a truly ambiguous scan is a one-tap "which season?", never a blocked sale).

### Receiving discrepancies

- Ordered-vs-received differences are a **soft flag — the flow never stops**. The discrepancy is logged with a structured outcome (credit note expected / brand acknowledged / write-off) and **stays open until explicitly closed** by the account manager.
- At arrival the goods are just counted. Damage is caught later, at selling; if damage is spotted at arrival, the piece enters stock **quarantined — not sellable** — and routes to the defective-return flow.

## OUTBOUND:

Everything that happens after stock is sellable at a location: selling at the POS, customer returns, stock transfer, goods return to the brand, stock counting.

Stock is held per **barcode + season + location**. What a location can sell = its physical stock minus whatever an open document is holding (a transfer on the road, a defective piece, a pending return). A piece's state is always derived from the document holding it — never set by hand.

**Ownership tag.** Every stock carries who owns it — **KDPS or the brand**. In the UI this is a filter view inside inventory (stock owned by KDPS / stock owned per brand), not a separate module. **V-flip** = when sales are over-shown to the brand to reach a target, those pieces flip from brand-owned to KDPS-owned. That's all it is — an ownership flip inside inventory management.

### Stock transfer (distribution)

- Stock that arrives at a store **belongs to that store** — and the option to distribute onward (store → store) is always open.
- **Warehouse → store is the main distribution.** A section predicts the store split for the stock (suggested by the system, adjusted manually — same as the inbound store split); the stock then moves to its assigned stores.
- **Every transfer generates a PT file in the KDPS format.** The PT is the source of truth that the receiving location owns those stocks. No stock moves anywhere without its PT.
- **Received = scanned.** When the physical goods arrive, every item is scanned and counted at the receiving place. Scanning at the warehouse (before dispatch) is an option too. A gap between sent and received is flagged on the open transfer.
- **Bihar ↔ Jharkhand:** the system just transfers the stock between the two states. The GST invoice + e-way bill are needed but are made **manually, outside the system** (already decided — see consolidation).
- Stock transfer is available at **every user level** — anyone moving goods can raise it.

### Customer side (POS)

The POS is the main outbound — it sells to the customer and takes the customer return/exchange. Customer dealings live at the POS. (The POS discussion comes later; only the functionality is fixed here.)

- **Customer return window** — a configurable number of days, opens when the customer buys. The store can override it, but only with permission from a senior KDPS member and a valid reason.

### Goods return to the brand

- **Who returns:** SOR and Consignment (brand-owned — uncapped) and Correction (KDPS-owned, but with an allowed return amount — a **configurable percentage**, negotiated with the brand, brand by brand). Outright never returns.
- **Return window to the brand** — configurable; the brand shares it, the warehouse team updates it in the system.
- **Defective pieces** — found at the store, the piece goes **not-sellable (quarantine)** and returns by one of three routes: the brand collects from the store / KDPS sends it from the store to the brand / it travels store → warehouse and is returned from there.

### Stock counting

Counting is done by scanning — the items are scanned and the count is made that way. The book is corrected to the physical reality through a logged adjustment.

## Open questions

Booking side:

- **Return-window details** — at season end, the return information and details come from the brand. How that lands in the system will be defined when the information is provided. (Parked — info to come.)
- **Abandoned drafts** — what happens to a booking draft that is never confirmed? No expiry decided yet.

CA questions (must be answered before the system handles live money):

1. **SOR/Consignment GST** — at what point is GST recognised on SOR/consignment goods, and how do we guarantee it is booked exactly once (single recognition, tied to one date + voucher number)?
2. **Recognition per brand** — is each SOR/consignment brand an "agent" arrangement or a true sale-or-return for GST purposes, and does the recognition point differ per brand?
3. **Deemed supply** — how do we run the ~6-month deemed-supply clock (CGST §31(7)) on SOR goods alongside the commercial 60–120-day return window, both counting from the same removal date?
4. **Late freight after PT** — when a freight bill lands after the PT is inwarded, do we adjust the unit rate forward-only or post a separate cost-correction event? (Re-posting is forbidden either way.)
5. **Sold before PT** — when a piece sells before its PT exists, do we bill it on a memo value and true-up later, or hold the sale?
6. **HSN & P RATE** — sign off the apparel GST slab rates per HSN, and confirm no brand embeds GST inside its P RATE column.

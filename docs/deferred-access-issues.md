## #149: Password policy is a single min-length rule — add Django's default validator set
Labels: bug, deferred-access

> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug
**Summary:** Only a minimum-length password validator is configured; add the rest of Django's default validator set. Enforcement is already wired — only the config is missing.

**Provenance:** From the closed Devin PR #65. Verified on `main` during triage (27 Jul): `AUTH_PASSWORD_VALIDATORS` holds the minimum-length rule and nothing else.

**Correction to the original report:** PR #65 claimed a common-password validator would reject the seeded demo passwords. It would not — none of them are common. Running the seeded list against Django's four defaults, seven fail: five for being too similar to their username (`admin`/`Admin@123`, `owner`, `ops1`, `brand1`, `steward`) and two warehouse logins for being under eight characters (which already breaks the single rule in place today). This does **not** need reseeding to land (see out of scope).

**Current behavior:**
Only `MinimumLengthValidator` is configured. The three other validators Django ships and enables by default in a new project — user-attribute-similarity, common-password, and numeric-only — are absent. The password-entry seam already calls Django's `validate_password()` on user create and update (the admin user-management serializer), and that is the only place a password is set through the app. So the enforcement point exists; it is simply running against a one-rule policy.

**Desired behavior:**
`AUTH_PASSWORD_VALIDATORS` carries Django's default set at minimum (min-length, user-attribute-similarity, common-password, numeric-only). Any password set or changed through the user-management API must satisfy that policy.

**Acceptance criteria:**
- [ ] The validator set matches Django's defaults at minimum.
- [ ] A test asserts that a weak password (e.g. common, numeric-only, or too similar to the username) is rejected at the user-management API seam, and a strong one is accepted.
- [ ] `npm run ci` is green.

**Out of scope:**
- Reseeding the demo accounts. The seed writes passwords directly and bypasses validation, so adding validators does not break seeding. The seeded passwords are printed on the login screen — a consciously-deferred alpha item — so bringing them into compliance rides with the pre-go-live security pass, not here. Do **not** add a "seeded accounts satisfy the policy" criterion.
- The file-download hole (#120) and the public-schema / CSRF hardening (its own issue).

## #148: OpenAPI schema and Swagger UI are public; CSRF trusted-origins defaults to a wildcard
Labels: bug, deferred-access

> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug
**Summary:** The OpenAPI schema and Swagger UI are served to unauthenticated callers, and the CSRF trusted-origins list defaults to a wildcarded preview domain when its env var is unset. Both are production-config hardening at the settings/URL seam.

**Provenance:** From the closed Devin PR #65. Verified live on `main` during triage (27 Jul): the schema and docs endpoints both answer 200 to a caller with no login.

**Current behavior:**
- The schema and Swagger-UI endpoints are mounted unconditionally, and drf-spectacular serves them to anyone rather than following the project's authenticated default. This publishes the entire API surface — every route, payload shape and field name — to an unauthenticated caller on the alpha. Low severity alone, but it need not be public.
- The CSRF trusted-origins list *defaults* to a wildcarded preview domain (`https://*.emergentagent.com`) when its environment variable is unset. The deployed alpha sets the variable explicitly, so this is not live today — it is a footgun for any future deployment that forgets to set it. (The related CORS credentialed-wildcard hole is already fixed on `main`; this is its last residue.)

**Desired behavior:**
- The schema and docs endpoints are unreachable to an unauthenticated caller in a production configuration (DEBUG off, CI flag unset), and remain available to developers and CI. Reuse the pattern the codebase already uses for the `admin` mount and the migration-names publication — gated on `DEBUG or CI`, not removed.
- The generated TypeScript client still builds against the schema (developers/CI can still reach it).
- The CSRF trusted-origins default no longer carries a wildcarded preview domain: when the env var is unset it resolves to empty (fail-safe, requiring explicit configuration), mirroring how the exact-origin CORS allowlist already defaults.

**Acceptance criteria:**
- [ ] In a production config, an unauthenticated request to the schema and docs endpoints does not succeed.
- [ ] In a developer/CI config, both endpoints are reachable and the TypeScript client generation still succeeds.
- [ ] With the CSRF env var unset, the trusted-origins list is empty — no wildcarded domain.
- [ ] The deployed alpha (which sets both env vars explicitly) is unaffected.
- [ ] `npm run ci` is green.

**Out of scope:**
- The file-download scoping hole (#120).
- The password policy — its own issue.
- Removing the schema endpoints entirely — the typed client needs them.

## #141: A store person can read every store's transfers, and every other store's outbound documents too
Labels: bug, deferred-access

> **Triaged 27 July 2026.** The question this issue left open - what a brand manager should see - is already answered by the ratified corpus (PRD #104, ADR-0003, and ticket #110), so nothing here waits on a human decision. The body is the spec; where a comment disagrees with this body, the body wins.

Found while building the in-page search (#102), and deliberately **not** fixed there - it is an access-control change, not a search one.

## What is wrong

The transfer list shows a store person **the whole network's transfers**, not just their own store's. Open Transfers as the Deoghar manager and a move between Bokaro and Hazaribagh - nothing to do with them - is sitting in the list.

Writing a transfer is properly gated: the system stops you dispatching from a store you do not work at. Reading one is not gated at all. The same is true of the transfer's own page: knowing its number is enough to open it.

The same gap covers the rest of the outbound documents - returns to brand, adjustments, write-offs and V-flips all list every store's.

The code knows: the NOTE at the top of `TransferListCreateView.get_queryset` (`app/backend/outbound/views.py`) says the list is not store-scoped on read and points at the brand-manager question this triage now answers.

## The ruling

Two rules, both already ratified and already shipped elsewhere. This issue only applies them to the outbound list and document endpoints.

**1. Store-scoped callers.** A transfer belongs to **both ends of the move**: visible when the caller's scope contains the source **or** the destination store. Returns to brand, adjustments, write-offs and V-flips are visible at their own store. These exact predicates are already settled and live in the top-bar search registry (`_scope_transfer` / `_scope_store` in `app/backend/search/views.py`); the list and detail endpoints must apply the same ones.

**2. Brand-scoped callers (the brand manager).** These documents carry no brand, so nothing can prove a row is theirs: **fail closed** - they see none. That is exactly what the top-bar search already does for a brand-scoped caller (ADR-0003), and it is a deliberate interim, not the end state: **#110** gives outbound documents a brand dimension and replaces fail-closed with cross-by-brand. Under PRD #104 the brand manager is not a transfer actor anyway (stores request, send and receive; the warehouse executes; the Operations Head approves; Owner overrides) - what they lose here is a read view that #110 restores properly, built from brands as this issue predicted.

Unrestricted callers (Owner, Accounts, HO roles with all-scope) are unchanged: they see everything.

## Agent brief

- The gap is read-side only: `TransferListCreateView`, `TransferDetailView`, and the RTV / Adjustment / Write-off / V-flip list and detail views in `app/backend/outbound/views.py` apply no scope in `get_queryset`. Writes are already gated via `enforce_store_scope`.
- Use the existing helpers in `masters/scoping.py` - `MarkDamagedView.get_queryset` and the transfer-gap list in the same file already scope reads correctly. Transfers need the two-ended variant (`Q(source_store_id__in=...) | Q(destination_store_id__in=...)`).
- Detail endpoints must **404** on an out-of-scope document - indistinguishable from one that does not exist, the fail-closed pattern `ScanLookupView` already documents.
- Express each doc type's scope predicate **once** and share it between these views and the search registry rather than writing it a second time. The #101 rewrite found the booking predicate hand-copied three times; do not repeat that here.
- #102's acceptance criterion "a store person only ever searches their own rows" currently passes vacuously on these lists; add or strengthen the test so it passes for real.
- If #105 (fold Write-off into Stock Adjustment) lands first, scope whatever correction documents exist at build time; do not resurrect a surface it removed.

## Acceptance criteria

- [ ] A store-scoped user's transfer list contains only transfers where one of their stores is source or destination; opening any other transfer by URL or number returns 404.
- [ ] RTV, adjustment, write-off and V-flip lists and detail pages: own store only; anything else 404.
- [ ] A brand-scoped user sees empty lists on these endpoints (fail closed, matching top-bar search), not errors and not everything.
- [ ] Unrestricted (all-scope) callers are unchanged.
- [ ] The in-page search (#102) on these lists filters only the scoped set, proven by a non-vacuous test.
- [ ] Each predicate exists in exactly one place, shared with the search registry.
- [ ] `npm run ci` green.

## Related

#101 (the same missing read scope on bookings) · #102 (where this surfaced) · #110 (brand becomes a real scope axis - supersedes the fail-closed interim for brand managers) · #104 (the actor-model PRD).

## #134: The Data Steward owns the product master
Labels: deferred-access

## Parent

#104 — PRD: Who may do what (the actor model). **Read the PRD body first.**

## What to build

One owner for the product master, which is what stops 20,000 SKUs becoming 30,000 near-duplicates across 40 brands.

**The ruling, settled 26 July** — it restates what the inbound design already said, and matches ERPNext, which grants product write to a single Item Manager and read-only to every other role:

- **Creating a product happens inside PT-making**, as a by-product of goods arriving. The Warehouse, a Brand Manager and a Store Manager all do this in the course of their job.
- **Once a product exists, only the HO Data Steward may edit, merge or correct it.** Nobody else, including the Warehouse that created it.
- **A Brand Manager may retag descriptive attributes** — season, collection, category — **on their own brands only**. Never identity: not the code, not the barcode, not the brand it belongs to.
- **Stores never edit products.**

The duplicate-merge path is the Data Steward's alone, because merging rewrites which product a stock movement pointed at.

## Acceptance criteria

- [ ] A Warehouse or Store Manager can bring a new product into existence through a PT, and cannot edit any product afterwards
- [ ] The Data Steward can edit, merge and correct any product
- [ ] A Brand Manager can change season, collection and category on their own brands, and is refused on identity fields and on other brands' products
- [ ] A store role cannot edit a product at all
- [ ] `npm run ci` green

## #133: Split Setup into product data and everything else
Labels: deferred-access

## Parent

#104 — PRD: Who may do what (the actor model). **Read the PRD body first.**

## What to build

Setup splits in two, so that "Products only" starts meaning products only.

The ratified table gives the Warehouse `setup: operate` labelled **"Products only"** and the Brand Manager `setup: operate` labelled **"Edit assigned products"**. The system has one all-or-nothing Setup rung, so those labels are decoration: whoever can add a product can also reach vendors, their bank details, brand terms and GST slabs. ## #132: Cost is hidden on stock that is not yours
Labels: deferred-access

## Parent

#104 - PRD: Who may do what (the actor model). **Read the PRD body first.**

> **Narrowed 26 July 2026.** This issue originally built a field-level access axis masking cost, landed value and margin from Warehouse and Store roles everywhere except a PT under construction. Anand withdrew that axis. What remains is the scope rule below - much smaller, and the part that was actually protecting something.

## What to build

Cost is hidden on stock that is not yours.

A Warehouse or Store person sees **everything** about the stock held at their own location - cost, landed value and margin, on stock screens, lists, count variances and reports. They can already read the PT that carries the rate, so masking the same number beside it protects nothing and stops them sizing their own business.

What they must not see is the cost of stock held **somewhere else**. There is one place in the system where that arises: the cross-location stock search a store uses to build a stock request (#74). A store looking at the warehouse's stock, or another store's, sees identity and quantity, and no money.

So this is a scope rule on the axis that already exists (`scope_type`), not a new axis and not a field group. Enforce it where cross-scope stock is served, and make it a rule rather than a per-endpoint habit: any endpoint that returns stock rows outside the caller's scope drops the money columns, and a new such endpoint inherits that without being edited.

A Brand Manager's brand scope works the same way: their own brands' cost, in every store; nothing for other brands.

## Acceptance criteria

- [ ] A store role sees cost, landed value and margin on its own store's stock, including count variances and reports
- [ ] A warehouse role sees the same for its own warehouse's stock
- [ ] Stock rows served for a location outside the caller's scope carry no cost, landed value or margin
- [ ] A Brand Manager sees cost and margin for their own brands in every store, and not for other brands
- [ ] Owner, Accounts and HO Operations see them everywhere they already have access
- [ ] The rule is enforced at one point; a new cross-scope stock endpoint is covered without touching it
- [ ] A test covers the cross-location search and its export path - a leak in either fails the build
- [ ] `npm run ci` green

- #130 - the ratified nine-role table

## #124: PT actors: who makes, who inwards, who reverses
Labels: deferred-access

> **Rewritten 26 July 2026 against the ruling in #104.** The body is the spec. Where a comment disagrees with this body, this body wins. The original question — "may break-glass post a PT?" — is answered here as one part of the whole PT actor ruling.

## Parent

#104 — PRD: Who may do what (the actor model). **Read the PRD body first.**

## What to build

Goods coming in get their actors, settled 26 July.

**Making a PT** — the Warehouse, a Brand Manager, or a Store Manager for goods delivered straight to that store. Nobody else. HO Operations comes out, IT Admin comes out, and the **HO Data Steward stops being a PT maker**.

**Inwarding a PT** (the act that makes stock real and raises what KDPS owes the brand) and **reversing one** — **Accounts** and **Owner** only.

- **HO Operations is removed.** They place the booking with the brand, and the buyer must never book their own bill. This is the three-way-match control and it is deliberate: Anand's first answer put HO Ops here and he changed it once the standard was on the table.
- **IT Admin is removed**, consistent with the ratified Admin-has-no-Money cell.
- **Break-glass passes.** `superadmin` bypasses every rule in the system by design; today it is refused here and honoured on master-data writes, so the codebase answers the break-glass question two different ways. It should answer once.
- The gate's error message must say what the gate actually does — the current one names "accounts/owner" while the code also admits `it_admin`.

**The buyer never inwards their own booking.** Beyond the role rule: a user who created the booking is refused on the PT that came from it, even if their role is otherwise allowed.

**Resolving flagged mappings** stays with the **Data Steward** and the **Warehouse** — and the Data Steward must be able to *see* the review queue they are responsible for. Today that role is refused the queue because Receive Goods was never granted to it (raised as item 1 of #125). Grant the narrow read, not the whole section, if the ladder allows it.

## Acceptance criteria

- [ ] Warehouse, Brand Manager and Store Manager can make a PT; HO Ops, Data Steward and IT Admin cannot
- [ ] Accounts and Owner can inward and reverse a PT; HO Ops and IT Admin are refused
- [ ] A user who created the booking is refused when inwarding the PT that came from it, whatever their role
- [ ] The break-glass account passes both PT gates, and master-data writes and PT writes answer break-glass identically
- [ ] The Data Steward can open the review queue and resolve flagged mappings, and cannot make a PT
- [ ] Every refusal message matches what the gate actually enforces
- [ ] `npm run ci` green

## #120: Any authenticated user can download any file — scope the download endpoint by the file's store
Labels: bug, deferred-access

> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug
**Summary:** The file-download endpoint has no scope check — any logged-in user can download any stored file network-wide. This is a P0.

**Provenance:** Surfaced by the stale Devin PR #65 (closed 26 Jul). Verified live against `main` during triage on 27 Jul: a Deoghar-only cashier downloaded a Bihar store's invoice and got a 200 with the file bytes. This is an oversight, **not** one of the two consciously-deferred alpha security items.

**Current behavior:**
The download endpoint fetches a stored file by primary key, gated only on being authenticated. Any logged-in user — a store cashier in Deoghar — can walk the ids and pull every uploaded bill, PT file and vendor invoice in the network, including the other state's documents. Two adjacent defects confirmed while verifying: a non-existent id raises and returns a 500 instead of a not-found, and because the miss and the refusal look different, the ids can be walked to learn which files exist.

Same class of defect as #101 (unscoped bookings). The scoping helpers already exist and are consumed by seven apps (`scope_by_store`, `scope_by_entitlement`, fail-closed per ADR-0003 — the sidebar is not the security boundary); this endpoint simply never called them.

**The scoping decision (settled during triage — stamp, don't inherit):**
A stored file has no store of its own today; it hangs off a goods-receipt, a booking, or a PT file, and each reaches a store by a different route (receipt → its store; PT file → the receipt behind it; booking receipt → the booking's destination store, which is null for warehouse/HO bookings). The file will carry its **own** store, stamped at upload time from the owning document, rather than being resolved by a three-way lookup at read time. This is the rule the architecture already committed to (ADR-0003: scope is a declared column, snapshotted at write time, not derived at query time). A file with no resolvable store (a warehouse booking receipt, a legacy orphan upload) is stamped null and is therefore visible to no store-scoped user — the same fail-closed behaviour ptmapper already documents for orphan PT uploads.

**Desired behavior:**
- The file's owning store is recorded on the file at upload time, across all three upload paths (invoice, booking receipt, PT file).
- A download succeeds only if the caller is **entitled** to the file's store. Entitlement, not the top-bar unit switcher: a user entitled to Deoghar and Patna who happens to have Deoghar on screen may still download a Patna file (mirror `scope_by_entitlement`, not the switcher-narrowed read gate).
- A file outside the caller's entitlement returns **not-found (404)**, not forbidden — so ids cannot be walked to prove a file exists.
- A file that does not exist returns the same **404**, never a 500.
- A brand-scoped user (brand manager) has no store entitlement and so downloads no store-hung files; this is correct and intended.

**Key interfaces:**
- `StoredFile` gains a nullable store dimension, populated by the upload helper (`StoredFile.from_upload` or its callers) from the owning document's store. Existing rows backfill to null.
- The download view applies the existing entitlement gate before returning bytes, and resolves absent/out-of-scope identically to a 404.

**Acceptance criteria:**
- [ ] A stored file records the store it belongs to, set when it is uploaded, for all three upload paths.
- [ ] A user cannot download a file outside their store entitlement; a test asserts the refusal at the API seam using a file belonging to another location.
- [ ] An out-of-scope file and a non-existent file both return 404 (no 500, no distinguishable "exists but forbidden").
- [ ] Files with no resolvable store are downloadable only by an unrestricted (all-scope) user.
- [ ] `npm run ci` is green.

**Out of scope:**
- The public API schema / Swagger docs, and the CSRF wildcard default — split to their own issue.
- The password policy — split to its own issue.
- Any other endpoint's scoping (#94 owns the wider audit, #101 owns bookings). How warehouse/HO booking receipts (null destination store) are scoped follows #101's decision, whatever it lands on.
- Demo credentials on the login screen and JWT storage — consciously deferred to the pre-go-live pass.

## #110: Brand scope becomes a real restriction, everywhere
Labels: deferred-access

> **Rewritten 26 July 2026 against the ruling in #104.** The body is the spec. The issue's first question — "ratify the axis, or drop it" — is answered: **ratified.** Everything else here stands.

## Parent

#104 — PRD: Who may do what (the actor model). **Read the PRD body first.**

## What to build

Brand stops being a label on a screen and becomes a real restriction.

**The ruling, settled 26 July:** a Brand Manager sees and acts on **their own brands only, in every store, on every screen and report** — stock, sales, margin, bookings, returns, offers. It is how they are paid and measured, and other brands' margins are not their business.

Today the word "Assigned brands" is display context and nothing enforces it. The `brand` scope axis was introduced alongside store/entity/region, works for stock and nothing else, and a safety fix made everything it cannot narrow **fail closed** — which stops the leak and leaves a brand manager staring at empty Approvals and Receive Goods screens that the ratified table grants them.

Three pieces:

**1. Ratify the axis in the ADRs.** ADR-0003 and ADR-0007 both say a user's scope is `all / entity / region / store-group / store` over LegalEntity → GSTIN → Store, with brand as a ledger dimension column and never a scope. #104 rules brand a real axis, so those ADRs must be amended consciously — per the rule on the architecture page that a design breaking a rule changes the rule first.

**2. Give the brand-less surfaces a brand dimension.** Approvals, GRNs, PT files and outbound documents carry no brand, so nothing can prove a row belongs to a brand manager. Decide per surface whether brand belongs on the row and how it is snapshotted at post time (the dimension rule in `CONTEXT.md`), then cross by it instead of failing closed.

**3. Replace the free-text brand match with a link to the brand master.** Stock brand fields are text holding whatever the PT printed, matched case-insensitively against a brand name that is not even unique. `PETER ENGLAND LTD`, `PE`, padded cells, punctuation and aliases all silently miss — and the manager gets a blank screen with no signal that anything was filtered.

## Acceptance criteria

- [ ] ADR-0003 and ADR-0007 cover brand as a ratified scope axis
- [ ] A Brand Manager sees their brands' rows — not zero, not everyone's — on every section the ratified table grants them
- [ ] Brand matching survives a renamed master and a PT that prints a variant spelling
- [ ] A Brand Manager filtered to nothing is told so, rather than shown an empty screen
- [ ] `npm run ci` green

- #130 — the ratified nine-role table.

## #101: Booking endpoints are unscoped — give the store person `booking: view` for their own store only

## The ruling

The hand-drawn Store Ops sketch files **Booking** under the store person's Inventory heading.
The ratified RBAC sheet gives the store person `booking: (none, "No")`.

Anand's ruling, 25 July 2026:

> They can only view what was booked for them for that particular store - just the view of what was booked for that particular store.

So: **`booking: view`, own store only, read-only.**

This is the third time the sketch has beaten the sheet, and unlike the first two it overturns an explicit "No" rather than filling a gap, so it is recorded as a ratified correction in the `rbac_matrix` module docstring - **by #130, not here.** After #130 lands, verify the cell and the docstring read as this ruling says before building on them.

## Why this is a bug, not just a grant

**The booking endpoints are unscoped today.**
The booking list-and-create view and the booking detail view both carry `permission_classes = [IsAuthenticated]` and nothing else.
The list filters only on user-supplied `status` / `brand` / `season`; the detail view has an unfiltered class-level queryset.

Any authenticated user can read the entire company's booking book, and fetch any booking by id.
The only thing keeping a store person out is that the sidebar hides the section, and **the sidebar is not the security boundary** (ADR-0003).
This is exactly the drift class #94 documents.

Flipping the matrix cell without building the scope would turn a hidden hole into an open one - which is why this issue must land close behind #130.

## What already exists - verified, don't re-derive

- **The predicate.** "Which bookings touch these stores" is already written, three times over: in the search app's booking doc-type, inline in the inbound app's pending-bookings view, and copied again in the multistore-booking test. All three read the same rule - a line's effective destination is its own store, or the booking's default when unset, and the booking is visible if **any** line lands here.
- **The general mechanism.** `masters/scoping.py` holds `visible_store_ids(user)`, `active_store_ids(user)` and `scope_by_store(qs, user, field=...)`, already consumed by inbound, outbound, stockledger, approvals, ptmapper, search and masters.
- **The columns.** `Booking.destination_store` and `BookingLine.store` both exist and are migrated. **No schema migration is needed for the scoping** - the matrix-cell data migration is #130's.
- **`0006`'s guard is now correct.** #100 is closed. If any follow-up migration is ever needed here, copy `0006` **as it now stands**: forward asks "is this still the seeded default?", reverse asks "is this still exactly what I wrote?", matching capability *and* label.

## The three settled design calls

### 1. Line-level rule: redact and re-derive, not header-only

The predicate decides which bookings you see. Nothing decides which **lines within one**.
The booking serializer embeds every line unfiltered, each exposing its store, and the totals are network figures - `booked_total` and `received_total` sum all lines, and `estimated_value_paise` is a **stored** field written once over all lines.

On a booking spanning Deoghar and Ranchi, a Deoghar user would see Ranchi's styles, quantities and money.

**Settled:** a store-scoped caller sees only the lines landing at their store, and the totals are recomputed from that visible subset.
Header-only was rejected because it fails the criterion below - the stored network value would still ship.

- `estimated_value_paise` must be recomputed at read time for a scoped caller and **never returned raw**. Do not mutate the stored value.
- `status` is judged across all lines. Return the booking's real status; do not present it as the store's status.
- **No new payload field.** The "this is your share, not the booking" fact is recorded as a serializer docstring plus a field-level note. An unrestricted caller's payload must be byte-identical to today.

### 2. The redaction belongs in the serializer, not the view

The inbound app's pending-bookings view serialises the **same** booking serializer to store staff today, with every line.
It has the identical leak, and it is the endpoint a store person actually reaches right now.

If the redaction lives in the serializer - reading the caller off the request in context, and no-op when the caller is unrestricted - both paths are fixed by one change.
If it lives in `get_queryset`, the bookings hole closes and the receive-goods hole stays open behind the same ruling.

**Serializer.** This is not scope creep: it is the cheaper place to satisfy a criterion already written, and it avoids writing the rule twice.

### 3. Brand manager: unchanged, deliberately

`brand_manager` holds `booking: (operate, "Create")` and is `scope_type="brand"`, so `visible_store_ids` answers `None` - which `masters/scoping.py` is explicit must never be read as "show everything".

Narrowing them by brand is possible, and is deliberately **not** done here.
A brand-scoped caller keeps today's behaviour on this endpoint.
Narrowing them is a fresh access decision affecting a persona this ruling never mentioned, and #94 owns the wider audit.
**Add a test that pins today's behaviour**, so the change, when it comes, is a conscious one.

Owner, HO, warehouse and accounts: byte-identical to today.

## What to build

- [ ] Promote the booking predicate into `masters/scoping.py` beside `scope_by_store`: takes a queryset and a user, returns it unchanged when the caller is unrestricted, and the `distinct()`-ed filter otherwise. Fail-closed - an unrecognised or empty scope means no rows, never everything.
- [ ] Point the **three** existing copies at it: the search doc-type, the inbound pending-bookings view, and the test copy. The test copy matters: leave it and it drifts from the code it guards.
- [ ] Feed it from **`active_store_ids`**, not `visible_store_ids` - both existing callers do, and this is a read, so it follows the unit the person is looking at.
- [ ] Apply it to the booking list and detail querysets. Another store's booking fetched by id returns **404** from queryset exclusion, not a post-hoc 403.
- [ ] Gate the endpoints **per action**. `require_section` is method-blind: gating a list-and-create view at `view` would let a store person **place a booking**, contradicting the ruling. Reads need `booking >= view`; writes need `booking >= operate`. Build that as a method-aware sibling of `require_section`, so the next section gets it free.
- [ ] Gate **three** endpoints, not two: list, detail, and the booking **draft** endpoint, which is still `IsAuthenticated`. Draft does not persist a booking but it is the first step of creating one, so it needs `operate`.
- [ ] Redact lines and re-derive totals in the serializer (see settled call 1 and 2).
- [ ] Verify #130 landed the store person's `booking: (view, "Own store")` cell, its migration, and the third docstring correction - **do not write them here.** If the cell is absent, stop: this issue is mislabelled and #130 has not run.
- [ ] **Flip the test that asserts the opposite.** The global-search test currently states that a store person has no Booking section and so cannot see a booking landing at their own store. The ruling reverses it. Invert it in the same change - a store person now sees their own store's bookings in search, and still does not see another store's. Do not leave it to fail.
- [ ] Confirm, don't change, the **no-store policy**: a booking with no store on the header and none on any line (booked at HO, allocated later) is invisible to every store-scoped user. That is deliberate and consistent with the ruling, and it means a store sees nothing until lines get stores. Assert it **at the endpoint**, not only against a re-typed predicate.
- [ ] Keep it read-only. There is **no** update or cancel endpoint for bookings at all, so "a store person cannot update or cancel" is already true - just assert it.

## Acceptance criteria

**Scope**

- [ ] A store-scoped user listing bookings receives only bookings with a line landing at one of their stores
- [ ] A store-scoped user fetching another store's booking by id gets a 404, not the record
- [ ] Within a booking spanning several stores, a store-scoped caller cannot see another store's lines, quantities, store names or values through **any** field of the payload
- [ ] `booked_total` and `received_total` returned to a store-scoped caller equal the sum over the lines that caller can see
- [ ] `estimated_value_paise` returned to a store-scoped caller is recomputed from the visible lines; the stored value on the row is unchanged
- [ ] The same redaction applies on the **receive-goods pending-bookings** endpoint, because the serializer is shared - asserted there too
- [ ] A booking with no store on the header or on any line is invisible to every store-scoped user, asserted at the endpoint

**Access**

- [ ] A store person can read bookings and **cannot** create one - asserted with a POST returning 403 while their GET returns 200
- [ ] The booking draft endpoint refuses a store person
- [ ] A user whose `booking` capability is `none` gets 403 on list, detail and draft
- [ ] A contract test fails if the booking endpoints stop agreeing with `section_access_for(role)`, parameterised over all six personas, covering read and write separately

**No collateral damage**

- [ ] An owner / HO / warehouse / accounts / brand-manager booking list and detail payload is byte-identical to today
- [ ] A test pins the brand manager's current unrestricted behaviour on this endpoint
- [ ] No new field appears in any payload

**Tidiness**

- [ ] The booking-scoping predicate exists in exactly one place: a grep for the duplicated filter returns **one** hit, and the test no longer carries its own copy
- [ ] The search test that asserted bookings are invisible to a store person now asserts own-store visibility and other-store invisibility
- [ ] `npm run ci` is green

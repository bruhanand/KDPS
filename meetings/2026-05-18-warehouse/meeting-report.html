04Commercial Models

How money flows between KDPS, brands, and vendors.

Important gap from this meeting The SOR vs Outright distinction — flagged in the KDPS master plan as the single highest-ROI safety net in the system — was not discussed. The discussion below covers the commercial mechanics that were covered. Schedule a dedicated session with Priyo ji on SOR before the next schema iteration.

Brand-funded vs KDPS-funded discounts

When a brand declares an offer (e.g. Van Heusen says "Flat 40% on jackets / suits / blazers"), the brand reimburses KDPS for the discount. KDPS must report every such sale back to the brand monthly to claim that reimbursement. This is the engine of the 1st–7th crunch.

KDPS-funded discounts (typically for ageing or dead stock) come out of KDPS's margin.

Commission, payment cycle, payroll dependency

Brand owes KDPS commission
→
KDPS submits monthly report by ~5th
→
Brand releases commission by ~7th
→
KDPS pays staff salaries

Miss the report deadline → commission delayed → payroll delayed. This is why the crunch week is non-negotiable today and why automating it is the single highest ROI investment.

05The Agent Guarantor Model

A critical layer of the business that is not in the existing KDPS master plan.

How it works

KDPS does not pay vendors directly at the point of booking. In every major sourcing city — Mumbai, Kolkata, Indore, Raipur, Bangalore — a local agent sits in the middle:

  • Agent guarantees to the vendor that KDPS will pay within the agreed credit cycle (30 / 45 / 60 / 90 days)
  • Agent guarantees to KDPS that the vendor will ship on time and in correct quantity
  • Agent handles defect / short-shipment adjustments (e.g. 100 pieces billed but 96 usable → agent updates the ledger or arranges return credit)
  • Agent earns 1–2% commission

Bookings themselves are entirely verbal — no paperwork at the booking stage. KDPS as a "known group" relies on this trust network instead of a formal procurement system.

Implication for the build Agents must be modeled as a first-class entity in the new system — not a text field on the vendor master. They are the de-facto API for vendor management and they are where the Vendor + Agent CRM (see §14) needs to live.

06MRP & Margin Formula

The deterministic math KDPS applies to set retail prices.

MRP = Base Rate
      + 1.1% (flat transport cost, applied immediately on receipt)
      + GST (per HSN classification)
      + Margin
        ├── 25%       for branded items
        └── 30–35%    for non-branded items

What can change the margin?

  • Demand signal from the previous cycle's sell-through (example given: bought 1000 pieces last cycle, sold 800–900 → trend confirmed → can hold margin or raise)
  • Currently calculated from operator memory ("back of mind we know")
  • Future state: Fashion Demand AI feeds this calculation programmatically
Why this is automatable now The formula is deterministic and stable. The AI does not need to "decide" the margin — it only needs to apply the rule. The variable input (demand signal) can be served from sales data once it's flowing.

08The PT File System

The single most important operational artifact in KDPS. Everything is gated on this.

What is a PT file?

A Product Tracker file is KDPS's internal representation of an inbound shipment. It maps every line of a vendor invoice to system-loadable stock entries — each with a barcode, MRP, size, HSN code, brand, and style code. Until a PT file exists, the goods cannot be inwarded into the system, cannot be billed to a store, and cannot be scanned at POS.

Source: Master PT File (branded only)

For branded vendors, the brand sends a consolidated master PT file every 15 days containing every dispatch to KDPS in that period, filtered by zone (East zone covers Bihar, Jharkhand, etc.). It includes:

  • Invoice / reference number (matches the line-level invoice)
  • Style code (e.g. AS-..., AW-...)
  • Per-piece barcode (unique)
  • MRP, WSP, Gross WSP
  • HSN code

Operations lead pulls the relevant invoice's lines from this master, generates the store-level PT file, and uploads it to the legacy system.

Edge case: quantity duplication A PT file with rows like qty: 1, 1, 1, 1 for the same style code is not duplication — each row is a different unique barcode for the same SKU. A row with qty: 2 means two pieces sharing a single barcode (rare). This must not be "deduplicated" by the AI.

13Barcode Rules & Edge Cases

Source of barcodes

  • Branded: brand supplies; barcode is the unique identifier per piece
  • Non-branded: KDPS generates manually (today via the legacy system)
  • About 50% of "non-branded" vendors actually do supply some barcodes — but the other 50% are pure manual

Known failure mode: the Jockey problem

Same barcode, multiple MRPs

A barcode shipped in two batches with different MRPs creates an ambiguity in the legacy system. At the POS, scanning the barcode throws "Stock not available" even though the item is physically in the store. The salesperson then:

  1. Asks customer to wait
  2. Calls head office
  3. HO instructs: "Do manual billing, we'll fix backend"
  4. Customer leaves with goods + manually written bill
  5. HO retroactively repairs the system record

This is operationally embarrassing and creates an audit gap (room for fraud — see §17).

Design note for the new system The schema must treat barcode + MRP as a composite key when reconciling stock movements, and surface explicit warnings on dual-MRP scans rather than silently failing.

15Store Receipt & Scan

How stock formally becomes "in store" — and the friction that produces.

  1. HO bills the stock to a target store via the legacy panel
  2. Store sees a "pending" stock-transfer record
  3. Store opens the transfer and scans every barcode to receive
  4. Only after scan-receipt can the item be sold at POS (same barcode is re-scanned)
  5. If store doesn't receive within 24h, HO follows up: "Bhai receive karo, kab bechoge?"

The same barcode is therefore scanned at least twice per item lifecycle inside the store (once for receipt, once for sale). This is structurally fine; the friction is in the legacy POS being slow and ambiguous when MRPs collide.

16Store Layout Psychology

Insight from the Sanskar (Ratu Road) outlet that shapes category strategy.

The Sanskar finding

  • Ground floor: 100% women's apparel
  • First floor: 100% men's apparel
  • Women's share of total sales: 70–72%

Stated reasoning: men buy clothes only when needed; women shop for ~12 distinct occasions per year. Convenience-first placement keeps women on the ground floor; men will climb stairs if they need to.

Implication for the build The non-branded female category (sarees, kurtis, kids' wear, petticoats) is simultaneously the operational center of gravity and the worst data-hygiene zone. Prioritize this workflow first — it is the hardest and the highest impact.

17Season Tagging

A recently improved discipline that the new system can lean on.

  • KDPS has been tagging stock with season for the last 8–9 months
  • Goal: floor staff can read the season tag and the barcode to identify stock age, without escalation
  • Floor manager has up to 10% discount discretion on female-oriented stores; anything beyond requires higher management approval
  • Higher management can authorize larger discounts because they know the product's age and remaining margin

Category rules

Physical bifurcation constraint

Only 2–3 KDPS stores (named: Gaya, Hazaribagh) have enough floor area to physically separate "offer" merchandise from "fresh arrivals." Reference: an 8×8 wall holds ~800–850 piece-items, leaving no breathing room. In all other stores, the entire store goes on sale simultaneously.

This matters for the new system because discount enforcement cannot rely on "section" metadata — it must be barcode-level.

19Discount Fraud Loophole

A daily cash leak that does not require AI to solve.

The pattern

  1. An item is eligible for 40% off (brand-funded EOSS)
  2. Salesperson tells the customer the offer is 20% off
  3. Customer agrees, pays the discounted price
  4. Salesperson bills it manually or at the lower discount
  5. The 20% gap is pocketed as cash
  6. Laundering via exchange: if the customer later returns and asks to swap, KDPS policy is MRP-to-MRP exchange. The new item is the same MRP, so there's no discount-history audit trail.

Why it works today

  • Discounts communicated via in-store placards, not enforced at POS
  • Customer often doesn't get a printed bill ("system down, I'll WhatsApp it")
  • Per-bill human audit impossible at KDPS volume
  • MRP-to-MRP exchange policy ignores discount history

The fix

No AI needed Hard-code brand-eligible discounts to the barcode in the new system. The POS computes the discount automatically. Any sale where applied_discount < eligible_discount is flagged. This is rules-based, not ML.

Recommendation: pull this forward from Phase 2 (Anomaly Watchdog) to Phase 1. The leak is daily and the fix is small.
"India में ही तो... हम लूप होल ढूंढते हैं... तो वो भी loophole ही ढूंढता है system में। क्यों दें scope अगर मेरे पास opportunity है उसको रोकने का?" — Operations lead, on why this matters

20The 1st–7th Crunch

The single highest-value automation target in the entire build.

The week of hell

  • Brands require previous month's sales report — with per-SKU per-store discount cross-check — by ~5th of the month
  • If submitted on time, brand releases KDPS's commission by ~7th
  • If commission lands → KDPS staff get paid
  • If delayed → cascading payroll delay → not an option

What the team does

  • Core management (Ops lead, Tanmay, Ankit ji) work 18–19 hours/day, mostly from home, multiple screens
  • Every sale must be cross-checked: was the brand-eligible discount applied at POS? If not, KDPS retroactively applies it on the report so the brand still reimburses
  • All PT-file work goes on hold for 7 days
  • Days 8–15: clearing the PT-file backlog
  • Effective normal-operations days per month: ~10
Cost of doing nothing Half of every month is consumed by activity that AI can fully automate. The current setup also makes the team fragile — one person sick during crunch week and salaries are at risk. This is the highest-priority Phase 1 target alongside PT-file automation.

23Image Capture & File Hygiene

Today's failure mode

  • Store staff send crooked, low-res invoice photos via WhatsApp
  • HO straightens images in Photoshop before OCR
  • Folder structure (SS26/, per-store folders, pending folders) is hand-maintained
  • WhatsApp Web search fails: "could not find message"

Proposed fix

  • PWA capture screen on receiving handheld validates at capture: blur + skew detection
  • If unreadable: reject + force retake — "Data is not clear, redo it"
  • Auto-convert to PDF
  • Auto-rename: {InvoiceName}_{Brand}_{Date}.pdf
  • Auto-file into the canonical folder/database structure
Quick win This is a ~1-week feature that eliminates the Photoshop step and the folder-management tax entirely. Pure front-end discipline + naming convention.

24Vendor + Agent CRM

A module that should be added to the master plan.

Requirements raised in the meeting

  • Agents (the local middlemen in each sourcing city) should be able to log in
  • Agent can verify physical receipts against system entries from the field
  • If 100 pieces billed but 96 usable: agent logs the defect, system updates ledger or initiates return-credit-note
  • Supplier metadata: credit-day terms (30/45/60/90), payment status, brand affiliation
  • Existing operations team already maintains an Excel-style supplier record — that becomes the seed for this CRM

Why this is a missing module

The original KDPS master plan treats "Brand" and "Vendor" as masters but does not model the Agent as a first-class entity, even though the entire payment-guarantee and defect-resolution flow runs through agents. This needs to be added to the schema before vendor management is built.

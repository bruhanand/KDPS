Where the rules live

Lesson 6 showed the request reaching the Brain. This lesson opens stage 4 — the rules. This is the real KDPS: the four models, GST, return windows, "flag don't block." It's where your whole design becomes code.

Why this lesson: this is the box you'll review the most. Bad rules = wrong money, wrong stock, angry stores. If you can tell a good rule from a bad one, you can keep the AI honest where it matters most.

1 Two kinds of "rules"

Validation vs business logic

People say "the rules", but there are really two kinds, and they do different jobs. Keep them apart in your head.

🔎 Validation

"Is this request even sensible?"

  • About the shape of the data
  • Generic — same for any app
  • Runs first (stage 3)
  • e.g. sku_id present? qty a positive number?
⚖️ Business logic

"Is this allowed by KDPS's rules?"

  • About the business meaning
  • Special to KDPS — your design
  • Runs after (stage 4)
  • e.g. SOR return window, GST slab, commercial model

🧠 Simple test: if the rule would be true for any shop's software, it's validation. If it only makes sense because of how KDPS works, it's business logic.

2 Rules must live in the Brain

Never only on the screen

This is the single most important idea in the lesson. A rule on the screen alone is not a rule — it's a suggestion.

  • The screen can be skipped, edited, or have a bug.
  • A clever person can send a request straight to the Brain, with no screen at all.
  • So if the Brain doesn't check the rule, the rule does not really exist.

⚠️ The greyed-out button trap. The screen greys out "Discount" for a cashier — looks safe. But if the Brain accepts any discount request without checking the role, the rule is fake. The screen is for comfort; the Brain is for truth. (Screen checks are still nice — they give fast feedback — but the Brain must check too.)

3 Validation — the bouncer at the door

Reject broken requests early

Validation throws out a request that doesn't even make sense — before any real work. A bad request gets a 400 and stops.

// stage 3 — validate, before touching anything
if (!sku_id)        return res.status(400).json({ error: 'sku_id is required' });
if (qty <= 0)      return res.status(400).json({ error: 'qty must be positive' });

🛡️ The golden rule of input: never trust the screen. Always assume the data coming in could be wrong or harmful, and check it in the Brain. Good validation is the wall that keeps rubbish out of your ledger.

4 Business logic — the KDPS rulebook

Your design, turned into code

This is where your spine comes alive. The clearest example: what happens on a sale depends on the brand's commercial model (Lesson 1's four models, stored on the brand row from Lesson 4).

// when a sale happens — the rule branches on the model
const brand = await db.brand.find(sku.brand_id);

if (brand.commercial_model === 'SOR' ||
    brand.commercial_model === 'CONSIGNMENT') {
  // brand owns it → we owe the vendor a commission as it sells
  accrueVendorPayable(sku, qty, brand);
}
// BNS / CORRECTION → KDPS already owns it (vendor paid at inward) → nothing here

Read it as plain words:

  • Find the brand for this SKU.
  • If it's brand-owned (SOR / Consignment) → record that we now owe the vendor.
  • If it's KDPS-owned (Buy & Sell / Correction) → nothing; the vendor was already paid at inward.

Other KDPS business rules that live right here:

RuleWhat the Brain checks / does
Return windowIs today within the SOR/Correction window? Alert at 30 / 15 / 7 days.
GSTPick the right slab by HSN + date, add the tax breakup.
Correction allowanceIs this return within the brand's capped budget?
Offers / EOSSApply the brand's discount rules for this store and date.

5 A real rule in code: GST

Slab-based, date-based — so keep it as data

Let's make one rule fully real. Indian apparel GST is tricky in two ways:

  • It is slab-based — the rate depends on the item's price.
  • It is date-effective — the government can change rates over time.

So the golden rule: keep the rates as data (rows you can change), not as numbers hidden in code.

// the slabs live as DATA — easy to change, no code edit (example rates)
const gstSlabs = [
  { hsn: '6109', upto: 1000,     rate: 5  },  // garment under ₹1000
  { hsn: '6109', upto: Infinity, rate: 12 },  // ₹1000 and above
];

// the rule: pick the right slab, then compute the tax
function gstFor(item) {
  const slab = gstSlabs.find(s =>
    s.hsn === item.hsn && item.price <= s.upto);
  const tax = item.price * slab.rate / 100;
  return { rate: slab.rate, tax };
}

In plain words:

  • Look at the item's HSN code and price.
  • Find the matching slab (under ₹1000 → 5%, else 12%).
  • Compute the tax — the Brain works it out; it is never typed in.

💡 Why data, not code: when the government changes a rate, you edit one row in the slab data — no developer, no re-deploy. Real slabs also carry from / to dates, so the Brain picks the rate that was correct on the sale date. Never hard-code a single GST number.

❌ Hard-coded
  • tax = price * 0.05 sprinkled in code
  • Wrong for ₹1000+ items
  • Breaks the day rates change
✅ Slabs as dated data
  • One rule reads the slab table
  • Right slab by HSN + price + date
  • Rate change = edit a row

6 Flag, don't block

KDPS's special rule — know the difference

Here's a rule unique to your design, and it's easy to get wrong. There are two ways the Brain can respond to a problem:

🛑 Block
  • Stop. Reject the request.
  • For things that are broken or forbidden.
  • Returns an error (400 / 403).
🚩 Flag
  • Allow it — but raise a warning.
  • For things that are unusual but real.
  • Saves the work, marks it for review.

The KDPS rule: block only what's invalid or not allowed; for unusual-but-real business cases, flag — never stop the store.

SituationBlock or Flag?What the system does
sku_id missing🛑 Blockreject 400 — the request is broken
cashier not allowed to discount🛑 Blockreject 403 — forbidden
selling below cost price🚩 Flagallow the sale, raise a flag for review
return past the Correction budget🚩 Flagallow, but warn — D4 sorts the money
stock goes −1 (sold before inward)🚩 Flagallow — the ledger self-heals (L1); just note it

🏪 Why this matters: a real shop must keep selling. If the system blocked every odd case, the counter would freeze and staff would hate it. So KDPS lets business flow and lets the owner review flags later — block only the truly broken or forbidden.

7 Compute, don't trust

The Brain works out the numbers itself

Money and stock numbers must be calculated by the Brain — never just believed from the request. This connects straight to Lesson 4 (derived profit) and Lesson 5 (on-hand = SUM).

Value❌ Wrong — trust the screen✅ Right — Brain computes
GSTtake the tax amount from the requestwork it out from HSN slab + price
Profita typed-in fieldrevenue − cost
On handa number sent by the screenSUM of the movements
Bill totaltrust the screen's totalre-add the lines in the Brain

💡 Why: if you trust a number from the screen, anyone can send a fake one — a ₹1 bill total, a 0% GST. Compute it in the Brain and the truth can't be faked. Trust nothing the screen sends about money.

8 The service layer — one home for the rules

So rules aren't copy-pasted everywhere

Many endpoints need the same rules. A sale, a return, and an exchange all need GST and the four-model logic. Where should those rules live?

❌ Copy-pasted
  • The GST rule pasted into every endpoint
  • Fix a bug in one, forget the others
  • They slowly drift apart
✅ One service layer
  • The rule written once in a "service"
  • Every endpoint calls it
  • Fix it once, fixed everywhere

A service layer is the part of the Brain that holds the business rules. It splits the Brain into three thin layers:

LayerIts jobKDPS example
Endpoint (controller)receive request, call services, reply — stays thinPOST /sales
Servicethe business rules — the real worksalesService.makeSale() — GST, models, flag-don't-block
Dataread / write the databaseINSERT the movement
// the endpoint stays thin — it just calls the service
app.post('/sales', requireLogin, async (req, res) => {
  const result = await salesService.makeSale(req.body);  // all the rules live in here
  res.status(201).json(result);
});

🔎 Reviewer's tip: if you see the same rule copied across two or three endpoints, that's a smell — it belongs in one service. Thin endpoints + rules gathered in services means you always know where to look, and a fix lands in one place. This is just "rules live in the Brain" (§2) made tidy.

Git, your undo button

The single skill that turns "I'm scared to let the AI touch my code" into "go ahead — I can undo anything." It's one idea you already understand: a ledger, for your code.

Why this lesson: you want to build KDPS without fear. Fear comes from "what if the AI breaks it and I can't get back?" Git is the answer — a save point you can always return to. This is the safety net under every other build skill.

1 It's a ledger — for your code

You already know how this works

Remember the stock ledger from Lesson 1? Nothing is ever overwritten — every change is a new entry, the full history is kept, and the truth is the sum of all movements. Git is the exact same idea, applied to your code.

📒 Stock ledger: each movement (+5 GRN, −1 sale) is added, never edited — you can rewind to any past balance.
💾 Git: each commit (a save point) is added, never edited — you can rewind your whole project to any past state.

A commit is one save point: a snapshot of every file, with a short note. They line up in order, like ledger rows:

  • a1f3first working bill screen
    Monday — the counter sale works end to end.
  • 7c20add GST line to the bill
    Tuesday — your last good save point. 👍
  • …you let the AI add discounts — it breaks the whole screen
    Not saved yet. Just messy files on your machine.
  • git restore . → you're back at 7c20, instantly
    The broken mess is gone. Nothing good was lost.

💡 The whole point: because 7c20 is saved, the AI's mess is never scary. Worst case, you throw away everything since your last save point and you're exactly back where you started. That's the end of the fear.

2 The only four moves you need

See · Save · Undo · (Branch)

Git has hundreds of commands. As a vibe coder you start with four. That's genuinely enough to be safe.

git statusSee — what's changed since my last save point? Run it all the time.
git add . Stage — line up all my changes, ready to save.
git commit -m "…"Save — make the checkpoint, with a note like "add return-window alert".
git restore .Undo — the panic button. Throw away everything since the last save point.

Strung together, they make the fearless loop — the rhythm of vibe coding:

commit (good state)→ let the AI build→ works?→ yes → commit/ no → git restore .

The one habit that makes it work: commit before you let the AI loose, not after it's already a mess.

3 Branches — a safe sandbox

For the genuinely risky experiments

Sometimes you want to try something big — "let the AI rebuild the whole stock screen" — without risking your working version at all. A branch is a side copy of the project.

🌿 git switch -c try-discounts makes a sandbox. Experiment freely. If it works, fold it back in (merge). If it doesn't, switch back to main and delete it — your working version never even saw the experiment.

You don't need branches on day one — commit + restore already keep you safe. But the day you think "this might be a disaster," that's what a branch is for.

4 Undo, two ways: restore vs revert

The one question: have you saved it yet?

You've met git restore — the panic button. It has a sibling, git revert. They sound alike but answer different moments, and the whole difference is one question: has the change already been committed?

git restoregit revert
Use when…the change is not saved yet (loose files)the change is already a commit in your history
What it doeserases the changes — like they never happenedadds a new commit that cancels the old one
Historynothing recordedboth the mistake and the fix stay visible
Commandgit restore .git revert <commit>

📒 The ledger way to remember it: a customer return in your stock ledger is a revert — you don't go back and edit the original sale row, you add a +1 return movement that cancels it, and both stay on record. restore is the opposite: scrapping a draft before it ever became a real ledger entry.

Rule of thumb: uncommitted mess → restore.  Committed mistake → revert.

5 Two more things worth knowing

Cloud backup · keeping secrets out

1 · A remote — your cloud backup. So far, every save point lives only on your laptop. A remote (like GitHub) is a copy in the cloud. Two reasons you want one: if your laptop dies, your KDPS code is safe — and it's where the app will later be deployed to your stores from.

git pushSend your save points up to the cloud copy.
git pullBring down changes from the cloud copy.
git clone <url>Copy an existing cloud project onto your machine.

2 · .gitignore — what Git should never save. A small list of files to skip. Two kinds: auto-generated junk (big folders you don't need), and — far more important — secrets.

🔒 The golden safety rule: never commit a password, API key, or database login. Once it's in a commit it's in the history forever — even after you "delete" it later. Put such files in .gitignore before your first commit. This matters more for KDPS than almost anything else here — it holds money and customer data.

The database — your ledger, made real

In Lesson 2 you met "the Memory" — the box that never forgets. This lesson opens that box. Inside it's just tables, and one of them is the stock ledger you already designed. By the end you'll be able to read the tables the AI builds and check they match your spine.

Why this lesson: when the AI builds KDPS, it will create database tables. If you can read a schema — the list of tables and columns — you can catch the most expensive mistakes (a count pretending to be a ledger, lost size×color) before they're baked in. This is the single highest-leverage thing to check.

1 A database is just tables

Rows and columns — you already use these every day

A database is a set of tables. A table is like one sheet in Excel: columns are the fields, rows are the records. That's it. Your stock ledger from Lesson 1 is literally one table — every movement is a row:

💡 The number that isn't there: notice there's no "stock on hand" column. On hand = SUM(qty) for that SKU = 3. It's calculated, never stored — exactly the ledger rule from Lesson 1. New rows are only ever added; nothing is edited. If you ever see a single stock_qty column that gets updated on each sale, that's a count pretending to be a ledger — the red flag this whole system avoids.

2 How tables link together

Keys & relationships

You don't repeat a SKU's full details on every movement row — you'd never keep it consistent. Instead each thing lives in its own table, and rows point at each other by id. Two more tables sit behind that ledger:

Purple = primary key — the row's own unique id.   Blue = foreign key — a pointer to another table's id.

🔗 Follow the chain: a stock_movement points to a sku (via sku_id), and a sku points to its brand (via brand_id). So from any single sale you can walk: piece → SKU → brand → and the brand carries the commercial model. That's your whole Lesson-1 spine, living as data: set SOR once on the brand row, and every sale of its SKUs inherits it.

3 Reading a schema & the checks that matter

Your job when the AI builds the tables

A schema is just the blueprint: the list of tables, their columns, and how they link. When the AI builds KDPS it'll show you one. You don't write it — you read it and sanity-check it against your spine. Four checks catch the costly mistakes:

❌ Red flag — a count

A stock_qty column on the SKU that gets overwritten each sale. No history, no audit. This is the count Lesson 1 warned about.

✅ Want to see — a ledger

A separate stock_movement table where rows are only added. On-hand is summed, never stored.

❌ Red flag — lost size×colour

Stock tracked at style level only — no size and colour columns. Breaks "SKU = Style × Size × Colour."

✅ Want to see — size×colour survive

The SKU table has its own size and colour columns, end to end.

🔎 Two more quick checks: ① the commercial model lives on the brand (not copied onto every product), and ② money fields like profit are derived (no hand-typed profit column). If the AI's schema passes these four-plus-two, your spine is intact.

Request, response & APIs

In Lesson 2 you met "the Brain" — the box that decides. This lesson shows how the screen talks to the Brain: it sends a request, the Brain sends back a response. That back-and-forth is how every app works.

Why this lesson: the Brain is where your rules and money live — the box you'll review most. Before the rules, you need to see how a message reaches the Brain and comes back. That path is the request→response cycle.

1 Quick recap: the Brain

The box that decides

From the four boxes in Lesson 2:

  • 🖥️ Screen — shows things, takes taps. Knows nothing on its own.
  • 🧠 Brain — decides what is allowed. This lesson.
  • 🗄️ Memory — the database (you learned this in L4–L5).
  • 🔌 Outside world — other systems (Tally, POS).

The Screen cannot be trusted to decide anything. It only asks. The Brain decides and remembers. So the screen and the Brain must talk — and that is what we look at now.

2 The request → response cycle

Think of a restaurant

This is the heart of the whole lesson. Picture ordering food in a restaurant — it is the same shape as an app talking to its Brain.

#What happens🍽️ In a restaurant🧾 In KDPS (making a bill)
1You askYou tell the waiter your orderClerk taps "Bill" — the screen makes a request
2It travelsWaiter walks to the kitchenThe request goes over the internet to the Brain
3The Brain decidesKitchen checks: do we have it?Brain checks rules: SKU exists? price right? GST ok?
4It uses the storeCook takes items from the store roomBrain reads / writes the database (the ledger)
5It comes backWaiter brings the foodBrain sends back a response
6You see itYou eatScreen shows "Sold — stock now 4"

💡 The one idea: the screen asks (request), the Brain answers (response). Nothing else moves between them. Every feature you build is just a new version of this trip.

3 The API — the Brain's menu

Each thing the Brain can do has an address

The Brain does not do "anything you say." It offers a fixed menu of things it can do. That menu is called the API. Each item on the menu is one endpoint — a thing the Brain can do, at an address.

What the screen wantsEndpoint (the address)
See all SKUs/skus
See one SKU/skus/NK-AM90-WHT-8
Make a sale/sales
See today's sales per brand/reports/sales-today

So an endpoint = one specific job + one address. The menu (API) is the full list of jobs the Brain offers the screen.

4 The four verbs

What you want done — and how it connects to SQL

With each request the screen also says what kind of action it wants. There are four main ones — and look how neatly they match the database verbs you already learned in Lesson 5:

VerbMeans🍽️ In the kitchen🗄️ Database verb (L5)
GETread"show me the menu"SELECT
POSTcreate"make a new dish"INSERT
PUT / PATCHchange"change my order"UPDATE
DELETEremove"cancel that"DELETE

🔗 Connect it: a request like POST /sales usually ends up as an INSERT into the stock_movement ledger. The verb on the outside maps to the database action on the inside. Same idea, two layers.

5 What travels: JSON

The shared language for the message

The request and response carry data. That data is written in a simple format called JSON — just label: value pairs. Both the screen and the Brain understand it.

→ Request  (POST /sales)
{
  "sku_id": "NK-AM90-WHT-8",
  "qty": 1,
  "store": "Store-7"
}
← Response
{
  "status": "ok",
  "bill_no": "BILL#902",
  "on_hand": 4
}
  • The screen sends what it wants to do (sell 1 of this SKU at Store-7).
  • The Brain sends back what happened (saved as BILL#902, stock is now 4).
  • JSON is just text — easy to read, for you and for the computer.

6 Status codes — "ok" or "error"

How the Brain says what happened

Every response also carries a small number — the status code — that says how it went. You only need the families:

CodeFamilyMeansKDPS example
200 / 2012xx — goodit workedsale saved
4004xx — your faultthe request was wrongsku_id was missing
401 / 4034xx — your faultnot logged in / not allowedcashier tries a manager-only action
4044xx — your faultnot foundthat SKU does not exist
5005xx — Brain's faultthe backend brokea bug on the server

🧠 Easy way to remember: 2xx = good · 4xx = your fault (the request) · 5xx = the server's fault. When a screen shows an error, the code tells you which side to look at.

7 Inside the Brain — the 6 stages

"The Brain decides" is really six small steps

Earlier we said step 3 is "the Brain decides." That is not one action. Inside, every request passes through a line of stages, in order — like stations in the kitchen. Each stage can stop the request and send back an error.

#StageIts job🧾 KDPS (POST /sales)
1Routefind the right code for this address + verb"POST /sales" → the make-a-sale code
2Gatekeepers (middleware)run checks before any workAre you logged in? Are you allowed?
3Validateis the request well-formed?Is sku_id there? Is qty > 0?
4Business rulesapply the real logicSOR vs outright, GST, flag-don't-block (L7)
5Databaseread / write the ledgerINSERT a −1 movement; read on-hand
6Responseshape the answer + status code201 + { status: ok, on_hand: 4 }

🚦 It stops at the first "no". If the gatekeeper says "not allowed", the request stops at stage 2 and returns 403 — it never touches the database. If validation fails, it stops at stage 3 with 400. Only a clean, allowed request reaches the ledger.

🧠 One more idea — the Brain forgets you. After it sends the response, it remembers nothing about you. So the next request must again say who you are (it carries a small login "token"). This is called stateless — and it is why the gatekeeper runs on every request, not just at login. More in Lesson 8.

8 What an endpoint really looks like

Real code — and you can already read it

Here is the make-a-sale endpoint as actual code (this is JavaScript, using a common tool called Express). The circled numbers match the stages above.

// POST /sales  — make a sale
app.post('/sales', requireLogin, async (req, res) => {

  const { sku_id, qty, store } = req.body;        // ① read the request (JSON)

  if (!sku_id || qty <= 0)                          // ③ validate the input
    return res.status(400).json({ error: 'bad request' });

  const sku = await db.sku.find(sku_id);          // ⑤ ask the database
  if (!sku)
    return res.status(404).json({ error: 'SKU not found' });

  await db.stock_movement.insert({              // ⑤ write the ledger (−1)
    sku_id, type: 'SALE', qty: -qty, store
  });

  const on_hand = await db.onHand(sku_id);      // read the new balance (SUM)
  res.status(201).json({ status: 'ok', on_hand }); // ⑥ send the response
});

Read it line by line — it is almost English:

The codeIn plain words
app.post('/sales', …)"When a POST comes to /sales, run this."
requireLoginThe gatekeeper (stage 2) — runs first; blocks anyone not logged in.
req.bodyThe JSON the screen sent (sku_id, qty, store).
res.status(400)…Send back a status code + JSON. Here: "your request was wrong."
…insert({ … qty: -qty … })Write a movement row — negative, because it's a sale (the ledger!).
res.status(201).json(…)"Created. Here's the result." The response.

🌍 Different tool, same shape. In Python it reads almost the same — don't worry about the language, worry about the shape:

JavaScript (Express)
app.post('/sales', ...)
Python (Flask)
@app.post('/sales')
def make_sale(): ...

Both say the same thing: "for a POST to /sales, run this code."

9 What is REST?

The agreed habits for building an API

Good news: you already learned REST — just not the name. REST is a set of agreed habits for designing an API so it is predictable. An API that follows them is called RESTful.

REST habitIn simple wordsExample
Addresses are nounsname the thing, not the action/skus, /sales
The verb says the actionGET / POST / PUT / DELETE on that thingGET /skus · POST /sales
Status codes say the resulta number for ok / error200 · 404
Statelesseach request carries its own infotoken sent every time

💡 Why you care: when an API is RESTful, you can guess how it works — GET /skus lists SKUs · GET /skus/5 is one SKU · POST /skus adds one · DELETE /skus/5 removes it. Predictable APIs are far easier to build and to review.

📎 Note: REST is the most common style, but not the only one (you may hear "GraphQL"). For KDPS, expect REST. What matters is the habit: nouns + verbs + status codes.

10 Your reviewer's lens

What to check in any endpoint the AI builds

When the AI builds an endpoint — especially one that writes (POST / PUT / DELETE) — run down this short list:

CheckThe question to ask
Who is allowed?Does it check the user's role before doing the action? (L8 next)
Is the input clean?Does it reject a bad request (missing/odd values) with a 4xx?
Is the write scoped?Does the database write touch only the right rows? (the WHERE from L5)
Is the answer clear?Does it return a sensible status code and response?

🧭 Tie it together: a request comes in → the Brain checks who and what → it talks to the database → it sends a response. You now know the whole path. The next lessons go inside step 3 — the rules (L7) and who's allowed (L8).

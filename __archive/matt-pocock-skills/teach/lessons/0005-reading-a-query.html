Reading a query

A query is how you ask the database a question. They look intimidating, but almost every one is the same short sentence with the words in the same order. Learn the sentence, and you can read what any query does — and catch the one that's dangerous.

Why this lesson: you said the database is the thing you most need to own. This is the floor: when you review code or a schema, you'll constantly see queries. Being able to read one — "what rows come back, and is this safe?" — is the core review skill.

1 Every query is one sentence

SELECT … FROM … WHERE …

To read rows out of a table you use SELECT. It has three core parts, always in this order. Read it right-to-left as plain English:

SELECT name, mrp① which columns you want back
FROM sku② which table to look in
WHERE brand_id = 12③ keep only rows that match

In words: "give me the name and MRP, from the sku table, for rows where the brand is 12 (Biba)." You get a small result table back:

result
namemrp
Anarkali Kurti2,400
Cotton Suit3,100

🔑 SELECT picks columns, WHERE picks rows. That one distinction unlocks 80% of queries. SELECT * means "every column"; a missing WHERE means "every row".

2 Adding things up

SUM + GROUP BY — your stock-on-hand query

Now the one you asked about. To get stock on hand you don't read a stored number — you add up the movements. SUM() is an aggregate: it squashes many rows into one total.

SELECT SUM(qty) AS on_hand
FROM   stock_movement
WHERE  sku_id = 'NK-AM90-WHT-8';   -- +5 −1 −2 +1
result
on_hand
3

That's one SKU. To get it for every SKU at once, add GROUP BY — "do the SUM once per bucket":

SELECT sku_id, SUM(qty) AS on_handtotal per…
FROM stock_movement
GROUP BY sku_id;…each SKU bucket
result
sku_idon_hand
NK-AM90-WHT-83
NK-AM90-BLK-97

💡 The rule of GROUP BY: whatever you bucket by goes in GROUP BY, and the rest gets an aggregate (SUM, COUNT, AVG). Want on-hand per store? Just bucket by both: GROUP BY sku_id, store. This single pattern powers most of your dashboards — sales per brand, pieces per store, revenue per day.

SUM(x) — total of a column
COUNT(*) — how many rows
AVG(x) — average
ORDER BY x DESC — sort, biggest first

Filtering groups: WHERE vs HAVING

One more filter — and it trips everyone up once. WHERE throws out rows, before grouping. HAVING throws out whole groups, after — so it's the one you use to filter on a total.

SELECT   sku_id, SUM(qty) AS on_hand
FROM     stock_movement
WHERE    season = 'SS26'        -- ① per-row: only this season's movements
GROUP BY sku_id
HAVING   SUM(qty) < 3;          -- ② per-group: only low-stock SKUs

The clauses run in this order: WHERE → GROUP BY → HAVING. So when WHERE runs, the totals don't exist yet — which is exactly why WHERE SUM(qty) < 3 is an error, and you must use HAVING instead.

Filter on…Use
a plain column value (season, store, colour)WHERE
a total or count (SUM(qty) < 3, COUNT(*) > 10)HAVING

🍳 One-liner: WHERE filters the ingredients; HAVING filters the finished dish. The tell-tale sign: HAVING almost always contains an aggregate (SUM, COUNT…).

3 Combining tables — JOIN

Walking from one table to another by id

First, a shorthand you'll see in almost every real query: right after a table name you can give it a short nickname (an alias). FROM stock_movement m just means "call it m", so you can write m.qty instead of the whole table name every time. This query nicknames three tables:

stock_movement → m the sales
sku → s the products
brand → b the brands

Now the problem a JOIN solves. A sale row in stock_movement only stores a sku_id — a code like NK-AM90-WHT-8. It does not hold the brand name. To print "Biba" you have to walk across tables, matching ids. That walk is a JOIN.

Here's "today's sales per brand" — the two JOIN lines read as plain sentences:

SELECT b.name, -SUM(m.qty)brand name + pieces sold
FROM stock_movement mstart from the sales…
JOIN sku s ON s.id = m.sku_id…find each one's SKU
JOIN brand b ON b.id = s.brand_id…then that SKU's brand
WHERE m.type = 'SALE'only sale rows…
AND m.created_at >= CURRENT_DATE…from today
GROUP BY b.name;one total per brand

(-SUM(m.qty) because sales are stored as negatives — the minus flips the total back to a friendly positive count.)

🔗 The reviewer's read of a JOIN: the ON should always match a foreign key to the primary key it points at — here m.sku_id = s.id, then s.brand_id = b.id. If a JOIN matches unrelated columns, or has no ON at all, every row gets paired with every row — an explosion that's almost always a bug.

💡 Pieces vs money live in different tables. Piece counts come from the movement ledger (above). Rupee revenue comes from the bill, where the selling price sits — same JOIN shape, but summing a price column. Keeping stock and money apart is deliberate: documents write ledgers.

4 Reads vs writes — and the dangerous one

The safety check every reviewer makes

Everything so far was a read (SELECT) — it just looks, changes nothing. There are also writes, which change data:

INSERT — add a new row
UPDATE — change existing rows
DELETE — remove rows
SELECT — read only (safe)

Here's the trap. On an UPDATE or DELETE, the WHERE decides which rows are hit. Forget the WHERE, and it hits every row in the table:

-- 😱 NO WHERE — this zeroes out EVERY movement, for every SKU
UPDATE stock_movement SET qty = 0;

-- ✅ scoped — only this one document's rows
UPDATE stock_movement SET qty = 0 WHERE document = 'BILL#902';

🚩 The #1 thing to catch when reviewing AI-written SQL: an UPDATE or DELETE with no WHERE clause. It's the database equivalent of "delete everything." For a system holding money and stock, this is the review check that matters most. (Your ledger design softens the blow — it's append-only — but never let an un-scoped write through.)

🧭 Reviewer's reflex: for any query the AI shows you, ask three things — (1) Read or write? (2) Which table? (3) What's the WHERE — does it scope to exactly the rows I mean? Answer those and you know what the query will do, and where its effects will land.

5 A method to read any query

How to think, in order — even with a scary one

Here's the single most useful habit. A query is written in one order, but it's far easier to read it in a different order — the order the database actually does the work. Beginners read top-down and get lost in SELECT before they even know what they're selecting from. Don't.

How it's written (top→bottom)

  1. SELECT
  2. FROM / JOIN
  3. WHERE
  4. GROUP BY
  5. HAVING
  6. ORDER BY / LIMIT

How to read it ✅

  1. FROM / JOIN
  2. WHERE
  3. GROUP BY
  4. HAVING
  5. SELECT
  6. ORDER BY / LIMIT

🚦 Step 0 — read or write? Glance at the first word. SELECT = a safe read. INSERT / UPDATE / DELETE = a write that changes data — and your eyes go straight to its WHERE.

Then walk these six steps, picturing the rows shrinking at each one:

  1. FROM / JOIN "What am I starting from?" Find the table(s). If there are JOINs, picture each row with its matches attached — one combined set of rows.
  2. WHERE "Which rows survive?" Apply the filter and throw the rest away.
  3. GROUP BY "Am I bucketing rows into piles?" If yes, picture one pile per group. (No GROUP BY but an aggregate like SUM? The whole thing is one pile.)
  4. HAVING "Which piles survive?" Filter the groups — usually on a total.
  5. SELECT "What does each output row show?" The columns and aggregates you get back. You read this late because it describes the output, not the source.
  6. ORDER BY / LIMIT "Sorted how, and how many rows?"

The method on our query

Apply it to "today's sales per brand" and it reads itself:

① FROM stock_movement m + JOINseach sale, with its SKU & brand attached
② WHERE type='SALE' AND todaykeep only today's sales
③ GROUP BY b.nameone pile per brand
④ (no HAVING)keep all piles
⑤ SELECT b.name, -SUM(m.qty)each row = a brand + its pieces sold
⑥ ORDER BY pieces_sold DESCbest-selling brand on top

🧠 The one-sentence habit: read FROM first, SELECT almost last. Start with "what rows am I working on," shrink them step by step, and only at the end ask "what do I show." Do that and even a 30-line query becomes a short story you can follow.

Chapter 11 · The read side

Reporting, Dashboards & Printing

The read side of the ERP: Report Builder vs Query vs Script reports, financial statements computed over the GL, dashboards / charts / number cards, and the Jinja print-format engine.

Why the read side decides whether your ERP survives

Everything in the previous ten chapters builds the write side: doctypes that capture business events, lifecycles that submit them, ledgers that record them as immutable truth. This chapter is about the read side — turning that truth back into something a human acts on: a balance sheet, a brand-profitability report, a KPI tile on a phone, a printed tax invoice. It looks like the least glamorous part of the system. It is, in practice, the part that determines whether the ERP is still being used in five years.

The reason is leverage. A live ERP grows a long tail of read requirements — every department, every owner, every auditor wants their cut of the data, sliced their way, printed on their letterhead. If each of those is a new screen, a new endpoint, a new SQL file shipped in a release, the read layer becomes a bottomless engineering backlog and the business waits weeks for a column. The durable ERPs solve this once: they make the read layer metadata plus a thin compute function, so adding a report, a chart, a KPI, or a print layout is a data change, not a code change. That is the single idea this chapter unpacks across reports, dashboards, and printing.

The governing principle

The read side is built as metadata over an immutable ledger. Reports are records with a type discriminator and a fixed compute contract; financial statements are computed live from the ledger, never stored; dashboards are records describing what to aggregate; print formats are templates rendered against the saved document. One generic runtime — filter form, pagination, export, permission check, caching, PDF — serves them all.

Two laws inherited from the accounting engine set the boundary of this chapter. Documents post the ledger; reports only read it. Nothing on the read side ever writes a balance, mutates a posting, or stores a derived total it cannot reconstruct from raw rows. The read layer is pure projection. Once you internalize that, the financial-statements engine below stops looking clever and starts looking inevitable.

Where the read side sits

In the five-layer vocabulary (master data → documents → ledgers → controls → intelligence), reporting, dashboards and printing are the intelligence band — plus a print sub-pipe hanging off the document layer. Crucially the band is a read-only consumer of everything below it; the arrows only point upward.

Part A — Reports: one storage doctype, three flavors

The first and most important architectural move is refusing to build three report subsystems. Report Builder, Query Report, and Script Report are not three products — they are one Report record with a discriminator that says how to run it. The expensive shared machinery — rendering the filter form, paginating, exporting to Excel, checking roles, caching, queuing heavy ones — is written once and serves all three.

Pattern

One storage doctype, three report flavors selected by a field

The idea

Build one report record type with a discriminator that says how to run it: saved columns (no code), an embedded SQL string, or a code module. The runtime — filter form, pagination, export, role-check, caching — is shared across all three.

The flavors are a spectrum of escape hatches: declare it if you can, write SQL if you must, drop to code only when you truly need to.

How ERPNext does it

Every report is a Report doctype stored as <name>.json with report_type in {Report Builder, Query Report, Script Report}.

  • Builder stores selected fields+order_by in a json blob — erpnext/stock/report/item_wise_price_list_rate/item_wise_price_list_rate.json.
  • Query stores a raw SQL string in query — erpnext/selling/report/customers_without_any_sales_transactions/customers_without_any_sales_transactions.json.
  • Script points to a sibling .py whose execute() returns the data — erpnext/accounts/report/general_ledger/general_ledger.json → general_ledger.py.

All carry ref_doctype, roles, is_standard, prepared_report.

Apply to any ERP

On Django/Postgres: a Report model with a type enum.

  • Builder = saved JSON of columns+filters fed to your generic list/queryset endpoint.
  • Query = a stored, parameterized SQL string — whitelist tables, bind params, never f-string user input.
  • Script = a dotted path to def execute(filters) -> (columns, rows, ...).

One serializer, one exporter, one permission gate serve all three.

The Report-Builder flavor: zero code

A Report Builder report is the cheapest thing in the system: it stores only the chosen columns and sort order as JSON and runs entirely through the framework's standard list query for its ref_doctype. No SQL, no Python. This is the right default for "show me these fields of this doctype with these filters" — the bulk of everyday operational reports. A user clicks columns into existence in the UI; what gets saved is a few lines of JSON.

The Query-Report flavor: SQL with the type in the alias

When a join or a sub-select is needed but no procedural logic is, a Query Report embeds a raw SQL string directly in the Report record. The clever (and slightly dangerous) Frappe convention is that each column's type is encoded in its SQL alias as label:fieldtype/options:width. The renderer parses the alias to know that a column is a Link to Customer (so it draws a clickable chip 120px wide) versus a plain string — without any separate column metadata.

SELECT
  `tabCustomer`.name          as "Customer:Link/Customer:120",
  `tabCustomer`.customer_name as "Customer Name::120",
  `tabCustomer`.territory     as "Territory:Link/Territory:120"
FROM `tabCustomer`
WHERE not exists(select name from `tabSales Invoice`
        where `tabCustomer`.name = `tabSales Invoice`.customer
          and `tabSales Invoice`.docstatus=1 limit 1)

erpnext/selling/report/customers_without_any_sales_transactions/customers_without_any_sales_transactions.json

Gotcha — SQL injection & the alias convention

Query Reports interpolate the SQL string directly, and the "Field:Link/Doctype:120" alias trick is a Frappe convention your renderer must parse. If you copy this pattern, parameterize binds and whitelist tables — a naive port that f-strings user filter values into the SQL is a textbook injection hole. Treat the alias-encoded column type as a presentation convenience layered on top of a parameterized query, never as an excuse to skip binds.

The Script-Report flavor: a pure compute function

For anything with real logic — period columns, tree rollups, derived summary cards — a Script Report is a Python module whose execute(filters) returns a fixed tuple. Three sibling files make up the report, each owning one concern:

<report>.json
Metadata: ref_doctype, roles, prepared_report, report_type: "Script Report".
<report>.js
The filter form, declared as data: frappe.query_reports[name].filters = [{fieldname, label, fieldtype, options, default, reqd}] — erpnext/accounts/report/general_ledger/general_ledger.js.
<report>.py
The compute: execute(filters) returning the result tuple.
<report>.html
Optional — a Jinja print template for the report itself (distinct from a document Print Format).

The fixed execute() contract

Pattern

Script Report fixed execute() contract

The idea

A coded report is a pure function: it takes filters and returns a fixed tuple of column-definitions, row-data, and optional message/chart/summary. Columns are data (label, fieldtype, options, width), not HTML.

Because columns carry their type, one generic renderer can draw any report, format each cell correctly, export it to Excel, and print it — without knowing anything about the report's subject.

How ERPNext does it

execute(filters=None) in each <report>.py returns the 6-tuple columns, data, message, chart, report_summary, primitive_summary.

columns are dicts like {fieldname, label, fieldtype: 'Currency', options: 'currency', width} built by get_columns() in erpnext/accounts/report/financial_statements.py.

The .js sibling declares the filter form as data — erpnext/accounts/report/general_ledger/general_ledger.js.

Apply to any ERP

Define a typed return contract: Column(fieldname, label, type, options, width) + rows: list[dict] + optional chart/summary.

Build one front-end table component (React) that reads column types to format cells — Currency, Link, Date — so every report renders, sorts and exports through the same widget.

Keep filter definitions declarative JSON so one form widget renders every report's filters.

Here is the contract made concrete. The profit-and-loss statement is almost insultingly small — it is literally Income minus Expense, both computed from the GL, then packaged into the fixed return tuple:

def execute(filters=None):
    period_list = get_period_list(...)
    income  = get_data(filters.company, "Income",  "Credit", period_list, ...)
    expense = get_data(filters.company, "Expense", "Debit",  period_list, ...)
    net_profit_loss = get_net_profit_loss(income, expense, period_list, ...)
    data = []
    data.extend(income or []); data.extend(expense or [])
    if net_profit_loss: data.append(net_profit_loss)
    columns = get_columns(filters.periodicity, period_list, ...)
    return columns, data, None, chart, report_summary, primitive_summary

erpnext/accounts/report/profit_and_loss_statement/profit_and_loss_statement.py

Gotcha — variable-length returns

execute() is documented as a 6-tuple, but most reports return only the first two or three elements — columns, data and maybe message. Your runner must tolerate variable-length returns: unpack defensively as columns, data[, message[, chart[, summary[, primitive]]]] rather than insisting on exactly six. A strict six-tuple unpack will crash on the simplest report.

The payoff of "columns are data, not HTML" is enormous: a single React table component reads fieldtype: 'Currency' and applies INR locale formatting; reads fieldtype: 'Link' and renders a navigable chip; reads fieldtype: 'Date' and formats per locale. Add a new Script Report and it renders, sorts, filters, and exports for free — you wrote one renderer, not one per report.

Part B — Financial statements: computed live, never stored

This is the showcase of the whole read side and the single most important durable principle in the chapter. Every financial statement — Balance Sheet, P&L, Trial Balance, General Ledger, AR/AP aging — is recomputed from the immutable ledger on every run. There is no stored "account balance" table to drift. The books and the reports are the same numbers because the reports are the books, aggregated.

Pattern

Statements are live queries over the ledger, never stored

The idea

Financial reports are recomputed from the immutable ledger every time. There is no stored balance to go stale. Period columns and account-tree rollups are assembled in memory from raw ledger rows.

The consequence is a guarantee you cannot get any other way: the report can never disagree with the ledger, because there is nothing else for it to read.

How ERPNext does it

erpnext/accounts/report/financial_statements.py is a shared engine:

  • get_period_list() builds the column periods.
  • get_accounting_entries() queries GL Entry via frappe.qb (pypika).
  • calculate_values() buckets each entry into its period column as debit − credit.
  • accumulate_values_into_parents() rolls children up the CoA nested-set tree (lft/rgt).

Balance Sheet = get_data('Asset','Debit') + Liability + Equity — erpnext/accounts/report/balance_sheet/balance_sheet.py. AR aging is built from Payment Ledger Entry rows at request time — erpnext/accounts/report/accounts_receivable/accounts_receivable.py.

Apply to any ERP

Keep an append-only journal as the source of truth. Compute statements with SQL: a single GROUP BY over the journal joined to the Chart-of-Accounts tree (Postgres recursive CTE or a nested-set lft/rgt for rollups), bucketed by period via CASE/date_trunc.

Never cache balances unless you add an explicit, reconcilable closing-snapshot mechanism — and even then keep a raw-ledger fallback.

The engine in two functions

The entire financial-statement engine is two short loops. The first buckets every GL entry into the right period column as a signed debit − credit; the second walks the account tree in reverse lft order (so children are visited before parents) and adds each child's period totals into its parent. That second loop is how a leaf account's balance rolls up into "Current Assets" and then into "Total Assets" with no stored subtotals anywhere.

def calculate_values(accounts_by_name, gl_entries_by_account, period_list, ...):
    for entries in gl_entries_by_account.values():
        for entry in entries:
            d = accounts_by_name.get(entry.account)
            for period in period_list:
                if entry.posting_date <= period.to_date:
                    if (accumulated_values or entry.posting_date >= period.from_date):
                        d[period.key] = d.get(period.key, 0.0) + flt(entry.debit) - flt(entry.credit)

def accumulate_values_into_parents(accounts, accounts_by_name, period_list):
    for d in reversed(accounts):  # accounts ordered by lft (nested set)
        if d.parent_account:
            for period in period_list:
                accounts_by_name[d.parent_account][period.key] = \
                    accounts_by_name[d.parent_account].get(period.key, 0.0) + d.get(period.key, 0.0)

erpnext/accounts/report/financial_statements.py

Balance Sheet then composes three calls to the shared get_data() — Asset (Debit), Liability (Credit), Equity (Credit) — and the P&L composes Income (Credit) minus Expense (Debit). General Ledger and Accounts Receivable re-query GL Entry / Payment Ledger Entry at request time. There is no stored balance table anywhere in the path.

Gotcha — the closing-snapshot shortcut that can desync

"Statements are never stored" is the rule, but ERPNext quietly adds a performance shortcut: a Period Closing Voucher writes an Account Closing Balance snapshot, and set_gl_entries_by_account() will read from it (gated by the Accounts Settings ignore_account_closing_balance flag) instead of summing all history. If you reimplement only the snapshot and not the fallback to raw GL, your numbers can silently desync. Treat closing balances as an optimization with a reconcilable raw-ledger fallback, never the source of truth.

Gotcha — nested set vs recursive CTE for rollups

The account rollup depends on a nested-set tree (lft/rgt) kept correct on every insert/move. Nested set is fast to read but fragile to write — a reorder rebuilds a swath of the tree. On Postgres a recursive CTE is simpler and avoids the rebuild-on-reorder cost at some read cost. Pick consciously; do not inherit ERPNext's choice by accident.

Gotcha — cross-DB query building leaks DB quirks

frappe.qb (pypika) emits DB-specific SQL. erpnext/accounts/report/financial_statements.py has explicit branches like a force_index hint (MySQL-only) skipped on Postgres, and Max()/Sum() wrapping of non-grouped columns purely to satisfy Postgres' stricter GROUP BY. A cross-DB query builder is convenient but leaks quirks at the edges — budget for it if you target more than one engine.

Applying to KDPS

This is the blueprint for every KDPS money report. Brand profitability, store P&L, dead-stock aging and EOSS margin must be computed live from the inventory + sales ledgers — cost from the PT/invoice at stock-in, revenue from POS at sale — exactly as ERPNext computes statements from GL Entry. Nothing is hand-entered or stored, which is precisely the "profitability is derived" rule, and it keeps Tally as the statutory book of record rather than a competing set of numbers. Because the reports aggregate the journals directly, size × colour survives end-to-end into the monthly brand reports — the report's grain is whatever the ledger's grain is.

Part C — Dashboards: charts and KPIs as records

A dashboard tile is the same idea as a report, shrunk to one number or one series. ERPNext models a chart or a KPI as a saved record describing what to aggregate over which doctype with which filter — and the framework compiles that record into a SQL aggregate. You only drop to code for the genuinely awkward cross-table metrics, through a named pluggable data source.

Pattern

Metadata-driven charts and KPI cards

The idea

A chart or KPI is a saved record describing WHAT to aggregate over WHICH doctype with WHICH filter — not bespoke code. The framework turns that record into a SQL aggregate.

Provide one escape hatch — a named server function — for the aggregations metadata can't express, so 95% of tiles are zero code and the last 5% are still pluggable.

How ERPNext does it

Dashboard Chart JSON: document_type, chart_type (Count/Sum/Average/Group By), value_based_on, based_on (date field), time_interval, timespan, filters_json — erpnext/stock/dashboard_chart/purchase_receipt_trends/purchase_receipt_trends.json.

Number Card JSON: document_type + function: Count + filters_json + dynamic_filters_json — erpnext/stock/number_card/total_warehouses/total_warehouses.json.

Escape hatch: a Dashboard Chart Source .py with @frappe.whitelist() @cache_source def get(...) returning labels + datapoints — erpnext/stock/dashboard_chart_source/warehouse_wise_stock_value/warehouse_wise_stock_value.py.

Apply to any ERP

Model Chart(source_doctype, agg_fn, value_field, group_field, date_field, interval, filters_json) and NumberCard(doctype, fn, filters). Generate the SQL from these fields.

Provide a registry of named server functions as an escape hatch (source='my_custom_fn') for cross-table or computed metrics, and cache their output keyed by (name, filters, timespan, user).

The escape hatch is worth seeing because it shows where the metadata stops. Warehouse-wise stock value can't be expressed as "aggregate one field of one doctype" — it sums Bin.stock_value grouped by warehouse — so it becomes a small whitelisted, cached function returning the chart's {labels, datasets} shape:

Gotcha — dynamic filters are user-contextual

A Number Card's dynamic_filters_json embeds executable expressions like frappe.defaults.get_user_default("Company") that run server-side per user. That is powerful — one card shows each user their own company — but it means the card's output is user-contextual. Your cache key must include the user / resolved defaults, not just the card name, or you will serve user A's number to user B.

The Workspace: a module landing page, also a record

The page that ties tiles together is itself metadata. A Workspace JSON lists the module's charts, number_cards, shortcuts and links (the doctype navigation), plus a content layout block. Building the Selling home page is therefore an exercise in declaring which existing chart and card records appear and in what order — not writing a dashboard page.

Applying to KDPS

Dashboards-as-metadata is how owners on WhatsApp and low-end Android phones get KPI tiles — today's sale, dead-stock value, top brands — without new code per metric. A KPI is a record ({doctype, agg_fn, value_field, filters}); adding "this week's exchanges" is a data insert. The per-user dynamic-filter trick maps to per-store scoping: the same "today's sale" card shows each store manager their own store. Keep the cache key store-aware.

Part D — Printing: a Jinja engine over the saved document

Printing is the part teams most often get wrong by building a second data pipeline — re-fetching, re-joining, re-formatting data just to put it on paper, then watching the printed invoice slowly diverge from the stored one. ERPNext refuses that. Printing is template rendering against the document object. The template reaches into the very same fields, child tables, locale formatters and translations the rest of the system uses, so what you store is exactly what you print.

Pattern

Jinja print engine over the saved document

The idea

Printing/PDF is template rendering against the document — not a separate data pipeline. The template accesses the same fields, child tables, locale-aware money formatters, translation, and a pluggable letter head.

So the printed artifact is provably the saved record, formatted — there is no second source that can drift.

How ERPNext does it

A Print Format doctype stores print_format_type: "Jinja", custom_format: 1, and an html Jinja string bound to doc_type — erpnext/selling/print_format/pos_invoice/pos_invoice.json.

The template uses {{ doc.name }}, loops {% for item in doc.items %} over child tables, formats money via item.get_formatted("rate") (currency/locale aware), translates via _("Invoice"), and injects {% if letter_head %}{{ letter_head }}{% endif %}.

Letter Head is a Frappe doctype; Company exposes default_letter_head and default_letter_head_report — erpnext/setup/doctype/company/company.json.

Apply to any ERP

Use a sandboxed template engine (Jinja2) with the document as context. Expose helpers: a locale money formatter, a translation function, and a letter-head/footer partial from a Letter Head table.

Store templates as records keyed by doc type so non-developers clone/edit them; render to HTML then PDF (wkhtmltopdf / WeasyPrint). Keep a standard (locked) vs custom (editable) flag.

The POS-invoice template is the pattern in miniature — letter head, translated labels, locale money, and a child-table loop, all reading the saved doc:

Gotcha — three flags decide which renderer runs

A Print Format carries print_format_type ("Jinja"), a custom_format flag, and a print_format_builder flag. The combination — not any single boolean — decides whether the raw html string is used versus a visual-builder layout. Don't assume one switch controls it; model the full combination explicitly or you'll render the wrong thing.

Gotcha — letter heads are split, document vs report

Company exposes default_letter_head (for documents) and default_letter_head_report (for reports) as separate fields. A single global header is a common oversimplification that bites the moment your report header must differ from your invoice header. Model two slots from day one.

Gotcha — standard vs custom ownership

is_standard: 'Yes' marks framework-shipped reports and print formats as read-only — owned by Administrator, synced from disk, overwritten on upgrade. User edits must clone to a custom copy or they vanish at the next release. Separate "standard" (code-managed, on disk) from "custom" (DB-managed, user-editable) records explicitly, the same way ERPNext does.

Applying to KDPS

The Jinja-over-document engine maps straight onto KDPS GST tax invoices and PT documents: one template per document type, locale-aware INR with Lakh/Crore formatting via get_formatted, the GST/HSN tax breakup looped from child rows, and per-store / per-state letter heads for the two GSTINs (Bihar and Jharkhand are distinct persons — the invoice header must carry the right GSTIN). Render HTML, then PDF through the existing code/scripts/generate-pdf.mjs helper. Because the template reads the saved document, the printed tax invoice is provably the stored one — exactly what an auditor wants.

Part E — Views and connections are configs, not endpoints

The last piece of the read side is the least visible: List, Report, Calendar, Gantt and Kanban are not five features — they are five presentations of the same stored records, each driven by a small declarative config. The "Connections" panel that shows a Sales Order's downstream documents is likewise a declaration, not hand-written joins.

Pattern

Views (List/Report/Calendar/Gantt/Kanban) are config over one doctype

The idea

The same stored records get many presentations from small declarative configs — not new endpoints. A list config adds status-color indicators and bulk actions; a calendar config maps which fields are start/end/title; the connections panel is a back-reference declaration.

How ERPNext does it

listview_settings[Doctype] = {add_fields, get_indicator(doc)->[label,color,filter], onload} — erpnext/stock/doctype/repost_item_valuation/repost_item_valuation_list.js.

frappe.views.calendar[Doctype] = {field_map:{start,end,id,title}, gantt:true, get_events_method} — erpnext/selling/doctype/sales_order/sales_order_calendar.js.

Connections: <doctype>_dashboard.py get_data() declares fieldname, non_standard_fieldnames and grouped transactions — erpnext/selling/doctype/sales_order/sales_order_dashboard.py.

Apply to any ERP

Build generic List, Calendar/Gantt and Kanban components that read a per-entity config: which fields to show, a status → color function, a date-field map, an optional grouping field.

Declare inter-entity links centrally (foreign key + label) so a "Connections" panel is generated, not hand-coded per screen.

The connected-documents panel makes the "declaration not code" point vividly. A doctype ships a tiny get_data() that names the back-reference fieldname linking children to it, any non-standard fieldnames, and how to group the related doctypes into tabs. The framework runs the link queries; you wrote no SQL:

        "fieldname": "sales_order",

        "transactions": [
            {"label": _("Fulfillment"), "items": ["Sales Invoice", "Delivery Note"]},
            {"label": _("Payment"), "items": ["Payment Entry", "Journal Entry"]},

Heavy reports: the prepared-report escape valve

One operational detail rounds out the read side. Some reports — a full stock balance across every warehouse and item — are too heavy to compute inside a web request. Rather than time out, the framework defers them.

A report record flagged prepared_report: 1 (for example the Stock Balance report) does not block. Frappe core runs execute() in a background job and stores the result as a Prepared Report document the user downloads when it's ready. From the user's side it is "request now, collect later"; from the system's side it keeps long aggregations off the request path.

The whole read side, on one page

Step back and the five parts are one architecture: metadata describing what to read, a thin compute function where logic is unavoidable, and one generic runtime that renders, exports, prints and caches. The table below is the same idea in five guises.

The payoff is the thing a long-lived ERP needs most: adding a report, a KPI, a chart, or a print layout becomes a data change, not an engineering project. The backlog of "can I get a column / a tile / a layout" stops being a release-gated queue and starts being self-serve metadata — which is the difference between an ERP that ossifies and one that keeps earning its keep.

Takeaways

  1. One report storage doctype, three flavors. A single Report record with a report_type discriminator — saved columns (Builder), embedded SQL (Query), or a code module (Script) — sharing one runtime for filter form, pagination, export, roles and caching. Don't build three subsystems.
  2. Columns are data, not HTML; execute(filters) is a pure function. Return typed columns (fieldtype, options, width) + rows so one generic table component renders, formats, exports and prints every report. Tolerate variable-length return tuples.
  3. Statements are computed live from the ledger, never stored. Balance Sheet, P&L, GL and AR/AP are SQL aggregates over the immutable journal, bucketed by period and rolled up the Chart-of-Accounts tree at request time — so the report can never drift from the books. Add closing snapshots only as a reconcilable optimization with a raw-ledger fallback.
  4. Dashboards are records, not code. A chart/KPI is {doctype, agg_fn, value_field, date_field, interval, filters} compiled to SQL, with a named-function escape hatch for cross-table metrics. Cache user-contextual cards by (name, filters, user).
  5. Printing is a template over the saved document. Render the record through sandboxed Jinja with locale money formatting, translation, child-table loops and a pluggable, document-vs-report letter head — so what you store is exactly what you print. Keep standard (locked) vs custom (editable) separate.
  6. Views and connections are small declarative configs over one entity. List indicators, calendar field maps, and the connected-documents panel are declarations the framework executes — not bespoke endpoints. Defer heavy reports to background "prepared reports" so phones never block.

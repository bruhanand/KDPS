Chapter 2 · Foundations

The Document Lifecycle & Controller Pattern

Draft → Submitted → Cancelled: the state machine every transaction obeys, the validate / on_submit / on_cancel hook chain, and why a submitted document must become immutable.

Why this subsystem is the spine of an ERP

An ERP is only worth building if its books can be trusted. Trust does not come from preventing every mistake at data-entry time — humans always fat-finger a rate or pick the wrong vendor. Trust comes from a guarantee about after the fact: that once a document has been posted, it can never be silently changed, and that every correction is itself a new, dated, traceable event. An auditor must be able to ask "what exactly did this invoice post, and when?" and get one unambiguous answer that nobody could have rewritten.

The document lifecycle is the mechanism that delivers that guarantee. In ERPNext it is astonishingly small at its core: a single integer column, docstatus, with three legal values — 0 = Draft (editable), 1 = Submitted (frozen / "posted"), 2 = Cancelled (reversed). Around that one column hangs the whole discipline of double-entry accounting and perpetual inventory: the moment a document moves from Draft to Submitted is the moment it writes to the ledgers; the only way back out is to Cancel, which reverses what was written.

Key idea

An ERP is trustworthy not because data can't be wrong, but because every posting is immutable and every correction is itself a new, traceable posting. The ledger only ever grows. That one sentence is the design contract this entire chapter implements.

This chapter walks the subsystem in the order you need it when building: the three-state machine, the ordered controller hook chain that hangs business logic off it, immutability and the cancel-and-amend correction path, how cancellation reverses postings on append-only ledgers, how human-readable status is derived rather than stored, and the deliberate "flag, don't block" split between hard invariants and soft policy limits. Each is presented as a reusable pattern: the durable idea, exactly how ERPNext implements it with file references, and how to rebuild it on a plain Django/Postgres stack.

Before the patterns, meet the documents. The lifecycle is a collaboration between a submittable transaction (the thing the user edits and submits), its child line items (which have no lifecycle of their own), the append-only ledgers it writes, and the settings singletons that supply the policy knobs the controllers read as they run.

Pattern 1 · The three-state submittable lifecycle on one column

Everything starts here. Every business document is a tiny state machine with exactly three states, and that state lives in one place so there is never any ambiguity about whether a document has been posted.

Pattern

Three-state lifecycle stored in one integer

The idea

A document is a state machine with three states — Draft (mutable), Submitted (posted, frozen), Cancelled (reversed). "Submit" is the one moment side effects fire (ledger postings); "Cancel" is the only way out and it reverses them.

This is the universal accounting concept of posting / unposting rendered as a two-bit column. The legal transitions are exactly Draft→Submitted and Submitted→Cancelled — nothing else.

How ERPNext does it

The Frappe base Document exposes docstatus (0/1/2) Frappe core. A doctype opts in with one line in its JSON: 

"is_submittable": 1

erpnext/accounts/doctype/sales_invoice/sales_invoice.json carries it. The framework then refuses ordinary edits once docstatus == 1, and ERPNext branches on the value directly to decide whether to post or reverse.

Apply to any ERP

On Django/Postgres add a docstatus smallint column with a DB CHECK (docstatus IN (0,1,2)) on every transaction table.

  • Expose submit() / cancel() service methods — never a raw UPDATE path.
  • Gate all writes: a row with docstatus >= 1 is read-only except through cancel.
  • Make submit() the single place that writes ledger rows, inside one DB transaction.

The crucial detail is that the lifecycle is data-driven by docstatus: the same method that posts when the document is submitted is reused, with a branch, to reverse when it is cancelled. The Sales Invoice's GL-posting method is the textbook example — one function, two regimes: 

if self.docstatus == 1:
    make_gl_entries(
        gl_entries,
        update_outstanding=update_outstanding,
        merge_entries=False,
        from_repost=from_repost,
    )
    self.make_exchange_gain_loss_journal()
elif self.docstatus == 2:
    make_reverse_gl_entries(voucher_type=self.doctype, voucher_no=self.name)

Gotcha · docstatus is the source of truth, not status

docstatus (0/1/2) is the framework's control variable. The human-readable status string ("Draft", "To Bill", "Cancelled"…) is derived from it (Pattern 5) and can drift if anyone sets it by hand. Never branch control flow on a stored status string — always recompute it, and key your guards off docstatus.

Pattern 2 · The ordered controller hook chain

The three-state machine is the skeleton; the business logic hangs off it as a fixed sequence of named hooks. ERPNext decomposes that logic into a deep inheritance chain so that each cross-cutting concern — tax math, stock movement, GL posting, status rollup — lives in exactly one layer, and the leaf document composes them with super().

Pattern

Lifecycle logic as ordered hooks layered by inheritance

The idea

Decompose lifecycle logic into named hooks that fire in a fixed order, and layer shared behaviour through a class hierarchy so each concern lives in one place. The leaf composes them with super().

This is the template-method pattern applied to a transaction: the framework owns the skeleton (when each hook runs); the subclasses fill in the steps.

How ERPNext does it

SalesInvoice.validate() calls super().validate() up into AccountsController.validate() for taxes, party and return validation (sales_invoice.py:289). on_submit() calls update_stock_ledger() then make_gl_entries() (sales_invoice.py:421); on_cancel() calls super().on_cancel() first, then its own reversal (sales_invoice.py:513).

Apply to any ERP

Build a base TransactionController with template-method hooks (validate / before_submit / on_submit / before_cancel / on_cancel) and subclass per concern (AccountingMixin, StockMixin).

  • The service layer calls the hooks in a fixed sequence inside one transaction.
  • On a non-OO stack, use an ordered list of registered handlers per event.
  • Always call the parent hook so invariants compose.

The two hooks that matter most are on_submit and on_cancel, because they are where the document touches the ledgers. Notice that on_cancel is the exact structural mirror of on_submit — same calls, same order, reversal regime — and that it opens by chaining to super().on_cancel(): 

def on_submit(self):
    ...
    self.check_prev_docstatus()
    self.update_prevdoc_status()
    if self.update_stock == 1:
        self.update_stock_ledger()
    self.make_gl_entries()

def on_cancel(self):
    super().on_cancel()
    self.update_prevdoc_status()
    if self.update_stock == 1:
        self.update_stock_ledger()
    self.make_gl_entries_on_cancel()
    self.db_set("status", "Cancelled")

erpnext/accounts/doctype/sales_invoice/sales_invoice.py — on_submit (:421) / on_cancel (:513)

Gotcha · on_submit and on_cancel must be exact mirror images

Every side effect created in on_submit (GL entries, stock ledger entries, prevdoc rollups, loyalty points, linked-doc updates) must be reversed in on_cancel, or the books leak. ERPNext pairs them line-for-line: make_gl_entries ↔ make_gl_entries_on_cancel, update_stock_ledger called in both, update_prevdoc_status in both. Forgetting one half is the classic reimplementation bug.

Gotcha · never override a hook without super()

The inheritance is six layers deep. Overriding validate or on_cancel without calling super() silently drops whole layers of invariants — tax math, party validation, status rollup — and you won't get an error, just wrong books. Always chain to super.

Pattern 3 · Immutability + cancel-and-amend

Now the heart of the trust guarantee. A posted financial or stock document must never be edited in place. Auditors need a permanent record of exactly what was posted. So to "change" a submitted document you do two things: cancel it (which reverses its ledger effects) and then amend it (create a new Draft that is a copy linked back to the cancelled original). The original, its reversal, and the amendment all persist forever; history is additive, never destructive.

Pattern

Cancel-and-amend instead of edit-in-place

The idea

A posted document is immutable. To correct it, post a reversal (cancel) and create a fresh draft that copies it and links back via an amended_from reference. The new draft re-runs the whole validate → submit chain and posts brand-new ledger entries.

Three rows now exist — original, reversal, amendment — and the audit trail is the complete chain, not a mutated record.

How ERPNext does it

Every submittable doctype carries an amended_from field — a no_copy, read_only Link to itself (sales_invoice.json: options: "Sales Invoice"). StatusUpdater.set_status keys off it: 

if self.get("amended_from"):
    self.status = "Draft"

The amendment gets its own naming-series name (e.g. ACC-SINV-2026-00042-1) and is validated from scratch.

Apply to any ERP

Give every document a nullable amended_from self-FK. Block UPDATE on submitted rows at the service/DB layer.

  • Provide one operation amend(original) that deep-copies the cancelled doc into a new draft with a new id and amended_from = original.id.
  • Re-validate and re-submit the copy — it posts fresh ledger rows.
  • The id convention (suffix -1, -2) lets you trace revision history.

The amendment is forced back to Draft the moment it is created, which is what re-arms the full lifecycle. The relevant slice of set_status: 

def set_status(self, update=False, status=None, update_modified=True):
    if self.is_new():
        if self.get("amended_from"):
            self.status = "Draft"
        return
    ...
    new_status = self.get_status()["status"]
    if new_status != _status:
        self.status = new_status
        if update:
            self.db_set("status", new_status, update_modified=update_modified)

The narrow exception: on_update_after_submit

There is exactly one sanctioned way to touch a submitted document without cancelling it: editing a small whitelist of fields via on_update_after_submit. Even this is not a free UPDATE — it re-posts the affected accounting:

erpnext/accounts/doctype/sales_invoice/sales_invoice.py:1149 implements on_update_after_submit and routes to repost_accounting_entries; the edit is guarded by the ignore_validate_update_after_submit flag (erpnext/controllers/accounts_controller.py:343). Everything outside that whitelist must go through cancel + amend.

Gotcha · amended_from must be no_copy + read_only, and the amendment needs a NEW name

If you copy amended_from as a regular editable field, or reuse the original id, you break both the audit chain and naming uniqueness. The -1 / -2 suffix convention is what lets you walk the full revision history of a document.

Gotcha · you cannot just UPDATE a submitted document

The only in-place edit is on_update_after_submit on a small whitelist, guarded by ignore_validate_update_after_submit, and even that re-posts accounting via repost_accounting_entries. If your "quick fix" path is a raw SQL UPDATE on a submitted row, you have abandoned the trust guarantee.

Pattern 4 · Cancellation reverses postings on append-only ledgers

Pattern 3 said cancel "reverses its ledger effects." This pattern is the concrete mechanism. Ledgers are append-only — you cannot delete a posted entry. So cancelling a document means posting equal-and-opposite entries (debit and credit swapped) so the net effect is zero, while both the original and the reversal survive. The document's on_cancel is the single owner of this reversal.

Pattern

Reverse by swapping debit/credit; never delete a ledger row

The idea

A ledger is INSERT-only. To undo a posting you insert its mirror — debit and credit swapped — so the running balance returns to where it was, while the table keeps both rows. The net is zero; the history is complete.

Every reversal row carries a back-reference to the source voucher so you can find, reverse and reconcile by document.

How ERPNext does it

general_ledger.make_reverse_gl_entries() selects the voucher's originals (where is_cancelled == 0 … for_update()), deep-copies each, swaps debit↔credit, stamps a "On cancellation of …" remark and re-posts (erpnext/accounts/general_ledger.py:607). StockController.make_gl_entries_on_cancel (erpnext/controllers/stock_controller.py:281) routes the stock side.

Apply to any ERP

Make ledger tables strictly INSERT-only — revoke UPDATE/DELETE, or enforce with triggers.

  • cancel(): load the doc's posted rows, insert reversal rows with debit/credit swapped + a voucher back-reference, all in one transaction with the docstatus flip.
  • Keep voucher_type / voucher_no (and an is_cancelled flag) on every ledger row.

The reversal loop is small and worth reading in full — it is the whole mechanism:

for entry in gl_entries:
    new_gle = copy.deepcopy(entry)
    new_gle["name"] = None
    debit  = new_gle.get("debit", 0)
    credit = new_gle.get("credit", 0)
    new_gle["debit"]  = credit
    new_gle["credit"] = debit
    new_gle["remarks"] = "On cancellation of " + new_gle["voucher_no"]
    new_gle["is_cancelled"] = 1
    if new_gle["debit"] or new_gle["credit"]:
        make_entry(new_gle, adv_adj, "Yes")

Two cancellation regimes — know which one you're in

ERPNext supports two ledger regimes, gated by is_immutable_ledger_enabled() (a toggle on Accounts Settings). The reverse-entries code branches on it, and copying the logic without noticing the branch produces wrong period balances.

RegimeWhat happens to the originalsWhat the reversal looks likeLedger shape
Classic Originals are flagged is_cancelled = 1 (mutated in place). Swapped reversal rows posted, also flagged is_cancelled = 1. Table is mutated; cancelled rows filtered out of reports.
Immutable ledger Originals left untouched (is_cancelled = 0). A dated reversal entry posted on the cancellation date (also is_cancelled = 0). Strictly append-only; period totals stay reproducible.
Gotcha · tell the link-checker to ignore the ledgers the doc owns

On cancel, ERPNext sets self.ignore_linked_doctypes = ('GL Entry', 'Stock Ledger Entry', …) (erpnext/accounts/doctype/sales_invoice/sales_invoice.py:564). Without it, Frappe's referential-integrity guard Frappe core would refuse to cancel a document that has dependent ledger rows — even though reversing those rows is the whole point of cancelling. If you build your own link-integrity check, you need the same escape hatch.

Gotcha · don't copy the reverse logic without the regime branch

Classic mode mutates originals; immutable mode never touches them and dates the reversal. Picking the wrong one gives you either a non-append-only ledger or balances that don't reproduce for a closed period. Decide your regime up front and make it explicit in cancel().

Pattern 5 · Derived status + cross-document propagation

A document's human-readable status ("Draft", "To Bill", "Completed", "Cancelled") is not stored ad hoc — it is derived from docstatus plus rollup fields (per_billed, per_delivered) through a declarative table of rules. And submitting a downstream document propagates fulfilment percentages back to its source and enforces over-fulfilment limits.

Pattern

Declarative status map + back-propagated rollups

The idea

Express status as a priority-ordered list of (status, predicate) rules over docstatus + rollup fields, and recompute it on every save. For document chains, keep per_billed / per_received columns on the source and update them transactionally when a downstream doc submits or cancels.

How ERPNext does it

StatusUpdater.status_map is a dict of [status, condition] pairs evaluated top-down (erpnext/controllers/status_updater.py:21). set_status / get_status compute it (:197 / :218). update_prevdoc_status() → update_qty() + validate_qty() roll child quantities up to the parent and call limits_crossed_error on overage (:193).

Apply to any ERP

Store a derived status string but compute it from a single declarative rule table ordered by priority; recompute on every save.

  • Keep rollup columns on the source; update them transactionally on downstream submit/cancel.
  • Validate cumulative fulfilment stays within a configurable tolerance.
  • Refuse to post against a predecessor that isn't itself submitted.

That last rule — refuse to post against an unsubmitted predecessor — is enforced by check_prev_docstatus (erpnext/accounts/doctype/sales_invoice/sales_invoice.py:1010), which you saw called first inside on_submit. The rollup chain looks like this on submit:

Sales Invoicesubmitted (docstatus 1)
update_prevdoc_statusroll billed qty up
Sales Orderper_billed += …
set_status"To Bill" → "Completed"
Note · status is recomputed, never trusted

Because status is derived, a stale or hand-edited status string is harmless to the books — the next set_status overwrites it from docstatus + rollups. This is exactly why control flow must key off docstatus, not the label.

Pattern 6 · Flag-don't-block validation

The last pattern is a discipline that runs through the whole lifecycle: distinguish hard invariants (must abort the transaction) from soft policy limits (warn, but let an authorised user through). Hard errors throw and roll the transaction back; tolerance breaches warn — and a privileged role can bypass the warning. This keeps real-world data entry unblocked without weakening the books.

Pattern

Hard invariants throw; soft limits warn with a role bypass

The idea

Two tiers of validation. Invariants that would corrupt the books raise and roll back. Policy limits (over-billing, over-receipt) emit a warning and proceed — optionally requiring a role to exceed.

Thresholds and override roles live in config rows, not code, so finance can tune tolerance without a deploy.

How ERPNext does it

Hard cases use frappe.throw(...) — 14 occurrences in erpnext/accounts/doctype/sales_invoice/sales_invoice.py, zero msgprint. Over-limit cases branch on role: limits_crossed_error throws OverAllowanceError for normal users, warn_about_bypassing_with_role msgprints for override-role holders (erpnext/controllers/status_updater.py:462).

Apply to any ERP

Split validation into two functions: invariants that raise (rolling back the transaction) and policy checks that warn and continue.

  • Drive thresholds and override-roles from config rows / a settings table.
  • Surface the warning to the UI but don't fail the write.
  • Gate the bypass on a permission the user holds.

The branch that downgrades a hard throw to a warning for an override role is the canonical example:

item["reduce_by"] = item[args["target_field"]] - item["max_allowed"]
if role not in frappe.get_roles():
    self.limits_crossed_error(args, item, qty_or_amount)        # frappe.throw(OverAllowanceError)
else:
    self.warn_about_bypassing_with_role(item, qty_or_amount, role)  # frappe.msgprint

erpnext/controllers/status_updater.py:462 — limits_crossed_error (:500) throws; warn_about_bypassing_with_role (:521) msgprints. OverAllowanceError defined at :12.

Gotcha · throw vs msgprint is a policy decision, not a style choice

frappe.throw aborts the DB transaction; frappe.msgprint does not. Throwing on a soft limit blocks legitimate data entry; only warning on a hard invariant corrupts the ledger. Keep tolerance thresholds and override roles in Settings Singles, and be deliberate about which tier each check belongs to.

Putting it together: editing a posted invoice

The patterns above interlock in one everyday operation — correcting a submitted Sales Invoice. Walk it end to end; this is the flow a consultant must be able to reproduce on any stack.

User opens submitted Sales Invoicedocstatus 1 — frozen
Click Cancelbefore_cancel → on_cancel fire
Reverse the postingsswapped-debit/credit GL rows, negative stock-ledger rows; update_prevdoc_status rolls back per_billed on the Sales Order
db_set status = "Cancelled"docstatus → 2
Click Amenddeep-copy into new Draft, amended_from = original, fresh naming-series id
set_status forces "Draft"docstatus 0 — re-armed
User edits → Submitvalidate → on_submit posts brand-new GL / stock entries

When the dust settles, three documents exist: the original, its reversal, and the amendment — every one of them permanent. That is the audit trail. The same shape covers the two policy-aware variants worth naming:

SUBMIT-WITH-ROLLUP-AND-LIMIT
Submitting an invoice against a Sales Order runs check_prev_docstatus (predecessor must be submitted), then update_prevdoc_status → update_qty rolls billed amount up to the SO and validate_qty checks cumulative billing against the over-billing allowance. A normal user over the limit gets frappe.throw(OverAllowanceError) and the whole submit rolls back; a bypass-role holder gets only a warning and the submit proceeds. set_status then recomputes the SO status from the status map.
CANCEL-UNDER-IMMUTABLE-LEDGER
With the immutable ledger enabled, make_reverse_gl_entries leaves the originals untouched (is_cancelled = 0) and inserts a dated reversal on the cancellation date, so the ledger table only ever grows and period totals stay reproducible. on_cancel sets self.ignore_linked_doctypes so the link-integrity guard permits the cancel even though those ledger rows reference the voucher.

Applying this to KDPS

This subsystem is the literal backbone of two of the twelve architecture rules in 00-system-architecture.html: "documents write ledgers" and "flag, don't block." The mapping is direct.

Applying to KDPS

Every KDPS event becomes a submittable document with docstatus 0/1/2 — GRN, PT (price-tag / value posting), Sale, Transfer, Return, EOSS markdown. Submit posts the stock ledger (quantity) and/or the value + vendor-liability ledger; cancel reverses them, exactly as above.

The SOR / consignment rule — "stock counted by quantity, value stays off-book until sale, vendor liability posts only on sale" — is this pattern with the value posting deferred to the Sale document's on_submit. The GRN posts a quantity-only stock-ledger row; no GL / liability entry fires until the Sale submits. Cross-state Bihar↔Jharkhand transfers (taxable IGST) are just two paired submittable documents whose GL + stock postings reverse cleanly on cancel.

Because money-critical corrections — a wrong P-RATE, late freight, a sold-before-PT case — must never be edited in place, KDPS adopts cancel + amend with amended_from as the only way to fix a posted PT or GRN. That gives the CA an immutable audit trail and satisfies "profitability is derived, never hand-entered." Since SKU = style × size × colour, the stock-ledger row the document writes must carry the full SKU so the reversal lands on the exact same line.

On the ratified Django/Postgres stack (ADR-0001): a docstatus smallint + CHECK on each transaction table, INSERT-only ledger tables (revoke UPDATE/DELETE), a TransactionController base class with the ordered hooks, an amend() service, and tolerance thresholds in a settings table. All-or-nothing posting and reversal must run inside one DB transaction the app fully controls — which is precisely why a BaaS was rejected.

Takeaways

  1. Model every business document as a three-state machine in one column — Draft (0) / Submitted (1) / Cancelled (2) — with a DB CHECK and submit() / cancel() service methods. docstatus, not the human status string, is your source of truth for control flow.
  2. Submit is the single transactional moment a document writes to the ledgers. Put GL and stock postings inside on_submit, inside one DB transaction. Nothing else writes the ledgers.
  3. Layer cross-cutting logic in a controller base class with ordered template-method hooks (validate → before/on_submit → before/on_cancel → on_update_after_submit → on_trash) and always call super() so invariants compose.
  4. Make on_cancel the exact mirror of on_submit — every side effect created on submit is reversed on cancel, line for line, or the books leak.
  5. A submitted document is immutable forever: never UPDATE or DELETE it. To change it, cancel (post equal-and-opposite reversals) and amend (deep-copy into a new Draft linked by amended_from, re-validate, re-submit). The only in-place edit is a whitelisted on_update_after_submit that re-posts deltas.
  6. Keep ledgers strictly INSERT-only. Cancel by inserting reversal rows with debit/credit swapped and a voucher back-reference. Decide your regime — classic (mutate originals) vs immutable ledger (date the reversal) — explicitly.
  7. Derive human-readable status and fulfilment percentages from docstatus + rollup fields via a declarative rule table; recompute on every save. Refuse to post against an unsubmitted predecessor.
  8. Split validation into hard invariants that throw (roll back) and soft limits that warn (proceed, with a role-based bypass). Keep thresholds and override roles in settings rows, not code.
  9. The headline: an ERP is trustworthy not because data can't be wrong, but because every posting is immutable and every correction is itself a new, traceable posting — the ledger only ever grows.

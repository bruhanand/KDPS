Chapter 5 · Documents & data

The Transaction Flow — Order → Receipt → Invoice → Payment

The universal order-to-cash and procure-to-pay graph, the mapped-document pattern, line-level "against" linking, fulfilment-percentage tracking, and the controller inheritance that each layer extends.

Why this subsystem is the spine of the whole ERP

Everything an ERP does commercially is a sequence of promises that gradually get kept. A customer is promised goods (an order); some of them ship (a delivery); some of what shipped gets billed (an invoice); some of what is billed gets paid (a receipt). The same shape runs in reverse on the buy side — you promise a supplier to buy, they ship, they bill, you pay. The single hardest thing in this whole domain is that these steps do not happen all at once and they do not happen in lockstep. An order of 100 units ships in three deliveries; two of those deliveries are invoiced together; the invoice is paid in two instalments; then 12 units come back as a return. A naïve "status flag on the order" model collapses the moment reality refuses to be tidy.

ERPNext's answer is to model the commercial lifecycle as an append-only directed graph of independent documents — one document per real-world event — linked by line-level "against" references, where fulfilment is a derived quantity recomputed by re-summing linked rows rather than a counter you increment. That one design decision buys you, for free: partial-fulfilment fan-out, idempotent and self-reversing cancellation, a complete audit trail, a declarative status state machine, and a structural guarantee against over-billing and over-delivery. This chapter is the reference you return to while building it.

Key idea Do not store "shipped" and "billed" as booleans on an order row. Model each event — promise, ship, bill, pay — as its own immutable, separately-submittable document, and make the order's per_delivered / per_billed a number you re-derive by SUMMING the linked downstream rows on every submit and every cancel. Status becomes a pure function of those percentages. Partial fulfilment, cancellation reversal, and the audit trail then fall out of the data model instead of being features you have to code.

The two flows are not two pieces of code. They are the same machinery with mirrored field names (delivered_qty ↔ received_qty, per_delivered ↔ per_received). The shared behaviour lives in a layered controller base-class chain; each concrete document type is mostly a small declarative spec plus a thin posting hook. The single files you will return to most are erpnext/controllers/status_updater.py (the fulfilment + status engine), the per-doctype erpnext/selling/doctype/sales_order/mapper.py (the document-generation spec), and erpnext/controllers/sales_and_purchase_return.py (returns as negated mirror documents).

The controller inheritance chain — where each layer adds one job

Rather than duplicate cross-document logic in every doctype, ERPNext composes it through a strict single-inheritance chain. Each layer adds exactly one responsibility, and a concrete document picks the right leaf as its Python class, inheriting the whole stack. This is the structural reason the two flows can share one set of mechanics.

Document Frappe core · frappe.model.document — save / submit / cancel lifecycle, docstatus
StatusUpdater fulfilment-percentage engine + status state machine
TransactionBase cross-document rate / qty / value validation
AccountsController party · currency · taxes · payment schedule · outstanding
StockController stock-ledger (make_sl_entries) + GL (make_gl_entries) posting
SellingController / BuyingController sell-side / buy-side leaf — Delivery Note, Sales Invoice, Purchase Receipt…

Read this bottom-up to understand a concrete document: a Delivery Note is a SellingController, which is a StockController, which is an AccountsController, … all the way up to the Frappe Document. When it submits, it runs update_prevdoc_status() (from StatusUpdater), then validate_with_previous_doc() (from TransactionBase), then posts stock and GL (from StockController). The doctype's own .py file is small — it supplies a status_updater list and a thin on_submit hook, and the chain does the rest.

Note · Frappe vs ERPNext The very top of the chain — save, submit, cancel, the docstatus field (0 draft / 1 submitted / 2 cancelled), and the get_mapped_doc mapper itself — are Frappe core framework features (see the document lifecycle). Everything from StatusUpdater down is ERPNext app code. When you rebuild this, the lifecycle + mapper are your framework layer; the controllers are your domain layer.

Pattern 1 — The universal transaction graph

The foundational decision. Everything else in the chapter is a consequence of getting this one right.

Pattern

One document per real-world event

The idea

Each distinct business event — promise, ship, bill, pay — is its own immutable, separately-submittable document, not a status flag on a single record.

The flow is a directed acyclic graph of documents, and fan-out is allowed: one order can spawn many partial deliveries. Posting to the ledgers happens only at submit.

How ERPNext does it

Separate DocTypes for Quotation / Sales Order / Delivery Note / Sales Invoice / Payment Entry (O2C) and Material Request / Purchase Order / Purchase Receipt / Purchase Invoice / Payment (P2P), each under its own directory.

Each is submittable — docstatus 0 draft, 1 submitted, 2 cancelled. Ledger posting happens in on_submit only.

erpnext/selling/doctype/sales_order/sales_order.py erpnext/stock/doctype/delivery_note/delivery_note.py erpnext/buying/doctype/purchase_order/purchase_order.py

Apply to any ERP

One table per event-type, each with a header (parent) row and item (child) rows, an explicit lifecycle column (draft / submitted / cancelled), and an immutability rule after submit.

Never overload a single "order" row with shipped / billed booleans. Model each event as an append-only document so partial fulfilment and audit fall out naturally.

The "append-only graph" framing is worth dwelling on. A document is never edited in place across the flow. You do not open the Sales Order and tick "delivered". You create a new Delivery Note from the order, copying the remaining quantities and recording a back-pointer. The order itself stays exactly as it was promised; what changed is a derived number on it. That immutability is what makes the audit trail trustworthy and what makes cancellation safe — there is nothing to "un-tick".

Applying to KDPS This is the backbone of D1 (vendor booking → Purchase Order), D2 (inbound: PO → GRN → PT/Purchase Invoice) and D3 (outbound: sale / transfer / return). Adopt the document-graph wholesale. The decided KDPS rule "GRN posts quantity / PT posts value + liability" is exactly ERPNext's split: the Purchase Receipt (a StockController) posts quantity to the stock ledger; the Purchase Invoice posts value + payable to the GL — two documents, two ledgers, one "against" link. That is the documents-write-ledgers rule, already proven in the source.

Pattern 2 — Line-level "against" back-links

Header-to-header links are not enough. If you only record "this delivery is against that order", you cannot answer "how much of the blue medium line is still owed" when an order has the same SKU on two lines or ships in pieces. Fulfilment must be tracked at row granularity.

Pattern

Two back-links per downstream line: parent Link + child-row id

The idea

A downstream line records both which upstream document and which upstream line it fulfils. Fulfilment is then summed by source-line, surviving size/colour/SKU splits and partial shipments.

How ERPNext does it

Delivery Note Item carries against_sales_order (a real Link to Sales Order) and so_detail (the Sales Order Item row name, stored as a Data field, no_copy=1). Sales Invoice Item carries sales_order / so_detail and the DN's dn_detail.

These are populated by the mapper's field_map: {"name":"so_detail","parent":"against_sales_order"}.

erpnext/stock/doctype/delivery_note_item/delivery_note_item.json erpnext/selling/doctype/sales_order/mapper.py

Apply to any ERP

Give every downstream line two FKs: source_document_id and source_line_id. Sum fulfilment by source_line_id, not by item code — that is what lets two partial deliveries of the same SKU reconcile correctly.

The header link is for navigation and joins; the line pointer is for the math.

Gotcha · soft pointers, not foreign keys so_detail / si_detail / dn_detail are Data fields holding a child-row name — they are not real DB foreign keys. Only the header link (against_sales_order) is a Link. ERPNext relies on application-level joins, not referential integrity, for line linking. Note the no_copy=1 flag: if you reimplement with hard FKs, you must replicate this, or amendments and document duplications will carry stale links across copies.
Applying to KDPS SKU = Style × Size × Colour must be the line granularity that the "against" links sum over. Put each size×colour on its own line with its own source_line_id, so a partial GRN that receives 8 of 10 blue-mediums and 0 reds reconciles per variant, not per style. Stock at style level only — the classic mistake — makes this pattern impossible.

Pattern 3 — The declarative mapped-document engine

The "Create > Delivery Note" / "Create > Invoice" buttons are not hand-written copy loops. They are a declarative spec interpreted by one engine: get_mapped_doc. You declare which tables map to which, which fields carry over, which rows to skip (already done), and a hook that computes the remaining quantity.

Pattern

Pre-fill the next document from the previous one, declaratively

The idea

Generating the next document is a configuration, not code: a map of {source table → target table, field renames, a row filter, a per-row transform}. The transform always emits the remaining quantity (ordered minus already-fulfilled).

How ERPNext does it

Frappe core get_mapped_doc(source, {Doctype:{doctype, field_map, condition, postprocess}}, postprocess).

In make_delivery_note: condition = lambda d: abs(d.delivered_qty) < abs(d.qty) skips fully-delivered lines; update_item sets target.qty = source.qty − source.delivered_qty — only the pending balance.

Same shape in make_purchase_receipt and the Sales Invoice mapper.

erpnext/selling/doctype/sales_order/mapper.py erpnext/buying/doctype/purchase_order/mapper.py

Apply to any ERP

Build one small mapping interpreter: a config of {source_table, target_table, field renames, row filter, per-row transform}. The transform always emits REMAINING quantity.

This one engine powers every "Create > X" button and guarantees you can never re-pull a line you already fulfilled.

The mapper for a Sales Order → Delivery Note line is small enough to read whole — and the whole percentage engine reads only the dict it produces:

def update_item(source, target, source_parent):
    target.qty = flt(source.qty) - flt(source.delivered_qty)
    target.amount = (flt(source.qty) - flt(source.delivered_qty)) * flt(source.rate)

mapper["Sales Order Item"] = {
    "doctype": "Delivery Note Item",
    "field_map": {"name": "so_detail", "parent": "against_sales_order"},
    "condition": lambda d: (abs(d.delivered_qty) < abs(d.qty)),   # skip done lines
    "postprocess": update_item,                              # emit pending balance
}
target_doc = get_mapped_doc("Sales Order", so.name, mapper, target_doc)

Read the three moving parts: field_map wires the back-links (Pattern 2); condition drops lines that are already fully delivered (so a second delivery never re-offers them); postprocess writes only the pending quantity. Those three together are the entire reason partial fulfilment "just works" — the next document can only ever be about what is still owed.

Gotcha · the mapper is not a pure function Business code passes extra kwargs (filtered_children, for_reserved_stock) and the condition sometimes reads frappe.flags.args — UI-supplied context leaks into the mapping. So the output is not purely a function of the source document. Keep this in mind when porting to a stateless API: make the equivalent context an explicit argument, not ambient state.
Gotcha · the mappers moved In recent ERPNext the mappers were refactored out of the doctype .py files into sibling mapper.py modules (e.g. erpnext/selling/doctype/sales_order/mapper.py). Grepping the doctype file for make_delivery_note / get_mapped_doc now returns nothing — the logic moved, the pattern did not go away.

Pattern 4 — Derived fulfilment percentages (SUM, never increment)

This is the load-bearing idea of the whole subsystem. Fulfilment is computed, never stored incrementally. On every submit and every cancel, the engine re-sums all submitted child rows pointing at a source line, writes that total back to the source line, then rolls the line totals up into a parent percentage. Because it is a re-sum, it is idempotent and self-healing.

Pattern

Re-SUM linked rows on submit and cancel — do not keep a counter

The idea

Status is derived. On every state change, re-sum all submitted rows linked to a source line, write it back, then compute per_x = SUM(min(fulfilled, ordered)) / SUM(ordered) × 100 and map it to a label.

Because it is a re-sum, cancelling a document auto-reverses fulfilment — the cancelled rows simply drop out of the next sum. No compensating logic.

How ERPNext does it

StatusUpdater.update_qty runs a SQL SUM(source_field) over all docstatus=1 rows where join_field = detail_id, writes it to target_field (e.g. delivered_qty), then _update_percent_field computes per_delivered and _determine_status maps it to Not / Partly / Fully.

Each doctype supplies the spec as self.status_updater. Hooked in on_submit AND on_cancel via update_prevdoc_status().

erpnext/controllers/status_updater.py

Apply to any ERP

Compute per_x as a re-sum over linked rows in a service that runs on submit and cancel. The min() clamp stops one over-shipped line from masking another unshipped line.

Resist the urge to increment a counter — counters drift, need compensating reversals, and cannot self-heal.

The per-doctype spec is pure data. A Delivery Note declares how its rows roll up to the Sales Order — the engine reads nothing else:

self.status_updater = [
    {
        "source_dt": "Delivery Note Item",
        "target_dt": "Sales Order Item",
        "join_field": "so_detail",
        "target_field": "delivered_qty",
        "target_parent_dt": "Sales Order",
        "target_parent_field": "per_delivered",
        "target_ref_field": "qty",
        "source_field": "qty",
        "percent_join_field": "against_sales_order",
        "status_field": "delivery_status",
        "keyword": "Delivered",
    },
]

The engine turns that spec into a write-back. The qty is re-summed and stored — never added to:

args["source_dt_value"] = (frappe.db.sql("""
    (select coalesce(sum({source_field}), 0)
     from `tab{source_dt}` where `{join_field}`=%(detail_id)s
     and (docstatus=1 {cond}) {extra_cond})
""".format(**args), {"detail_id": args["detail_id"]})[0][0] or 0.0)

frappe.db.sql("""update `tab{target_dt}`
    set {target_field} = {source_dt_value} {update_modified}
    where name=%(detail_id)s""".format(**args),
    {"detail_id": args["detail_id"]})

The parent percentage clamps each line with min() before averaging — the small detail that prevents a serious bug:

sum_ref = sum(abs(record[ref_key]) for record in child_records)
if sum_ref > 0:
    percentage = round(
        sum(min(abs(record[target_field]), abs(record[ref_key]))
            for record in child_records) / sum_ref * 100, 6)
else:
    percentage = 0
# _determine_status: <0.001 -> 'Not X', >=99.999999 -> 'Fully X', else 'Partly X'
Gotcha · the min() clamp is not optional The parent percentage is sum(min(fulfilled, ordered)) / sum(ordered). Without the min(), an over-delivered line would push the average above 100 and hide a sibling line still at 0%, so an incomplete order would wrongly show "Completed". The clamp caps each line at its own ordered quantity before they are averaged. If you build this yourself and skip the clamp, you ship that bug.
Gotcha · you MUST call the engine on cancel too Because percentages are a raw SUM over docstatus=1 rows, correctness depends on running update_prevdoc_status() in both on_submit and on_cancel. Miss the on_cancel call and fulfilment never reverses. Order matters too: Delivery Note calls update_prevdoc_status() before update_stock_ledger(), because the reserved-qty in Bin depends on the freshly-updated delivered_qty (see the comment at erpnext/stock/doctype/delivery_note/delivery_note.py).

Pattern 5 — The declarative status state machine

Human-readable status ("To Deliver", "To Bill", "Completed") is not set imperatively in business code. It is a lookup table of (label, predicate) over the document's own derived fields, evaluated top-down — the first (or last) match wins. This keeps status logic in one declarative place per doctype and makes it impossible for the status to drift from the percentages it is supposed to summarise.

Pattern

Status as an ordered list of (label, predicate) over derived fields

The idea

Express status as an ordered list of (label, condition) evaluated against the document's own derived fields (percentages + docstatus). Pick the first/last matching label.

Status is then a pure function of the numbers — it can never disagree with them.

How ERPNext does it

The status_map dict, e.g. Sales Order "To Bill" = eval:(self.per_delivered>=100 or self.skip_delivery_note) and self.per_billed<100 and self.docstatus==1; "Completed" = both percentages ≥ 100.

get_status() reverses the list and returns the first match via frappe.safe_eval against self.as_dict().

erpnext/controllers/status_updater.py

Apply to any ERP

One ordered predicate list per document type, over its derived fields. Evaluate top-down, take the first match.

Keep it data, not scattered if branches across the codebase — that is what stops status and fulfilment from drifting apart.

The conditions are stringly-typed Python ("eval:...") run through frappe.safe_eval. Powerful, but a footgun — see the warning below. The pattern itself is sound; on your own stack you can express the same idea as a list of (label, lambda doc: ...) pairs, getting the declarativeness without the runtime-string risk.

Gotcha · stringly-typed eval, and an asymmetry to watch Conditions are runtime-evaluated strings — easy to get subtly wrong and a maintenance/security surface. Note the real asymmetry in the source: Sales Order's branches use per_billed < 100 while Purchase Order uses per_billed == 100 in several places. The two flows are mirrors but not byte-identical; do not assume you can copy one spec verbatim to the other.

Pattern 6 — The over-fulfilment guard (tolerance + role override)

You should not be able to deliver or bill more than was ordered — that is the classic over-delivery / over-billing error (and fraud) vector. ERPNext makes it structurally hard by default: after computing fulfilled-vs-ordered, it rejects anything beyond a configurable tolerance, unless the caller holds an authorised override role (in which case it warns instead of blocking).

Pattern

Reject beyond ordered × (1 + tolerance) unless an override role is held

The idea

After computing fulfilled vs ordered, reject if fulfilled > ordered × (1 + tolerance%) — unless the caller holds an override role, in which case warn and proceed.

This single check makes both over-delivery and over-billing impossible by default.

How ERPNext does it

StatusUpdater.validate_qty → check_overflow_with_allowance: overflow_percent = (target − target_ref)/target_ref × 100; if it exceeds the allowance and the user lacks role_allowed_to_over_deliver_receive / over_bill → throw OverAllowanceError.

get_allowance_for reads item-level tolerance first, then global Stock / Accounts Settings.

erpnext/controllers/status_updater.py erpnext/stock/doctype/stock_settings/

Apply to any ERP

One reusable guard on the base controller: compute overflow %, compare to a tolerance resolved item-level-then-global, throw unless an override role is present.

Configurable globally and per-item. Inherited by every document type for free.

overflow_percent = ((item[args["target_field"]] - item[args["target_ref_field"]])
                    / item[args["target_ref_field"]]) * 100
if overflow_percent - allowance > 0.01:
    item["max_allowed"] = flt(item[args["target_ref_field"]] * (100 + allowance) / 100)
    item["reduce_by"] = item[args["target_field"]] - item["max_allowed"]
    if role not in frappe.get_roles():
        self.limits_crossed_error(args, item, qty_or_amount)
    else:
        self.warn_about_bypassing_with_role(item, qty_or_amount, role)
Gotcha · the cap is soft for some callers Tolerance resolves item-level first, then global, and is silently bypassed for users holding the override role and for internal customers/suppliers (limits_crossed_error returns early). A reviewer expecting a hard cap will be surprised that a role can exceed it with only a warning. If your business needs a true hard cap, do not wire an override role at all.

Pattern 7 — Cross-document consistency validation

A downstream line must stay consistent with its source line: the same rate within tolerance, no orphaned references, and no two lines secretly consuming the same source row. This is a separate concern from fulfilment totals, and it lives one layer up the chain, in TransactionBase.

Pattern

On save, assert each downstream line matches its source line

The idea

A downstream line must be consistent with its source: same rate (within tolerance), the reference must exist, and no two lines may point at the same source row.

How ERPNext does it

TransactionBase.validate_with_previous_doc / compare_values reads the referenced source rows by ref_dn_field and asserts compare_fields — throwing "Invalid reference" on orphans and "Duplicate row" if two lines share a source row.

validate_rate_with_reference_doc enforces same rate (Stop vs Warn, via Buying/Selling Settings).

erpnext/utilities/transaction_base.py

Apply to any ERP

On save of a downstream doc, fetch each referenced source row and assert the invariants (rate equality, reference exists, no double-link).

Centralise it in the base controller so every doctype inherits it — one place, every document.

Pattern 8 — Returns as negated mirror documents

The elegant payoff of everything above: a return / credit note is not a special table. It is the same document type, with is_return=1, a return_against pointer to what it reverses, and negative quantities — validated so cumulative returns can never exceed the original. Because the quantities are negative, the stock ledger, the GL, and the fulfilment percentages all reverse for free: they are the same sums, now with negative terms.

Pattern

Returns are ordinary documents with negative lines + a return_against link

The idea

A return is an ordinary document with an is_return flag, a return_against FK, negative lines, and a guard: SUM(prior returns) + this ≤ original.

One returns engine for every direction. The negative qty makes ledgers and percentages reverse for free.

How ERPNext does it

make_return_doc() sets is_return=1, return_against=source.name, negates qty / tax / payment amounts. validate_returned_items sums get_already_returned_items and throws StockOverReturnError if the total would exceed what was received/delivered.

The same code serves Sales Invoice (credit note), Delivery Note, Purchase Receipt and Purchase Invoice (debit note).

erpnext/controllers/sales_and_purchase_return.py

Apply to any ERP

Implement returns as normal documents with is_return + return_against + negative lines + the cumulative-return guard.

Do not build a parallel "returns" subsystem. Reuse the document graph; the sign does the work.

Key idea Notice that returns required almost no new machinery. The same mapper builds the document, the same status engine sums the (now negative) rows into a per_returned, the same stock/GL posting runs. That is the dividend of "fulfilment is a SUM, not a counter": anything that adds rows — partial deliveries, returns, cancellations — reconciles through one re-sum, in one place.
Applying to KDPS Use the negated return_against document for returns-out and exchanges (an exchange is a return + a fresh sale). For SOR/consignment, model the same graph but create the value/liability document (the PT) later — stock comes in on the GRN (qty), but the vendor liability posts only on sale, tracked with the same per_billed-style number so you always know what is still off-book. A cross-state (Bihar↔Jharkhand) transfer is two mirror documents linked by line — exactly ERPNext's internal-customer/supplier delivery+invoice pair — which is precisely how the taxable IGST supply falls out.

The flows, end to end

Now that every pattern is on the table, here are the four sequences a consultant needs to be able to trace by hand.

O2C — order to cash

On Delivery Note submit, update_prevdoc_status() sums delivered_qty back to each Sales Order Item, recomputes the Sales Order's per_delivered + delivery_status, then runs update_stock_ledger() + make_gl_entries() (the order matters — Pattern 4's cancel-order gotcha). The Sales Invoice's status_updater spec rolls billed_amt up to per_billed / billing_status. The Payment Entry settles the invoice's outstanding_amount and the flow closes.

Partial fulfilment fan-out

One Sales Order spawns N Delivery Notes. Each DN's condition (delivered_qty < qty) pulls only the unshipped balance, and update_qty re-sums all submitted DN rows by so_detail — so per_delivered climbs monotonically to 100 across the N documents without any document knowing about the others. That independence is the whole point: each delivery is a self-contained fact; the order's progress is a query over those facts.

Cancellation reversal

Cancelling a Delivery Note re-runs update_prevdoc_status() in on_cancel. Because per_delivered is a fresh SUM over docstatus=1 rows, the cancelled DN's rows simply drop out of the sum, and the Sales Order's per_delivered / status fall back automatically — no compensating entry is written. This is the cleanest illustration of why "derive, don't increment" matters: there is no reversal logic to get wrong, because there was never an addition to undo.

Returns

make_return_doc("Delivery Note", source) builds a DN with is_return=1, return_against=source, and negative qty. validate_returned_items sums get_already_returned_items and blocks over-return. The negative rows then flow through the same status engine (producing per_returned) and the same stock/GL posting, reversing inventory and value.

Gotchas — the things that bite reimplementers

Consolidated, because these are exactly where a from-scratch build goes wrong. Each is drawn from the real source behaviour.

so_detail is a soft pointer, not a foreign key
so_detail / si_detail / dn_detail are Data fields holding a child-row name; only the header link is a real Link. ERPNext relies on application-level joins. If you use hard FKs, you must replicate no_copy=1 so amendments/duplications don't carry stale links.
The engine must run on cancel, in the right order
Percentages are a raw SUM over docstatus=1 rows, so update_prevdoc_status() must run in both on_submit and on_cancel. And it must run before the stock-ledger post, because reserved-qty in Bin depends on the freshly-updated delivered_qty.
Never drop the min() clamp
The parent percentage is sum(min(fulfilled, ordered)) / sum(ordered). Without min(), an over-delivered line pushes the average over 100 and hides a sibling still at 0%, so the order wrongly shows "Completed".
The over-fulfilment cap is soft for override roles
Tolerance is item-level then global, and is silently bypassed for users holding role_allowed_to_over_deliver_receive / over_bill and for internal customers/suppliers. Don't assume a hard cap.
Status conditions are runtime eval: strings
Run through frappe.safe_eval against self.as_dict(). Powerful but stringly-typed and easy to get subtly wrong — note the asymmetry (Sales Order per_billed < 100 vs Purchase Order per_billed == 100). Don't copy a spec across the two flows verbatim.
Invoices can post stock directly — the flow has two shapes
A Sales Invoice with update_stock=1 (POS / own-store) posts the stock ledger itself, without a prior Delivery Note. Return invoices add their own zero-qty rules. Reimplementers who model "invoice always follows delivery" break POS and own-store flows.
The mapper is not a pure function of the source doc
get_mapped_doc's condition reads frappe.flags.args and business code passes filtered_children / for_reserved_stock kwargs — UI context leaks in. Make that context an explicit argument when porting to a stateless API.
The mappers moved out of the doctype files
Refactored into sibling mapper.py modules. Grepping the doctype .py for make_delivery_note now returns nothing — the logic moved, the pattern did not disappear.

Rebuilding it on Django / Postgres — the minimal kit

Stripped to essentials, you need three things, and the patterns above tell you exactly what each one does. Build these and the two flows, partial fulfilment, cancellation reversal, the audit trail and the over-fulfilment guard all fall out.

  1. An abstract Document base — a lifecycle column (draft / submitted / cancelled), submit() / cancel() methods, an immutability rule after submit, and header+lines tables. This is your Frappe-Document equivalent (see the document lifecycle).
  2. A small get_mapped_doc-equivalent mapping interpreter — config of {source_table → target_table, field renames, row filter, per-row transform}, where the transform always emits the remaining quantity. One interpreter powers every "Create > X" action.
  3. A fulfilment service that, on submit and cancel, re-sums linked lines by source_line_id, writes the total back, recomputes per_x = sum(min(fulfilled, ordered))/sum(ordered), derives the status from an ordered predicate list, and runs the over-fulfilment guard. Do not increment counters.

Layer shared behaviour into a base-class chain mirroring ERPNext's — status engine → cross-doc validation → accounting → stock/GL → sell/buy leaves — so each concrete document type is a small declarative spec (its status_updater mapping, its mapper config) plus a thin posting hook, not bespoke code. The accounting ledger and stock ledger chapters cover the two posting hooks this chapter's documents call on submit.

Takeaways

  1. Model the commercial lifecycle as an append-only DAG of documents — one per real-world event (promise, ship, bill, pay), never as status flags on a single order row. Immutability after submit is what makes the audit trail and cancellation trustworthy.
  2. Link downstream lines to source lines with two back-links — a header Link for navigation and a source-line id for the math. Sum fulfilment by source-line, not by item code; that is what survives SKU / size / colour splits and partial shipments.
  3. Make fulfilment a DERIVED quantity: re-SUM linked rows on submit AND cancel. Never increment a counter. This single decision buys partial-fulfilment fan-out, idempotent self-reversing cancellation, and the audit trail for free.
  4. Clamp each line with min(fulfilled, ordered) before averaging into the parent percentage — otherwise an over-shipped line hides an unshipped sibling and the order wrongly reads "Completed".
  5. Generate the next document from a declarative mapper that filters out done lines and emits only the remaining quantity — so you can never re-pull what you already fulfilled.
  6. Derive status from an ordered list of (label, predicate) over the percentages, so status can never drift from the numbers it summarises.
  7. Put a tolerance + role-override over-fulfilment guard on the base controller. It makes over-delivery and over-billing structurally impossible by default, and every document type inherits it.
  8. Implement returns as ordinary documents with is_return + return_against + negative lines and a cumulative-return cap. The negative sign reverses stock, GL and percentages through the existing engine — no parallel subsystem.
  9. Push shared behaviour into a layered controller chain (status → cross-doc validation → accounting → stock/GL → sell/buy leaves) so each concrete document is a thin declarative spec plus a posting hook — not bespoke code.

Chapter 12 · Synthesis

The Build-Any-ERP Playbook

The capstone: a step-by-step method for standing up a new custom ERP, a copy / adapt / skip decision matrix against ERPNext’s patterns, the non-negotiables, the classic pitfalls, and KDPS as a worked example.

What this chapter is

The eleven chapters before this one each took apart one mechanism inside ERPNext: the meta-model, the document lifecycle, the general ledger, the stock ledger, the transaction graph, masters & the party, the tax/pricing engine, permissions, the workflow engine, extensibility, and the read side. This chapter does not introduce a new mechanism. It is the method — the order you build them in, the patterns you copy verbatim versus the ones you adapt or skip, the handful of things you must never cut, the mistakes that look reasonable and aren’t, and a full worked mapping onto a real engagement (KDPS).

The intended reader builds custom ERPs on a conventional stack — most often React + Django + PostgreSQL — and wants ERPNext’s twenty years of hard-won structure without inheriting Frappe, its JSON metadata runtime, or its operational surface. The whole handbook’s thesis lands here: an ERP is small at its core and varied at its edges. A balanced append-only ledger, an immutable document lifecycle, and a snapshot discipline are tiny and stable; the variety — every brand’s tax slab, every commercial model, every report — lives in data the small core interprets. Get the core right and the rest is configuration. Get it wrong and you will hand-code the same four behaviours per table forever.

The one sentence Build the smallest possible generic engine — schema-as-data, two append-only ledgers, an immutable document lifecycle — then push every business difference into data the engine reads. Documents post the ledgers; reports read the ledgers; masters snapshot onto transactions; corrections are new postings, never edits. Everything else is detail.

1 · The method — an ordered build sequence

Build an ERP in dependency order, not wishlist order. Each step below produces something real and testable, and each depends only on the steps above it. Resist the urge to start with the screens the client is excited about (the POS, the dashboard); those sit at the top of a tall stack and collapse without the foundation. The sequence is the spine of this handbook read top to bottom.

a · Map the domainmasters · documents · ledgers — classify every entity (ch 13)

c · Define the ledgers & posting rulesdocuments post, reports read; double-entry GL + stock ledger (ch 03, 04)
d · Build masters with snapshot-into-transactiontemplate/variant, party, snapshot, defaults cascade (ch 06)
e · Build the transaction graphorder → receipt → invoice → payment, derived status (ch 05, 02)
f · Layer tax & pricing as datacharge-type interpreter, date-effective rates, rule engine (ch 07)
g · Add the control planepermissions matrix · workflow (if needed) · extensibility seams (ch 08, 09, 10)
h · Build the read sidereports + dashboards + print, all live over the ledger (ch 11)

a · Map the domain into masters, documents, and ledgers

Before any code, take the business and sort every noun into exactly one of three buckets, using the taxonomy from chapter 13:

  • Masters — the editable "current truth": who you deal with and what you sell (Item, Customer, Supplier, Warehouse, Account, Company). Long-lived, mutated for cosmetic fields, frozen for ledger-bearing fields.
  • Documents — one per real-world event: a promise, a shipment, a bill, a payment. Immutable once posted. These are the only things that write ledgers.
  • Ledgers — the append-only "historical truth": the general ledger (money) and the stock ledger (quantity/value). Never edited, only appended.

Then draw the two canonical flows your business runs (procure-to-pay and order-to-cash) and identify which ledger each document touches. Do this on paper first. The map is the architecture; the rest is implementation. KDPS’s own five-layer architecture (master data → documents → ledgers → controls → intelligence) is exactly this bucketing.

b · Build the meta-model / schema discipline first

ERPNext’s deepest idea (chapter 1) is that a schema is data, not code: one uniform declaration per entity — its fields, types, relationships, and a few flags (submittable, single, naming, permissions) — feeds one generic engine that derives the table, the API, the form, the ORM handle, the permission checks, and the audit columns. You don’t have to adopt a JSON runtime to keep the discipline. On Django, the equivalent is: a small base model that every entity inherits (audit columns + lifecycle), a tiny set of structural conventions (a "submittable" mixin, a "child table" convention, a "single/settings" convention), and a generic admin/API layer driven off the model metadata Django already exposes. The non-negotiable is that every entity shares the same shape so cross-cutting behaviour is written once.

Don’t over-build the meta-layer You are not rebuilding Frappe. You want the discipline (uniform audit columns, one lifecycle, typed links, a naming strategy) — not a runtime that compiles JSON into tables. A Django abstract base model plus a handful of mixins gets you 90% of the leverage at 5% of the cost. Adopt the metadata habit, skip the metadata VM.

c · Define the ledgers and the posting rules

This is the spine, and it comes before any document, because every document exists to post here. Build the general ledger (chapter 3) as one immutable append-only table of one-sided postings (account, debit XOR credit, voucher identity, optional party + against-voucher + dimensions), with balances always computed by SUM(debit) - SUM(credit) and never stored. Build the stock ledger (chapter 4) as a parallel append-only event log per (item, location) carrying the running balance and valuation snapshot. Funnel every poster through one service that enforces the two laws:

The two laws Documents post the ledger. No document mutates a balance directly; on submit it composes a balanced set of postings and hands them to one shared posting function that validates total-debit == total-credit (with a round-off tolerance) and inserts rows.
Reports read the ledger. Trial balance, P&L, balance sheet, AR/AP aging are pure aggregations of ledger rows. There is no stored "account balance" anywhere, so the books can never drift from the report.

Set the chart of accounts up as a typed nested-set tree (Asset/Liability/Income/Expense/Equity → Balance Sheet vs P&L) where only leaves are postable. Make analytical slices (cost center, branch, brand) configurable dimensions copied onto every posting, not hard-coded columns. This step is the hardest to retrofit and the cheapest to get right early.

d · Build masters with snapshot-into-transaction

Now the masters (chapter 6). Three durable moves: model variation as data (a template + an attribute catalog + a variant table — "SKU = style × size × colour" is rows, not columns); abstract "who we transact with" into a polymorphic (party_type, party) pair so new party kinds need no ledger change; and above all, snapshot master values onto the transaction line at creation. Copy the name, rate, accounts, and tax onto the document, resolved through a per-company defaults cascade (item → item-group → brand → company). The master is the editable present; the transaction is the frozen past. Add immutability guards (ERPNext’s cant_change()) on the few master fields the ledger depends on (valuation method, is-stock-item). This is what lets you fix a typo in a customer name next year without corrupting last year’s books.

e · Build the transaction graph with status tracking

With ledgers and masters in place, build documents as an append-only DAG (chapter 5) linked by line-level "against" references, each its own submittable record (chapter 2). The decisive design choice: make fulfilment a derived quantity — re-SUM linked child rows on every submit and cancel — never a mutable counter. That single decision buys you partial-fulfilment fan-out, self-reversing cancellation, an audit trail, a declarative status state machine, and a structural guard against over-billing/over-delivery, all for free. Put shared behaviour in a layered controller chain (status engine → cross-doc validation → accounting → stock/GL → sell/buy leaves) so each concrete document is mostly a small declarative spec plus a thin posting hook.

f · Layer tax and pricing as data

Only now add money rules (chapter 7), as a small generic calculation engine over declarative rows — never per-scenario code. Each tax/charge is a typed row whose charge_type is an opcode the engine interprets, and rows compose by referencing earlier rows; that one mechanism expresses GST, cess-on-tax, tax-on-freight, fixed charges, and per-unit levies. Every rate and price is effective-dated and category-scoped data with per-item override maps, so a GST slab change is a new row, never a deploy. Discounts/promotions are declarative rules matched by dimension + qty/amount slab + condition + validity, resolved by explicit priority.

g · Add the control plane

Permissions (chapter 8) come after the data model is real, because they gate it: make authorization a data matrix (role × action × permlevel) plus row-level scopes, enforced by one engine that AND-s a WHERE clause into every query — never if-statements scattered across controllers. Add the configurable workflow engine only if the business genuinely needs configurable approvers/conditions; otherwise a hard-coded status suffices. And bake in the extensibility seams (chapter 10) — a custom-field table, named hook points, idempotent ordered migrations — from day one, because retrofitting "never fork the core" is impossible.

h · Build the read side last

Reports, dashboards, and print (chapter 11) come last because they read everything below. Build them as metadata plus a thin compute function over the immutable ledger: one report record with a type discriminator and a fixed execute(filters) → (columns, rows, chart, summary) contract; financial statements computed live from the GL via a chart-of-accounts tree rollup; dashboards as records, not code; print as a sandboxed template over the saved document. Adding a report becomes a data change, not an engineering project.

2 · Copy / Adapt / Skip

ERPNext is a twenty-year-old generalised product serving every industry in every country. You are building one focused ERP for one business. That difference is the whole decision: some of ERPNext’s structure is universal accounting truth you copy verbatim; some is a good idea whose implementation you should rebuild idiomatically on your stack; and some is generality you simply don’t need and should consciously skip to stay small. Below is the matrix, with the reason for each verdict.

Pattern (chapter)VerdictWhy
Double-entry GL — balanced one-sided postings, one posting service, balances derived (ch 3) COPY This is 500-year-old accounting truth, not an ERPNext invention. Total-debit == total-credit, append-only, never store a balance. Reimplementing it "simpler" is the single most expensive mistake you can make. Copy the structure exactly.
Immutable submitted documents — draft → submitted → cancelled on one column; cancel-and-amend, never edit (ch 2) COPY Trust comes from immutability + traceable corrections, not from data being un-wrong. The three-state machine and "cancel posts reversing entries, amend creates a new linked draft" is universal. Copy it verbatim.
The controller hook chain — ordered lifecycle hooks (validate → before/on_submit → on_cancel) with shared behaviour inherited (ch 1, ch 5) COPY The pattern — cross-cutting posting/validation in base classes, leaf documents compose with super(), on_cancel is the exact mirror of on_submit — is stack-agnostic. On Django, base model + Django signals or an explicit hook dispatcher. Copy the shape; pick your stack’s mechanism.
Naming series — human-readable IDs like ACC-SINV-2026-00042 as a configured pattern (ch 1) COPY Auditors, GST returns, and staff all reference documents by these numbers; a UUID is unusable on a printed invoice. A per-series counter with prefix + fiscal year + zero-padded sequence is cheap and you cannot retrofit it onto posted history. Copy it.
Snapshot masters onto transactions + per-company defaults cascade (ch 6) COPY Non-negotiable for correct history. The mechanism (copy name/rate/accounts/tax onto the line at creation, guard the structural master fields) is the same on any stack. Copy.
The DocType meta-model — schema compiled from JSON at runtime (ch 1) ADAPT Keep the discipline (uniform shape, audit columns, typed links, flags) but not Frappe’s runtime VM. On Django, use real models.py + an abstract base + a thin metadata layer (a CustomField table for runtime additions). You get migrations, typing, and tooling your team already knows.
Stock valuation — FIFO/LIFO/moving-average behind one strategy interface (ch 4) ADAPT Keep the architecture (valuation isolated in a pure, db-free strategy module; store enough state per row to resume; a checkpointed repost engine for back-dated entries). But implement only the method(s) your business actually uses. KDPS needs cost-from-PT, so most stock is moving-average; you don’t need all four methods on day one.
Pricing Rule / Promotional Scheme engine — declarative rule matching by dimension + slab + condition + priority (ch 7) ADAPT The model is exactly right for slab/condition discounts. Adapt the storage to your stack and the matching to your real offer shapes (B2G1-lowest-free, value slabs, per-store dates). Keep the "compile a friendly scheme into flat matchable rules" idea; trim conflict-resolution generality to what you need.
Accounting dimensions — extensible analytical tags injected onto every posting (ch 3) ADAPT You want the capability (slice the ledger by store/brand/territory). On Django, a few explicit nullable FK columns on the GL row, populated from the document snapshot, are simpler and faster than ERPNext’s runtime field injection. Adapt to explicit columns; keep them out of the posting math.
Full multi-company — every account/ledger row stamped with company, separate charts, inter-company (ch 3) ADAPT KDPS is one legal entity with two state GSTINs — that is multi-GSTIN, not multi-company. Stamp a company/gstin dimension on rows so you can split returns, but don’t build inter-company eliminations, per-company charts, and consolidation you’ll never use. Adapt down to the dimension you need.
Subcontracting / manufacturing — BOM, work orders, the BuyingController subcontract chain (ch 5) SKIP A fashion retailer buys finished goods and sells them. There is no production. Skip the entire subcontracting subsystem; it is dead weight and a maintenance liability for a buy-store-sell business.
The full permlevel machinery — numeric field-level security tiers (ch 8) SKIP / TRIM Keep role × action and row-level scope (you absolutely need "this user sees only their store"). But the numeric permlevel field-tier machinery is heavy. Most field-hiding needs are met by a serializer field-filter for the handful of sensitive fields (margin, cost). Add tiers only if a real requirement demands them.
The generic Workflow engine — admin-configurable approval state machines (ch 9) SKIP (at first) If approvals are fixed, single-actor, and won’t need configurable approvers/conditions, a hard-coded status field is correct and far simpler. Switch to the configurable engine the moment business users need "who approves what, under which condition". For KDPS’s early build, hard-coded status is right.
The regional-override / app-layering system — hooks.py, separate india_compliance app (ch 10) SKIP That machinery exists so one product serves every country without forking. You are building one ERP for India. Bake GST in directly (as date-effective data — see non-negotiables), don’t build a plugin runtime to host a tax regime you’ll never swap out.
The rule behind the table Copy what is universal truth (double-entry, immutability, snapshot, naming). Adapt what is a good idea with a heavy implementation (the meta-model, valuation, pricing, dimensions). Skip what is generality for a product you’re not building (multi-company consolidation, manufacturing, plugin runtimes, configurable workflow you don’t yet need). When unsure, ask: "is this accounting law, or is this ERPNext serving someone else’s business?"

3 · Non-negotiables — what you must NOT cut

Everything in section 2 is a judgement call except these five. Cut any of them and you don’t have a smaller ERP — you have a broken one that will silently corrupt money or history. Each of these has burned a real project; treat them as load-bearing walls.

Non-negotiable · Double-entry balance Every financial posting must balance: total debit == total credit per voucher, enforced in exactly one place every poster funnels through, with a small round-off tolerance that auto-inserts a round-off line rather than rejecting the transaction (ch 3, erpnext/accounts/general_ledger.py · process_debit_credit_difference). The moment one code path can write an unbalanced or one-sided entry, your trial balance is wrong and no report can be trusted. There is no "simpler" version of this.
Non-negotiable · Audit columns + immutability Every record carries the same audit columns (owner, creation, modified, modified_by, docstatus) injected by the framework, not hand-added per table (ch 1). A submitted accounting or stock document is immutable forever — never UPDATE, never DELETE. To change it you cancel (post reversing entries) and amend (a new linked draft). Ledgers only ever grow. An auditor must be able to see exactly what was posted and exactly how it was corrected. Cut this and you have no audit trail, only a mutable database.
Non-negotiable · Idempotent, ordered, logged migrations Schema and data evolution is an ordered list of single-purpose scripts that each run exactly once per environment and are written to be safely re-runnable, with a persistent log of what has run (ch 10, erpnext/patches.txt). On Django this is the migrations framework plus guarded data migrations (if not exists checks). The day you patch production by hand, you lose reproducibility across environments and you cannot stand a new store up cleanly. Build this from commit one.
Non-negotiable · Snapshotting masters onto transactions A transaction line must copy the master’s name, rate, accounts, and tax at creation, never reference the live master for posted values (ch 6, erpnext/stock/get_item_details.py · get_basic_details). If you read the live master at report time, last year’s books rewrite themselves the moment someone edits a customer or a price. The master is the present; the document is the frozen past. This is not an optimisation — it is correctness.
Non-negotiable · GST / tax as date-effective data Tax rates, slabs, and templates must be effective-dated and value-scoped data (valid_from, value bands, tax category), selected by the document’s posting date — never constants in code (ch 7, erpnext/stock/get_item_details.py · _get_item_tax_template). Apparel GST is slab-based and changes by government notification; a hard-coded 5%/12% will silently mis-post every transaction the day a slab moves, and re-running an old period will apply today’s rate to last year’s sales. Effective-dating is the only correct model.

4 · Classic pitfalls

These are the mistakes that look like reasonable engineering and quietly destroy an ERP. Each one is tempting because it is simpler in the short run. Each has a fix that is the corresponding pattern from an earlier chapter.

Pitfall · Storing balances instead of deriving them

The temptation: a balance column on Account (or qty_on_hand on Item) that you increment on each posting — "so reports are fast." The reality: the moment two postings race, or a cancellation is missed, or a back-dated entry lands, the stored balance diverges from the sum of the ledger and you can never tell which is right.
The fix: balances are always SUM(debit) - SUM(credit) (ch 3). If read performance hurts, add a reconcilable snapshot cache (like ERPNext’s Bin) that is a rebuildable projection of the ledger, never the source of truth — and that you can recompute from scratch at any time.

Pitfall · Editing posted documents

The temptation: "the invoice has a typo, just UPDATE the row." The reality: the ledger postings it already made are now inconsistent with the document, the audit trail is a lie, and any report run against the old period silently changes.
The fix: a posted document is immutable (ch 2). Cancel (which posts reversing entries) and amend (a new draft linked by amended_from). The original, the reversal, and the amendment all survive forever. Corrections are new postings, never mutations.

Pitfall · Stock without valuation or a repost engine

The temptation: track quantity as a running integer and "figure out cost later." The reality: quantity is trivial (a sum of deltas) but cost is path-dependent — moving-average and FIFO both depend on the order of receipts — and a single back-dated GRN makes every later valuation wrong, so your COGS and margin are quietly garbage.
The fix: isolate valuation behind a pure strategy module, store the running balance + valuation snapshot on each ledger row, and build a checkpointed, resumable repost engine plus a freeze-date gate from day one (ch 4, erpnext/stock/stock_ledger.py · update_entries_after). This is the price of carrying running balances, and it is not optional.

Pitfall · Hand-entered profitability

The temptation: a margin or profit field someone types in, or a "cost" field on the sale. The reality: it is wrong the moment a price changes, it can’t be audited, and it lets staff (accidentally or otherwise) report whatever number they like.
The fix: profitability is derived — cost from the PT/invoice captured at stock-in (snapshotted onto the stock ledger valuation), revenue from POS at sale. Never hand-entered (ch 6). Margin is a report query over two ledgers, not a column.

Pitfall · Coding variants instead of modelling them

The temptation: a size and colour column on Item, or worse, a separate table per attribute, or stock tracked at style level. The reality: stock-at-style-level is wrong (size × colour must survive end-to-end), and adding "sleeve length" next season becomes a migration and a code change.
The fix: model variation as data — a template Item + an attribute catalog + a variant table with a (variant, attribute, value) join (ch 6, erpnext/controllers/item_variant.py). Adding an axis is a row, not a migration. This is KDPS’s "SKU = style × size × colour" stated as schema.

Pitfall · Permissions as if-statements

The temptation: if user.role == 'manager' and ... scattered through controllers and views. The reality: the rules drift apart, you cannot audit "who can do what" without reading all the code, and "give the auditor read-only access" becomes a sprint.
The fix: authorization is a data matrix (role × action × scope) enforced by one engine that AND-s a WHERE clause into every query, with row-level scope (one store/warehouse) decoupled from roles (ch 8). A read-only auditor is just rows that grant read and withhold write/submit — no special code. Keep the matrix queryable so an admin screen can render and audit it.

The common thread Every pitfall above is the same mistake wearing different clothes: storing a derived fact as if it were a source fact (a balance, an edit, a margin, a variant column, a permission decision). The cure is always the same: keep one append-only source of truth and derive everything else from it on read.

5 · Worked example — KDPS

KDPS Lifestyle is a multi-brand Indian fashion retailer: 50+ stores across Bihar & Jharkhand, 20,000+ SKUs, 40+ brands, today running per-store POS + Tally + Excel. It is the perfect stress test for the method because it has every interesting wrinkle — variant SKUs, consignment ownership, two-state GST, a split between quantity-recognition and value-recognition, and a statutory book of record (Tally) that lives outside the new system. Below, every KDPS concept maps onto an ERPNext pattern and the chapter that explains it.

SKU = style × size × colour — stock must be tracked at size×colour, not style Template/variant/attribute model: a template Item with has_variants, a variant per concrete SKU pinning one value per axis, attributes as master data 06

Applying to KDPS · the two recognition points The subtlest KDPS rule is that physical possession and financial liability are recognised at different moments. Goods arriving on consignment (SOR) bump the stock ledger by quantity immediately, but no GL value and no vendor liability post until the item sells. This is exactly why stock and GL are two separate ledgers (ch 4) rather than one: a single event posts to whichever ledgers its commercial model says it should. An outright purchase posts both ledgers at GRN/PT; a consignment item posts the stock ledger at GRN and the GL only at sale. Model ownership as a snapshotted dimension and let the posting composer decide which ledgers fire — never branch this in document code.
Applying to KDPS · Tally as an external mirror, not a competitor Tally remains the legal book. The trap is trying to make the new ERP be Tally or trying to read balances back from Tally. Instead: the new ERP owns the operational GL (so it can power live margin, store P&L, and dead-stock reports the moment a sale posts), and a one-way sync exports balanced vouchers into Tally for statutory filing. Because the new GL already composes balanced postings (ch 3), the Tally voucher is just a second projection of the same posting list — built by the same composer, gated by a freeze date, idempotent on re-run. The CA-sensitive single-recognition rules (when SOR/consignment GST is recognised, the 6-month deemed-supply clock) are encoded once in that composer.

6 · A minimal ERP skeleton

Here is the smallest set of entities to start any ERP. If you stand up exactly these — and nothing else — you have a working spine: you can receive goods, sell them, bill, get paid, and produce a trial balance and a stock report, all immutable and auditable. Everything in section 1’s method bolts onto this. Build them in roughly the order listed; each depends mostly on the ones above it.

The skeleton, entity by entity

Company master
The legal/operating entity. Carries the default currency (the book of record) and the default accounts. Every Account and every ledger row is stamped with it. For KDPS, one Company with a GSTIN dimension for the two states. (ch 3)
Account master · tree
A nested-set tree (lft/rgt, parent_account, is_group) classified by root_type (Asset/Liability/Income/Expense/Equity). Only leaves are postable; reports roll subtrees up. This is your chart of accounts. (ch 3)
GL Entry ledger
One immutable append-only table of one-sided postings: account, debit XOR credit, voucher_type/voucher_no, optional party_type/party + against_voucher + dimensions. Balances are SUM(debit) - SUM(credit), never stored. One posting service enforces balance. (ch 3 · erpnext/accounts/general_ledger.py)
Item master
The SKU master, with the template/variant/attribute model so variation is data. Guard structural fields (valuation method, is-stock-item) once transactions exist. (ch 6)
Warehouse master · tree
A nested-set location tree (region → store → bin); forbid transactions against group nodes; enables subtree rollups ("total stock under a region"). (ch 4)
Stock Ledger Entry ledger
Append-only per (item, warehouse) event log keyed by posting_datetime + voucher, carrying actual_qty and the running balance + valuation snapshot. Cancel the source voucher, never the SLE. (ch 4 · erpnext/stock/stock_ledger.py)
Party master
The polymorphic (party_type, party) pair so the ledger never links directly to Customer or Supplier. AR/AP are just GL rows tagged with a party + the document being settled. New party kinds need no ledger change. (ch 6 · erpnext/accounts/party.py)
Sales Invoice + child line table document
One sell-side submittable document. On submit it snapshots master values onto its lines, composes balanced GL rows (revenue + tax + receivable) and Stock Ledger Entries (issue), and recomputes status. On cancel it mirrors exactly. (ch 2, ch 5)
Purchase Invoice / Receipt + child line table document
One buy-side submittable document. For KDPS this splits into the GRN (posts the stock ledger by quantity) and the PT (posts the GL value + vendor liability) — the two-recognition-point pattern. (ch 4, ch 5)
Payment Entry document
Settles receivables/payables. Posts GL rows against the party + the invoice being settled (against_voucher); outstanding and aging fall out of summing those tagged rows. (ch 3)
Naming Series setup
A per-series counter producing human-readable IDs (ACC-SINV-.YYYY.-). Auditors and GST returns reference these; you cannot retrofit them onto posted history. (ch 1)
Role + Permission control
The access matrix as data: per-entity rows of (role × action-flags), with row-level scope (one store) AND-ed into every query. Enforced by one engine, never if-statements. The submit/cancel actions also gate the lifecycle. (ch 8)

The shared base every entity inherits

Across all of the above, two things are not per-entity and must be built once: the audit columns + lifecycle (owner, creation, modified, modified_by, docstatus, and the draft→submitted→cancelled machine) on a base model every entity inherits; and the controller hook chain (validate → before/on_submit → on_cancel, on_cancel mirroring on_submit) so posting and validation are inherited, not repeated. On Django: an abstract base model + a hook dispatcher (or signals) wired in one place.

Why this is enough to start With these entities you can run the full procure-to-pay and order-to-cash loop, every document is immutable and auditable, every balance is derived, and your trial balance and stock report are live queries that can never drift. Tax templates, pricing rules, workflow, dashboards, and the Tally mirror all bolt onto this spine without changing it. Start here, slice vertically, and grow the data — not the engine.

Takeaways

  1. Build in dependency order, not wishlist order: map the domain → meta-model discipline → ledgers + posting rules → masters with snapshotting → the transaction graph → tax/pricing as data → control plane → read side. The exciting screens sit at the top of the stack and collapse without the foundation.
  2. Obey the two laws without exception: documents post the ledgers, reports read the ledgers. Balances are always derived (SUM(debit) - SUM(credit)), never stored.
  3. Copy universal truth, adapt heavy implementations, skip generality you’re not building: copy double-entry, immutability, the hook chain, naming, snapshotting; adapt the meta-model, valuation, pricing, dimensions to your stack; skip multi-company consolidation, manufacturing, the plugin runtime, and configurable workflow until a real requirement demands them.
  4. The five non-negotiables are load-bearing walls: double-entry balance, audit columns + immutability, idempotent ordered migrations, snapshotting, and GST/tax as date-effective data. Cut any and you have a broken ERP, not a smaller one.
  5. Every classic pitfall is the same mistake: storing a derived fact (a balance, an edit, a margin, a variant column, a permission decision) as if it were a source fact. The cure is always to keep one append-only source of truth and derive everything else on read.
  6. KDPS validates the method: variant SKUs, SOR/consignment as a dimension that decides which ledgers fire, two-GSTIN tax, GRN-posts-quantity / PT-posts-value as two ledgers, and Tally as an external GL mirror — every wrinkle maps cleanly onto a pattern from chapters 01–11.
  7. Start from the minimal skeleton and grow the data, not the engine. Company, Account, GL Entry, Item, Warehouse, Stock Ledger Entry, the Party, one sales + one purchase document, Payment Entry, Naming Series, Role + Permission — on a shared base of audit columns + lifecycle + hook chain — is a complete, auditable spine.

The Tax & Pricing Engine

Tax templates, charge types, inclusive vs exclusive, item-level overrides, the calculation controller, pricing rules and promotional schemes, price lists, and how regional tax (GST) plugs in as data, not code.

Why this subsystem decides whether your ERP survives the real world

Every ERP eventually meets a tax authority and a sales floor, and both move faster than your deploy pipeline. A government changes a GST slab with three weeks' notice. A regional manager invents a "buy two get the cheapest free, but only in Patna stores, only this weekend, stacked on top of the existing 20% off but not below cost" promotion and expects it live tomorrow. If tax rates and discount logic live in your application code, every one of these is an engineering ticket, a regression risk, and a release. The system that hard-codes tax = amount * 0.18 is dead on arrival — not because the arithmetic is wrong, but because the arithmetic is the easy part and putting it in code is the expensive mistake.

ERPNext's tax and pricing engine is the canonical answer to this problem, and it is worth studying closely because it is two cooperating subsystems built on a single idea: tax and price are configuration rows interpreted by a generic calculation engine, never hand-coded per scenario. A tax is a row. A discount is a row. A regional levy is a row that references an earlier row. The engine is a small interpreter that walks items against those rows. When the law changes, you insert a dated row; when a promotion launches, you author a scheme that compiles into rows. Code does not move.

Key idea

Build tax and pricing as a small generic calculation engine over declarative data rows, not as per-scenario code. A tax/charge becomes a typed row whose charge_type is an opcode the engine evaluates; rows compose by referencing earlier rows. Every rate and price is effective-dated, category-scoped data with per-item overrides. Discounts are declarative rules matched by dimension, slab, condition and validity, resolved by an explicit priority. Statutory behaviour layers in through a region-keyed override seam. This single shape expresses GST, VAT, cess-on-tax, tax-on-freight, fixed charges, per-unit levies, value-slab discounts, and buy-X-get-Y — with no new code per case.

This chapter walks both halves. We start with the tax side: the template, the charge-type interpreter, inclusive vs exclusive back-solving, per-item rate overrides, and the rounding discipline that keeps the books reconciled. Then the price side: price lists, item prices, the pricing-rule matcher, and the promotional-scheme generator that compiles ergonomic promos into flat runtime rules. We close with the regional-override seam that lets India GST ship as a separate app while core carries zero GST math — and the takeaways a builder returns to.

The tax side — a typed-row interpreter

The tax half of the engine is the more subtle of the two, because it has to compose. A transaction carries a child table of tax/charge rows. Each row is a tuple: (charge_type, rate, account_head, row_id, included_in_print_rate). The single class erpnext/controllers/taxes_and_totals.py walks every item against every tax row and treats charge_type as a small instruction set. This is the heart of the whole subsystem.

PATTERN

Charge-type as a tiny interpreter (composable tax stack)

The idea

A tax or charge is not a hardcoded formula but a typed row whose charge_type is an opcode the engine evaluates. Rows compose by referencing an earlier row, so cess-on-GST, tax-on-freight, surcharges and per-unit levies all emerge from data — no new code per levy.

Never branch on country or tax name. Branch only on the opcode.

How ERPNext does it

get_current_tax_and_net_amount in erpnext/controllers/taxes_and_totals.py switches on charge_type:

  • On Net Total — rate% of the item's net amount.
  • On Previous Row Amount / Total — reads taxes[row_id-1]'s running per-item tax or grand total. This is how stacking works.
  • Actual — a fixed amount distributed proportionally by net.
  • On Item Quantity — rate × qty.

Each row carries a row_id pointing at the row it composes on.

Apply to any ERP

Model tax lines as rows with an enum kind and an optional depends_on_row. Evaluate them in order, in a single pass per item, keeping a per-item running total so "on previous total" rows can read it.

The cardinal rule: never branch on country or tax-name in code — only on charge_type. GST, VAT, cess, freight tax and fixed fees are then all the same five branches.

Here is the interpreter itself. Note how compactly five real-world tax behaviours collapse into five branches of one switch, and how composition (On Previous Row …) just indexes back into the same taxes table by row_id:

if tax.charge_type == "Actual":
    current_net_amount = item.net_amount
    actual = flt(tax.tax_amount, tax.precision("tax_amount"))
    current_tax_amount = item.net_amount * actual / self.doc.net_total if self.doc.net_total else 0.0
elif tax.charge_type == "On Net Total":
    current_tax_amount = (tax_rate / 100.0) * item.net_amount
elif tax.charge_type == "On Previous Row Amount":
    current_net_amount = self.doc.get("taxes")[cint(tax.row_id) - 1].tax_amount_for_current_item
    current_tax_amount = (tax_rate / 100.0) * current_net_amount
elif tax.charge_type == "On Previous Row Total":
    current_net_amount = self.doc.get("taxes")[cint(tax.row_id) - 1].grand_total_for_current_item
    current_tax_amount = (tax_rate / 100.0) * current_net_amount
elif tax.charge_type == "On Item Quantity":
    current_tax_amount = tax_rate * item.qty

Gotcha — the Actual remainder lands on the last item

Actual distributes a fixed amount proportionally by net_amount, but integer/fraction division leaves a remainder. ERPNext dumps that divisional remainder onto the last item (via actual_tax_dict). If you reimplement proportional distribution and forget the last-item correction, you silently lose pennies and the per-item breakup will not sum to the charge total.

Applying to KDPS

India GST on apparel is exactly this composition: CGST and SGST are each "On Net Total"; a cess (where it applies) is "On Previous Row Total" stacking on the GST row; a fixed handling charge would be "Actual". KDPS never needs GST code — it needs a tax template whose rows carry the right charge_type and account_head, plus the per-item slab override below.

Inclusive vs exclusive — back-solving the net

Indian retail quotes MRP — the price including tax. So the entered amount is gross, and the engine must recover the tax-exclusive net before it sums anything. Get the order of operations wrong and every downstream total is off.

PATTERN

Inclusive vs exclusive by back-solving a tax fraction

The idea

When price already includes tax, you recover the tax-exclusive net before summing by dividing the gross by (1 + sum of tax fractions). The sum must respect row composition so stacked inclusive taxes are handled correctly.

How ERPNext does it

determine_exclusive_rate computes a cumulated_tax_fraction from get_current_tax_fraction, which converts each inclusive row's rate (including "On Previous Row" composition) into a fraction. It then sets item.net_amount = item.amount / (1 + cumulated_tax_fraction). The included_in_print_rate flag on the tax row is the inclusive switch. adjust_grand_total_for_inclusive_tax later reconciles a tiny residual.

Apply to any ERP

Keep one boolean inclusive per tax row. If any inclusive row exists, run a pre-pass that turns rates into fractions (respecting composition), divide the entered amount by (1+sum) to get net, then run the normal exclusive pass on that net.

Store both net and gross; reconcile rounding into one adjustment field.

if (not self.discount_amount_applied and item.qty
        and (cumulated_tax_fraction or total_inclusive_tax_amount_per_qty)):

Gotcha — inclusive interacts with discounts, and order is load-bearing

Net is back-solved from gross before a document discount is applied. And adjust_grand_total_for_inclusive_tax only absorbs a residual up to 5/10^precision — larger diffs are dropped, not raised. If you compute discount first then back-solve, or expect the reconciliation to swallow any size of error, your inclusive-MRP totals will drift. The sequence — back-solve, then discount, then reconcile a bounded residual — is not optional.

Per-item rate override — slab variation as data

The same tax account ("Output GST") must charge 5% for one HSN and 12% for another, on the same invoice. You cannot model that on the tax-template row, because the row has one rate. The answer is a per-item override map resolved at calculation time.

PATTERN

Per-item rate override against a shared account (HSN/slab variation as data)

The idea

The same tax account must charge different rates for different items. Resolve the rate at calc time from a per-item map, falling back to the template row's rate when the item has no override for that account.

An explicit "not applicable" sentinel — distinct from 0% — lets an item remove itself from a tax account entirely.

How ERPNext does it

Item Tax Template holds {tax_type(Account) → tax_rate} rows. get_item_tax_map in erpnext/stock/get_item_details.py flattens it to a JSON map stored on the item line as item_tax_rate. _load_item_tax_rate parses it; _get_tax_rate returns the item's rate if the account matches, else the row rate. The sentinel NOT_APPLICABLE_TAX = "N/A" exempts the item from that account.

get_item_tax_map:887 · _load_item_tax_rate:344 · _get_tax_rate:383

Apply to any ERP

Carry a per-line JSON/map {account_id: rate}. In the engine, when computing a tax line, look up the item's override for that account first; fall back to the line's default rate.

Support an explicit "not applicable" sentinel distinct from 0% so exemptions and reverse-charge are unambiguous.

def _get_tax_rate(self, tax, item_tax_map):
    if tax.account_head in item_tax_map:
        rate = item_tax_map[tax.account_head]
        if rate == NOT_APPLICABLE_TAX:
            return NOT_APPLICABLE_TAX
        return flt(rate, self.doc.precision("rate", tax))
    return tax.rate

Gotcha — "not applicable" is not 0%

NOT_APPLICABLE_TAX = "N/A" is a sentinel distinct from rate 0. It removes the item from that tax account entirely — no row in the breakup. Treating "not applicable" as 0% produces phantom zero-rated breakup rows and breaks reverse-charge handling, where the difference between "taxed at zero" and "this account does not apply" is legally and arithmetically real.

Date- and value-effective master selection

Rates and prices change over time. The naive instinct — edit the rate in place — destroys history and silently re-prices last year's invoices when you reopen them. The discipline is to never mutate a rate row; insert a new dated one, and select by effective date at transaction time. This pattern recurs for both Item Tax Templates and Item Prices.

PATTERN

Date-and-value-effective master selection

The idea

Rates and prices change over time and by qualifying conditions, so selection must pick the right version by effective date and value band — never by overwriting history. Old invoices keep the rate that was in force when they were posted.

How ERPNext does it

_get_item_tax_template in erpnext/stock/get_item_details.py keeps only templates with valid_from <= validation_date (bill_date ‖ posting_date ‖ transaction_date), within minimum_net_rate..maximum_net_rate (is_within_valid_range), matching tax_category; then sorts valid_from desc and takes the newest. Item Price selection mirrors this with valid_from/valid_upto.

valid_from filtering:825 · is_within_valid_range:868 · item price ordering:1132

Apply to any ERP

Give effective-dated masters valid_from/valid_upto, optional value bands, and a category key. Selection = filter to rows valid on the transaction date and matching category, order by valid_from desc, take the first.

Never mutate an old rate row — insert a new dated one.

This single selection rule turns a GST slab change into a data entry task. The accountant inserts a new Item Tax Template with valid_from set to the notification date; invoices before that date keep selecting the old one, invoices after select the new — with zero code change and full history intact.

Gotcha — precedence is date AND value AND category

Item Tax Template selection is simultaneously date-effective, value-banded (minimum_net_rate..maximum_net_rate) and tax_category-scoped; the newest valid valid_from wins. A template with no validity is a fallback only, used when none with validity match. Get the precedence wrong and you silently apply last year's GST slab — the kind of error nobody notices until an audit.

Applying to KDPS

The CLAUDE.md rule "apparel GST is slab-based and date-effective — model it as data, not code" is this pattern. Each HSN-slab is an Item Tax Template with a valid_from; a slab revision is a new dated row. And the five money-critical CA-ruling items (SOR single-recognition, deemed-supply clock, late freight, sold-before-PT, no-reposting) should sit behind an effective-dated rate/rule table for exactly this reason: a CA ruling changes data, not code.

The price side — price lists and dated item prices

Before any discount, an item needs a base rate. ERPNext keeps prices in two layers. A Price List is a Setup master flagged selling or buying, scoped to a currency. Item Price rows give the base price_list_rate for one item in one price list (optionally per UOM, per customer), and they are date-effective with valid_from/valid_upto — the same effective-dated selection pattern above. The selling-price flow runs price resolution first, then layers discounts on top:

get_item_detailsfetch Item Price (date-effective price_list_rate)
Pricing Rule enginematch by apply_on / qty / amount / condition / priority → rate_or_discount
apply_price_discount_rulewrites price_list_rate / discount onto the item line
calculate_item_valuesrate = price_list_rate − discount (+margin); amount = rate × qty
calculate_taxes_and_totalsnet, taxes, grand, rounded

The separation matters: the base price is a quiet, dated master fact; the discount is a rule that competes with other rules. Conflating them — putting "sale price" directly in the price list — loses the audit trail of why a line was cheaper. ERPNext keeps the list price and records the discount as a derived adjustment, so a printed invoice can show "MRP ₹2,000, less 20% = ₹1,600" rather than just ₹1,600.

The pricing-rule matcher — declarative discounts

This is the price-side counterpart to the charge-type interpreter, and the same philosophy drives it: a discount is data, matched and resolved by a generic engine, never a hand-coded promotion. The matcher in erpnext/accounts/doctype/pricing_rule/utils.py is where every offer KDPS ever invents will live.

PATTERN

Rule-matching pricing engine with slabs, conditions and priority

The idea

Discounts and prices are declarative rules matched against a transaction by dimension (item / group / brand / customer / territory), quantity or amount slab, validity dates and a free-text condition — then resolved deterministically by an explicit priority. Ties are an error, not a coin-flip.

How ERPNext does it

get_pricing_rules/_get_pricing_rules build SQL across the Pricing Rule {Item Code | Item Group | Brand} child tables, expanding groups via nested-set lft/rgt (_get_tree_conditions). filter_pricing_rule_based_on_condition runs the rule's condition through frappe.safe_eval. filter_pricing_rules_for_qty_amount enforces slabs. filter_pricing_rules keeps the max priority, prefers matching currency/price-list, and throws MultiplePricingRuleConflict on an unresolved tie.

Apply to any ERP

Store rules as rows with: target dimension + ids, qty/amount min/max, validity dates, an optional sandboxed boolean expression, applicable-for filters, and an integer priority. Match = filter by all predicates; resolve = max priority, then a stable tiebreak, else error. Keep the action (set rate / % off / amount off / free qty) as data the engine applies — not code.

The output of a matched rule is rate_or_discount ∈ {Rate, Discount Percentage, Discount Amount}, plus an optional margin and an optional free product (buy-X-get-Y, including recursive). The two load-bearing details are the sandboxed condition and the priority resolution:

A note on the sandboxed condition

frappe.safe_eval(cond, None, doc.as_dict()) Frappe core evaluates a free-text boolean against the whole document — so a rule can say customer_group == "Wholesale" and grand_total > 50000 without any new code. This is enormous expressive power from one field, and it is why ERPNext rarely needs custom discount code. The safety comes from safe_eval's restricted execution environment, not from the rule author. On your own stack, do not reach for raw eval — build or borrow a restricted evaluator first.

Gotcha — group matching is a tree walk, and ties throw

Two traps live in this matcher. First, Item Group / Customer Group / Territory matching uses nested-set lft/rgt tree expansion, so a rule on a parent group must match items in child groups. A flat equality match silently fails for hierarchical masters. Second, when priority cannot break a tie, ERPNext throws MultiplePricingRuleConflict rather than picking arbitrarily (except in shopping-cart context). A custom engine that quietly picks one will diverge from ERPNext and from what your accountant expects — a "wrong but consistent" discount is worse than a loud error.

The promotional-scheme generator — compile, don't interpret promos

The pricing-rule matcher is powerful but low-level: one rule per item-set per slab per applicable-for value. Authoring a "buy 3 get 1, buy 5 get 2, across these four brands, in these eight stores" promotion as raw pricing rules is dozens of rows by hand. ERPNext solves this with a generator that lets you author the friendly form once and compiles it down to flat rules the matcher already understands.

PATTERN

Generator master that compiles into runtime rules

The idea

Author promotions ergonomically as slab tables, but keep the runtime engine simple by compiling the friendly form into many flat, individually-matchable rules. The runtime never special-cases promotions — it just sees more rules.

How ERPNext does it

Promotional Scheme holds price_discount_slabs and product_discount_slabs. on_update → update_pricing_rules → get_pricing_rules → prepare_pricing_rule/set_args create one Pricing Rule doc per slab × applicable-for value, tagged with promotional_scheme and promotional_scheme_id. on_trash/get_invalid_pricing_rules clean up orphans.

Gotcha — the generated rules are the runtime source of truth

A Promotional Scheme is a code generator. Editing the scheme regenerates the Pricing Rule docs; changing "Applicable For" is blocked once transactions exist (raise_for_transaction_exists). Applying to KDPS

KDPS's brand-specific offers map onto this model exactly. Value slabs and gifts-above-threshold are price/product discount slabs; B2G1-with-lowest-item-free is the recursive free-product rule (ERPNext's get_product_discount_rule); per-store applicability is the applicable-for dimension (warehouse/store); start/end dates with fallback are rule validity + priority. Author one Promotional Scheme per brand offer, let it compile to flat rules matched by store/brand/date/priority — and the POS calc engine stays a single dumb matcher.

Regional statutory logic — GST as a plugin, not a fork

The final pattern is the one that makes the rest portable. India GST, UAE VAT and Italian e-invoicing are all statutory behaviour that must layer onto a country-agnostic core without editing it, selected at runtime by the company's country. ERPNext does this with a hook table plus a decorator — and ships GST itself as an entirely separate installed app.

PATTERN

Regional statutory logic via override hooks (no core fork)

The idea

Country-specific tax behaviour must layer onto a country-agnostic core without editing it, selected at runtime by the entity's region. Each jurisdiction is a plugin that registers overrides and seeds data, not a branch in core.

How ERPNext does it

@erpnext.allow_regional Frappe core wraps a core function; at call time it looks up its own dotted path in frappe.get_hooks("regional_overrides")[get_region()] and dispatches to the last-installed app's implementation, else runs the default. erpnext/hooks.py's regional_overrides maps e.g. UAE/Italy update_itemised_tax_data. India GST ships as a separate app plugging into these seams plus the generic Item Tax Template / Tax Category data.

allow_regional: __init__.py:133 · hooks.py:624 · update_itemised_tax_data:1257

Apply to any ERP

Make tax-touching functions overridable: register override tables keyed by region, resolve the active region from the company/tenant, and dispatch via a decorator. Ship statutory packs as plugins that register overrides and seed data (templates, categories) rather than branching core.

def caller(*args, **kwargs):
    overrides = frappe.get_hooks("regional_overrides", {}).get(get_region())
    function_path = f"{inspect.getmodule(fn).__name__}.{fn.__name__}"
    if not overrides or function_path not in overrides:
        return fn(*args, **kwargs)
    # Priority given to last installed app
    return frappe.get_attr(overrides[function_path][-1])(*args, **kwargs)

This separation is the feature, not a gap.

Applying to KDPS

The two-GSTIN / cross-state-IGST requirement maps directly onto Tax Category: an "In-State" category selects a CGST+SGST template, an "Out-of-State" category selects an IGST template, and the transaction's place-of-supply picks the category. That is exactly ERPNext's mechanism — no special cross-state code. Because KDPS is on Django/Postgres, you reimplement the calc engine as a single in-memory pass, but you keep this same separation: GST math behind an effective-dated rate table and a region/category selector, so a CA ruling changes data, and Tally (the statutory book of record) is fed from the same posted figures.

Rounding — the part that bleeds money if you get it wrong

Everything above is the easy 90%. Rounding is the hard 10% where naive reimplementations lose pennies and fail reconciliation. ERPNext treats it as a deliberate, layered concern, and you must too. There are three distinct mechanisms, and skipping any one breaks the books.

set_item_wise_tax — error-diffusion
Per-item tax is derived as a delta of a running cumulative total, not as "round this item's tax in isolation". Each item's tax = (cumulative tax through this item) − (cumulative tax through the previous item). This guarantees the per-item breakup sums exactly to the row total. Naive "round each item then sum" will not reconcile, and adjust_rounding_in_item_wise_tax_details will throw "Item Wise Tax Details do not match".
round_based_on_smallest_currency_fraction
The final grand total snaps to the currency's smallest fraction (e.g. nearest rupee), and the difference is recorded in a single rounding_adjustment field — so the snap is auditable, not silent.
The inclusive residual
adjust_grand_total_for_inclusive_tax reconciles the tiny diff left by back-solving inclusive tax into grand_total_diff — but only up to a bounded threshold, as noted earlier.
Gotcha — the calc is a stateful, mutating, fixed-point pipeline

The whole calculation is a single class instantiated per save (calculate_taxes_and_totals.__init__ runs .calculate()); it mutates the document in place and is re-run when a document-level discount forces recomputation (need_recomputation → calculate(ignore_tax_template_validation=True)). Reimplementers who treat it as a pure function miss that it iterates to a fixed point. Model it as an idempotent pipeline you can re-run, not a one-shot formula — and keep the error-diffusion discipline so breakups always reconcile to totals.

The full tax flow, end to end, ties these together: a template is copied into the doc's taxes rows → each item loads its item_tax_rate JSON map from its selected Item Tax Template → calculate_taxes walks items × tax rows, evaluating charge_type and overriding rate per item → set_item_wise_tax builds the per-item breakup via error-diffusion deltas → calculate_totals sums to grand_total → set_rounded_total snaps to the currency fraction and records rounding_adjustment.

Takeaways

  1. Tax and price are data, not code. A tax is a row; a discount is a row; a regional levy is a row that references another row. The engine is a small interpreter. When the law or a promotion changes, you insert rows — code does not move.
  2. Make charge_type an opcode. Five branches — On Net Total, On Previous Row Amount/Total, Actual, On Item Quantity — express GST, cess-on-tax, tax-on-freight, fixed charges and per-unit levies. Rows compose via row_id. Never branch on country or tax name in code.
  3. Back-solve inclusive tax before summing. If a price includes tax, divide gross by (1 + cumulated_tax_fraction) to recover net first, respecting composition; then run the exclusive pass; then reconcile a bounded residual. Order of operations is load-bearing.
  4. Override rates per item against a shared account via a {account: rate} map, with a "not applicable" sentinel distinct from 0%. This is how one invoice carries multiple HSN/GST slabs against one Output GST account.
  5. Effective-date everything. Rates and prices get valid_from/valid_upto + value bands + a category key. Select by transaction date, order valid_from desc, take the first. Never mutate an old rate row — a slab change or CA ruling is a new dated row.
  6. Discounts are matched rules resolved by priority. Filter by dimension (with nested-set tree expansion), qty/amount slab, sandboxed condition and validity; resolve by max priority; throw on an unresolved tie. Keep the action (rate / % / amount / free qty) as data.
  7. Compile ergonomic promos into flat rules. A Promotional Scheme generator fans out into individually-matchable Pricing Rules tagged with their source id, so the runtime never special-cases promotions and regeneration stays idempotent.
  8. Ship statutory packs as region-keyed plugins. A decorator dispatches tax-touching functions to the active region's override, else the default. Core carries zero GST/VAT math; jurisdictions register overrides and seed template/category data.
  9. Treat rounding as a first-class concern. Error-diffusion deltas so per-item breakups reconcile to totals, currency-fraction snapping, and a single auditable rounding_adjustment field. This is where naive reimplementations lose money and fail reconciliation.
  10. The calc is a stateful, re-runnable pipeline that mutates the document and iterates to a fixed point after document discounts — not a pure one-shot formula. Build it idempotent.

# Deliver

`/deliver 118`, or `/deliver next` for the oldest unassigned `ready-for-agent` issue.

One issue through seven gates, in order, ending at an open PR with evidence.
A human merges.

A gate is a stop point.
When it fails and the fix is outside the issue's scope: stop, report, leave the branch as it is.
Keep the gate as strong as it is and the issue as small as it is.

Keep your context to the issue, the code you write, and one verdict per gate.
Implementation runs here because the code is the thing you must keep; every heavy gate runs in a subagent capped with a word limit and the shape of its reply.
Scratch files (CI logs, screenshots, QA notes) go in the session scratchpad, never the repo.

## Gate 0 - Issue still current

The issue is already triaged, so take scope, testability and design conformance as settled.
Three checks:

```bash
gh issue view <n> -R bruhanand/KDPS --comments
git fetch origin --prune
gh pr list -R bruhanand/KDPS --state open --json number,title,headRefName,files
```

1. **Body matches the comments.**
   A ruling left in a comment while the body holds the old spec means two specs, and TDD will faithfully build the wrong one (that is how #96 got built wrong).
   Say which two disagree, ask for the body to be rewritten, stop.
2. **Declared blockers are closed.**
3. **No open PR touches the same files for the same reason.**

Any check fails: comment on the issue prefixed `> *This was generated by AI during delivery.*`, and stop.

## Gate 1 - Claim and branch

```bash
gh issue edit <n> -R bruhanand/KDPS --add-assignee @me
git checkout main && git pull --ff-only origin main
git checkout -b <type>/<n>-<slug>        # feat/ fix/ chore/ refactor/
```

Another agent may share this working tree: move work with commits, never `git stash`, and a dirty tree holding someone else's work is a stop.

## Gate 2 - Implement

Use `/tdd` at the seams the issue names; prefer an existing seam, fewest seams wins.
To orient, send an `Explore` subagent and ask for paths plus a two-line summary.

Money paths (ledgers, postings, GST, valuation, documents/FSM): run `/grill-with-docs` on the design before writing code, and route every posting through `post_entries`.

Commit in small, honest steps.

## Gate 3 - Quick checks

The full gate takes five minutes and runs once, at Gate 7.
Here, check only what you touched, in seconds:

```bash
cd app/backend && uv run pytest <the one test file> -q
cd app/backend && uv run mypy core config
npm --prefix app/frontend run typecheck
```

## Gate 4 - Simplify

Send to a `general-purpose` subagent, synchronous:

> Run the `/simplify` skill over the diff against `main` and apply the fixes. Do not run `npm run ci` - the full gate runs once, later. Check only the files you touched: `uv run pytest <affected file> -q`, `npm --prefix app/frontend run typecheck`.
> Return in **under 150 words**: what you changed, one line each. No diffs, no code.

Simplify is quality only; Gate 5 still runs.

## Gate 5 - Review

Run `/code-review main` (it already fans out to two capped subagents).

Fix every **Spec** finding, or record a deliberate deviation and its reason in the PR body.
Fix hard **Standards** violations; name the judgement-call smells you consciously left.
Re-run only the affected test file after a fix.

**Two rounds, then escalate** - a finding that survives two honest attempts is telling you something about the design.

Read [ESCALATION.md](ESCALATION.md) before acting on any finding that touches **money**, that the design corpus does not settle, or that has outgrown the issue.
In one line: fix it when you can quote the rule you are applying, ask when you cannot, and money always goes back to the human.

## Gate 6 - Live QA

Start the full gate in the background, then QA while it runs (pytest builds its own database; the browser drives `kdps_dev`):

```bash
npm run ci > "$SCRATCH/ci.log" 2>&1 &     # read it at Gate 7
```

QA lives entirely in one `general-purpose` subagent, synchronous.
Give it the issue's acceptance criteria, the branch name, the path to [LIVE-QA.md](LIVE-QA.md), and:

> Follow LIVE-QA.md exactly. Save screenshots to the scratchpad directory and reference them by path.
> Return in **under 300 words**: the four precondition results as one line; then per flow - name, pass or fail, and for each fail what you clicked, what you expected, what happened, and the network or console line that proves it; then the screenshot paths; then any out-of-scope defect you filed, with its issue number.
> Do not paste accessibility trees, network dumps, console logs or screenshots into your answer.

Fix a failed flow in your own context, then send a **fresh** subagent to re-drive only the failed flows.
Two re-drives at most, then [ESCALATION.md](ESCALATION.md).

## Gate 7 - The gate, then the pull request

```bash
tail -40 "$SCRATCH/ci.log"
```

This is the acceptance gate and the only time it runs: ruff format + ruff + mypy strict + `makemigrations --check` + import-linter + pytest + frontend tsc/vitest.
**Green means green** - cloud CI runs a subset and does not substitute.
Grep the log for failures rather than reading it whole.

Red: fix, re-run the full gate, wait for it.
A pre-existing unrelated failure: fix it if small and say so in the PR, otherwise open a separate issue.

```bash
git push -u origin HEAD
gh pr create -R bruhanand/KDPS --base main --title "<type>: <what changed> (#<n>)" --body-file <file>
```

```markdown
Closes #<n>

## What changed
<plain language, two or three sentences>

## Gates
- `npm run ci`: green
- `/simplify`: <applied / nothing found>
- `/code-review main`: <n> Spec findings (all fixed | listed below), <n> Standards findings
- Live QA: <n> flows exercised, <n> API calls asserted, console clean

## Live QA evidence
<per acceptance criterion: what was clicked, what rendered, which endpoint fired with which status>
<screenshots attached>

## Deliberate deviations
<anything the review flagged that was consciously kept, with the reason. Delete if none.>

## Not covered
<anything a human must check by hand. Delete if none.>
```

Comment the same summary on the issue and **stop**: the PR stays open, the issue stays open, nothing deploys.
Under `/loop`, call `ScheduleWakeup` with `stop: true` here.

## Running several at once

`/deliver <n>` fans out across separate sessions, under two hard constraints:

- **The dev stack is single-tenant** (Postgres `:55432`, API `:8001`, Vite `:3000`), so only one session holds Gate 6 at a time; LIVE-QA.md says how to detect and wait.
- **The working tree may be shared**: leave other sessions' branches and history alone.

Holding for the stack: run Gates 0 to 5 fully, queue for Gate 6, and say plainly that you are waiting.

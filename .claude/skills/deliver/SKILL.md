# Deliver

Take **one** issue from `ready-for-agent` to an **open PR with evidence**, and stop there.

Usage: `/deliver 118`, or `/deliver next` to take the oldest unassigned `ready-for-agent` issue.

This skill never merges, never pushes to `main`, and never closes the issue.
A human reviews and merges.

## The gates

Each gate is a stop point.
If a gate fails and you cannot fix it inside the issue's scope, **stop, report, and leave the branch as it is**.
Do not widen the issue to make a gate pass, and do not weaken a gate to make the issue pass.

| # | Gate | Runs in | Fails when |
|---|---|---|---|
| 0 | Issue still current | here, 3 checks | A ruling sits unmerged in the comments, a blocker is open, or a PR collides |
| 1 | Claim + branch | here | - |
| 2 | Implement (TDD) | **here** | - |
| 3 | Green (`npm run ci`) | here, logged to file | Any lint, type, migration, import-contract or test failure |
| 4 | Simplify | subagent | - |
| 5 | Two-axis review | subagents | An unfixed Spec finding, or a hard Standards violation |
| 6 | Live QA | subagent | A screen, API call, or console is not clean in a real browser |
| 7 | PR | here | - |

Gates 5 and 6 can also produce a finding that must **not** be fixed on the branch at all - see [ESCALATION.md](ESCALATION.md).

## Context discipline

**Your context holds the issue, the code you write, and one verdict per gate. Nothing else.**

Gate 2 runs here because the code you write is the thing you must keep, and Gate 0 is three cheap commands.
Every other gate reads a lot or prints a lot and ends in a short answer, so it goes to a subagent that returns that answer and nothing more.

Three rules:

- **Never read a screenshot into this context.** The QA subagent looks at them and writes down what it saw.
- **Never paste a full CI log.** Redirect it to a file and read the failing lines.
- **Cap every subagent.** Tell it the word limit and the exact shape of what to return.

If a subagent comes back with a wall of text, that is a bug in the prompt you gave it, not something to work around.
Scratch files (CI logs, screenshots, QA notes) go in the session scratchpad directory, never in the repo.

## Gate 0 - Is the issue still what it says it is

Anand reviews issues before they reach you, so do not re-litigate scope, testability or design conformance.
Three checks only, inline, no subagent.

```bash
gh issue view <n> -R bruhanand/KDPS --comments
git fetch origin --prune
gh pr list -R bruhanand/KDPS --state open --json number,title,headRefName,files
```

1. **Does the body still match the comments?**
   A ruling or decision left in a comment while the body holds the old spec means the issue carries two specs.
   That is how #96 got built wrong.
   Do not implement it: say which two disagree, ask for the body to be rewritten, and stop.

2. **Are the declared blockers closed?**
   An open blocker means it is not ready, whatever the label says.

3. **Is another open PR touching the same files for the same reason?**
   That is a collision. Say so and stop.

All three pass, go. Any one fails, comment on the issue (prefixed `> *This was generated by AI during delivery.*`), and stop.

TDD will faithfully build whatever spec you hand it, tests and all.
These three checks exist because that is exactly the problem: they are the only failures TDD cannot catch by being rigorous.

## Gate 1 - Claim and branch

```bash
gh issue edit <n> -R bruhanand/KDPS --add-assignee @me
git checkout main && git pull --ff-only origin main
git checkout -b <type>/<n>-<slug>        # feat/ fix/ chore/ refactor/
```

Branch off fresh `main` unless the issue declares a blocker that is merged elsewhere.

**Never `git stash` in this workspace.**
Another agent may be writing to the same working tree, and one stash/pop pair has already swapped a whole diff before.
If the tree is dirty with work that is not yours, stop and say so.

## Gate 2 - Implement

This is the one gate that runs in your own context, because the code you write is the thing you must keep.

Use `/tdd` at the seams the issue names.
Prefer an existing seam to a new one; the fewest seams wins.

If you need to find your way around first, send an `Explore` subagent and ask for file paths and a two-line summary, not excerpts.

Money-path work (ledgers, postings, GST, valuation, documents/FSM) carries two extra obligations:

- Run `/grill-with-docs` on the design before writing code, per the money-slice process.
- Every posting must go through the kernel (`post_entries`), never around it.

Typecheck and run the single affected test file often.
Commit in small, honest steps on the branch.

## Gate 3 - Green

A failing `npm run ci` prints thousands of lines, and you need about ten of them.
Always log it to the scratchpad and read the tail:

```bash
npm run ci > "$SCRATCH/ci.log" 2>&1; echo "exit=$?"; tail -40 "$SCRATCH/ci.log"
```

Grep the log for the specific failure instead of reading it whole.
Re-runs during the fix loop can be narrowed: `uv run pytest <one file>`, `npm --prefix app/frontend run typecheck`.
Run the full gate again only when you think you are done.

This is the acceptance gate: ruff format + ruff + mypy strict + `makemigrations --check` + import-linter + pytest + frontend tsc/vitest.

**Green means green.**
Cloud CI runs only a subset, so a green GitHub Actions run does not substitute for this.
If you find a pre-existing failure unrelated to your issue, fix it if it is small, and say in the PR that you did.
If it is not small, open a separate issue and note it - do not leave a red gate undescribed.

## Gate 4 - Simplify

Send this to a subagent (`general-purpose`, synchronous), so the whole diff and its reasoning stay out of your context:

> Run the `/simplify` skill over the diff against `main`, apply the fixes, then run `npm run ci` (logging to a file, reading only the tail).
> Return in **under 150 words**: what you changed, as one line each, and whether CI is green. Do not paste diffs or code.

If it reports CI red and cannot fix it, pull the change back into your own hands.

Simplify is quality only.
It does not hunt for bugs, so it never replaces Gate 5.

---

## Gate 5 - Review

Run `/code-review main`.
It already fans out to two parallel subagents capped at 400 words each, so it is cheap - leave it as it is.

Handle the findings by axis:

- **Spec findings** (missing requirement, scope creep, wrong implementation) - fix all of them, or, if a finding is a deliberate deviation, record the reason in the PR body.
- **Standards findings** - fix hard violations.
  Judgement-call smells are yours to weigh; state the ones you consciously left.

Re-run `npm run ci` after any fix.

**Two rounds, then stop.**
If a finding survives two honest attempts to fix it, it is not a bug you are failing to squash - it is telling you something about the design.
Escalate rather than try a third time.

---

## When a finding is more than a bug

Fix ordinary findings and move on.

Read [ESCALATION.md](ESCALATION.md) before acting when a finding touches **money**, when the design corpus does not settle it, when the fix has outgrown the issue, or when it survived two fix attempts.

The rule in one line: fix it when you can quote the rule you are applying, stop and ask when you cannot, and **anything about money always comes back to Anand**.

## Gate 6 - Live QA

This is the gate that matters for an ERP, and it is the one no other skill covers.
Tests passing is not evidence a screen works.

It is also by far the most expensive gate to hold in context: every screenshot is an image, every accessibility snapshot is a page of tree, every network dump is a page of JSON.
**Run it in a subagent and never look at the pictures yourself.**

Spawn one `general-purpose` subagent, synchronous, with: the issue's acceptance criteria, the branch name, the path to [LIVE-QA.md](LIVE-QA.md), and this brief:

> Follow LIVE-QA.md exactly. Save screenshots to the scratchpad directory and reference them by path.
> Return in **under 300 words**: the four precondition results as one line; then per flow - name, pass or fail, and for each fail what you clicked, what you expected, what happened, and the network or console line that proves it; then the screenshot paths; then any out-of-scope defect you filed, with its issue number.
> Do not paste accessibility trees, network dumps, console logs or screenshots into your answer.

If a flow fails, fix it here in your own context, then send a **fresh** subagent to re-drive only the failed flows.
Do not reuse the first one; its context is full of what it already looked at.

QA is where the worst findings surface: a screen showing the wrong money, a user seeing another store's data, a button that posts twice.
Two re-drives at most, then read [ESCALATION.md](ESCALATION.md).

## Gate 7 - Pull request

Push the branch and open a PR against `main`:

```bash
git push -u origin HEAD
gh pr create -R bruhanand/KDPS --base main --title "<type>: <what changed> (#<n>)" --body-file <file>
```

PR body:

```markdown
Closes #<n>

## What changed
<plain language, two or three sentences>

## Gates
- `npm run ci`: green
- `/simplify`: <applied / nothing found>
- `/code-review main`: <n> Spec findings (all fixed | listed below), <n> Standards findings
- Live QA: <n> flows exercised, <n> API calls asserted, console clean

## Live QA evidence
<per acceptance criterion: what was clicked, what rendered, which endpoint fired with which status>
<screenshots attached>

## Deliberate deviations
<anything the review flagged that was consciously kept, with the reason. Delete if none.>

## Not covered
<anything a human must check by hand. Delete if none.>
```

Then comment the same summary on the issue, and **stop**.

Do not merge.
Do not close the issue.
Do not deploy.

If this was invoked under `/loop`, call `ScheduleWakeup` with `stop: true` here - the work is done and further wakeups are waste.

## Running several at once

Anand fans out by invoking `/deliver <n>` in separate sessions or workspaces.
Two constraints follow, and both are hard:

- **The dev stack is single-tenant.** One shared Postgres on `:55432`, API pinned to `:8001`, Vite `strictPort` on `:3000`.
  Only one session can hold Gate 6 at a time.
  LIVE-QA.md tells you how to detect and wait rather than kill.
- **The working tree may be shared.** Never stash, never `git checkout` a branch another session is on, never `--force` anything.

If a parallel session has the stack, do Gates 0 to 5 fully, then queue for Gate 6.
Say plainly that you are waiting.

Integration contracts — one per edge

Rule 7 made concrete: every connection to the outside world is a written contract — what we push, what we pull, the join key, what happens on retry, the daily reconciliation, and the failure queue. Four edges touch the books: POS, Tally, Bank, WhatsApp.

25 June 2026 · Assembled from the locked module designs (D2 inbound · D3 outbound · D4 payments · D6 Tally · D7 analytics) and the 16 Q&A decisions. The architecture is the constitution; this is the edge appendix a developer builds the adapters from.
The one principle every edge obeys (Rule 7). Never assume the other side received anything. Every push is retry-safe and idempotent; every pull is deduplicated on a stable key; a tie-out runs daily and lists exactly what didn't match; anything that fails goes to a named queue with a named owner — the shop floor never waits on an integration (Rule 5: flag, never block). Every edge sits behind a swappable adapter, so the outside system can be replaced without touching the spine.

The contract shape — read every edge this way

Each of the four edges below is written to the same six-line shape, so a developer can build any adapter from a single mental model.

LineWhat it answers
PushWhat KDPS sends out, and when.
PullWhat KDPS reads in, and how often.
Join keyThe single field both sides agree identifies a record. If it's wrong, everything double-counts or goes missing.
Retry / idempotencyHow a re-send or a re-read avoids creating a duplicate. The heart of "exactly once".
Daily reconciliationThe once-a-day tie-out that proves the two sides agree, and surfaces the few that don't.
Failure queueWhere a mismatch waits, who owns it, and why the floor keeps moving regardless.

1 · POS edge behind one swappable adapter 3 spike Qs open

Scope note (26 Jun 2026): the POS edge is deferred — it is the last module, not in the current build. Ten Software will sell API access at a cost plus lead time; when POS is built, KDPS uses their API if it is ready, else builds its own (decided then). The contract below is the target design for that module. The most important edge: this is where the sale actually happens. Two concurrent sources sit behind one adapter — the bought Ten Software POS that runs the counters today, and a future KDPS-owned POS built in parallel (Q8). They are not a migration with a cut-over date; they coexist. Critically, each store runs exactly one POS — a hard configuration invariant — so the two sources never overlap inside a store. The Sale document is source-agnostic: source = Ten Software | manual bill | KDPS POS, and all posting logic lives on the Sale, never in the adapter.

Push
Item master per store (barcode → MRP, tax/HSN, brand, season, category), pending-inward quantities per store (so the counter scans goods in against them), and EOSS / offer price rules per barcode per store with start/end dates. Bulk on first load, incremental thereafter.
Pull
Line-item sales per bill (barcode, qty, rate=MRP, disc%, disc amt, net, store, date/time, payment mode, bill no, cashier, season if echoed), SOH per store, and the daily collection (cash / card / UPI totals). Cadence: a near-real-time poll plus an authoritative end-of-day batch that is the daily close and the negative-SOH catch.
Join key
Barcode + season. The supplier barcode is a non-unique scan-alias pointing to a SKU cohort, not the identity itself (Q7) — brands reuse the same barcode in a later season. Season is inferred at the adapter, not demanded of the POS (Q6, no re-barcoding): one cohort match → post; many → oldest-season-first (FIFO); genuinely ambiguous → one-tap "which season?"; never block. The adapter re-attaches season via the effective-dated (SCD-2) master for that barcode at that store on that sale date. A true two-SKU collision is caught at inbound (internal barcode assigned), not here.
Retry / idempotency
Dedup key = store + bill-no. Each store runs one POS, so the two sources never share a bill-no space — the key is collision-free by the "one store, one POS" invariant. For the KDPS-owned POS, every sale also carries a client-UUID generated offline at the terminal; the server does an idempotent upsert keyed on that UUID and returns the same Sale-ID on any retry, so an offline outbox can re-send safely after a network drop with zero double-posting. Re-reading the same Ten Software bill on the next poll resolves to the same store + bill-no and is a no-op.
Daily reconciliation
POS recon, daily: their SOH per store ↔ our stock-ledger SOH per store (the EOD batch). Also reconciles our ledger vs paper bills (manual fallback) and dispatched-vs-received for transfers. A negative SOH explained by a known allocation → auto-creates the missing inward; unexplained → HO exception. Negative SOH never persists.
Failure queue
An unmatched bill, an unresolved barcode-season, or an unexplained negative SOH lands in the HO exception queue with a plain-words reason; the counter keeps selling. A POS that is down falls back to the manual bill — a real document reconciled later — so a sale is never lost.
Reader before writer (Q8 guardrail). The adapter ships first as a reader of Ten Software. Ten ingest and the daily POS recon must be green before any KDPS-owned-POS store goes live. Counter bills are normal B2C GST tax invoices — no IRP/IRN (e-invoicing is B2B-only). Idempotency is non-negotiable: a client-UUID per sale, an idempotent server upsert, offline outbox, and offline bill-numbering at the terminal are the thin spike's success criteria.

2 · Tally edge designed (D6, locked 20 Jun)

Scope note (26 Jun 2026): the Tally / accounting sync is deferred — not in the current build. The contract below is the design of record for when it is built. The statutory edge: KDPS stays the live operational truth; Tally stays the filed book of record (Rule 4). Every business event was already booked in the spine and payments — D6 only copies those events into Tally as proper GST vouchers, one-way, exactly once, with a daily tie-out. Route is hybrid: a deterministic structured export is the real contract; Vyapar TaxOne imports it today, with direct Tally-XML as the fallback and the future self-built path.

Push
GST-ready vouchers — purchase / TIR (recognition point keyed per brand to the supplier's invoice timing — Q4/F9: arrival if tax-invoiced at delivery, else deferred to sale; CA-pending), daily consolidated sales per store (per-bill only for a customer GSTIN), combined money-in with the tender split, payments, DN/CN, and SOR/Consignment settlement journals. Cross-state stock moves are legally a taxable IGST supply between distinct persons, but the system only records the move and flags it as cross-state (for awareness/reporting) — the IGST tax invoice and the e-way bill are produced manually by KDPS, outside the system (26 Jun 2026 scope decision); intra-state moves are stock-ledger-only, no voucher (Q3 / F3). GST is computed once by KDPS at the right dated slab and carried, never recomputed downstream.
Pull
Acknowledgement / import logs only — which vouchers Tally accepted. Tally is never read for truth; it is fed.
Join key
KDPS-owned deterministic voucher number — e.g. DEO-SAL-20260620-001 (store · type · date · sequence). One number is both the idempotency guard and the tie-out key. Tally auto-numbering is rejected because it would lose the join key and duplicate on retry.
Retry / idempotency
Exactly-once via an outbox (F9 noted): the voucher is staged in an append-only outbox with its deterministic number; Tally runs with prevent-duplicate-voucher-number ON, so a retry of an already-accepted number simply bounces — exactly once. A first-live-test check confirms the number passes through TaxOne unchanged rather than being reassigned. (F9 caution: the SOR lot carries a gst_recognised=(date, voucher_no) invariant so GST is recognised once — at the arrival voucher or the settlement journal, never both; one convention, CA to confirm — see spike list.)
Daily reconciliation
Tally tie-out, daily: what KDPS sent ↔ what Tally accepted, matched on the unique voucher number. Totals match → green; otherwise it lists exactly which vouchers didn't land. Separately, a daily AP-to-Tally tie-out reconciles the KDPS payables balance against Tally's control account — the safety net against silent drift.
Failure queue
A refused voucher goes to a plain-words "needs attention" list ("brand name not found", "already there") — fixed and re-sent. Owner: the Patna accountant (already lives in Tally). Cadence: once a day. The shop floor never waits; back-office cleanup only (Q3/Q4/F9 — the tie-out and failure queue are first-class, built as their own slice, not deferred).
Open for the client / CA (parked, non-blocking). Bihar & Jharkhand are one Tally company with two state GSTINs (one PAN; confirmed 26 Jun 2026) — that settles where each store's vouchers are addressed. Whether the SOR delivery invoice charges GST at delivery (C5 / Q4) is the only detail affecting how the purchase is recorded, and is the input to the gst_recognised convention.

3 · Bank edge designed (D4)

The proof-of-money edge — read-only. KDPS pushes nothing to the bank; it pulls statements and uses them for two reconciliations: money-out (did the vendor payment actually leave) and money-in (did the store's reported collection actually land). The bank is a variable — three banks, ICICI access first — so it sits behind its own adapter like every other edge.

Push
Nothing. The bank edge is read-only.
Pull
Bank statements (CSV / PDF to start, an API pull where a bank allows it), daily. For the money-in side these are joined with acquirer / aggregator settlement reports (Pine Labs / Razorpay / Paytm…) so the card and UPI rails can be disaggregated — client to confirm which acquirers and arrange the daily reports.
Join key
UTR (the bank reference) is the primary key; where a UTR isn't present, date + amount + store ref is the fallback match. An AI bank-narration parser turns INF/NEFT/IN4260… gibberish into "this credit = Allen Solly refund / this store's UPI settlement" using the UTR + narration; the UTR is the match key for both reconciliations.
Retry / idempotency
Statements are re-pullable and overlapping by nature, so each bank line is deduplicated on (UTR, amount, date) — re-importing yesterday's statement matches existing lines and creates nothing new. A captured payment UTR auto-closes its payable exactly once (the payment roundtrip); a second sight of the same UTR is a no-op.
Daily reconciliation
Bank audit, daily, on two rails. Money-out: vendor payments ↔ bank debits on UTR — auto-closes the payable, chases the DN-without-CN gap. Money-in (three-rail): cash deposits, card settlements (gross − MDR, by MID/terminal), and UPI ↔ bank credits, matched by narration / UTR with fuzzy, many-to-many logic. The lag (T+1 cash, T+2 card net-of-MDR, T+1 UPI) is carried as "expected / in-transit" until the money lands, so the audit can always say why a number differs.
Failure queue
Only genuinely late, short, or missing settlements are flagged — raised on the day, for the day's named owner (store user confirms their own store's deposit; HO sees all). Money carries a real hard gate: no vendor payment without bank + GSTIN, and no pay before reconciliation is clean (Rule 5 + the D1 pay-gate). Unmatched lines wait in the recon exception queue; they never block the counter.

4 · WhatsApp edge designed (D7) AI lives upstream

The owner-facing edge — outbound only. Owners live on WhatsApp, not logins. This edge carries the daily digest, deadline alarms and anomaly alerts out; it reads nothing back. Everything it sends is produced in the read-only intelligence layer — a wrong message wastes attention, never corrupts a book (Rule 8).

Push
The digest (a day-close exception feed), deadline alarms (return windows 30/15/7, payment due dates, EOSS windows) and anomaly / leakage alerts. Both the digest TYPE and its TIMING are per-user configurable (Q15) — configuration data, not code (Rule 12, "variation is data, not code"). The default is a 9 PM close-of-day digest; a user can choose a different cut, a different time, or a different recipient role.
Pull
Nothing. The edge is one-way out.
Join key
Phone number per role — each recipient maps to a role, and the role's per-user config decides what they receive and when.
Retry / idempotency
Each scheduled message carries a (recipient, digest-type, period) key, so a retry after a send failure resends the same message rather than a second copy. A delivery webhook failure re-queues; a duplicate provider callback for an already-sent key is dropped.
Daily reconciliation
A daily send log — every scheduled digest/alarm for the day vs what the provider confirmed delivered, per recipient. A digest that was due but never confirmed is surfaced for re-send.
Failure queue
An undelivered or bounced message lands in a small delivery exception list (bad number, provider error) for re-send or a contact-detail fix. Nothing in the spine waits on a WhatsApp send.

Open spike & forward questions — close before the slice that consumes them

These do not block the foundation build; they gate the specific slices that touch them, and they have lead time — so they start now in parallel (Q14). Three are Ten Software spike questions about exactly how much the POS edge can carry.

Ten Software POS spike spike now

  • Can the sale line carry season / MRP? If Ten Software echoes the season or the sale-line MRP, season resolution becomes deterministic and the MRP gives a second collision-check; if not, the adapter infers season from the SCD-2 master (Q6) and the one-tap fallback stands.
  • Void / edit handling. How does the POS represent a voided or edited bill, and does it come through the pull as a reversal line with a reference to the original bill-no? This decides how the adapter reverses a posted Sale idempotently.
  • Stable bill-no. Is the bill number stable and unique per store (never reused, never renumbered)? The whole dedup key (store + bill-no) and the "one store, one POS" invariant depend on it.

Plus the load-bearing access questions (already drafted for Ten Software): a documented API for sales / SOH / returns / collections pull and master / pending-inward / offer push; auth scoped per store; rate limits; a test store; timeline.

Tally / GST forwards client & CA

  • One Tally company with two state GSTINs (C3 / Q3, confirmed 26 Jun 2026 — one PAN, one Tally company) — drives voucher addressing.
  • SOR delivery invoice — GST at delivery or not (C5 / Q4) — sets the gst_recognised convention so the arrival voucher and the settlement journal never recognise GST twice (F9). One convention, CA confirms.
  • Cross-state IGST (Q3) — KDPS is one PAN / one Tally company with two state GSTINs (confirmed 26 Jun 2026); the IGST transfer invoice and e-way bill are produced manually by KDPS, so the slab basis and any e-way carve-out are CA mechanics outside the system.
  • IRN / e-invoicing ownership (open, 26 Jun 2026) — assign an owning module and confirm applicability at the CA sitting. Most is external / manual: counter bills are B2C (no IRN) and the cross-state paperwork is manual; but B2B / cross-state IGST invoices need an IRN if KDPS is over the e-invoicing turnover threshold.

Bank forwards client

  • Acquirer settlement reports — which acquirers (Pine Labs / Razorpay / Paytm…) and daily access — the feed that makes the card / UPI rails reconcile.
  • Bank statement access per bank (ICICI now; three banks total) — read-only API where available, else CSV/PDF.

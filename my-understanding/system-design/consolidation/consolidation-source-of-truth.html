6 · Module reference (faithful, compact) — built from the eight locked designs

The content the presentation is built from. The full truth for each module lives in its own design document; this is the essence so it is never re-derived or hallucinated.

Master Records & Users base layer

Solves: the same lists kept differently everywhere; anyone could change anything; no audit trail.

Has: one owned home for every master — vendor & commercial terms, brand, store/warehouse, SKU (brand+style+colour+size), barcode+season, the season calendar (Open → EOSS → Closed), date-effective GST/HSN, the offer rulebook, users & roles. An edit-rights grid; the "dangerous four" need a second pair of eyes (brand terms, GST slabs, vendor bank/GSTIN, user roles); every change logged; documents snapshot masters so today's edit never rewrites yesterday's bill.

AI: drafts only — reads brand offer sheets, suggests category/vendor cleanup; a person confirms.

Vendor & Buying spine · start

Solves: orders live in people's heads; no track of booked-vs-received or return deadlines.

Has: a Booking per vendor + brand + season; status derived from goods received (Booked → Partially → Fully received → Return-window → Closed); the four commercial models snapshotted (Outright / Correction 25-18-10 / SOR / Consignment); a return-allowance budget per brand; return-window alarms at 30/15/7 days.

AI: reads the brand's order paper → drafts the booking; you confirm.

Goods In spine

Solves: every arrival re-typed by hand into Excel; no priced size×colour stock; no reconciliation.

Has: the Shipment as anchor; invoice → GRN (count, flag-don't-block) → PT file (priced stock-in) → store split → Tally export; SKU + barcode+season identity; stock-in cost frozen; postings happen at Patna inward (stock ledger + vendor liability per commercial model).

AI: reads invoices into data; chat-assist builds the non-branded PT; fuzzy item-name match. The PT conversion / recon / pricing / Tally export are plain software.

Selling & Stock spine · end · Offers inside

Solves: POS per store with no central truth; exchange/transfer/returns/counts all manual; discounts run on memory with no proof the right one applied.

Has: one machine for sale, exchange, inter-store transfer, defective/GR return, seasonal return, EOSS and stocktake; free-to-sell = physical − locked; per-piece states. Offers/Discounts (inside): the rulebook (trigger + reward + dials, eight patterns, open model), applied per item, best-for-customer, with a daily applied-vs-rulebook audit. V-flip handles dead/over-window stock.

AI: markdown suggestions on dead stock (cost floor + step-down) → human authors; reads brand offer sheets into rules.

Money cross-cutting

Solves: what's owed to which brand is guesswork; cash-to-bank unchecked; duplicate/fraud risk.

Has: a two-layer payable + payment model with bill-wise allocation; tiered approvals (maker ≠ checker ≠ payer); the vendor ledger (Opening + Invoices − cash discount − goods return − Payments + Interest = Due); a daily three-rail store-collection audit (cash / card / UPI vs bank); SOR/Consignment payable accrues on sale.

AI: bank-narration reader, duplicate-payment guard, vendor bank-change fraud alert, one-line approver brief, cash-to-bank auto-match, brand-statement reconciler, ask-anything — all read-only, a human approves.

Accounting (Tally) cross-cutting

Solves: everything re-keyed into Tally by hand.

Has: GST-ready vouchers pushed exactly once (KDPS-owned voucher number as the key); daily consolidated sales per store (per-bill only for GSTIN buyers); the day's tender split; purchase booked at arrival; IGST for cross-state moves; a daily tie-out + a plain-words "needs attention" list. Tally stays the statutory book; GST is computed once, carried, never recomputed downstream.

AI: none — by design.

The Brain — Reports & AI AI lives here

Solves: month-end built by hand; no daily picture; no early warnings.

Has: a 9 PM WhatsApp digest (an exception feed, not a report); size-level forecasts that feed the store split; a dead-stock & markdown hunter; profit & store scorecards; an anomaly/leakage watchdog; a one-click brand report-maker; and a read-only assistant you can ask. Built on a clean data spine (canonicalization → a metrics layer where every number is defined once → a data-trust score).

AI: reads ledgers, masters and POS; writes only messages, reports and suggestions — never a ledger posting. Code computes, AI narrates, a human decides.

9 · Best-practice research — verdict & sharpenings 21 Jun 2026

Four parallel research passes — ERP architecture, fashion-retail ERP, AI-in-ERP, MCP/agent access — each with cited sources. The findings cross-corroborate.

Verdict: every principle already locked here is the mainstream best-practice shape. No source recommended a different structure. The work now is enforcing the rules mechanically, not changing them.

Confirmed as best practice

  • Modular monolith on one relational database (not microservices) — the consensus for a single-developer build; the same shape as ERPNext and Odoo. (Fowler "MonolithFirst"; Thoughtworks; Shopify)
  • Documents → append-only ledgers, balances/stock derived not stored, corrections = reversing entries. (Modern Treasury; ERPNext immutable ledger; Kleppmann)
  • Snapshot masters onto documents so history never changes. (Odoo; ERPNext; "Immutable Invoices")
  • AI at the edges, never on the books — exactly what Microsoft, SAP, Oracle, NetSuite and Workday all ship (AI drafts/suggests; a human posts). (vendor AI docs)
  • MCP read-only tools over a semantic/metrics layer, never raw SQL. (Anthropic MCP; dbt; Cube)
The edge — use it in the pitch: SOR / Outright / Correction / Consignment as a first-class ownership dimension (vendor liability posts only on sale) is a structural advantage. The Indian incumbents (Ginesys, GoFrugal) bolt SOR on as a flag — none model it first-class. And both bridge to Tally rather than replace it, validating the Tally approach.

Sharpenings to fold into the build

AreaSharpening
Master dataVersion the masters that drive history (GST slab, GSTIN, cost, price) with effective dates — not only snapshot — so an old bill never changes. (SCD Type 2)
Tally pushMake the push idempotent (outbox + KDPS voucher number) so a retry can never double-post. (confirms the D6 direction)
AI traceabilityGive the AI its own login identity; log the AI suggestion and the human decision separately. (Microsoft's pattern)
SOR complianceTrack a second clock per consignment lot — India GST deems a supply at ~6 months even if unsold — alarm it alongside the vendor return window. (Section 31(7) CGST)
Forecast dataLog stockout windows per store-SKU from day one — without it, size curves and forecasts are quietly wrong. (Increff True ROS; Oracle size profiles)
The assistantNever a raw "ask anything over the database" — it answers through the same defined metrics the reports use, or it gives confident wrong numbers. (dbt; BIRD/Spider benchmarks)
Don't over-buildNo microservices, no full event-sourcing — one DB, append-only ledgers. (the #1 research warning for an AI-assisted build)

Agent runtime — a reframe to decide

The earlier instinct was a self-hosted open runner + open model. At ~50-store scale a hosted top model is cheaper and more accurate for the assistant (self-hosting only pays off above ~10–30M tokens/day, and hosted models top the function-calling benchmarks). The one strong reason to self-host is GST data residency — whether ledger data may leave India. decide in the stack grill

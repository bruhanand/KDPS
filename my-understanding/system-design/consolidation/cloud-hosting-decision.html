Where do we host the KDPS system?

Comparing Google Cloud, AWS and Azure for the exact build: a TypeScript app + managed PostgreSQL + file storage, all data in India, talking to Google's AI in Mumbai, run by one developer, serving ~50 stores.

21 June 2026 · Sources cited inline (provider docs, the DPDP Act, RBI) · Verify final prices in each provider's calculator before committing

The recommendation, in one line

Host everything on Google Cloud, Mumbai region (asia-south1): Cloud Run for the app + Cloud SQL for PostgreSQL + Cloud Storage for files + Secret Manager.

Because the system already calls Google's AI (Vertex AI) in Mumbai, putting the rest of the system in the same Google region removes a whole class of problems: no second cloud to run, no cross-internet hop to the AI, one login/permission system, and the AI data never leaves Google's India region. For one developer running a money-critical system, that simplicity is the deciding factor — not price (all three are cheap at this size).

1 · Data residency & the law (DPDP Act 2023)

The most important myth to kill: you do NOT legally need a "sovereign" Indian cloud for a private retailer.

Bottom line: Hosting in any of the three hyperscalers' India regions legally satisfies "data stays in India" for a private fashion retailer. India's DPDP Act does not impose strict localisation on this kind of data — it uses a "blocklist" model, and as of June 2026 no country is even blocked. A MeitY-empanelled sovereign cloud is a government-procurement rule, not a private-company rule.
  • DPDP is permissive, not GDPR-strict. Section 16 lets the government restrict transfers only to specific countries it notifies — until then, transfer is free. No restricted-country list has been notified. This is the opposite of the common assumption that India bans data export.
  • Sovereign / MeitY-empanelled cloud is for government, PSUs and nationalised banks — it does not govern private-sector cloud procurement. (All three hyperscalers are empanelled anyway, so even a future banking relationship is covered.)
  • The one genuinely strict rule — RBI payment-data localisation (6 April 2018) — binds payment system operators (card networks, gateways, banks), not a merchant using a third-party gateway. As long as the ERP stores only a gateway reference/token and tender type (never raw card numbers/CVV), this is the gateway's obligation, not ours.
  • DPDP Rules 2025 (notified 14 Nov 2025) add a conditional localisation hook only for "Significant Data Fiduciaries" and only for data categories the government later names. A 50-store apparel chain is very unlikely to be an SDF, and no category has been named. Not a concern today.
What this means for design: Pinning everything to an India region is the zero-risk, costs-nothing default — it pre-empts any future country-block, any SDF designation, and any client/bank demand, without re-architecting. So we choose an India region by choice, not because the law forces it. Keep data region-locked so any future tightening is absorbed automatically.

2 · The deciding factor — sitting in the same cloud as the AI

This is what makes Google Cloud the right call rather than a coin-flip.

Google Cloud (app + AI together in Mumbai)

  • FREE App→AI traffic stays inside Google's Mumbai region — same-region traffic is free (no egress).
  • SIMPLE One permission system: Cloud Run runs as a Google service account; grant it the Vertex AI role and it calls the AI with no API keys, no secrets to store or rotate.
  • FAST No public-internet hop — lowest latency to the AI.
  • IN INDIA AI request data is region-pinned in Mumbai (data-at-rest in India).

AWS or Azure (app calls Google AI across the internet)

  • EGRESS Every AI call leaves the cloud to the public internet and bills as data-transfer-out (AWS Mumbai ~$0.109/GB; Azure ~$0.12/GB after 100 GB free). Dollar cost is tiny for text-sized AI calls — but it's real plumbing.
  • TWO IAMs You manage AWS/Azure permissions and Google permissions. No SSO between them.
  • BRIDGE AUTH To call Vertex you must either ship a Google service-account key into the other cloud (a long-lived secret to guard & rotate — leak risk) or wire up Workload Identity Federation (more secure, more setup).
  • PUBLIC PATH Traffic to the AI rides the open internet (TLS only) unless you pay for private interconnect.
The honest counter-move: the two-cloud tax disappears entirely if you stay single-cloud on the AI too — i.e. use Amazon Bedrock (on AWS) or Azure OpenAI (on Azure) instead of Vertex. But the design has already chosen Vertex/Gemini in Mumbai (D7). Given that choice, Google Cloud is the only option that keeps the whole system single-cloud. Switching the AI provider to avoid Google hosting would be the tail wagging the dog.
One caveat to track on Vertex (not a blocker): Google guarantees your AI data is stored at-rest in India when you use the Mumbai regional endpoint — but its stronger "ML-processing happens in-region" guarantee is currently documented only for US/EU, not Asia. Practically: always use the asia-south1 regional endpoint (never the global one), and never send raw PII/payment data to the AI. Re-confirm coverage with Google over time. (See sources below.)

Money-critical rule, applies to all three: do not let the database scale to zero, and keep one warm app instance (min-instances = 1). The next request after an idle period is usually a sale or a ledger posting — a multi-second cold-start mid-transaction invites double-submits. One warm instance costs only ~$10–15/month and removes the risk entirely.
Supabase — worth knowing, not the pick. Supabase (managed Postgres + auth + storage + APIs) runs on AWS Mumbai (ap-south-1), so it satisfies data-in-India and would cut solo-dev burden fast. But for a money-critical multi-tenant ERP its tenant isolation rides entirely on Postgres Row-Level Security — which is off by default, silently returns empty on a blocked read, and is bypassed by the service key. That's a real cross-tenant-leak footgun for ledgers, and point-in-time recovery is a paid add-on (~$100+/mo). Fine to revisit, but raw Cloud Run + Cloud SQL gives a simpler, more auditable mental model for money.

Use Cloud SQL, not AlloyDB, to start (AlloyDB is always-on, 2-vCPU minimum, pricier — overkill for 50 stores). Move up only if analytics load demands it.

Why Google over the others

  • Single cloud end-to-end because the AI is Google's — one IAM, no cross-cloud key, no AI egress, lowest AI latency.
  • Lowest-ops compute for a solo dev (deploy from source, no Dockerfile, built-in logs).
  • Longest backup retention (up to 365 days) — good for financial records.
  • Legally clean for data-in-India (same as the others).

The tradeoffs you're accepting

  • Costs ~₹8–12k/month more than Azure at this size (worth it for simplicity; shrinkable).
  • Vertex's in-region processing guarantee isn't documented for Asia yet — mitigate by using the regional endpoint and never sending raw PII/payment data to the AI.
  • If budget ever trumps simplicity, the clean fallback is Azure + Azure OpenAI (single-cloud the other way), not a Google-app-calling-AWS-AI mix.
Locks cleanly to existing architecture rules: "AI at the edges only" and "documents write ledgers" mean the browser/PWA is a fast client but the server on Cloud Run is the single writer of any ledger or GST posting. The PWA caches the app shell + master data (SKUs, price lists, offer rules, GST slabs) for weak networks, but never does optimistic offline money writes — every rupee commits server-side, and any queued write must carry an idempotency key so retries can't double-post.

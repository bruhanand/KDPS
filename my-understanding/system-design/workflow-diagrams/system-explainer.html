1What KDPS is

An AI-powered, fashion-retail-aware operating system that replaces a fragmented stack of per-store POS + Tally + Excel + WhatsApp groups with one coherent, audit-ready platform.

KDPS is being built for a multi-brand Indian fashion retailer running across Bihar & Jharkhand with stores in Ranchi, Deoghar, Bhagalpur, Hazaribagh, Bokaro and beyond. The current operation is functional but human-heavy at every stage — staff manually re-type invoice rows into per-person Excel sheets, account managers chase PT files over WhatsApp, payments are released on memory, and reconciliation only happens after the fact.

The goal is not "another inventory app." It is a single canonical truth for inventory, sales, money, and people — wired to the brands' systems via PT files, to Tally via the TIR format, and to owners/managers via WhatsApp. Fashion-specific assumptions override generic ERP defaults: SKUs always carry size×color, every brand is either Sale-or-Return or Outright, every item has a Season and a Collection, and EOSS discounts must be enforced at POS with a full audit trail.

Five domain invariants you cannot violate

1 · SKU = Style × Size × Color

Never collapse stock to a single barcode. "Size 8: 3 units, Size 9: 0 (STOCKOUT)" is the granularity, not "Nike 11 units."

2 · Dual-track: SOR vs Outright

Each brand is one or the other (or hybrid). Drives ownership, return windows (60–120 days for SOR), margin, EOSS funding, and agent behaviour.

3 · Season & Collection tagging

Every item carries Season (SS26, AW26), Collection (Core/Fresh/Clearance), and Age. Auto-detected from PT style codes.

4 · Profitability is derived

Cost from PT/invoice at stock-in. Revenue from POS at sale. Margin computed per transaction. No separate P&L entry flow.

5 · EOSS discount control

During EOSS, the active offer must be applied from the scanned barcode, overrides must require approval, and each bill must keep discount and margin history.

2Requirements

What the system must do (functional), how it must behave (non-functional), and the non-negotiables (domain). Click a tab to switch.

  • FR-1
    Invoice ingestion (mandatory entry point). Upload PDF/photo of vendor invoice from any device. Auto-extract header + line items. Triggers Agent 1 (Invoice Reader). No downstream processing happens without an invoice.
  • FR-2
    PT file ingestion & mapping. Upload vendor PT file (varying format per brand). Auto-detect headers and map to KDPS taxonomy. Triggers Agent 2 (PT Mapper). Brand-specific mapping rules versioned, editable without code.
  • FR-3
    GRN (Goods Receipt Note) creation. Confirm physical receipt independently of invoice. Mark shortages, damages, scan barcodes, manual entry fallback. The third leg of 3-way reconciliation.
  • FR-4
    Non-branded SKU creation. For local goods with no barcode/MRP: classify, generate KDPS barcode, derive MRP via cost+transport+GST+(20–25%) margin, prevent duplicates via similarity detection. Centralised SKU registry.
  • FR-5
    Stock ledger by Style × Size × Color. Per-SBU view, real-time updates, inter-SBU transfer with barcode scan, and immediate deduction on completed sale. Drives stockout alerts, transfer suggestions, dead-stock classification.
  • FR-6
    POS harvester (15-min sync). Reads any POS export (CSV/Excel/API), deducts stock by barcode, captures sale price + discount + promo applied. Agent 4. Works against multiple POS systems including the existing TEN.
  • FR-7
    3-way reconciliation. Nightly fuzzy match: Invoice ↔ GRN ↔ PT. Mismatches surface, never get buried. Agent 3.
  • FR-8
    SOR return deadline tracking. Track return window (60–120 days from PT date) per SOR brand. Alert at 30 / 15 / 7 days. Highest-ROI safety net — missing a deadline = dead stock KDPS owns by default.
  • FR-9
    Goods Return (GR) processing. Three types: Seasonal (10% allowance), Defective, Unauthorised stock (debit note). Track against SOR deadline. Vendor ledger reconciliation.
  • FR-10
    Payment lifecycle (PASCS). Eligible → Requested → Approved → Executed → Confirmed → Reconciled. Eligibility requires invoice + GRN + PT + TIR aligned. Lump-sum payments attribute across multiple invoices. Pre-tax CD calc. Multi-level WhatsApp approval by amount/vendor threshold.
  • FR-11
    Bank statement reconciliation. Upload bank PDF, system matches transactions to executed payments by ref/amount. Closes the payment loop. Status → Reconciled.
  • FR-12
    Attendance (face + GPS + liveness). Browser-based check-in for store staff, no app install. Tied to incentive eligibility. Agent 5. face-api.js, runs in the browser.
  • FR-13
    Sales incentive auto-calc. Target-based + per-unit + brand-specific (SPF) + tiered. Tied to attendance (absences reduce eligibility). Per the Definitive Plan §7.
  • FR-14
    EOSS module. Pre-EOSS markdown suggestions, POS-enforced discount rules, manager approval above floor limit, daily WhatsApp summary, SOR brand-funded portion calc. Drives margin from 25% → 18%.
  • FR-15
    Daily digest at 9 PM. WhatsApp summary: revenue, stock, attendance, alerts. Per-SBU and consolidated. Agent 6. Primary observability surface for owners.
  • FR-16
    Fashion Demand AI (weekly). Size-level forecasting, store affinity, weather-aware. Outputs replenishment recommendations. Agent 7. Prophet + scikit-learn.
  • FR-17
    Dead Stock Hunter (daily). Hot / Warm / Cold / Dead (45+ days zero sales). Per-SBU action recs differ by SOR vs Outright. Agent 8.
  • FR-18
    Profitability tracker (continuous + weekly digest). Per-brand, per-store, per-style P&L. Margin derived per transaction. Agent 9.
  • FR-19
    Anomaly Watchdog (continuous). Shrinkage, fraud, stuck transfers, payment anomalies. Agent 10.
  • FR-20
    Tally / TIR sync. Phase 3: XML export. Phase 4: TallyPrime API push nightly. GST-ready vouchers (purchase, sales, stock journals, credit notes). Tally remains the book of record.
  • FR-21
    Store closure workflow (5-step). Mark Closing → AI stock categorisation → Liquidation dashboard → Staff reassignment → Final reconciliation. Must produce zero leftover stock + Tally closing entries.
  • FR-22
    New store setup. AI-suggested seed stock from similar stores' sales curves; regional size distributions differ (North vs South India). Reduces opening dead-stock.
  • FR-23
    Network → store drilldown dashboards. Region → Store → Brand → Style → Size. Metabase. Replaces ad-hoc Excel reports.
  • FR-24
    Vendor / brand master with commercial model. SOR vs Outright vs Hybrid, agreed margin model (25-18-10 / B&S / Consignment), CD%, credit days, agent details, bank account. Drives downstream rules.
  • FR-25
    Promotional offer master (date-bound). GWP / ATV / threshold offers per brand-season with start/close dates. POS Harvester attributes sales to active offers. Solves the monthly sales-report pain from Conversation 1.
  • FR-26
    Audit trail. Every classification, mapping, override, approval, payment carries who/when/why. Immutable. The PRD's §4.F gap.
  • NFR-1
    Mobile-first PWA. Runs in-browser. Camera, barcode, face-recognition all in browser. No app store install — staff turnover is high.
  • NFR-2
    WhatsApp as the primary interaction surface. Approvals (payments, transfers, markdowns) happen in WhatsApp, not a web admin panel. Owners read digests in WhatsApp. Web admin is for ops desks; WhatsApp for everyone else.
  • NFR-3
    Indian context. ₹ INR, Lakh/Crore formatting, GST mandatory (GSTIN/HSN/tax breakup), Hindi training videos, English dashboards. Tally is the book of record.
  • NFR-4
    Volume. 20K SKUs × 50+ SBUs ≈ millions of stock rows. ~200 invoices/day during peaks. PostgreSQL sized accordingly; partition by SBU/season.
  • NFR-5
    Cost envelope. ~₹25–40K/month operational including hosting, AI inference, WhatsApp BSP. Hetzner 2-server hosting. Claude Vision via Anthropic API with prompt caching for the Reader.
  • NFR-6
    Latency budgets. Invoice upload → PT in < 60s. POS sync 15-min. Reconciliation nightly. Daily digest at 21:00 IST. Real-time stock visibility, batch back-office.
  • NFR-7
    Onboardability. 10 new vendors/month must onboard with zero code changes. Reader generalises across formats; Rule Engine versioned mapping rules.
  • NFR-8
    Auditability. Every row, every override, every approval — who/when/why. Immutable change log. Required for Tally reconciliation and disputes.
  • NFR-9
    Resilience. Store can keep selling during internet outage; manual billing reconciles next day (per Conversation 1). Agents retry; reconciliation engine is idempotent. Network at stores is unreliable.
  • NFR-10
    Role-based access. Warehouse staff / store manager / account manager / finance / owner. Tied to approval thresholds. ERPNext provides the role primitive.
  • NFR-11
    Storage. Invoice photos, PT files, employee docs in object storage with free egress (Cloudflare R2). ~50–200 GB at scale.
  • NFR-12
    Extensibility. ERPNext extension over conformance — fashion retail assumptions override generic ERP defaults. Per CLAUDE.md.
  • DI-1
    SKU = Style × Size × Color. Every stock table, dashboard, transfer, and forecast preserves the size–color matrix. Single-barcode SKUs silently break dead-stock alerts.
  • DI-2
    SOR vs Outright as a first-class dimension. Set in Brand Master, drives ownership, return window, margin, EOSS, and per-agent behaviour. Not a flag — a top-level dimension in every schema, API, UI.
  • DI-3
    Season & Collection on every item. Auto-detected from PT style code. Aging thresholds configurable (30/60/90 days). Drives EOSS, dead-stock, demand forecasting.
  • DI-4
    Profitability is derived, never entered. Cost from PT at stock-in, revenue from POS at sale. No separate P&L data entry flow exists.
  • DI-5
    EOSS discount history. Every discounted sale must preserve original MRP, discount %, final selling price, offer rule, funding source, cashier, approver if any, and timestamp. Needed for margin, brand-funded claim, and leakage audits.
  • DI-6
    Cash Discount on pre-tax base only. CD reduces principal; GST line is unchanged because vendor has already remitted GST on the original taxable value. Tested invariant in pdf-to-pt/tests/test_pricing.py.
  • DI-7
    Non-brand MRP composition order. (Base + Transport) → GST → margin. Margin must be in [20%, 25%]. Round to ₹5. Wrong order produces ~5–8% systematic mispricing.
  • DI-8
    Invoice is the mandatory entry point. No GRN, no PT, no payment without an invoice in the system. Per PRD §IINE workflow.
  • P1
    Phase 1 (M1–M3): Real-Time Stock Engine. FR-1 through FR-8 + FR-15 + FR-23 + FR-24. Hard cut at M3: PT → stock visible by Style×Size×Color across 5 SBUs with nightly reconciliation running.
  • P2
    Phase 2 (M4–M5): Fashion AI + Profitability + Scale. FR-16, FR-17, FR-18, FR-19, FR-14. Roll out from 5 → 25 → all 50+ SBUs. Adds the intelligence layer.
  • P3
    Phase 3 (M6–M7): Workforce + Payments + Incentives. FR-10, FR-11, FR-12, FR-13, FR-21, FR-22. Tally XML export. Money + people layer.
  • P4
    Phase 4 (M8): Tally Auto-Sync + Polish. FR-20 (TallyPrime API). Performance, training (3 batches), docs, source handover. Sealing the system.

GGlossary (system-level)

For ingestion-specific terms (PT, GRN, TIR, SOR, EOSS, HSN, etc.) see the ingestion glossary.

SBU (Strategic Business Unit)

A single profit-and-loss unit — a store, a warehouse, or a franchise location. KDPS has 50+ SBUs across Bihar & Jharkhand.

EBO vs MBO

Exclusive Business Outlet (single brand, brand-managed) vs Multi-Brand Outlet (multiple brands, KDPS-managed). Different commercial structure: EBO = flat 20% commission to store; MBO = 25-18-10.

IINE

Inventory Ingestion & Normalisation Engine. Module 1 of the system. Turns vendor invoices + PT files + physical receipts into one canonical normalised dataset.

PASCS

Payment Authorisation & Settlement Control System. Module 2. Sits after IINE; enforces that money moves only when invoice + GRN + PT + TIR are aligned and approved.

TEN

The existing POS / ERP system referenced in Invoice Status: Uploaded In TEN. KDPS coexists with / wraps it during transition; eventually replaces.

BSP (WhatsApp Business Solution Provider)

Required intermediary for WhatsApp Business API. Not free — adds to the operational cost envelope.

GWP / ATV (offer types)

GWP = Gift With Purchase ("Buy ₹7,999 get a duffel bag"). ATV = Average Transaction Value bump ("Buy ₹14,999 get ₹3,000 off"). Date-bound, brand-specific. Tracked in the Offer master.

SPF (Sales Performance Factor)

Brand-specific incentive multiplier applied per unit sold of that brand. Part of the incentive auto-calculator.

Liveness check

Anti-spoofing for face recognition — confirms a real person is present (blink, head turn) rather than a photo. Runs in browser via face-api.js.

Hetzner

European-based bare-metal / cloud hosting. Chosen for cost efficiency at the system's scale (~₹12K/month for 2 servers).

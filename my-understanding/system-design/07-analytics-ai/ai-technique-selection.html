The right tool for each AI job

Sourced analysis · 21 Jun 2026 · principle: AI at the edges, never on the books · stack: Google Cloud Mumbai + Vertex AI · "best tool for each job," not one model for everything.

The one rule that decides everything

Three techniques, in rising order of cost, latency, and unpredictability. Always pick the lowest one that does the job; only climb when it genuinely fails.

  1. Plain code (deterministic) — rules, math, string matching, lookups. Exact, instant, free, auditable, never hallucinates. Every money number lives here.
  2. Classical / statistical ML — gradient-boosted trees, time-series models, isolation forest. Learns patterns from numbers; needs data + a small MLOps loop (train, validate, monitor, retrain).
  3. LLM (Gemini / Claude) — for language and vision: reading documents, writing prose, understanding a typed question, mapping messy text. Brilliant at the edges, wrong for math.
Why money math is always code — "LLMs are not calculators" A peer-reviewed study (npj Digital Medicine, 2025) measured base GPT-4o at ~36% accuracy on hard calculations and LLaMa-3.1 at ~11%; bolting on a deterministic calculation tool lifted GPT-4o to 95.2% — a 13× error cut. The conclusion: "without specialized tools, LLMs remain fundamentally unreliable for calculations, regardless of model size." LLMs tokenise numbers as text, not quantities, so they pattern-match instead of computing. Every rupee figure in KDPS — totals, margins, discounts, balances — is computed in code; the LLM only ever narrates numbers code already produced.

Detailed reasoning, task by task

1Invoice / document reading LLM vision + code validation

Approach
LLM vision, not traditional OCR/IDP, with deterministic validation wrapped around it.
Model
Gemini 2.5 Flash (or Flash-Lite) as the default; escalate degraded scans / complex tables to Gemini 2.5 Pro.
Agent?
No. One vision call per document → JSON. A plain pipeline, not an agent.

Why it beats OCR/IDP here: KDPS has 40+ brands with no shared invoice/PT template. Classic OCR/IDP (Google Document AI, Textract, ABBYY) is strongest on fixed, repeating layouts and weak on the line-item breakdown KDPS needs — in one head-to-head Document AI merged description/qty/price/amount into a single unstructured string ("unsuitable for automated workflows"), and scored ~40% on complex tables. LLM vision wins exactly where layouts vary, on degraded photos, and on line-item structure (Gemini "near-perfect" on tables). Where OCR still wins — raw speed, determinism, cost at massive scale — does not apply to KDPS's volume.

Flash vs Pro: both carry a 1M-token context (any invoice fits). Flash input/output is ~$0.30/$2.50 per 1M tokens vs Pro's $1.25/$10 — roughly 4× cheaper. Gemini 2.0 Flash was benchmarked at ~6,000 pages per $1 at near-frontier accuracy. Default to Flash; route only low-confidence/ugly documents to Pro.

The risk to design around: LLMs fabricate values not present (they fill blanks with plausible guesses). Google itself concedes pure-LLM parsing hallucinates and grounds its own "Gemini layout parser" in OCR to reduce it. Mitigation fits the system's "flag-don't-block" rule: arithmetic checks (line items must sum to total), schema/type validation, confidence scores, and human review on anything below threshold. The LLM extracts; code verifies the math.

When to add ML later No classical-ML stage needed. The natural evolution is a confidence-routing layer: cheap path for clean docs, Pro/human for the hard tail. Keep a labelled set of corrected extractions as a quality benchmark.

2Fuzzy item-name / product matching rules → embeddings → LLM

Approach
A three-tier waterfall, climbing only when the cheap tier fails — the standard entity-resolution pipeline (AWS, Splink, dedupe all do this).
Method
Tier 1: normalize + Levenshtein / Jaro-Winkler (deterministic). Tier 2: Vertex embeddings + vector nearest-neighbour. Tier 3: LLM only on the ambiguous residue.
Agent?
No. Each tier is one operation; the residue is a single LLM judgement call.

Why this order: "MN garments" vs "M N Garments" is pure surface variation — casing, spacing, punctuation — solved by normalization + string distance. No embeddings or LLM needed. Jaro-Winkler is the classic, fast record-linkage metric. String distance can't capture meaning (reordered descriptors, abbreviations, brand synonyms) — that's where embeddings earn their place (Vertex text-embedding-005 for English/codes, text-multilingual-embedding-002 for Hindi/mixed script, ~sub-second, very cheap). The LLM is reserved for the genuinely ambiguous pairs — like dedupe's active-learning frontier of ~50%-confidence cases.

Why LLM is not the default: entity-matching papers show LLMs are 100–1000× the cost and latency of an edit-distance or vector comparison (self-hosted Llama2 at 22.6s/inference vs sub-second alternatives), are non-deterministic, and even GPT-4 "finds the term 'match' ambiguous." At KDPS's volume that is the wrong default. Use it as the precision backstop, never the firehose.

Fits the existing D7 crosswalk This is exactly the brand/season "canonicalization crosswalk" already designed — a human-curated map plus fuzzy auto-suggest for the long tail. The three-tier waterfall is the engine under that auto-suggest.

3Demand forecasting & size curves classical ML — LLM is the wrong tool

Approach
Purpose-built forecasting models with a real MLOps loop. LLMs explicitly excluded from the forecasting engine.
Method
Baseline: BigQuery ML ARIMA_PLUS / AutoETS. Workhorse: LightGBM (gradient-boosted trees, via Nixtla MLForecast). Slow movers: Croston / SBA / TSB. Size curves: forecast style demand, then disaggregate onto an empirical size profile.
Agent?
No — a scheduled training/inference pipeline.

The evidence that LLMs are wrong for forecasting (this is settled):

  • NeurIPS 2024 spotlight — "Are Language Models Actually Useful for Time Series Forecasting?" Across three LLM-based forecasters, deleting the LLM matched or improved accuracy in up to 26/26 cases, while cutting compute ~1000× (6,642M params / 3,003 min → 0.245M params / ~2 min). LLMs added cost, not accuracy — and didn't help even in few-shot, low-data settings.
  • M5 (Walmart product×store retail, ~6,400 teams) — 1st, 2nd, 3rd place all used LightGBM. And ~92.5% of expert teams failed to beat a trivial exponential-smoothing benchmark — sophistication ≠ accuracy.
  • M4 (100k series) — pure ML/neural methods lost to plain ARIMA/exponential smoothing; the winner was a stats+NN hybrid, not pure ML and certainly not an LLM.

The right methods, mapped to KDPS: LightGBM for SKUs with history + covariates (price, promo, calendar) — it cross-learns across thousands of correlated series. ETS/ARIMA/Theta as fast, mandatory baselines. Croston/SBA/TSB for the long tail of slow-moving SKUs with many zero-sales weeks (most of a 20,000-SKU catalog). Size curves are a disaggregation problem: total style demand split by an empirical S/M/L/XL profile — not language.

Data needed (and two traps): sales history (ideally ~1 year for yearly seasonality), price, promotion flags, calendar/holidays. Trap 1 — stock-out censoring: when an item was out of stock, recorded sales understate true demand and bias forecasts downward in a "spiral-down"; demand must be uncensored before fitting. Trap 2 — cold start: new SKUs have no history, so you forecast from attributes (category, colour, price band, brand, season) borrowing from similar past SKUs — which only works if the product-attribute master (D8) is clean. This makes master data a hard prerequisite for forecasting.

On the Google Cloud stack Start in-warehouse with BigQuery ML ARIMA_PLUS (and ARIMA_PLUS_XREG for regressors) as the cheap baseline; run Nixtla/LightGBM as Vertex AI custom training for the workhorse tier. Both are native to GCP — no extra infra.

4Markdown / dead-stock / clearance rules first, ML later

Approach
Deterministic signal/rules engine now; ML price-optimization later, only when data supports it. LLM not used.
Method
Build first: age / sell-through / weeks-of-cover triggers that flag candidates and suggest a markdown step. Later: elasticity-based price optimization (regression / ML).
Agent?
No — a rules pipeline that proposes; a human approves (copilot, not autopilot).

Why rules first: ML price-optimization is fundamentally an elasticity estimation + constrained optimization problem, and elasticity is data-hungry — practitioners cite needing ~12–24 months of transaction history with genuine price variation, plus substitutes, promos, inventory, seasonality (McKinsey's module used ~10 TB of records). KDPS won't have that clean signal on day one. So the literature's own framing applies: when elasticity information is only partial, retailers fall back to rules — and that's the correct starting point, not a compromise. Deterministic triggers (this SKU is 90 days old with <40% sell-through → propose markdown) are explainable, auditable, and immediately useful.

Why ML pays off later: once enough price-varied history exists, ML price-optimization is where the money is — McKinsey reports dynamic pricing lifting margin 5–10%; one controlled fashion-markdown study showed ~86% profitability improvement vs manual. That is the upgrade target, not the v1.

Why never an LLM: setting an optimal clearance price is math (elasticity, margin, sell-through constraints), not language. LLMs are probabilistic text models that don't compute exact quantities — wrong instrument entirely.

5Anomaly / leakage / fraud detection rules → classical ML

Approach
Deterministic rules for known leakage patterns first; statistical/ML anomaly detection for the unknown patterns later. LLM only to explain a flagged case.
Method
Rules: duplicate invoice numbers, discount over threshold, cash variance, payment to inactive vendor. ML: Isolation Forest / LOF for unsupervised outliers; gradient-boosted trees if labelled fraud exists.
Agent?
No — a detection pipeline that flags; humans investigate.

Why classical, not LLM: this is numeric tabular data, and the honest evidence is that LLMs are at best on par with classical methods at far higher cost — never a clear win. In the tabular-anomaly study, classical ECOD often surpassed unaligned LLMs, and the paper notes "once data is preprocessed to numbers, LLMs cannot reliably detect errors" because anomaly detection needs density estimation and thresholding — computation, not language. Separately, gradient-boosted trees dominate supervised tabular learning (incl. fraud) over deep nets, because tabular features have no spatial/sequential structure that deep models exploit.

Build order: deterministic rules catch the known, high-value leakage cheaply and auditably (duplicate invoice numbers, over-threshold discounts, cash gaps) — AP-fraud tools ship exactly these out of the box. Then layer Isolation Forest for the patterns nobody thought to write a rule for. Rules give precision and explainability; ML extends reach.

Where the LLM does help — explanation, not detection Classical ML/rules decide what is anomalous; an LLM can turn a flagged row into a readable investigation note ("this ₹X payment matches invoice 4471 already paid on 3 Jun"). Augment, never replace — and never let it make the money decision.

6Daily digest narration LLM over code-computed numbers

Approach
Code computes every number; the LLM writes the human sentence around them, in Hindi or English.
Model
Gemini 2.5 Flash — fast, cheap, strong multilingual, ample for short prose.
Agent?
No. One call: a computed-numbers payload in, a paragraph out.

Why this is the textbook LLM use: generating fluent, tone-appropriate prose over a fixed set of facts is exactly what LLMs are best at. The trick — and the safety property — is that the LLM receives numbers already computed by code and is told to phrase, not calculate. This sidesteps the arithmetic weakness entirely: there is no math for it to get wrong. It also handles Hindi/English naturally, which matters for owners living on WhatsApp.

Guardrail: the prompt passes structured numbers and forbids deriving new ones; a quick code check can confirm the figures in the output string match the payload. This is the system's "code computes, AI narrates" rule made literal.

7Conversational assistant LLM over a semantic/tool layer

Approach
LLM that selects from a governed semantic/metrics layer — not free text-to-SQL. Numbers come back from the layer (code), never from the model.
Model
Claude Sonnet or Gemini 2.5 Pro (both on Vertex). Sonnet leads on tool-use/instruction-following; Gemini Pro is strong multilingual. Either works; pick on cost and your own Hindi test.
Agent?
Light agent. A tool-calling loop is justified only for multi-step or clarifying questions; a simple "question → one metric query → answer" stays a single call.

Why a semantic layer beats free text-to-SQL: raw text-to-SQL fails quietly — even frontier models hit only ~17–21% on enterprise-scale schemas (Spider 2.0), and a wrong query returns a plausible but false number. A constrained semantic layer flips the failure mode: dbt's 2026 benchmark measured the semantic layer at 100% accuracy in scope vs 62–64% for text-to-SQL, because "if it picks the right metric and dimensions, the query is guaranteed to be correct" and failure looks like an error message, not a wrong answer. For a system whose whole principle is trustworthy money numbers, that property is decisive — the LLM chooses which pre-defined metric to fetch; it never authors arithmetic.

Agent vs single call: follow Anthropic's rule — use the simplest thing that works. A fixed question→metric→answer path is a workflow (single call). Reserve the full tool-calling loop for genuinely open-ended, multi-turn exploration where you can't predict the steps. Agents "trade latency and cost for better task performance" — only pay that when the task demands it.

Model availability — stays inside GCP Claude (Sonnet, Haiku) runs on Vertex AI Model Garden, so a Gemini-vs-Claude choice doesn't mean leaving Google Cloud. Note: Claude multi-region endpoints are US/EU only today — confirm the India-region position in Model Garden if strict residency is required.

8Payments copilot rules/ML detect + LLM parse & brief

Approach
Split the job. Deterministic code owns duplicate detection and all amounts; LLM owns the messy free-text narration and writing the "safe to pay" brief.
Method
Code: duplicate-payment match on vendor + invoice-no + amount(±tolerance) + date-window; threshold/variance rules. LLM (Gemini Flash): parse bank narration → vendor/store/purpose. Optional fuzzy/ML layer for near-duplicate invoice numbers.
Agent?
No. Parse = one call; detection = deterministic; brief = one call.

Why this split: bank narration is unstructured, multilingual, and bank-specific — per-bank regex parsers break constantly. This is where an LLM genuinely earns its keep: one vendor (Inscribe) measured coverage jumping from 18%→94% on non-English account-number extraction by adding an LLM. But the amount, value date, debit/credit are already structured — keep those deterministic; never ask the LLM to restate or compute money.

Duplicate / fraud detection stays deterministic: the right approach is multi-field matching (same vendor + invoice number + amount within tolerance + date inside a rolling window, e.g. 90 days), plus rules for same-amount-to-two-vendors and changed bank details. This is exact, auditable, and the AP-fraud industry standard — duplicates/errors run 1–2.5% of payments processed. A fuzzy/ML layer is the later upgrade to catch near-duplicates ("INV-001" vs "INV1"). On a flag: hold and escalate to a human — "flag-don't-block."

The brief: once code has matched, validated, and flagged, an LLM writes the one-paragraph "safe to pay / hold because…" summary over those computed facts — the same narrate-don't-calculate pattern as the daily digest.

Cross-cutting verdict

Where agents add value — and where they're overkill

An "agent" = a model that runs a multi-step, tool-calling loop and decides its own next move. Powerful, but expensive, slower, and harder to control — and most projects don't need it.

Gartner — the cautionary data Gartner predicts (25 June 2025) that over 40% of agentic AI projects will be cancelled by end of 2027, citing escalating costs, unclear business value, and inadequate risk controls — plus "agent washing" (rebranding chatbots/RPA as agents), with only ~130 vendors worldwide judged to offer genuine agentic AI. The lesson for KDPS: don't reach for an agent because it's fashionable.
Gartner press release — https://www.gartner.com/en/newsroom/press-releases/2025-06-25-gartner-predicts-over-40-percent-of-agentic-ai-projects-will-be-canceled-by-end-of-2027 · CDO Magazine coverage (agent washing, 130 vendors) — https://www.cdomagazine.tech/aiml/over-40-of-agentic-ai-projects-likely-to-be-abandoned-by-2027-gartner-forecast

The decision rule (Anthropic, "Building Effective Agents"): "find the simplest solution possible, and only increase complexity when needed… for many applications, optimizing single LLM calls with retrieval and in-context examples is usually enough." Use an agent only for "open-ended problems where it's difficult to predict the required number of steps and you can't hardcode a fixed path" — and where you can trust its decisions. Agents "trade latency and cost for better task performance."

Why deterministic code must compute every money number

Restating the spine rule with its evidence: LLMs are not calculators. Base models score ~11–36% on hard arithmetic; the fix is to give them deterministic tools, after which accuracy jumps to ~95% — i.e. the code does the math, not the model. In KDPS terms: totals, margins, discounts, taxes, balances, sell-through, duplicate-amount matches — all computed in plain code against the ledgers. The LLM's only relationship to a number is to read one code produced and wrap a sentence around it. This is "AI at the edges, never on the books," made concrete.

Bottom line for the meeting The "best tool for each job" instinct is exactly right and is backed by the evidence: vision LLM for reading documents, classical ML/stats for forecasting and anomalies (LLMs are measurably the wrong tool there), deterministic rules for markdown signals and duplicate detection, and language LLMs (Gemini Flash / Claude Sonnet) only at the language edges — narrating, parsing text, answering questions over a governed metrics layer. Money math is always code. Start simple everywhere; add ML where data earns it. Use an agent for one task at most.

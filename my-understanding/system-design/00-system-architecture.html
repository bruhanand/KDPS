System Architecture — the whole picture

One frame that every design discussion fits into. The spine (booking → inbound → outbound) produces documents; documents write ledgers; everything else reads them. The design is now substantially complete — D1–D8 are locked; only D9 (migration & rollout) remains before the consolidation pass and the build. This page holds the rules every module must obey, where each piece sits, and what is left.

How to use this document. Before any design discussion, read the 12 rules and find the module's slot in the discussion plan. Every discussion ends by answering the same three questions: what documents exist, what life cycle does each have, and what does each post to which ledger. If a discussion produces an answer that breaks a rule here, either the answer is wrong or the rule must be consciously changed on this page first — never silently.

Why this exists. Vendor management and inbound were designed one at a time and came out consistent by instinct. From outbound onwards the modules start touching money, statutory books and AI — instinct is not enough. This page made the shared skeleton explicit so the later discussions (outbound, payments, offers, Tally, analytics) could run independently and still snap together — which they did. Only rollout (D9) now remains.

The 12 rules — every module obeys these

These are the best practices of every serious retail/ERP system, written as binding rules. All are now in force across the eight locked designs (D1–D8) — each rule notes where.

1

Every business event is a document with a life cycle

Nothing happens "loosely". A booking, a goods receipt, a sale, a transfer, a return, a payment — each is a numbered document with line items and an explicit status flow (a state machine). No document, no event.

✓ Already in force: Booking (Booked → Partially → Fully received → Return window → Closed; statuses derived from GRNs, arrival lives on the Shipment — revised 10 Jun 2026), GRN (writes the stock ledger as a quantity movement — qty, location, condition, season — no unit cost), PT (writes the priced valuation + vendor liability per model at Patna inward).
2

Documents write ledgers; ledgers are never hand-edited

Stock-on-hand, payables and cash positions are sums of postings, never typed numbers. Corrections are reversing entries — nothing is ever deleted or overwritten, so the history always explains the present.

✓ Already in force: inbound defines SOH as derived from cumulative movements.
3

Master data lives in one place; documents snapshot it

Terms, prices and margins are maintained on the master — but the moment a document is created, it copies (snapshots) what it uses. Changing a brand's margin tomorrow must not rewrite yesterday's booking.

✓ Already in force: commercial model is snapshotted onto each booking.
4

Every fact has exactly one owner

Stock truth = the stock ledger. The sale moment = POS (we ingest it, we don't recreate it). Statutory truth = Tally. Offer logic = the offer rulebook. Everyone else reads. Two owners for one fact is how systems start lying.

✓ Already in force: POS kept external; KDPS owns truth up to store allocation.
5

Flag, never block

Validation failures and mismatches raise a flag into a named exception queue with a named owner — the goods, the sale, the file keep moving. Blocking the floor to satisfy the software is how staff stop using the system.

✓ Already in force: GRN soft discrepancy flags; unmapped-PT queue; Patna exception-only approval.
6

Derived numbers are computed, never typed

Profitability = cost from PT/invoice at stock-in, revenue from POS at sale. Aging = today minus stock-in date. MRP = formula. If a number can be computed, a human typing it is a bug.

✓ Already in force: non-branded MRP = base + 1.1% transport + GST + category margin (non-branded → v2).
7

Integrations are contracts, reconciled daily

Each edge (POS, Tally, bank, WhatsApp) is a written contract: what we push, what we pull, on what join key, what happens on retry. Every contract has a daily reconciliation and a failure queue. Never assume the other side received it.

✓ Already in force: POS contract joined on barcode; TIR export in strict reproducible format.
8

AI at the edges only AI

AI reads messy inputs (vendor invoices, fuzzy item-name matching) and writes read-only outputs (forecasts, digests, anomaly alerts, split suggestions). AI never posts to a ledger and never sits inside a document's approval path. A wrong forecast wastes attention; a wrong posting corrupts the books.

✓ Already in force: AI reads non-branded invoices (non-branded → v2); TIR is explicitly "pure algorithm, no AI".
9

Identity discipline on every line

Quantity exists only at SKU level (brand + style + colour + size) — style-level stock is meaningless. Every piece has a barcode; every item carries season/collection; every commercial line carries its model (Outright / Correction / SOR / Consignment). No line without identity.

Conscious exception (10 Jun 2026): booking lines are style + size only — a booking posts to no ledger; full SKU grain begins at GRN/PT. See D1 §10 (deliberate trade-offs).
✓ Already in force: SKU & barcode registry in inbound; model snapshot in vendor management.
10

Every action has an actor

Who created, who edited, who approved, when — on every document. Approvals are steps inside the document's state machine, not emails on the side. Roles say who may take which step.

✓ In force: WH approval and Patna inward gates; full roles & separation-of-duties grid designed in Payments (D4).
11

Deadlines are data, not memory

Anything that can expire is stored with its date and alarmed before it dies: SOR return windows (60–120 days), offer start/end dates, payment due dates, season EOSS windows. No deadline lives in anyone's head.

✓ Already in force: booking carries "return window open" as a status; offers carry start/end with fallback.
12

Variation is data, not code

The things that vary between brands, stores, states and seasons live as configuration rows, never as branches in the program. Document types, posting reasons, commercial models (Outright / Correction / SOR / Consignment), offer rules, roles & rights, taxonomy (category / season / collection), GST slabs and the report/digest schedule are all data a steward can add or change — adding a new brand model, a new offer pattern, a new GST slab or a new season must never need a code release. The kernel that posts the books stays small and frozen; everything business-specific is a row above it. Test: if a business change forces editing code instead of a master row, the design has leaked.

✓ Already in force: commercial models, season calendar and GST as date-effective HSN+price-band rows (D8); offer rulebook as data (D5); RBAC as configurable rights (D4); per-user digest type & timing as config (D7).

How we build — the development process

Decided 10 June 2026 from a verified deep-research pass over Anthropic's Claude Code guidance, GitHub's Spec Kit, Thoughtworks and ledger-engineering sources. The short version: one thin planning layer upfront, then one verified slice at a time — never all PRDs written first, never one module built to completion before the next starts.

1 · Two upfront artifacts — instead of a PRD library

The constitution: this page (the 12 rules) — every spec and every coding session obeys it. The feature inventory: the whole system enumerated as user-testable, end-to-end outcomes ("a branded shipment's PT converts, posts to stock + vendor ledgers, and the store sees pending inward"), each carrying a pass/fail status. It is born in the consolidation pass after the design discussions close (D9). This inventory is the master PRD — a checklist, not a book. The documented failure it avoids: full upfront spec sets drift, slow feedback "as in early waterfall", and push agents to one-shot whole systems until context runs out mid-build.

2 · Specs just-in-time, one vertical slice at a time

When a slice starts: a session interviews Anand → writes a self-contained spec (names the files and interfaces, states what is out of scope, ends with a runnable end-to-end verification step) → a fresh session executes it. Slices cut down through the layers (document + posting + screen together), never sideways through one layer. Slice #1 is the walking skeleton: one branded shipment travels booking → GRN → PT → ledger postings → store split → POS push, using real sample files — proving every layer and every edge contract before anything is widened.

3 · The agent verifies its own work

Golden files from the ~150 real invoices and the real PT/ledger samples: file in → expected PT / postings out, diffed in CI. Ledger invariants as tests written before the posting code: postings are append-only; every balance equals the sum of its postings; every ledger row traces to a document. Every spec ends with a check the agent can run itself — CI green is "done"; "looks done" never counts.

4 · Risk tiers — money code is always supervised

Ledger postings, payments, Tally vouchers: synchronous, watched sessions — never unattended auto-accept loops. Screens, reports, scaffolding: autonomous sessions are fine. A read-only AI code review runs after every change; on money-touching code it is mandatory and a green test suite still gets a human read (agents can satisfy visible tests while failing hidden ones).

5 · Externals are spiked before the stack is locked

POS (Ten Software), Tally import, the existing barcode tool: working empirical spikes first. No spec-first process can generate correct code for behaviour nobody has documented — these three answers shape the stack choice, so they come before it.

Honest gaps in the evidence: rollout engineering (migrations discipline, per-store feature flags, staging seeded with real data) had no verified sources — D9 designs it from first principles. And the research base is vendor-heavy (Anthropic on its own tool, GitHub on its own kit; Thoughtworks the only neutral voice) — the ledger-specific applications are sound extrapolation, not sourced ERP practice.

Tech shape — deliberately boring

One codebase, one database (a modular monolith)

Modules in code mirror the modules on this page, with clean internal boundaries — but it is one application over one relational database. No microservices, no queues between services, no second database. One developer, fifty stores: the architecture must be strong by being simple, not clever. The 12 rules are enforceable precisely because everything lives in one place.

Browser app, light and offline-tolerant

Each store runs on a computer (the POS machine); KDPS is a browser app on it — no installs, light pages, works on bad networks, big tap targets for any low-end device staff use. Hindi where staff face it. Owners get WhatsApp, not logins. INR everywhere in Lakh/Crore format (₹28,50,000).

Degraded modes are designed, not improvised

POS down → manual bill fallback (a real document, reconciled later). Internet down at a store → capture offline, sync when back. Tally rejects a voucher → failure queue, not a phone call. Every edge has a "what if it's down" answer in its contract.

Stack — ratified. The engine language, framework, database and hosting are now decided in ADR-0001 (25 Jun 2026): Python/Django back end, React/TypeScript PWA front end, PostgreSQL, hosted in an India region. Typed at both ends with a generated typed client at the API seam; not Frappe — ERPNext's contracts are re-implemented as plain Django models so the kernel stays small and frozen (Rule 12). See adr/0001-stack.md and consolidation/stack-decision.html. Nothing else on this page depends on that choice.

Glossary — architecture vocabulary

Document
A numbered record of one business event, with line items and a status life cycle (booking, GRN, PT, sale record, transfer note, payment proposal…).
Posting
An append-only entry a document writes into a ledger. Corrections are reversing postings, never edits.
Ledger
A derived book of truth (stock, vendor, cash). Only documents write it; humans and AI only read it.
Master / snapshot
Master = the maintained reference (brand terms, SKU). Snapshot = the copy a document takes at creation so later master edits don't rewrite history.
Exception queue
Where flagged mismatches wait for their named owner. The flow never blocks on them (Rule 5).
Contract (edge)
The written push/pull agreement with an outside system, with join key, retry behaviour, daily recon and a failure queue.
Spine
The chain of stock-carrying modules: booking → inbound → outbound. Everything else attaches to it.

What a proven ERP teaches the KDPS build

ERPNext and india-compliance, reverse-engineered into what KDPS should borrow, adapt, skip, and build better.

25 June 2026 · Inspiration for the home-built Django / React-TS / PostgreSQL system — not an adoption of Frappe.

What this is & the verdict

What this is

This is an engineering study, not a product decision. We take erpnext and its india-compliance app apart at source-code grain and hold every piece up against the KDPS design (the architecture, the eleven rules, and the D1–D8 module designs). The goal is to make KDPS's home-built system battle-tested by reference: where a fifteen-year-old, production-proven Indian-GST retail system has already solved a problem the way we want it solved, we borrow the pattern; where it solves a problem a way that fights a KDPS domain fact, we diverge consciously and write down why.

This is NOT a decision to adopt Frappe/ERPNext. The stack stays exactly as decided: a browser-based React (TypeScript) PWA front end, a Python/Django back end, and PostgreSQL in an India region. We re-implement ERPNext's contracts (the submit/cancel lifecycle, one central posting engine, atomic naming series, accounting dimensions, RBAC-as-data, child tables) as plain Django models and migrations. We do not adopt the Frappe metadata DocType runtime — that meta-engine is the one thing this study most firmly tells us to leave behind.

How to read it

Every area below carries a one-word lean and the rest of the study walks it row by row, citing the real ERPNext / india-compliance file path in monospace so each claim is checkable against /Users/anand/Code/erpnext/. The four verbs:

  • BORROW the pattern is right for us almost as-is — re-implement the contract in Django.
  • ADAPT the shape is right, the policy or grain must change for a KDPS fact.
  • KDPS-NOVEL ERPNext has no equivalent — greenfield, build it ourselves.
  • SKIP present in ERPNext but unwanted (multi-currency planes, perpetual GL coupling, history reposting).

The verdict

ERPNext validates the KDPS spine more than it threatens it — and vindicates every deliberate departure. The modular-monolith / one-Python-app / one-relational-DB / all-or-nothing-ledger shape is exactly what ERPNext proves works for Indian GST retail, so the KDPS architecture stands on battle-tested ground. The single biggest borrow is ERPNext's one-engine, append-only, balance-or-fail, correct-by-reversal posting contract (accounts/general_ledger.py + accounts/doctype/gl_entry/gl_entry.py): every document emits a balanced leg-set to one make_gl_entries that writes immutable rows inside a single transaction and never mutates them — the literal reason a BaaS like Supabase was rejected. The single biggest divergence is the cluster the business forces: frozen lot-exact landed cost (no moving-average, no repost_future_sle history rewrite), SOR/consignment value off-book until sale (no equivalent anywhere in ERPNext or india-compliance), and Tally as the statutory book fed once by deterministic vouchers — severing ERPNext's perpetual stock→GL coupling, which is precisely what makes SOR native rather than a hack. Net: borrow the accounting heart, keep our own kernel, build the governance shell and the season/ownership dimensions ERPNext never had.

How ERPNext works — the parts that matter to KDPS

A guided tour of ERPNext's engine for someone who has not read the source. Every business document in ERPNext follows the same shape: a typed record with a draft/submit/cancel lifecycle, whose controller emits balanced ledger rows on submit and reverses them on cancel. Ten cards below walk the engine from the framework skeleton up to the India GST layer. File paths are real and checkable.

1 · DOCUMENT FRAMEWORK
What it is
Every record is a DocType: a JSON schema plus a Python controller subclassing frappe.model.document.Document (tree masters use NestedSet). is_submittable:1 turns on the state machine: draft (docstatus 0) → submitted (1) → cancelled (2); a submitted doc is immutable except fields flagged allow_on_submit.
Audit + hooks
Free audit fields on every doc (owner, creation, modified, modified_by, optional track_changes). Ordered controller hooks: autoname → before_insert → validate → on_update → for submittables on_submit / on_cancel → on_trash. Ledgers are written only in on_submit and reversed in on_cancel — see stock/doctype/stock_entry/stock_entry.py:323 (posts stock + GL) and :346 (reverses both).
2 · GL POSTING ENGINE
What it is
One engine writes all double-entry. A submitting document builds a gl_map of legs (each a GL Entry: account, party, debit/credit, dimensions, voucher_type/voucher_no/voucher_detail_no back-reference) and hands it to make_gl_entries in accounts/general_ledger.py:34.
Guarantees
process_gl_map merges same-account legs and splits by cost-center; save_entries → process_debit_credit_difference enforces Σdebit = Σcredit (auto round-off for residue, else throws). Each leg is built by accounts/services/base_gl_composer.py:27 get_gl_dict; a worked assembly (customer/income/tax/COGS) is accounts/doctype/sales_invoice/services/gl_composer.py:22. A single GL row can never be edited or cancelled — gl_entry.py:325 on_cancel hard-throws; cancel = swapped-sign reversing rows via make_reverse_gl_entries (general_ledger.py:607).
3 · STOCK LEDGER + VALUATION + PERPETUAL INVENTORY
What it is
A second ledger carries quantity. Each Stock Ledger Entry (SLE) is one (item × warehouse) movement: actual_qty (signed delta), qty_after_transaction (running balance), valuation_rate, stock_value, and the load-bearing stock_value_difference. Engine: stock/stock_ledger.py — process_sle:847, get_moving_average_values:1523, update_queue_values:1562 (FIFO/LIFO bins in stock/valuation.py), update_bin:1751 (the running-balance cache).
Two halves
Back-dated entries trigger repost_future_sle:215 — ERPNext rewrites history to keep averages/queues correct. If perpetual inventory is on, controllers/stock_controller.py:224 → stock/services/base_stock_gl_composer.py:20 posts each SLE's stock_value_difference to GL (DR inventory / CR expense), so the value ledger mirrors the stock ledger by construction.
4 · BUYING FLOW — PO → PR → PI
What it is
Purchase Order = intent; posts nothing, only updates ordered_qty (buying/doctype/purchase_order/purchase_order.py:371). Purchase Receipt = goods arrived; posts stock and books DR Inventory / CR Stock-Received-But-Not-Billed (stock/doctype/purchase_receipt/purchase_receipt.py:359 + services/gl_composer.py) — no supplier liability yet. Purchase Invoice = the bill; CR Creditors / DR SRBNB, netting SRBNB to zero (accounts/doctype/purchase_invoice/purchase_invoice.py:607 + services/expense_account.py).
Notes
A PI with update_stock=1 collapses receive + bill into one voucher. Landed freight/duty capitalize into valuation_rate ("landed ex-GST cost") via the Landed Cost Voucher (stock/doctype/landed_cost_voucher/landed_cost_voucher.py:205) or inline valuation taxes (controllers/buying_controller.py:406).
5 · SELLING FLOW — SO → DN → SI + COGS
What it is
Sales Order reserves qty, posts nothing. Delivery Note posts stock-out (delivery_note.py:491). Sales Invoice posts revenue + receivable + tax (sales_invoice.py:421, GL in services/gl_composer.py:253). Cost flows automatically: controllers/selling_controller.py:515 set_incoming_rate derives the unit cost; the COGS double-entry (DR COGS / CR Stock-in-Hand from stock_value_difference) is stock/services/base_stock_gl_composer.py:58.
Counter sale + returns
A single SI with update_stock=1 posts stock + revenue + COGS together — the right shape for a retail counter. Returns are the same doc with is_return=1 + return_against, with every qty/amount negated (controllers/sales_and_purchase_return.py:430); a return reverses COGS at the original cost.
6 · POS — INVOICE / PROFILE / OPENING-CLOSING / CONSOLIDATION
What it is
POS Invoice subclasses Sales Invoice (accounts/doctype/pos_invoice/pos_invoice.py:33) — a fast retail path with mandatory multi-mode payment capture and a live stock guard. In "POS Invoice" mode it defers per-sale GL; in "Sales Invoice" mode each bill posts immediately (pos_settings/pos_settings.py:24). POS Profile is the per-till config (warehouse, accounts, payment methods, allowed users).
End of day
Opening Entry records the drawer float; Closing Entry reconciles counted vs system-expected cash per mode and on submit triggers consolidation (pos_closing_entry/pos_closing_entry.py:212) → pos_invoice_merge_log/pos_invoice_merge_log.py groups POS Invoices by customer + dimension into one real Sales Invoice that posts GL in bulk. The consolidated_invoice flag makes re-runs idempotent. No offline mode in stock ERPNext.
7 · PRICING RULES + PROMOTIONAL SCHEMES
What it is
One DocType — Pricing Rule (accounts/doctype/pricing_rule/pricing_rule.json) — encodes trigger + reward + dials: apply_on (Item / Item Group / Brand / Transaction) with qty/amount slabs and date window, and a Price action (Rate / Discount %/Amount) or Product action (free item, same_item, is_recursive for BOGO). The runtime brain is utils.py: get_pricing_rules, filter_pricing_rules (item beats group beats brand; keeps max priority).
Authoring
Promotional Scheme (accounts/doctype/promotional_scheme/promotional_scheme.py:363) is a slab builder: author rising slabs once, and set_args explodes each slab into atomic Pricing Rules (linked by promotional_scheme_id for idempotent regeneration). Schemes never run at sale time — only the generated rules do. Offers post nothing to GL; they only adjust rate.
8 · PAYMENTS + PAYMENT LEDGER
What it is
Payment Entry (accounts/doctype/payment_entry/payment_entry.py) is one money movement: payment_type Receive/Pay, a party, paid_from/paid_to (one side always the party control account, the other bank/cash), and a references child table — the allocation linking the payment to outstanding bills (one payment splits across many bills). difference_amount must be zero at submit.
Outstanding is derived
AR/AP is not a column — it is a sum of an append-only Payment Ledger Entry (accounts/doctype/payment_ledger_entry/), a signed projection of every GL line hitting a Receivable/Payable account. Bill-wise outstanding = Σ amount where against_voucher = bill (accounts/utils.py:2305 query_for_outstanding). Advances are negative outstanding, matched later by reconciliation (utils.py:515 reconcile_against_document). No maker/checker — only docstatus.
9 · ITEM VARIANTS / MASTERS / ACCOUNTING DIMENSIONS
What it is
Item is the master (stock/doctype/item/item.json, key = item_code). Template-vs-variant is one self-link: has_variants marks a template, variant_of points a variant back at it. Each size×colour is a real Item row with its own stock ledger; codes are deterministic via controllers/item_variant.py:437 make_variant_item_code (STYLE-RED-SM). Many barcodes per item via the Item Barcode child table (unique, no-copy).
Slicing the ledger
Warehouse is a NestedSet tree, each leaf with its own inventory GL account (warehouse/warehouse.py:55). Cost Center is a first-class column on every GL Entry (use as Store). Accounting Dimension (accounts/doctype/accounting_dimension/accounting_dimension.py:129) injects any master — e.g. Brand — as a GL column, so a brand-wise trial balance falls out. Deterministic voucher numbers via autoname:"naming_series:" with atomic per-prefix counters.
10 · INDIA GST MODEL (india-compliance)
What it is
ERPNext core removed GST in v14 (erpnext/patches/v14_0/remove_india_localisation.py); the live model is a bolt-on app. Config: GST Settings (singleton) holding a GST Account child table mapping CGST/SGST/IGST/cess to real GL accounts per company (gst_india/doctype/gst_account/). GSTIN lives on Address + Company with a 2-digit gst_state_number (Bihar = 10, Jharkhand = 20, in constants/__init__.py). Apparel slab rates are date-effective data in the Item Tax Template, not code.
Intra vs inter
overrides/transaction.py:572 is_inter_state_supply compares place-of-supply state vs source GSTIN state: same state → CGST + SGST (rate/2 each); different → IGST (full). Per-line tax amounts are written back onto every item row; GL is tagged company_gstin so two GSTINs stay distinct. e-Way Bill / e-Invoice / GSTR-1 payloads are produced from the same line data. No SOR / deemed-supply clock — that is greenfield for KDPS.
Read this card stack as one sentence: a typed document, on submit, emits balanced legs into two append-only ledgers (money in GL, quantity in the SLE), never edits a posted row, and reverses by sign-flip on cancel — with masters, dimensions, pricing rules, payments and the GST layer all feeding that one posting contract.

This is the centrepiece. For each of the eight kernel areas, the table below pins every KDPS concept against the actual ERPNext (Frappe + india-compliance) mechanism, with a verdict and the concrete pattern to reuse or the reason KDPS must build its own. The two headlines across all eight areas. The single biggest BORROW is the one-engine, append-only, balance-or-fail, correct-by-reversal posting contract (accounts/general_ledger.py::make_gl_entries + process_debit_credit_difference + gl_entry.py::GLEntry.on_cancel → make_reverse_gl_entries), wrapped with the accounting-segment trio — Cost Center (Store), Accounting Dimension (Brand), GSTIN-on-Address/GL-tag — so every posting line is sliceable by store, brand and state-GSTIN for free. Does a proven ERP validate KDPS's design?

We tested the KDPS design against ERPNext — a fifteen-year-old, battle-hardened, double-entry, append-only ledger engine built for exactly our domain: Indian multi-entity GST retail and distribution. ERPNext is the right adversary because the KDPS spine already borrows from it in spirit. The headline finding: ERPNext confirms the load-bearing patterns and vindicates every deliberate departure. Where KDPS is stricter than ERPNext, the strictness is a precise patch for a real ERPNext leak — not gold-plating. Every claim below is checkable against a real source path in erpnext/ or india-compliance/.

One-line verdict. Borrow ERPNext's contracts (documents -> append-only ledgers, correction-by-reversal, one posting engine, naming series, dimensions, RBAC-as-data, variant SKU, batch-wise frozen cost). Reject its kernel (perpetual stock->GL auto-posting, moving-average / FIFO recompute, repost_future_sle history rewriting, the runtime DocType meta-engine). That line — copy the behaviours, refuse the meta-runtime — is Rule 12.

Part 2 · The load-bearing tensions

Four places where ERPNext's behaviour and KDPS's rules collide head-on. Each is a real architectural fork with a money consequence. Three resolve clearly in KDPS's favour; the fourth (cost) is not even a contradiction — it is a configuration ERPNext already ships.

Tension A — Frozen cost vs continuous revaluation + history rewrite. ERPNext never freezes unit cost: valuation_rate = stock_value / qty_after_transaction (stock/stock_ledger.py process_sle), and a sale's outgoing_rate is computed at issue time from the current FIFO queue (update_queue_values:1562) or moving average (get_moving_average_values:1523). Worse, a back-dated receipt fires repost_future_sle (stock_ledger.py:215), which rewrites the cost, value-delta and GL of already-posted sales (repost_item_valuation.py:492). Moving-average is correct for fungible stock (flour, fuel) where "which unit sold" is unanswerable; fashion is the opposite — a Style×Size×Colour piece is identity-bearing and its landed cost is knowable and fixed from the PT line it arrived on. Reposting would silently restate margins already reported to a brand owner, and corrupt the per-lot rate SOR settlement is paid on.

Recommendation: cost-freeze, not FIFO-recompute + reposting. Freeze landed-ex-GST cost on the PT-lot at stock-in, forever; a correction is a new dated event, never a rewrite. This is not a fight with ERPNext — it ships the exact feature: map PT-lot -> Batch with use_batchwise_valuation (stock_ledger.py:1619, BatchNoValuation) and each unit consumes at its own lot's frozen rate, lot-exact, no blending. Borrow the SLE shape (append-only, item×warehouse, actual_qty / qty_after_transaction / stock_value_difference, Bin as a derived cache) plus batch-wise valuation; delete moving-average/FIFO recompute and repost_future_sle.
Tension B — External Tally as the book vs ERPNext-is-the-book. In ERPNext the GL is the accounting truth: every stock movement auto-posts a balanced pair off stock_value_difference (base_stock_gl_composer.py:66; perpetual controllers/stock_controller.py:178), so inventory value and the books can never drift — reconciliation is free by construction. KDPS deliberately severs this: Tally is the statutory book of record (the accountant files GST from it; it is the legal record), fed one-way, exactly once, via deterministic vouchers. KDPS's own ledgers are an operational/analytics sub-ledger. Making KDPS the book would mean replacing the accountant's tool — out of scope, high-risk, and it would own GST-compliance liability in v1. The cost KDPS must consciously fund: ERPNext gets stock↔GL reconciliation free; KDPS must build the daily Tally tie-out (join on voucher number) and a failure queue.

Recommendation: external Tally as the book; borrow ERPNext's GL as the internal ledger model only. Keep Tally statutory and KDPS operational — one owner per fact (R4); two systems claiming to be the book is how systems start lying. But adopt ERPNext's GL engine wholesale as the internal model: append-only with the hard throw (gl_entry.py:325), correction-by-reversal in the immutable variant (general_ledger.py:716-718), one make_gl_entries for all documents, Σdr=Σcr at write, full voucher_type/voucher_no/voucher_detail_no drill-down (this powers "profitability is derived"), and the party sub-ledger where against_voucher = Tally Agst Ref = KDPS Allocation. Strip the statutory claim; keep the model.
Tension C — Snapshot vs live master rates. ERPNext is largely live: a Sales Invoice reads the customer account, income accounts and tax templates at submit, and moving-average valuation recomputes against current state. Its one safeguard against history-drift is reposting — it lets masters move and then rewrites the past to match. KDPS forbids the rewrite (Tension A), so it has given up that escape hatch. Two distinct jobs are needed: snapshot (the document copies the master values it used — protects that one bill) and effective-dating (SCD Type-2 on the masters that drive history — so a back-dated new document picks the right historical value). GST is the proof: the apparel slab changed 22 Sep 2025 (5% ≤ ₹2,500/piece, 18% above) — it must be dated data, computed once at sale, carried, never recomputed (R6). ERPNext's India-Compliance bolt-on confirms the posture: GSTIN/HSN are a regional layer over a tax-agnostic core (no gstin in core supplier.json; only generic tax_id), not baked into posting.

Recommendation: snapshot is mandatory because reposting is forbidden. Snapshot at document creation (R3) and SCD-Type-2 the four history-driving masters — GST slab, GSTIN, cost, price. Carry brand / season / and crucially state-GSTIN as ERPNext-style dimensions on every ledger leg (base_gl_composer.py get_gl_dict) — but as declared FK columns, not runtime-injected fields — so Bihar↔Jharkhand cross-state transfers post as IGST taxable supplies natively, instead of ERPNext's two-companies workaround.
Tension D — Perpetual-inventory GL coupling: does KDPS need it? ERPNext, when perpetual inventory is on (stock_controller.py:190), couples stock to GL automatically: every receipt does DR Inventory / CR Stock-Received-But-Not-Billed; every issue does CR Inventory / DR COGS; the PR->SRBNB->PI chain nets to DR Inventory / CR Creditors (purchase_invoice/services/gl_composer.py). The deep misfit: a Purchase Receipt always capitalises value and parks an SRBNB credit — it assumes ownership transfers on receipt. There is no native "counted in quantity, value off-book, liability posts only on sale." But KDPS does not own the accounting book (Tension B), so there is no KDPS GL that needs to stay tied to inventory — the auto value->GL machinery is dead weight.

Recommendation: keep the SLE quantity track; sever the auto value->GL coupling — and that severance is what makes SOR native. GRN posts quantity only, with the SOR lot flagged not-owned; value reaches the books only through the deterministic Tally voucher at the right grain. The vendor-liability leg's trigger becomes config: "inward" for Outright/Correction (= ERPNext's PI/Creditors at arrival), "sale" for SOR/Consignment. One mechanism, trigger-as-config — the kernel's config-not-code principle. The single biggest data-model divergence (SOR) is paid for by the single biggest deletion (perpetual GL). Worth keeping even so: the landed-cost formula (buying_controller.update_valuation_rate:406; landed_cost_voucher.py:205) — valuation taxes (freight/duty) capitalise into cost, GST credits a recoverable input account, not inventory; that is "landed ex-GST." Borrow the formula and the Landed-Cost-Voucher pattern for late freight bills, but compute it KDPS-side and freeze it.

Part 3 · Stack & architecture: confirmed

The modular monolith is confirmed — ERPNext is the fifteen-year proof. ERPNext is a single deployable Python app, modules-as-folders (erpnext/stock/, erpnext/accounts/, erpnext/selling/) over one relational schema — no microservices, no per-module DB. The ledger requires it: Σdebit=Σcredit inside one DB transaction (general_ledger.py process_debit_credit_difference) needs a single transactional relational DB — the exact reasoning KDPS used to reject Supabase/BaaS and pick PostgreSQL with hand-built posting. ERPNext independently arrived at the same constraint, in the same language (Python), for the same domain. KDPS's spine is on battle-tested ground.

Two places KDPS is better than the reference, deliberately: (1) PostgreSQL row-level security per store/GSTIN is stronger isolation than ERPNext's app-level company filter — the database itself enforces the Bihar/Jharkhand "distinct persons" boundary instead of trusting every query to remember a WHERE company=; (2) state-GSTIN as a first-class ledger dimension, where ERPNext is state-blind. Both are conscious upgrades, not deviations to justify.

Framework patterns to re-implement in Django — copy the contract, write it as plain Django models + migrations + explicit posting functions, golden-file tested per slice. Never inherit a generic base that mutates global behaviour.

What NOT to copy.
  • The metadata-driven DocType meta-engine. ERPNext's power and pain are the same artifact: a runtime that reads JSON schemas and dynamically builds tables, forms, permissions, and even injects columns at runtime (accounting_dimension.py:158). The Frappe meta-runtime is a whole second framework — it is not even vendored alongside the erpnext app, confirming it is a separate engine. Runtime-generic is the opposite of compiler-checked money-safety and directly violates R12. Use plain Django models + migrations; flexibility comes from config tables, not a meta-engine.
  • MariaDB — it has no real RLS. PostgreSQL is a deliberate upgrade for per-store/GSTIN isolation.
  • The four-currency-plane GL machinery (gl_entry.json company/transaction/reporting currencies). KDPS is INR-only — keep only debit/credit in INR (e.g. a sale line of Rs 28,50,000 carries one debit and one credit, no exchange rate). Drops a large slice of complexity.
  • Perpetual SLE->GL auto-coupling + FIFO/moving-average reposting (base_stock_gl_composer.py:66; repost_future_sle at stock_ledger.py:215) — contradicts frozen cost, SOR off-book-until-sale, and Tally-as-book. Borrow the SLE shape and batch valuation only.
  • Company-only multi-entity scoping — regressing to it loses the state-GSTIN dimension the two-GSTIN domain rule needs.
The one genuinely unreconciled point — "TypeScript end-to-end." With a Python/Django backend, types stop at the API boundary. ERPNext (Python + JS, no shared type system) proves the split-language model ships fine in production, but also proves "types flow DB->screen in one language" is not literally achievable. Restate the goal consciously as: typed React PWA (TS) + typed Django (mypy/pydantic) + a generated OpenAPI typed client at the seam — not one language. This is the only stack claim where the two KDPS design docs disagree, and the reference offers no cover.
Bottom line. A proven ERP does validate KDPS's design — the spine (documents -> append-only ledgers -> correction-by-reversal, modular monolith, one transactional relational DB, deterministic Python posting) is exactly what ERPNext ships and exactly what KDPS planned. Every divergence (PostgreSQL+RLS over MariaDB, frozen per-lot cost over moving-average reposting, external Tally over perpetual-GL, INR-only over four currencies, declared FK columns over runtime-injected dimensions, plain Django over the meta-runtime) is a conscious correction of an ERPNext property that conflicts with a KDPS domain rule — not a gap in KDPS's thinking. Borrow the proven data shapes piecemeal; reject the kernel; hand-build the commercial-model dimension, the deadline-alarm layer, and the config-driven posting kernel under the 12-rule constitution. That is precisely the stance the consolidated design already takes.

Where KDPS is genuinely better / beyond ERPNext

ERPNext gives us the load-bearing primitives — the two-ledger split (stock ledger = quantity, GL = value), batchwise valuation for lot-frozen cost, an append-only balanced-posting engine, the supplier-liability GL leg, the variant engine for SKUs, and proven idempotent batch-posting. But six things that make KDPS what it is have no native home in ERPNext. For each, we keep ERPNext's plumbing underneath and build the missing model on top. The recurring pattern: borrow the leg, move the trigger; borrow the storage shape, build the meaning above it.

The one-line rule throughout: ERPNext's mechanisms are the read/storage model; KDPS's data and rules are the write/decision model that sits above and decides what ERPNext's machinery emits, and when.

1 · The four commercial models as a first-class ownership dimension

Ownership is the single fact that drives money, returns, GST, and settlement for KDPS — and it differs brand-by-brand and changes season-by-season. ERPNext hardwires ownership to transfer at goods receipt. Confirmed in three places that make it structural, not configurable:

  • Purchase Receipt always capitalises value into inventory. purchase_receipt.py:359-383 (on_submit) calls update_stock_ledger() then make_gl_entries(). The GL composer (purchase_receipt/services/gl_composer.py) unconditionally books DR Inventory (make_item_asset_inward_gl_entry, :57-71) / CR Stock-Received-But-Not-Billed (make_stock_received_but_not_billed_entry, :73-160). No branch leaves value off-book.
  • The liability leg fires from the invoice, never from the sale. purchase_invoice/services/gl_composer.py make_supplier_gl_entry (:80-127) credits Creditors for the grand total. The only triggers offered are "at receipt" or "at invoice."
  • No return-window deadline anywhere. PO/PR/PI carry per_received/per_billed (purchase_order.py:131-142) but no per-lot 60-120 day clock, no SOR-window alarm, no India 6-month GST timer.

The web docs confirm the same: the only "consignment" path ERPNext offers is a dedicated consignment warehouse plus manual stock entries and adapted returns — a workaround over generic warehouse plumbing, not a model.

2 · SOR/Consignment, the deemed-supply 6-month clock, and once-only GST recognition

ERPNext assumes ownership transfers at receipt and the india-compliance app has no deemed-supply timer. A full-app grep confirms it: every "consignment" hit in india-compliance is e-waybill transport status — CONSIGNMENT_STATUS = {"In Movement": "M", "In Transit": "T"} (india_compliance/gst_india/constants/e_waybill.py), unrelated to ownership. The only "6 month" reference is a GSTR-3B filing-recency fallback (india_compliance/gst_india/doctype/gst_invoice_management_system/gst_invoice_management_system.py) — a return-period helper, not a goods-on-approval clock. There is no stored deadline saying "this lot must be recognised as a supply by date X."

So india-compliance gives us excellent GST computation and GSTIN/state plumbing (per-line CGST/SGST vs IGST via overrides/transaction.py, HSN slabs as date-effective data, company_gstin on every GL line) — but the SOR ownership model, the per-lot deadline, and once-only recognition are greenfield.

The real statutory rule (CGST Act, s.31(7)). Goods sent "on approval for sale or return" are removed before the supply is known. GST is deemed to occur — and a tax invoice must be issued — at the earlier of: (a) the buyer accepting the goods (for KDPS: the moment a piece sells), or (b) six months from the date of removal (the brand's dispatch / KDPS receipt), even if the piece never sold. A piece sitting unsold past six months is a deemed supply: the brand must raise a tax invoice and GST becomes due regardless of an actual sale. This is a different deadline from the 60-120-day commercial return window, and it is the one ERPNext/india-compliance entirely lack.

If KDPS does not alarm this clock: (a) the brand is forced to raise a deemed-supply invoice KDPS never anticipated, and (b) KDPS may take input-credit timing wrong — exactly the money-bug Rules 6 and 11 exist to prevent ("deadlines are data, not memory").

How to build it (borrowing ERPNext underneath). Two legs (already in ERPNext), but move the liability-leg trigger to sale; add an effective-dated lot carrying two timers; add an exception queue; guard recognition so GST fires exactly once.
  • Qty leg — borrow the non-valuated SOR location. Receive SOR/Consignment into a dedicated SOR warehouse mapped to a no-value posture, using ERPNext's warehouse_type classifier + per-warehouse account field (erpnext/stock/doctype/warehouse/warehouse.json — warehouse_type line 233, account line 97). The warehouse either posts no inventory GL (qty visible, value off-book) or posts to a memo/off-balance account — never KDPS Stock-in-Hand, never SRBNB. ERPNext shows it must be a location property, not a per-line flag, so the stock ledger stays honest about ownership. Our stock-ledger row already carries owned-flag + unit cost; for SOR/Consignment owned-flag is false.
  • Liability leg — keep ERPNext's PI/Creditors entry, fire it from the sale. make_supplier_gl_entry (CR Creditors, party=Supplier) is exactly the posting we want. Only the trigger moves from goods-receipt to the sale event (or the deemed-supply alarm). On a SOR sale, the Sale document fires the vendor-liability posting at the settlement rate. The GL entry's shape is unchanged; only when it fires.
  • Effective-dated SOR Lot, two clocks. Model a first-class SOR Lot (child of the PT/GRN, one per brand-season-shipment), SCD Type-2, storing: removal_date (start of both clocks), commercial_window_days (brand snapshot), return_window_due = removal_date + window (clock 1, alarmed 30/15/7d), deemed_supply_due = removal_date + 6 months (clock 2, statutory, code-fixed), qty_remaining, and gst_recognised (the once-only guard). Two timers run in parallel against the same lot — clock 1 commercial (return goods), clock 2 statutory (recognise the supply) — different owners, different actions, never collapsed.
  • Exception queue (flag, never block — Rule 5). Clock 1 → owner = buyer/account manager, action = trigger Seasonal Return before window closes. Clock 2 (for qty_remaining > 0) → owner = Patna accountant, action = recognise unsold pieces as a deemed supply: fire the deferred liability + GST leg without a sale, raise the journal/voucher to Tally, book the brand's deemed-supply invoice. Reuses the existing edge-contract/recon queue pattern.
The F9 risk — GST recognised twice. Our Tally design creates a Purchase voucher at arrival for every brand including SOR (no special-casing at the statutory layer), and separately the SOR/Consignment settlement crosses as a Journal voucher per brand per period. If both carry GST for the same pieces, GST is recognised twice. The rule that prevents it: GST is recognised exactly once per piece-lot, at the earlier of sale or the six-month deemed-supply date — never at both arrival and settlement. Concretely: (1) pick one convention as a code-level invariant — either arrival-voucher-is-memo (SOR arrival voucher carries no input GST; the sale/deemed-supply alarm carries it) or arrival-voucher-is-statutory (GST at arrival, settlement journal is money-only, zero-GST); (2) enforce with the gst_recognised = (date, voucher_number) guard on the lot — whichever event fires GST first sets it; any later event books money/qty only, GST suppressed; (3) the deterministic voucher number (DEO-SAL-20260620-001, prevent-duplicates ON) is the join key the daily tie-out uses to detect a second GST hit. Reuse india-compliance for the amount (per-line CGST/SGST vs IGST via is_inter_state_supply in overrides/transaction.py, date-effective slab from Item-Tax-Template, company_gstin), never the timing.

4 · AI at the edges

ERPNext has no AI layer at all. Its posting machinery is deterministic code welded to Frappe's DocType lifecycle:

  • The GL engine (erpnext/accounts/general_ledger.py — make_gl_entries, process_gl_map, save_entries/make_entry) is pure arithmetic: build balanced legs, enforce Σdebit = Σcredit (process_debit_credit_difference, :460), write immutable rows.
  • The composers (sales_invoice/services/gl_composer.py:compose, accounts/services/base_gl_composer.py:get_gl_dict) are deterministic mappers — account + amount + dimensions, nothing inferred.
  • Inputs are assumed clean. No invoice-reading, no fuzzy name-matching, no narration parsing, no fraud heuristic, no natural-language query. A Purchase Invoice is a form a human fills; ERPNext never reads a messy PDF to produce one. The only "intelligence" is configured rules (pricing, reorder levels) — still deterministic config.

So the gap is total — by design, matching Rule 8 (AI at the edges only) and the consolidated note that AI "only sees edge data and computed numbers, never raw customer/payment data."

Why KDPS needs AI exactly where ERPNext assumes it away. Inputs are not clean (40+ brands, 25+ formats; non-branded vendors send nothing structured — the transaction is the master-creation event). Owners live on WhatsApp, staff speak Hindi, phones are low-end Android — no analyst pores over reports, the system must narrate itself. One developer, fifty stores — no human watches all the leakage, dead stock, duplicate payments, vendor-bank fraud and markdown timing; AI watches and ranks, humans act on the top five. And the books must stay exact — precisely because AI is fallible, it must be kept off the ledger.
How to build it (borrowing ERPNext underneath). Edge-AI is a separate read-only application tier producing drafts, suggestions, and messages. It never calls the posting engine. A human always converts an AI draft into a real document, and the document — not the AI — posts.

5 · Fashion: variants, season, aging, and the EOSS V-flip

The headline: ERPNext models a garment SKU well and a garment lot poorly. Its variant engine is a near-perfect fit for brand+style+colour+size, so adopt it almost unchanged. But everything that makes fashion fashion — that value decays by season and age, that one scan code spans many pieces, that unsold stock gets ownership flipped and liquidated — has no native home. ERPNext's nearest mechanism, the Batch, is a shelf-life/expiry construct, not a merchandising cohort. So KDPS borrows its plumbing (batchwise valuation, the SLE batch path) but builds the season cohort, the V-flip, and the aging→markdown ladder on top.

SKU = brand + style + colour + size — borrow almost as-is

The variant engine is exactly KDPS's SKU grain: a template Item (has_variants=1) per Brand+Style; every Colour×Size a real variant pointing back via variant_of (item.json:540,168), each with its own stock ledger — so size×colour survives end-to-end, the domain non-negotiable. Attributes are data (Item Attribute + Item Attribute Value {value, abbr}, pinned in Item Variant Attribute, item_variant_attribute.json:30-47). Codes are deterministic (make_variant_item_code() → TEMPLATE-<abbr>-<abbr>, item_variant.py:437). brand and item_group are already present. The only small gap: ERPNext attribute values are global enumerations, but KDPS's COLOR may be a P/M/E tier (Premium/Medium/Economy) and SIZE may be "Free Size" — two extra controlled-vocab values, not a structural gap. Borrow the engine unchanged; seed the attribute lists from the PT Master Sheet.

The piece cohort = barcode + season — partially borrow, mostly build

KDPS's unit-of-tracking is not the SKU and not a serial — it is the cohort barcode + season, where one barcode → many pieces (count under a barcode, never a per-piece serial). Season is system-derived (FAMILY(Mon-YY)), never free text; each season is a distinct cohort that aging, dead-stock, SOR-window and V-flip all run per.

  • The barcode half — borrow. Item Barcode is a child table, one Item → many barcodes, each {barcode (unique, no_copy), barcode_type, uom} (item_barcode.json). unique+no_copy means one scan resolves to one variant globally — exactly KDPS's scan key, including "vendor's EAN, else POS-generated."
  • The season-cohort half — build on Batch. ERPNext has no Season, Collection, or Age field anywhere on Item. The nearest analog is Batch — but it is shelf-life/expiry, not a cohort. Verified fields (batch.json, autoname batch_id): batch_id (cohort key → carry the PT-lot identity), item (the variant), manufacturing_date/expiry_date (repurpose manufacturing_date as stock-in date = aging anchor; KDPS has no expiry), use_batchwise_valuation (the load-bearing borrow), supplier (the D1 vendor), reference_doctype/reference_name (link back to the PT).
Borrow the plumbing, build the object. Batch gives three things free: a per-lot row the SLE can carry (serial_and_batch_bundle path), use_batchwise_valuation for frozen lot cost, and manufacturing_date as an age anchor. But Batch is not a governed season — no family, no Mon-YY derivation, no Open → EOSS/markdown → Closed lifecycle, no brand-label mapping, and batch_id is free Data. So KDPS builds a first-class Season master (D8: governed house calendar) and a Cohort = one PT-lot per (variant, barcode, season), implemented as a Batch row with custom fields injected: season (Link → Season master, from system-derived FAMILY(Mon-YY)), collection (Link), manufacturing_date reused as stock-in date (so age = today - manufacturing_date is computable, Rule 6), and owned_flag + commercial_model snapshotted from the booking (what carries SOR's not-owned state and what the V-flip toggles). A scan hits an Item Barcode row → the variant; the Batch (cohort) carries season, stock-in date, frozen cost, ownership. The SLE tracks qty per (item, warehouse, batch) — count under a barcode, never a serial. Cross-season reuse of the same barcode = a new Batch row (oldest-first at till), which falls straight out because season is on the Batch, not the barcode.

Season / collection / age → markdown + dead-stock — build entirely

There is nothing in ERPNext turning age into a price action. Batch's expiry_date is a hard cutoff (block/expire), the opposite of fashion markdown (progressively discount, never block). Aging drives money: a piece's correct selling price falls with age and sell-through — the engine behind D7 dead-stock & markdown and D5's AI markdown helper. Because age and season now live on the Batch/Cohort and cost is frozen there: aging = today - Batch.manufacturing_date in the metrics layer (never stored); markdown band = a deterministic function of (age, weeks-of-cover, sell-through, broken-size-runs) against the frozen cost floor, output a proposed offer band a human approves into a real D5 offer (which posts nothing — only lowers price), so the aging ladder never touches a ledger; dead-stock/V-flip trigger = cohort age crossing a season-lifecycle threshold, expressed as a band table (config, Rule 12).

EOSS V-flip (ownership flips to KDPS) — build entirely

ERPNext has no concept of ownership flipping. Its closest motions — Stock Reconciliation (changes qty/rate) or a warehouse-to-warehouse Stock Entry — neither change who owns the goods, and both would rewrite valuation, which KDPS forbids. At end-of-season, brand-owned (SOR/Consignment) stock that didn't sell gets flipped to KDPS for liquidation: keep the real brand, set owner = KDPS, status = liquidation, display label "V<brand>", barcode unchanged, and the piece drops out of brand reports while staying on the shelf.

How to build it (borrowing ERPNext underneath). The V-flip is a small submittable document (D3, Rule 1) operating on the Batch/Cohort — not the Item, not the barcode. Its on_submit: toggles Batch.owned_flag → true, Batch.commercial_model → KDPS-liquidation, Batch.status → liquidation, sets display_label = "V"+brand — leaving Item.brand, the variant, and every Item Barcode row untouched (barcode unchanged is automatic). It posts the brand EOSS settlement claim to the vendor ledger (D4) and the discount to D5. "Drops out of brand reports" falls out for free: D7's brand reports filter on Batch.owned_flag = brand-owned (or commercial_model ≠ liquidation), so a flipped cohort self-excludes without re-tagging the brand. ERPNext supplies the transaction shape (the standard Frappe docstatus/on_submit/on_cancel lifecycle, stock_entry.py pattern); KDPS supplies the meaning (ownership flip). Putting V-flip on the cohort, not the SKU, is the key move: the same barcode keeps resolving to the same brand+style+colour+size; only that lot's ownership/value/reporting status changed — impossible in stock-ERPNext without inventing the cohort layer.

One-barcode → many-pieces, frozen lot cost — borrow the batch-valuation path, drop the recompute

Count-under-barcode is native: the SLE tracks qty (actual_qty/qty_after_transaction) per (item, warehouse), Batch sub-key via serial_and_batch_bundle — quantities, never serials. And use_batchwise_valuation makes each Batch carry its own valuation (update_batched_values, stock_ledger.py:1619; BatchNoValuation) — the one ERPNext feature giving lot-exact frozen cost instead of a moving/blended rate. KDPS's domain fact is unit cost = landed ex-GST, frozen at stock-in, never re-blended. Default ERPNext (FIFO/Moving Average) violates this — it recomputes outgoing_rate and reposts history (repost_future_sle, stock_ledger.py:215). Per-batch valuation is the escape hatch: model every PT-lot as a Batch with use_batchwise_valuation=1, write landed ex-GST as the batch's incoming rate, each sale reads that lot's cost for true per-SKU margin.

What KDPS must drop / suppress. (1) Moving-average / FIFO blending — replaced by batch-wise valuation so cost is lot-anchored. (2) repost_future_sle history rewriting — a back-dated correction must be a new append-only event, never a rewrite of prior sales' cost (Rule 2); disable reposting, use reversing entries. (3) Perpetual SLE→GL auto-posting — ERPNext posts stock_value_difference to inventory at receipt; KDPS holds SOR/Consignment count-only, value off-book until sale, and keeps statutory truth in Tally. Borrow the SLE shape and Batch valuation, but break the automatic receipt-time GL hit.

6 · The swappable POS adapter + Tally-fed-once

ERPNext's POS is native and authoritative: the register is the accounting system. POSInvoice literally subclasses SalesInvoice (pos_invoice.py:33 — class POSInvoice(SalesInvoice)), and a global toggle POS Settings.invoice_type (pos_settings.py:24) decides whether each sale writes a deferred-GL POS Invoice or a full immediate Sales Invoice. Either way the sale becomes ERPNext's book — no external statutory ledger downstream — and the POS UI is welded to the doctypes by synchronous frappe.call with no offline mode (grep for offline/localStorage/indexedDB/navigator.onLine in selling/page/point_of_sale/ returns nothing).

That is two gaps. POS-as-book vs POS-as-one-writer: Rule 4 (one owner per fact — the sale moment is owned by whatever made the sale; we ingest, never recreate) and the D3 decision "our system = book of record, POS = sale counter" mean KDPS cannot let any single POS be the ledger. Today the writer is Ten Software; tomorrow a KDPS PWA POS or a manual bill. ERPNext has exactly one writer and it is internal. Book-is-final vs Tally-is-statutory: ERPNext's GL is the filed truth; KDPS's statutory truth is Tally, fed one-way (D6).

The good news. ERPNext already proves the two things KDPS needs to borrow. The invoice_type toggle is living proof that the same downstream ledger can be fed by two different upstream writers (fast deferred path, slow immediate path) — KDPS generalises this from a global mode into a per-Sale source tag. And the consolidation engine (pos_invoice_merge_log.py) proves a safe, idempotent, retryable batch-posting pattern — the shape KDPS needs for adapter sync and the daily Tally push.

How to build it (borrowing ERPNext underneath).

  • The adapter contract (Rule 7, swappable boundary). Join key = barcode + season per line (what lets Ten Software and a future KDPS POS be interchangeable). Dedup key = store + bill_no (a re-sent bill is rejected, never double-written) — KDPS's version of ERPNext's consolidated_invoice idempotency flag (pos_invoice.py:118 "already consolidated", the IfNull(consolidated_invoice,"")=="" exclusion in build_invoice_query at pos_closing_entry.py:406), implemented as an explicit unique key rather than a Frappe doc-flag.   • What the Sale posts (KDPS rules ERPNext lacks). Revenue/cost derived, not from the POS feed: cost = frozen landed-ex-GST PT unit cost, revenue = POS line; offers post nothing.
  • Tally-fed-once — the external statutory boundary ERPNext doesn't have. Deterministic voucher number = idempotency guard + join key: DEO-SAL-20260620-001 (store·type·date·seq), pushed with prevent-duplicates ON (D6 Q4) — the same idempotency idea as consolidated_invoice but pointed at an external book; a retry hits Tally's duplicate guard → exactly-once, the same number is the daily tie-out join key.   • Manual-bill fallback + safe reversal. Risks, open questions & what to borrow first

The four tensions resolve cleanly in KDPS's favour, and the SOR/GST gap has a known shape. What remains is a short list of decisions that are still genuinely open, plus the few places where the design quietly inherits a cost or a liability it must consciously fund. None of these block the foundation build; all of them must be answered before any vertical slice that touches money, and several need a CA or a vendor to confirm. Below: the unresolved points, then the ordered borrow plan that bridges into the build.

1 · Risks & open questions

Read this as a pre-build checklist. Each row is a place where the design has made a choice that is right but not free, or has named a question it has not yet closed. The "recommendation" column is the action that retires the risk, with its owner.
Risk / open question Why it matters Recommendation
Cost-freeze vs reposting decided
KDPS freezes landed cost at stock-in and forbids history rewrite; ERPNext reposts the past on any back-dated receipt.		 This is not a contradiction — batch-wise valuation (PT-lot → Batch, use_batchwise_valuation) ships the freeze. But it means KDPS deliberately deletes ERPNext's correctness mechanism (repost_future_sle, stock_ledger.py:215). The danger is a developer later "fixing" margins by re-enabling a recompute, silently restating margins already reported to a brand. Make "no reposting" a code-level invariant, not a convention: there is no path that recomputes a posted SLE's outgoing_rate or valuation_rate. A back-dated correction posts a new dated adjusting SLE. Borrow the SLE shape + batch valuation; remove FIFO/moving-average and the repost machinery entirely.
Reposting / back-dated entries policy open
What exactly happens when a buyer fixes last week's PT rate, or a piece sells before its PT is keyed?		 The freeze answers "don't rewrite," but the operational rule for the correction itself is not fully written: which dated event posts, at what grain, against which Tally voucher, and how the original and the correction both appear in the audit trail. This is the highest-frequency real-world case (rate typos, late freight). Write a one-page "corrections" rule before the inbound slice: every correction is a new event with today's date and a reason code, linked back to the original via voucher_detail_no. Adopt ERPNext's immutable-ledger reversal variant (general_ledger.py:make_reverse_gl_entries) verbatim. Decide the "sold-before-PT" case explicitly (SRBNB-style memo value, or block-the-sale) — Anand + accountant.
SOR GST double-recognition (F9) open
The Tally design raises a Purchase voucher at arrival for every brand including SOR, and the SOR settlement crosses as a Journal voucher. If both carry GST for the same pieces, GST is recognised twice.		 This is a real money-bug: input credit taken twice, or the supply recognised at arrival and again at sale. It sits at the intersection of the two hardest divergences (SOR ownership + Tally-as-book), so it cannot be tested away later — it must be designed out. Pick one invariant and enforce it with a gst_recognised = (date, voucher_no) guard on the SOR lot: either (a) arrival voucher is a memo (no GST; sale or deemed-supply alarm carries it), or (b) arrival voucher is statutory (GST at arrival; settlement journal is money-only, zero-GST). Whichever event fires GST first sets the flag; every later event for that lot books money/qty only. Use the deterministic voucher number as the tie-out join key. Confirm the chosen convention with the CA.
Consignment / SOR has no off-the-shelf model greenfield
ERPNext always capitalises value at receipt and parks SRBNB; "consignment" in india-compliance is only e-waybill transport status (constants/e_waybill.py). No counted-but-unvalued ownership state exists.		 Two of KDPS's four commercial models (SOR, Consignment) need goods on the shelf that the brand still owns: qty visible, value off-book, liability on sale. This is the single biggest data-model divergence and the one with no proven template to copy. Build it on ERPNext's nearest mechanism, not from scratch: receive into a non-valuated SOR location (warehouse.json warehouse_type + per-warehouse account) so the qty leg posts with value off-book; keep make_supplier_gl_entry's Creditors leg but move its trigger from receipt to sale (trigger-as-config: "inward" for Outright/Correction, "sale" for SOR/Consignment). This is the payoff of severing the perpetual GL coupling — SOR becomes one clean rule, not a hack.
Deemed-supply six-month clock greenfield
CGST s.31(7): goods on approval are a deemed supply at the earlier of acceptance (sale) or six months from removal, even if never sold. ERPNext/india-compliance have no such timer (every "6 month" hit is a GSTR-3B filing fallback).		 A SOR piece unsold past six months becomes a taxable supply regardless of an actual sale — the brand must raise a deemed-supply invoice and GST falls due. If KDPS doesn't alarm this, the floor is blind to a statutory deadline and input-credit timing goes wrong. This clock is distinct from the 60–120-day commercial return window. Model an effective-dated SOR Lot carrying two clocks off one removal_date: clock 1 = removal_date + brand window (return), clock 2 = removal_date + 6 months (deemed supply). Alarm both at 30/15/7 days into a named exception queue (flag, never block). Owner of clock 2 = Patna accountant; action = recognise unsold qty_remaining as a deemed supply via journal to Tally. Confirm the six-month interpretation with the CA.
Tally reconciliation is not free must-fund
ERPNext gets stock↔GL reconciliation by construction; KDPS severs that coupling and keeps Tally as the book, fed once.		 The compensating cost is a build, not a saving: KDPS must build the daily Tally tie-out (join on the deterministic voucher number) and a failure queue. This loop is the price of "one owner per fact" — it is not optional, and it's easy to under-scope as "we'll add it later." Treat the tie-out + failure queue as a first-class slice, scheduled alongside the first slice that posts to Tally — not an afterthought. The deterministic voucher number (DEO-SAL-20260620-001) is both the idempotency guard and the join key; design the queue's owner and SLA up front.
State-GSTIN as a ledger dimension design now
ERPNext is state-blind — company is its only entity scope; cross-state needs a two-companies workaround.		 Bihar and Jharkhand are separate "distinct persons" (two GSTINs); cross-state transfers are taxable IGST supplies. If state-GSTIN isn't a first-class dimension on every ledger leg from day one, retrofitting it after data exists is painful and error-prone. Carry state-GSTIN (plus brand, season/collection, store/warehouse) as ERPNext-style accounting dimensions on every leg (base_gl_composer.py:get_gl_dict) and as part of the merge key — from the kernel, before the first posting slice.
Effective-dating the four history-driving masters design now
Snapshot protects one document; SCD Type-2 lets a back-dated document pick the right historical value.		 Having forbidden reposting, snapshot is mandatory — but snapshot alone is not enough. A new document with a back-dated posting_date must read the master as it was on that date. GST especially: apparel slab changed 22 Sep 2025 (5% ≤ Rs 2,500/piece, 18% above) — must be dated data, computed once, carried, never recomputed. SCD-Type-2 the four masters that drive history: GST slab, GSTIN, cost, price (brand terms versioned by season). Make snapshot a uniform constitutional rule, not the inconsistent per-document behaviour ERPNext has.
Late freight / landed-cost after the fact open
A freight bill that arrives after the PT is keyed must raise the frozen landed cost — but reposting is forbidden.		 ERPNext's Landed-Cost-Voucher reposts valuation across past stock. KDPS can't repost, so the rule for late freight is genuinely open: does it adjust the lot's frozen rate going forward only, or post a separate cost-correction event? Borrow the LCV formula (Valuation taxes capitalise into cost, GST → input-credit account; buying_controller.update_valuation_rate, landed_cost_voucher.py:205) but compute KDPS-side and freeze. Decide the late-freight posting rule with the accountant before the inbound slice.
CA / vendor questions to close external Several decisions above hinge on confirmations KDPS cannot make alone.
  • CA: confirm the SOR GST convention (arrival-memo vs arrival-statutory) and the six-month deemed-supply interpretation for the brands' actual contracts.
  • CA: confirm the late-freight / landed-cost-after-PT posting rule and the "sold-before-PT" treatment.
  • Brands/vendors: confirm per-brand return windows (60–120 days) and SOR settlement rate basis — these feed clock 1 and the on-sale liability leg.
  • Ten Software POS / Tally / barcode tool: the three external spikes (API shape, import format, barcode generation) have lead time — confirm contracts in parallel with the foundation build.

2 · What to borrow first, in what order

The divergences are three deletions, not a redesign. ERPNext's ledger engine is KDPS's "documents-write-ledgers" pattern, proven. Borrow it wholesale, then delete the three pieces that fight the freeze (moving-average/FIFO recompute, repost_future_sle, perpetual stock→GL auto-posting). The order below builds the kernel first, because everything above it depends on a posting engine that already enforces the rules.

  1. The kernel — borrow first, before any module. The append-only, balance-enforced posting engine that every later slice writes through. Borrow as one unit:
    • docstatus lifecycle (Draft / Submitted / Cancelled) — documents are submitted, never silently edited.
    • deterministic naming — the DEO-SAL-20260620-001 pattern (store·type·date·seq) as both idempotency guard and Tally join key.
    • audit / immutability — append-only ledger; GLEntry.on_cancel hard-throws (gl_entry.py:325); correction = reversal in the immutable variant (general_ledger.py:make_reverse_gl_entries), original untouched, reversal dated today.
    • GL Entry engine — one make_gl_entries for all documents (general_ledger.py:34); modules never INSERT ledger rows directly; Σdebit = Σcredit enforced at write (process_debit_credit_difference) — the literal reason Supabase was rejected; full voucher_type/voucher_no/voucher_detail_no back-reference for drill-down.
    • Stock Ledger Entry (SLE) shape — append-only per (item × warehouse), signed actual_qty, running qty_after_transaction, stock_value_difference, soft is_cancelled, Bin as last-balance cache. Method-agnostic; carries the frozen lot cost via batch-wise valuation (use_batchwise_valuation).
    • accounting dimensions — per-leg slicing (store/warehouse, brand, season/collection, state-GSTIN) on the merge key from day one (base_gl_composer.py:get_gl_dict).
    • party sub-ledger — against_voucher + update_outstanding_amt = KDPS's Allocation = Tally's Agst Ref; reuse for vendor ledger and SOR liability.
    Delete here: perpetual stock→GL auto-posting (stock_controller.py:178), moving-average/FIFO recompute, and repost_future_sle. Value reaches the books only via the Tally voucher.
  2. The GST model — second. Once the kernel posts cleanly, layer GST as date-effective data over a tax-agnostic core (india-compliance's posture): per-line CGST/SGST vs IGST chosen by inter-state test (overrides/transaction.py), date-effective apparel slab from the Item-Tax-Template, company_gstin tagged on every leg. Borrow the computation; KDPS owns the trigger and the once-only guard. Effective-date the four history-driving masters here (slab, GSTIN, cost, price).
  3. Pricing & landed cost — third. The landed-ex-GST formula (buying_controller.update_valuation_rate): Valuation taxes (freight/duty) capitalise into the frozen valuation_rate; GST credits a recoverable input-tax account, never inventory. Borrow the LCV pattern for late freight — but compute KDPS-side and freeze, never repost.
  4. Payments & party ledger — fourth. With the party sub-ledger from the kernel, build vendor liability, SOR-liability-on-sale, and Allocation against the against_voucher mechanism already borrowed. The two-document split is proven: GRN = Purchase-Receipt (qty), PT = Purchase-Invoice (value + liability via make_supplier_gl_entry) — supplier ledger touched only by the value document.
  5. POS ideas — last to borrow, first the customer sees. ERPNext's POS patterns (offline-first sync, idempotent submission, daily consolidation into one Tally sales voucher) are worth lifting after the engine underneath is solid — the POS is only as honest as the ledger it writes to.
The one-line trade to keep visible. The single biggest data-model divergence (SOR) is paid for by the single biggest deletion (perpetual GL coupling). Sever the auto value→GL, and SOR's "counted but unvalued, liability on sale" stops being a workaround and becomes one config line: the liability leg's trigger is "inward" for Outright/Correction, "sale" for SOR/Consignment. Everything else is borrowed, not built.

KDPS · D1 · Module Design

Vendor Management Module

Master record of who KDPS buys from, and the bookings placed against them — tracked from order to delivery, verification, and return.

Scope — decided 10 June 2026
Version 1 manages branded vendors only. Non-branded vendors — and the Agent record, which exists only for them — are parked for v2. Their design is kept untouched in §13, and non-branded vendor records get their own data-input discussion before they enter any version. This is module scope only — the non-branded inbound flow (invoice → PT, the PT Mapper) is core v1; see the Inbound design.

1.What this module is

Three records: the vendor, the brands under it, and the orders (bookings) placed against them — brand by brand.

In v1 the module holds three records:

  • VVendor — the company KDPS buys from (the legal entity): contact, plus statutory & bank identity. One vendor can carry many brands.
  • BrBrand — a label under a vendor. Its commercial model and return terms live here, because they are decided brand by brand, not vendor-wide.
  • BBooking — an order placed with one vendor for one brand, for one season, tracked all the way to delivery and return.

The job: make a booking real from the moment it is placed — not only when goods arrive — so booked-vs-received is always accounted.

A fourth record — AAgent — exists only for non-branded vendors and is parked for v2 (§13).

2.Vendor

v1: branded vendors only — direct relationships, no agent.

Branded

  • Direct contact. No agent.
  • Data is fixed / standardised and loaded later (e.g. Madura brands).
  • Runs on one of the four commercial models (§3) — set per brand (two brands under one vendor can run different models), carried per booking.
  • Two margins: normal-sale and discount-sale.
  • Return window matters.
  • Payment-terms field on the record; the actual terms per brand are a named input for D4 (§11).

Statutory & payment identity added 10 June

Needed for GST paperwork now and for payments (D4) later. Lives on the vendor record; every document snapshots what it uses (Rule 3).

  • GSTIN — more than one allowed: brands bill from different states, so each billing state's GSTIN is kept.
  • State and PAN — never typed: read out of the GSTIN itself (first two digits = state code, middle ten characters = PAN). Derived, not entered (Rule 6).
  • Registered address.
  • Bank details — account name, account number, IFSC.

Flag, never block (Rule 5):

  • A vendor can be saved incomplete — missing GSTIN / PAN / bank raises a flag in the exception queue.
  • The hard gate sits in D4: no payment to a vendor without bank details and a GSTIN on file.
  • Day-to-day booking work is never held up.

3.The four commercial models

Set per brand (each brand under a vendor can run a different model), and carried on each booking. Terms are snapshotted onto the booking, so later changes don't rewrite history. The models differ on two things: who owns the goods and what return rights exist (corrected 13 June Q&A).

Outright · KDPS owns

Buy & Sell (BNS)

KDPS buys outright and owns the stock. Two sub-types: with vendor barcode (MRP capped) or without barcode (KDPS sets MRP).

Returns: none.

Correction · KDPS owns

25-18-10

KDPS buys and owns the stock, but the brand grants a capped return allowance: 25% full-price margin, 18% during EOSS/discount, 10% goods-return allowance — calculated on delivered (serviced) goods, not booked. The 10% is stretchable per brand (→ 12% / 15%). Return-allowance design in §8.

Returns: KDPS applies for return manually, within the window and within the allowance.

SOR · Brand owns

Sale or Return

Goods belong to the brand. KDPS sells and takes commission; all unsold stock goes back, no cap (old / new / season is not checked). To get more, KDPS raises a fresh booking.

Returns: return everything unsold within the window.

Consignment · Brand owns

Consignment

Same core as SOR — goods belong to the brand, unsold goes back, no cap — but the brand keeps topping up: KDPS can pull more without a fresh booking each time.

Returns: the vendor takes back unsold stock themselves.

SOR and Consignment are the same concept (brand-owned, return the unsold); the only difference is the rolling top-up. Treat as near-identical downstream.

How the model is stored — two axes, label derived

The brand record does not store the friendly name as a free choice. It stores two plain facts and the system derives the Outright / Correction / SOR / Consignment label from them — so the same data answers cleanly however the client describes a deal:

  • Ownership — does KDPS own the goods, or does the brand?
  • Return terms — none, capped, or uncapped — plus a rolling top-up yes/no flag that separates Consignment (tops up) from SOR (fresh booking each time).

Screens still read the four familiar names. Ownership is also what decides GST timing downstream, so storing it as its own axis keeps that derivation honest.

4.Booking — structure

  • Belongs to: one vendor + one brand + one season. Never mixes brands. One vendor can have many bookings — one per brand per season.
  • Lines: per style-code → per size: quantity. No colour at booking — a deliberate choice, see §10.
  • Quantity-only, plus one optional estimated order value for planning. No hard pricing — MRP/cost is set later at inward. No spending cap either — also deliberate, see §10.
  • Commercial model + snapshot of its terms (margins, return window, return allowance %) carried on the booking.
  • Identity: auto-generated booking number (e.g. BK-SS26-0012), plus an optional field for the vendor's own receiving/order reference.
  • Season: picked by the handler at booking time from the system-derived season list — never free text (inbound Q39).

5.How a booking is created

The create flow — season first

  1. Pick the season. Seasons follow a fixed pattern; if next season doesn't exist yet, the handler clicks Generate Season and the system creates it from the pattern. A season can be deleted only while empty (no bookings against it); once it has data, it can't be deleted.
  2. Pick the vendor, then the brand — or skip straight to upload and let the system read the vendor and brand off the document.
  3. Upload the receiving → review the draft → confirm. Only then is it Booked.

Who owns the season list (open/close) is a D8 master-data question; the Generate / delete-empty buttons live here.

Branded — upload-driven

  • Order placed by in-person visit; vendor gives a printed receiving document.
  • Handler uploads the receiving; the Receiving Reader reads style / size / quantity and drafts the booking.
  • Clear computer-printed doc → mostly auto-filled. Asks for a clearer photo only when too much is unreadable.
  • Even at 70–80% read, it presents what it has; handler completes and confirms.
Guardrail
The Receiving Reader never creates the final order silently. It always produces a draft → handler reviews and confirms → only then it becomes Booked.

6.Receiving & verification

  • The order list captured here pre-fills the GRN. When the shipment arrives, the receiver opens the order list, enters what physically came in, and writes a required note on anything short or damaged — then presses Generate GRN. It is a confirm-and-adjust screen, not data entry.
  • One booking ↔ many GRNs. Stock can arrive over several shipments; each arrival creates its own GRN until the booking closes.
  • Over-receipt allowed: items/sizes that weren't booked can still be received — the same screen adds a line, flagged as a variance with a required remark. The original order line is kept, flagged.
  • Damaged on arrival = received-but-flagged: the piece enters stock as quarantined (not sellable) and routes to the defective-return flow.
  • Where it happens: warehouse-delivered shipments are counted + GRN'd at the warehouse; store-delivered shipments are received by the store operator in their own login against the order (counted-by, auto-stamped), then the warehouse person finalises the GRN and converts the PT (entered-by) — see inbound Q38.
Module boundary
The GRN object itself lives in the Inbound module. Booking provides the order list that pre-fills it, and receives the close-out when goods are verified. The two modules share the order list and the received result.

Direct receipt — a GRN with no booking added 25 June

Goods can land at a store or the warehouse with no booking ever recorded — it happens for branded brands too, not only non-branded. The system must take them in, so the shipment, not the booking, is the real anchor of inbound: a GRN is allowed to stand alone with no parent booking at all.

  • "Receive without order". The receiver opens a plain simple-receipt GRN (no order list to confirm against) and counts what physically came in. The commercial model is taken from the brand's current terms at the moment of receipt — snapshotted, like everywhere else (Rule 3) — defaulting to Outright if the brand isn't yet known, flagged for head office. No phantom booking is invented — that would pollute booked-vs-received.
  • The status lifecycle is unaffected. The booking statuses in §7 are computed from a booking's own GRNs; a booking-less GRN sits in no booking's GRN-set, so it simply never touches the lifecycle. No new status is needed — the machine is robust to a missing parent by construction.
  • Retro-link. If a booking for these goods turns up later, the receiver can attach the Direct GRN to it. The link re-runs the booked-vs-received and invoice match as a tracked correction (a new dated event, never a silent rewrite of history).

The posting side of this — quantity in at the GRN, value and vendor liability at the PT — is owned by Inbound (see the Inbound design).

7.Booking status lifecycle

Receiving statuses are computed from the booking's GRNs — never set by hand. Close and cancel are the only manual steps, always with a remark. Nothing closes automatically.

Booked → Partially received → Fully received → Return window open (Correction / SOR / Consignment) → Closed / Cancelled
Changed 10 June — arrival belongs to the shipment
"Arrived · not received" used to be a booking status — it isn't any more.
  • Arrival is a fact about one shipment, and one booking can have several shipments, each at its own stage.
  • So it now lives on the Shipment record, owned by Inbound.
  • The booking screen still shows "1 shipment arrived, awaiting count" as live information from Inbound — it just isn't the booking's status.

A booking can never again sit in two states at once.

The Correction return allowance — the season GR budget designed 10 June · reassigned to Correction 13 June · basis option added 16 June

Think of it as a refund budget the brand gives KDPS — one budget per brand per season. It belongs to the Correction model only — SOR and Consignment return everything unsold with no cap, so they need no budget. Built so KDPS can tell the brand its own number instead of asking for it (the owner's ask, 21 May: "my purchasing this season was X, so my 10% is Y").

  • Basis is chosen per brand — money or quantity: either % of the season's delivered value (e.g. 10% of ₹10,00,000 = ₹1,00,000 of return-room) or % of the delivered quantity (e.g. 10% of 2,000 pieces = 200 pieces). Whichever the brand uses, that's how KDPS tracks it. Default 10%, stretchable per brand to 12 / 15.
  • Budget fills as goods arrive (PT by PT): each priced stock-in adds its share to the budget. It can't fill at booking — bookings carry no prices or final counts yet.
  • Budget empties as goods go back: every Correction return (the D3 return document) draws it down in the same unit — rupees of stock-in value, or pieces. Later markdowns / EOSS never distort it.
  • Past the limit: the return still goes (Rule 5 — flag, never block). It lands in the exception queue with the over-limit amount shown; what the over-limit costs in rupees is D4's call (§11).
  • Always computed, never typed (Rule 6): balance = budget − used. Shown plainly on the vendor/brand page — "Madura · SS26 — used ₹40,000 of ₹1,00,000" — and on every Correction booking; the 30 / 15 / 7-day window alerts include the balance.
Open:
  • Confirm with each brand which basis it uses (% money or % quantity) and on what figure (delivered value ex-GST, per inbound Q36).
  • The window's anchor date (from receipt? from season end?), settled in D3 — because return picking depends on it.
  • Levi's variant computes on actual buying — confirm in the "what's fixed vs what changes" discussion.

9.Standing rules

  • Every edit needs a remark from the handler — who and why. Full audit trail.
  • Nothing auto-closes. Close and cancel are manual.
  • The system stays flexible, but changes go through authorisation rather than silent direct edits.
  • Booking is real from creation — booked-vs-received is tracked end to end.

10.Two deliberate trade-offs

Both were implicit until now. Written down so they read as chosen, not forgotten.

(a) No colour on booking lines

Booking lines are style + size, so booked-vs-received is matched at that grain only. It posts to no ledger anyway — full SKU identity (style × colour × size) starts at GRN/PT. And for branded orders the colour is already on the vendor's own document; colour is mostly a non-branded concern, where the order detail is loose. Recorded as a conscious exception on Rule 9 of the architecture page.

Risk: right styles and sizes in wrong colours is caught by eye at receiving, not by the system.
Rethink when: colour-level disputes with brands become real, or the Receiving Reader proves it can read colour reliably.

(b) Quantity-only — no spending cap

A booking carries quantities and one optional estimated value, no hard budget gate. KDPS has never run an open-to-buy budget, and a hard gate would block the floor (Rule 5). Over-ordering is held in check the way it is today — by the people placing the orders and, later, by analytics watching the buy — not by the system refusing a booking.

Risk: over-ordering becomes visible only after the goods and the liability arrive.
Rethink when: D7 analytics shows season buys drifting from plan — the first step would be a read-only season-buy view, never a blocking control.

11.Inputs handed to D4 (payments)

Named here so the payments discussion starts with them already on the table.

InputWhat D4 must settle
Correction return-allowance settlementThe allowance (GR budget) is tracked here (§8). D4 decides the money: how a return shows up in the vendor's account, and what an over-the-limit return costs or recovers.
Payment terms per brandThe field exists on the vendor record (§2); the actual terms data is still owed by the client. D4 turns terms into due dates and payment proposals.
Bank details & GSTIN as the pay gateThe vendor record carries them (§2); D4 enforces them: no payment to a vendor without bank details and a GSTIN on file.

12.Out of scope (for now)

Deliberately parked

  • User roles / access / approval hierarchy — one person does vendor management today, so the module is built for that single handler. Multi-user roles can come later.
  • Hard pricing / MRP — set later at inward, not at booking.
  • SKU / barcode creation — SKUs and barcodes are created at the Inbound stage (PT step), not at booking. Booking is quantity-only.

Now defined (no longer parked): GRN ownership — the GRN lives in the Inbound module against this order list; Booking provides the list and receives the close-out (see §6).

13.v2 — parked: non-branded vendors & agents

Decided 10 June 2026: v1 manages branded vendors only. Everything below is the 8–9 June design, kept whole — parked, not deleted.

Before this enters any version

Non-branded buying runs on verbal orders, agent introductions and handwritten notes. It needs its own data-input discussion — how orders, items and prices actually get into the system, and how vendors without a GSTIN are recorded — before it is scheduled into any version.

AAgent

Applies to non-branded vendors only. Brands are dealt with directly.

  • One fixed agent per city. Full details stored (name, contact, city).
  • Introduces non-branded vendors; once a relationship forms, the vendor contact can become direct — but the agent stays on record.
  • Accountable for a booking until stock is delivered and verified.
  • Surfaced on every open / partially received booking as "who to call," with call outcomes saved in remarks.

Non-branded vendor

  • First found through an agent; contact may later become direct.
  • Created in the system by the handler.
  • Fields: name, contact, commercial model, margin %, return window, payment terms.
  • Linked to its city's agent.

10 June note: the statutory & bank identity of §2 will apply here too — many non-branded vendors have no GSTIN, and their data-input discussion must settle how that is recorded.

Non-branded booking creation

  • Verbal/agent order ahead of season — handler types it manually.
  • Option to upload an image (a note from the vendor) to auto-fill, then review and create.

Booking ties that return with it

  • A non-branded booking also belongs to its accountable agent (one vendor + one season + the agent).
  • On open / partially received bookings the agent is the chase contact, call outcomes in remarks.

Booking & Inbound

The first half of the system — from placing an order with a vendor to stock becoming sellable at the store. This document covers what we've designed, every edge case it handles, what we need from you, and what comes next.

1.The spine

One clean line — order placed, goods received and documented, stock live at the store.

Booking placed→ Goods + invoice arrive→ Counted & checked → GRN→ PT file made→ Head office inwards→ Split to stores→ Sellable at counter
The one rule behind it all
Nothing is trusted until the physical goods, the invoice and the PT file agree. The system makes the data clean and traceable, so accounting and payment can rely on it without anyone re-doing it in Excel.

2.Module 1 — Vendor & Booking

The record of who we buy from, and every order placed against them — live from the moment it's placed, not only when goods arrive.

2.1 · Three records

  • AAgent — one fixed contact per city, for non-branded vendors only. Introduces vendors (the contact may later become direct, but the agent stays on record) and is accountable for a booking until stock is delivered & verified. On every open or partly-received booking the agent shows as "who to call," with call outcomes saved as remarks.
  • VVendor — a brand (dealt with directly, no agent) or a non-branded supplier (found via an agent). Carries name, contact, commercial model, margin, return window and payment terms.
  • BBooking — one vendor + one season (+ the agent, if non-branded). Never mixes vendors; one vendor can have many bookings.

2.3 · How a booking is structured

  • Lines: per style-code → per size: quantity. Quantity-only, plus one optional estimated order value for planning — no hard pricing at booking (MRP/cost is set later, at inward).
  • Identity: an auto booking number (e.g. BK-SS26-0012), plus an optional field for the vendor's own order/receiving reference.
  • Season is chosen by the handler at booking time; the commercial model + its terms ride on the booking.

2.4 · How a booking is created

Branded — upload-driven

  • Order placed in person; the vendor gives a printed receiving document.
  • The handler uploads it; the system reads style / size / quantity and drafts the booking.
  • A clear printed doc auto-fills mostly; even at 70–80% read it shows what it has for the handler to complete.

Non-branded — manual + optional upload

  • Verbal / agent order ahead of season — typed in by hand.
  • Option to upload a photo of the vendor's note to auto-fill, then review and create.
Guardrail
The reader never creates the final order silently — it always makes a draft → the handler confirms → only then it becomes Booked.

2.5 · Receiving → GRN

  • The order list pre-fills a screen. When goods arrive, the receiver enters what physically came in and writes a required note on anything short or damaged, then presses Generate GRN. It's a confirm-and-adjust screen, not data entry.
  • One booking ↔ many GRNs — stock can arrive over several shipments until the booking closes.
  • Over-receipt (items/sizes not booked) → add a line on the same screen with a required remark; the original order line is kept, flagged.
  • Damaged on arrival → counted as received but quarantined (not sellable), routed to the defective flow.

2.6 · Booking status

Booked→ Arrived · not received→ Partially / Fully received→ Return window open (SOR / Consignment)→ Closed / Cancelled

Close and cancel are always manual and always need a remark — nothing closes by itself.

3.Module 2 — Inbound Ingestion

Turning a real-world arrival into clean, accounting-ready stock — branded and non-branded handled differently.

3.1 · The Shipment is the anchor

One vendor arrival = one Shipment. Its invoice, GRN, PT file, store-split and accounting export all hang off it, each with its own status. A Shipment is "done" only when all its lines resolve.

3.2 · Branded mostly automatic

An arrival counts as branded when all three are true: invoice + goods together · every item has a vendor barcode · the PT file is retrievable when asked. Then one of two paths, by where goods land:

A · Store delivery (most common)

Goods + invoice at store→ Store counts & checks→ Invoice + details to warehouse person→ Warehouse makes GRN + PT→ Head office inwards→ Store scans → sellable

B · Warehouse delivery

Goods + invoice at warehouse→ Count & check + GRN at warehouse→ Head office inwards→ Allocate → sellable

Brand PT → KDPS PT is automatic software (fixed per-brand rules). The vendor barcode is kept. A store-delivered shipment may then be redistributed store → store.

3.3 · Non-branded AI-assisted

About 99% arrives at the warehouse with an invoice only. The system reads it and fills the gaps with the operator.

Upload invoice → AI reads→ Chat: what's filled vs missing→ Operator fills (colour, size, call vendor)→ Editable Excel PT→ Barcode per piece→ Inwarded → sellable
  • Colour: a real colour if a brand file gives one; otherwise the operator tags it Premium / Medium / Economy by price, in the chat, by their own judgment (no fixed price bands).
  • Size: used if the invoice states it; if missing, the line is "Free Size" — we don't guess sizes item-by-item.
  • Price (untagged): MRP = base + 1.1% transport + GST + per-category margin (30–35%, overridable).
  • No duplicates: the same product (vendor + style + size) rolls up to one SKU; each new piece still gets its own barcode. A central registry enforces this.

3.4 · SKU vs barcode — kept separate

  • SKU = the sellable type: Brand + Style-code + Colour + Size. Used for stock, reorder and dead-stock. One product type = one SKU.
  • Barcode = the unique ID of a single piece. Five identical kurtis get five barcodes, so one SKU → many barcodes.
  • Season matters: within a season a barcode is unique; some brands reuse a barcode in a later season, so a unit is identified by barcode + season.
  • Each piece carries a condition — good, or damaged-quarantined.

3.5 · GRN, checks, splitting & accounting

  • Discrepancy never blocks. Ordered-vs-received gaps are flagged and logged, but goods are physically in and must sell — the account manager resolves each (credit note / acknowledged / write-off) and it stays open until closed.
  • Two human gates: warehouse approval, then head-office inward. The system auto-checks (required fields, GST vs HSN, margin band) and flags only problems; a person approves for accountability.
  • Store split: manual now (every split recorded), AI-suggested later from sales history.
  • Nightly reconciliation matches Invoice ↔ GRN ↔ PT. The accounting export is generated after head-office inward — exact, reproducible, no manual reshaping.

5.How it's built

  • AI only at the edges — reading invoices and the non-branded assistant. Everything touching money (pricing, tax, the accounting export, reconciliation matching) is exact software, never guessed.
  • The app is the record; WhatsApp is the nudge that links back into it.
  • Audit trail is automatic — every action logged (who, what, when, before → after).
  • Roles & scoping — a store sees only its own shipments; warehouse and head office are network-wide.
  • POS is not rebuilt — we integrate with tensoftware.in via its API.

6.Questions for you

A few answers and one set of sample files let us lock the design and start building.

A · Brand & vendor terms

  • For each brand/vendor, which commercial model — SOR (25-18-10), Outright (Buy & Sell), or Consignment?
  • For each SOR brand — what is the return window and the return allowance (e.g. 10%)?
  • What are the payment terms per brand/vendor?

B · POS integration (tensoftware.in)

  • Please share access to the POS API and its documentation. We'll work out the capabilities we need from the docs.

C · Barcode & SKU

  • When the same style-code arrives next season — a new SKU, or reuse the existing one?
  • We need a deep-dive on your current barcode-generation tool — how it works, its inputs and outputs — so we can integrate now and replace it later.

D · Non-branded product rules

  • When a non-branded invoice names a real colour but there's no brand file — should we ignore it and use the Premium/Medium/Economy tier? (current assumption: yes)

E · Sample files

  • Sample brand PT files — one per brand format. (The one set still pending; invoices and formats are already in hand.)
